# LibreNMS 原生采集切换与工作区改动推送记录

## 问题现象与提交目的

项目此前导入了 LibreNMS 的 MIB/YAML 规则，但硬件采集仍由 Nexora 的 Python OID 适配器执行；SNMP 诊断也没有稳定展示 LibreNMS 原生当前行。因而“HCL 可读、真实设备 Grafana 无数据”的现场原因不能仅凭已有代码确定。本次按用户要求切换到完整 LibreNMS runtime 采集路径，打通诊断、时序出口和 Grafana 展示，并一并纳入工作区中 Docker 容量测试任务的代码修改。

真实设备的厂商/型号/系统版本尚未提供；用户明确跳过 HCL/真实设备验证并在 push 后自行验证。因此本记录不把部署现场的空数据根因标记为已证实。

## 根因与解决方案

- 旧路径把规则数据当成采集引擎使用：Python 侧仍自行选择 OID、转换厂商值并轮询硬件；部分模板诊断、监控编译与后台轮询仍能走到旧逻辑。LibreNMS 的 PHP discovery/poller、原生实体和当前值没有成为唯一硬件数据源。
- 新增 opt-in 的 LibreNMS 完整运行时 Compose profile、独立 MariaDB/Redis/持久化、隔离网络和密钥配置；新增运行时 API 客户端、设备/实体同步投影、硬件诊断 API 与同步周期。CPU/内存原生值保持兼容现有 `nexora_hw_cpu_usage_percent` / `nexora_hw_memory_usage_percent` 指标和资产筛选标签，并保留原生实体身份及采样时间。
- 删除 Python 厂商硬件 OID 采集和旧发现回退入口。Nexora 仍负责设备登记/凭据映射/权限、原生结果投影、诊断展示和时序桥接；IF-MIB 接口采集、系统身份识别及用户手动 SNMP GET/WALK 保持原有职责。
- `/monitor/snmp-walk` 现在展示 LibreNMS 原生诊断快照及 CPU、内存、传感器、光模块、无线实体结果。Grafana 保留 CPU/内存指标契约，并添加通用原生无线传感器表格；对 LibreNMS 未明确提供的 AP/Radio 归属留空，不猜测实体类型。
- 全量回归审查补回仍被资产身份识别使用的 sysObjectID 厂商前缀注册表引用；删除针对已移除 Python 自动 OID 发现重试函数的过时测试，并将光模块测试改为验证原生行保留、非光学行过滤和不读取 SNMP 凭据。
- 批处理过期样本测试夹具补齐 `last_sample_at`，并验证它不会被旧样本覆盖。`last_seen` 记录同步观察时间、`last_sample_at` 记录设备样本时间，生产比较逻辑保持只依据实际样本时间。
- 同次纳入的 Docker 容量压测修正：API 合成设备不再给后台 A-Loop 填入虚构管理 IP，避免它们被当成真实设备探测；长时测试在即时查询前重新写入 VictoriaMetrics 验证样本，避免样本超过查询时间窗。

## 未验证项与风险

- 未执行 Compose 容器运行时、LibreNMS discovery/poller、原生 Influx v1 到 VictoriaMetrics 写入链、浏览器 Grafana 现场查询或 HCL/真实设备验证；当前无法确认用户部署问题的具体故障层。
- 用户计划在 push 后验证 HCL/真实设备。现场结果需按“SNMP 可达性 → LibreNMS OS/实体发现 → poller 当前值 → datastore 写入 → VictoriaMetrics → Nexora 投影 → Grafana 查询”逐层记录，不应回退 Python 厂商硬件轮询。
- `.github/workflows/release.yml` 的 main push 先运行质量门禁，成功后会把净化后的 Ubuntu 发布树 force-push 到配置的公开发布仓库；本次只计划推送当前仓库 main，不手工创建版本 tag 或 GitHub Release。
- 若部署后发现指标语义、租户隔离或采集故障，可回退本次提交；无生产数据库/真实设备变更，也没有在本地启动或写入生产时序数据。Compose 的 LibreNMS volumes 仅在用户显式启用 profile 后使用，回滚运行环境时按部署文档保留或单独备份其状态卷。
