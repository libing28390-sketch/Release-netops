# 告警、IPAM、LLDP 与监控错误及 v1.0.9 发布

## 问题现象与根因
- 告警站点显示内置标识，100% 缩放时窄列导致主机、站点、等级和状态拥挤换行；页面没有统一从 CMDB sites 目录解析名称。
- IPAM 库存/核对按 IP 单键合并跨 VRF 的人工记录；周期发现忽略投影禁用策略，部分或未采集设备也被用于老化；终端把交换机名称存作站点。空采集的 `0 == 0` 成功判断还有相同风险。
- LLDP 远端 chassis ID 与 subtype 的 OID 使用不正确；整表预算与行数太低，截断结果未明确标为不完整，二进制 chassis 信息丢失。
- PostgreSQL 重复发生整数/布尔比较、接口计数 int4 溢出与 NULL 接口拓扑边主键冲突。自动发现失败或无硬件类别时反复探测，重复解析相同 MIB token；原始采样与计数基线的提交边界不同。
- 用户要求今天全部代码推送 main，并覆盖源标签与公有 Release 的 v1.0.9，保持产品版本号。

## 解决方案
1. 告警 API 提供 site_id；共享目录 hook 和导出 helper 从 CMDB site_name 映射，目录中的合法名称即使像 ID 也保留。表格使用最小宽度、单行关键字段和横向滚动。
2. 人工地址按租户/VRF/规范化地址匹配；周期任务遵守投影策略，老化要求 owner 已完整覆盖；端点站点通过合法 CMDB 归属取名称。空证据返回 partial。
3. LLDP 使用正确 OID 与 chassis subtype，保留 octets；30 秒/10000 行预算，沿用设备端口；超时/截断保留 partial 和失败信息，不把不完整发现当作完整快照老化。
4. MIB 查询按 INTEGER 激活契约，先筛规则再解析，请求内缓存符号；自动发现失败退避 120/240/480/900 秒，空硬件结果等待 900 秒。m0262 扩宽原始及聚合计数；原始样本和持久化基线共同提交，成功后才更新内存基线。拓扑投影按 tenant 加锁并复用事实 ID，防止 NULL/空接口导致冲突。
5. 收集脚本以受限输出权限保存诊断；公有发布白名单保留脚本和说明。构建日期及发布说明更新为 2026-10-02，版本仍是 1.0.9。使用现有 Actions 正式门禁生成公开发布树与附件。

## 未验证项与风险
本机没有 Docker 和真实设备环境，未执行生产部署，也不能保证线上 CPU 已降低。旧 CPU 包分析显示主线程及可见 SNMP/数据库调用频繁，日志打印没有主导 CPU 的证据。SNMP exporter 超时的认证/ACL/设备原因仍需现场确认。

旧 network_endpoints/ip_inventory 缓存仍以 IP 为唯一键，未重设计跨 VRF 存储。历史错误 site 或 stale 前缀没有批量回填。m0262 可能锁表并重写遥测数据，应先备份并安排窗口；启动自动应用待执行迁移。
