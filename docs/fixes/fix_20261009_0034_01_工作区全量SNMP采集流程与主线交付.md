# 工作区全量 SNMP 采集流程与主线交付

## 问题现象与目的

需要确认 LibreNMS manifest 中的厂商数为何大于本地 MIB 一级目录数，并把当前 SNMP 从资产导入到硬件采集、存储、Grafana 展示及诊断的真实调用链写清楚。工作区还包含移除 Nexora 手工硬件 OID/Profile 规则、同步 LibreNMS MIB 与来源清单、更新导入反馈和监控看板的代码，需要在完整验证后提交到 `main`。

## 根因

- `source-manifest.json` 同时记录 Nexora 资产厂商、OS profile 厂商、OS profile、上游 MIB 来源路径和本地 MIB 分组，使用单一“厂商数量”理解会混淆这些不同范围。
- 遗留的自定义 OID Profile、旧 PHP 辅助/传感器文件和相关前端入口可能被误认为 LibreNMS 运行规则。
- 定时硬件发现对同分 OS 规则曾存在选择首条规则的风险。
- 通用接口 SNMP exporter 与硬件 discovery YAML 是两条采集链路；目前没有固定 LibreNMS 来源校验通过的接口 module，不能把接口样本误报为仍在采集。
- Windows Git 的 `core.autocrlf=true` 会把本地原始 CRLF 规则/MIB 文件规范化为 LF Git 对象，导致暂存/部署后的字节与 manifest SHA-256 不同。
- Profile 入口清理时误删了仍被 LibreNMS MIB ZIP 上传、同步和状态接口共用的内存状态初始化；wireless Grafana 查询也未一致限定 `source_type="librenms_rule"`，会留下混入历史/其它来源数据的可能。
- 新增迁移 279 后，原生 LibreNMS migration 测试继续用 `registered[-1/-2]` 固定期望 277/278，迁移顺序扩展使断言过期。

## 解决方案

- 以固定 LibreNMS commit `6c26b4fe4a40f7b392c19c36a44257212736e38c` 的 OS YAML、MIB 和来源哈希为本地硬件规则资源；歧义匹配 fail closed，不再回退到自定义厂商 OID。
- 清理自定义指标 Profile 页面/API/运行入口，并增加迁移清除数据库绑定；更新 SNMP 诊断与资产导入反馈文案。
- 校正 manifest/README 对 26 个资产厂商名、25 个 OS profile 厂商、23 个本地 MIB vendor scope 与 35 个上游来源目录的说明；增加目录映射回归测试。
- 在 `.gitattributes` 对固定 LibreNMS `resources/definitions/**` 与 `mibs/**` 设置 `-text`，并重新规范化暂存对象，保证 Windows 和 Linux checkout 均保留上游原始来源字节。
- 新增完整流程图文档，明确 14 个没有 discovery YAML 的 profile、31 个当前解析器未抽出结构化硬件定义的 YAML，以及接口 exporter 当前没有新样本的限制。
- 修复 Grafana 无线面板 presentation ID 与生成器不一致的问题，并补充受影响的迁移、后端、前端和监控测试。
- 恢复 MIB 同步状态变量，并在同步状态接口查询本地 LibreNMS 规则数量；更新后台导入测试以执行 FastAPI `BackgroundTasks`。
- 总览与无线看板的无线指标统一限定 `source_type="librenms_rule"`；移除依赖未由当前 LibreNMS 规则采集的 AP 终端明细行和表，按当前 261 个面板更新目录断言。
- migration 注册测试改为按版本号核验 277、278、279，避免因后续迁移追加而错判既有注册。
