# 问题现象

v1.0.9 tag 的 Knowledge Engine Promptfoo Gate 报告 `0/50 passed; status=FAIL`，但现有脱敏日志没有给出失败阶段或异常类别，无法判断是 RAG 业务回归、Provider 运行时错误还是 GitHub runner 依赖问题。

# 根因

现有 Provider 为了避免泄露 SQL、连接串和响应体，将所有异常统一转换为 `PROVIDER_EXECUTION_FAILED`；报告脚本只读取 `failureReason`，没有读取 Promptfoo 的 `error` 或安全 metadata，导致 50 条失败被压缩成一个无诊断信息的汇总。

# 解决方案

- Provider 只记录异常类名和固定执行阶段，不记录异常消息、请求内容或凭据。
- Provider 入口层覆盖导入/初始化异常，避免 Python wrapper 直接退出造成 50 个无分类错误。
- 脱敏报告读取 `error` 字段并输出安全的 `error_type`、`error_stage`，同时在 CI 日志汇总失败类别。
- 增加回归测试，确保错误诊断不会泄露变量、URL、token 或 provider 错误正文。

# 验证命令与结果

- Promptfoo 报告测试：1 passed。
- Provider/report Python 编译：通过。
- PostgreSQL-only scanner：0 violations。
- 本机隔离 PostgreSQL Provider 契约：50/50 cases pass。

# 未验证项

GitHub Actions 的 Linux/Node 22 Promptfoo runner 需要在推送诊断改动并重新触发 tag 后确认；当前 Windows 主机缺少 Node 24 的 better-sqlite3 原生绑定，不能代替该 runner。

# 风险与回滚方式

诊断字段只包含经过字符过滤的 Python 异常类名和固定阶段，不改变 Provider 返回语义或 Promptfoo 断言。若 runner 仍失败，可根据新类别继续修复；必要时回滚本次诊断提交，不影响已推送的 v1.0.9 服务端代码。
