# 修复记录：修复监控编译PostgreSQL事务中止并实现全自动编译发布

## 1. 问题现象
1. 在生产/Docker部署环境（如 `https://192.168.18.139`）中，CMDB 已录入 2 个站点（`WH-DC-01`, `WH-DC-02`）且仅有华三（H3C）网络设备。
2. Grafana 监控大盘站点下拉列表仅显示单站点 `WH-DC-01`，且存在历史遗留测试标签（如虚拟思科核心交换机标签），大盘各面板提示 `No data`。
3. 调用采集器编译接口 `/api/monitoring/collectors/collector-local/compile` 报 HTTP 500 错误；后台日志提示 PostgreSQL 事务中止：`current transaction is aborted, commands ignored until end of transaction block`。
4. 用户明确提出诉求：监控采集器的编译与发布不应由运维人员手动去前端点击“编译”与“发布”按钮，必须实现全生命周期 100% 纯自动化联动。

## 2. 根因分析
1. **PostgreSQL 强事务语义与查询字段不匹配**：
   - 在 `backend/api/monitoring_v1.py` 的 `_load_compile_inputs` 中，查询服务器资产的 SQL 使用了 `LEFT JOIN sites s ON (s.id = pa.site_id OR s.id = pa.site)` 并且查询了 `pa.tenant_id`。然而在 PostgreSQL 中，`physical_assets` 表并无 `site` 和 `tenant_id` 列，导致该查询引发数据库异常。
   - 在 PostgreSQL 中，事务内任何一条 SQL 报错都会将该事务标记为 `ABORTED`。原本的 `except Exception:` 代码块仅捕获了异常而未执行 `conn.rollback()`，导致后续执行 `SELECT * FROM snmp_modules WHERE enabled = 1` 时直接被 PostgreSQL 拦截报错：`current transaction is aborted, commands ignored until end of transaction block`，采集器编译彻底失败。
   - 同样地，在 `preview_monitoring_plan` 中查询设备时引用了不存在的 `cli_platform`, `os_version`, `firmware_version` 等列且未 rollback；`monitoring_overview` 中查询了不存在的 `d.device_category` 列。
2. **测试静态 targets 遗留**：
   - 部署模板 `monitoring/vmagent/scrape.yml` 中保留了写死的 `192.168.204.128:9100`（带 `site_name: WH-DC-01`）；`monitoring/vmagent/targets/linux_targets.yml` 和 `snmp_targets.yml` 中残留了初始测试时填入的虚拟思科设备配置，导致 Grafana 读到历史脏标签。
3. **采集器配置缺乏自动同步引擎**：
   - 原先架构依赖前端手动点击或手动 API 调用 `compile` 与 `publish`，在资产/设备新增、编辑、删除、批量导入或服务重启后无法自动重新生成 vmagent/snmp_exporter 的 targets 文件。

## 3. 解决方案
1. **修复 SQL Schema 契约与 PostgreSQL 事务回滚**：
   - 修复 `backend/api/monitoring_v1.py` 中 `_load_compile_inputs`，移除 `pa.site` 和 `pa.tenant_id`，规范化 JOIN 条件为 `LEFT JOIN sites s ON s.id = pa.site_id`；并在异常捕获块中强制执行 `conn.rollback()`，确保连接状态清洁。
   - 修复 `preview_monitoring_plan` 中的查询字段与回滚处理。
   - 修复 `backend/api/monitoring.py` 中 `monitoring_overview` 的查询投影，将设备类型投影为 `'network_device' AS device_category`。
2. **清理硬编码与静态测试 Targets**：
   - 清理 `monitoring/vmagent/scrape.yml` 中的静态主机配置，保持由 targets 文件动态抓取。
   - 将 `monitoring/vmagent/targets/linux_targets.yml` 与 `snmp_targets.yml` 重置为标准的空列表 `[]`，等待系统根据 CMDB 真实设备全自动生成。
3. **构建监控采集器全自动联动引擎 (`collector_sync_service.py`)**：
   - 新增 `backend/services/collector_sync_service.py`，封装 `sync_all_monitoring_collectors(user)`：自动根据当前 CMDB 中的真实资产与设备，编译所有采集器方案并自动发布生效，全程无需人工干预。
   - 提供带 2 秒防抖（debounce）的后台异步触发器 `trigger_async_monitoring_sync()`。
   - 在后端启动入口 `backend/main.py` 的后台初始化线程中自动触发一次全量编译与发布；并在 APScheduler 定时任务中加入每 5 分钟自动巡检同步。
   - 在设备与资产的全生命周期操作中（`create_asset`, `update_asset`, `delete_asset`, `import_assets`, `create_device`, `update_device`, `delete_device`, `import_devices`）在提交数据库事务后自动调用 `trigger_async_monitoring_sync()`，实现录入/修改/删除即时生效。

## 7. 风险与回滚方式
- **风险**：短时间内高频大规模批量操作设备/资产可能产生多次编译任务，但已通过 `collector_sync_service` 的单飞锁（`_sync_lock`）和 2 秒防抖机制消除并发重入与资源耗尽隐患。
- **回滚方式**：可通过 `git revert` 回退代码改动；采集器 targets 文件可随时由手工或重跑全量同步重新生成。
