# RBAC 执行权限整改

## 现象

系统存在角色/profile/资源范围多套语义；一部分工单、即时命令、脚本、计划作业、Playbook 和后台恢复路径没有持续、统一地验证主体、租户/设备范围、批准内容与凭据权限。单靠界面隐藏或粗角色判断不足以保护网络变更。

## 根因

- 授权能力分散在 route、服务和 worker，入口间的权限谓词与对象范围不一致。
- 计划作业与脚本依赖可变字段/粗角色，执行时间未充分复核 owner、租户、批准 manifest 和当前用户状态。
- 配置审批展示字段可能由客户端提供；高权限凭据传入和输出保护规则缺少统一门禁。
- 旧数据 owner 归属若采用大小写不敏感的首条匹配，会在用户名大小写冲突时误归属。

## 修复

- 集中声明资源/动作授权与拒绝优先规则；加强租户和资源 scope 检查，普通用户/管理员 UI 收敛不改变服务端授权边界。
- 新增 PostgreSQL 迁移 `m0281_rbac_execution_authorization.py`，持久化配置审批 MFA 限流/TOTP 一次性消费，并为作业和脚本授权状态提供迁移支持。
- 旧任务 owner 只做精确映射；无法确定 owner 的作业禁用并要求重新授权，避免猜测租户。
- 迁移将历史非管理员账号规范为受限的普通申请者，只保留同租户工单能力；保存旧角色、profile 与资源范围快照，供人工追溯。运行时拒绝 Viewer 携带旧管理员/执行 profile。
- 绑定服务端规范化操作 manifest 与审批通知；执行阶段重新验证作业/工单/设备范围/主体与当前权限。
- 仅在明确授权的管理员凭据角色下传入 enable 密码；跨租户、tenantless 设备的非全局管理员执行失败关闭。
- 对执行错误/输出进行脱敏和受保护存储，补充安全回归测试。

## 影响文件

- 后端 RBAC、用户/scope、变更工单、配置审批、automation/device、Playbook、scheduled job、scheduler/platform registry 服务。
- PostgreSQL migration `m0281_rbac_execution_authorization.py`。
- 安全和 NSOT scope 回归测试。
- 用户、计划作业、告警审批等权限 UI 和对应计划/walkthrough 文档。

## 同一提交中并入的此前已授权工作区改动

- PostgreSQL exporter 初始化只抑制成功 SQL/NOTICE 输出，保留失败退出状态和错误信息，避免明文密码出现在部署日志。
- 资产导入复用 SNMP `sysName`、区分 pending/online/offline 状态、缩短导入提示并降低重复检查；资产设备总数统一由 summary API 驱动。
- 公共表格默认分页统一为 10 条，并同步相关旧测试断言。
- 对齐先前 GitHub Actions 回归中受影响的测试契约和 fixtures。
- 上述事项的实现过程分别记录在对应 `docs/plans/` 与 `docs/walkthrough/` 文档中；本次合并没有把 `.agents/`、`.codex/`、`handoff.md` 或本地构建/日志产物纳入交付。

## 回滚与恢复

1. 如需回滚应用代码，优先按部署版本回滚到前一稳定提交，并停止相关变更作业，避免旧 worker 与新授权数据混跑。
2. 本迁移增加持久化安全状态和 owner/tenant 标记，不应在应用回滚时自动删除表或回填列；先备份 PostgreSQL，再基于迁移内容制定单独的人工 schema 回滚。
3. 被迁移禁用的 `reauthorization_required` 作业需要管理员复核原始创建人、目标范围和操作 manifest 后重新授权，不能直接批量启用。

## 剩余风险

- 主线发布门禁若运行完整 backend pytest，仍需根据其最终 CI 结果复核；本地未完成全后端 suite。
- 对旧数据迁移后的未知 owner 和租户策略需要运维人工复核。
- `main` push workflow 会同步发布独立公开 Release 仓库；提交推送前需显式处理该发布影响。
