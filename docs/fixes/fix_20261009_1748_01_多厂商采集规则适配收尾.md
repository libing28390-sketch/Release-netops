# 多厂商采集规则适配收尾

## 问题与目标

固定 LibreNMS 来源已纳入硬件与无线采集，但 Python 执行器在少数 profile 上仍与上游轮询语义有差异。需要把现有 MIB vendor buckets 内可追溯的无线入口完整对齐，修复发现到样本的单位、索引与聚合偏差，并提交可审查的来源、实现、测试与文档。

## 根因

- LibreNMS 无线统一 dispatcher 只是入口；实际发现和采集规则由具体 OS 类实现。固定 bundle 有 20 个 dispatcher rule keys，覆盖 9 个现有 vendor buckets；其它 13 个 bucket 在 pinned revision 没有无线 OS 规则。H3C/Comware 有 MIB，但没有上游 Comware wireless discovery。
- Cisco Cellular discovery 对 RSRQ/SNR 应用 0.1 归一化因子时，轮询计划没有继承该因子，后续采样值与发现值不一致。
- Huawei VRP 上游把同一 SSID 的 2.4 GHz 与 5 GHz 客户端数相加并统计控制器总量；既有 Python poll plan 只能读取单一表 OID。
- IOS AIR 的 Python radio 标签对齐曾按字符串排序 suffix；双位 ifIndex 会导致 radio 描述错配。Ruckus Hotzone 的两个频段客户端传感器共享默认身份 suffix，会让相同指标键互相覆盖；Ruckus Hotzone 与 Ubiquiti AirOS 主 profile 也缺少独立的完整轮询行为回归。

## 修复

- 固定来源清单包含 LibreNMS wireless dispatcher、相关 OS adapter 和当前 vendor bundle 中的 MIB；29 个 PHP 文件仅作为固定上游来源材料，执行器继续使用 Python，不调用 PHP。
- 完成 20 个上游 wireless rule key 的 Python 适配与来源核验，并保留清晰标注的 H3C 本地 MIB adapter。没有为上游未提供无线 OS 规则的 bucket 臆造规则或引入新的 vendor/MIB。
- Cisco Cellular 轮询计划继承 discovery conversion factor，增加 RSRQ/SNR 发现与采样一致性回归。
- 新增 `table_multi_sum` poll plan，按索引后缀跨 OID 聚合 Huawei VRP WLAN 客户端计数；空频段对已有 SSID 贡献 0，不完整 walk 或无任何匹配记录时不伪造结果。
- 将 IOS AIR suffix 排序改为数字顺序并补足双位索引覆盖；分开 Ruckus Hotzone 2.4/5 GHz 客户端身份并补充两个 profile 的标量映射、转换及实际 poll sample 行为测试。
- 完善固定 bundle 文档、采集规则审计计划和 walkthrough；当前 v8 生产部署事实与 v8 后代码修复分别记录，避免把尚未部署的代码写成线上状态。

## 生产状态与边界

- `nexora-netops:wireless-v8-20261009` 为此前已部署并验证的生产版本；本文所述 v8 后修正未经本次发布前不可视为已部署。
- 生产现场有 Cisco/H3C 设备；Ruckus 等其它 profile 通过固定源码与模拟 SNMP 回归核验，现场尚无对应设备端到端证据。
