# 扩展经 LibreNMS 核实的多厂商光模块 SNMP 适配

## 问题现象

LibreNMS 全厂商核查完成后，项目光模块 SNMP 查询仍缺 Cisco、Arista 和 Nokia 1830 的明确 DOM 实现；实体传感器端口映射、scale/precision 和状态枚举还需要按上游行为校验。原有文档也仍记录为六家适配器且新基线 Actions 状态过时。

## 根因

- Cisco/Arista 的 ENTITY-SENSOR 表使用实体索引，而不是统一的 IF-MIB ifIndex；必须通过传感器描述或实体父级/alias 找到端口。
- Cisco 的传感器 type、scale、precision 是枚举和独立缩放字段；将 raw value 直接当 dBm 会产生错误读数。
- Nokia 不同平台的模块索引映射不同；仅 Nokia 1830 有可按 ifIndex 安全关联的已审计路径。LibreNMS Edgecore/Nokia ISAM 实现依赖额外型号或槽位推导。
- ENTITY-SENSOR 的 notPresent、uninitialized、unknown 状态不能作为有效 DOM 值。

## 解决方案

- 增加 Cisco IOS/IOS-XE/IOS-XR/NX-OS、Arista EOS 和 Nokia 1830 SNMP-only 适配器；Cisco 严格处理 dBm 类型、scale、precision、ifIndex RowPointer 与实体 parent，Arista 只接受 DOM Rx/Tx 描述并精确匹配 IF-MIB ifName，Nokia 1830 要求 ifIndex/AdminStatus Up。
- 未能确定接口映射、实体传感器状态缺失/无效、未知 Cisco scale 或无效数值时不输出该记录；不引入 CLI/Netmiko fallback。
- 完成 LibreNMS 41 家资产厂商的能力分类并记录官方上游代码与 MIB 线索；仅 MIB/元数据不足以启用 DOM 轮询。
- 将实施计划和 walkthrough 中的适配器、审计矩阵、Actions 基线与在线验证限制更新到当前事实。

## 风险与回滚方式

设备固件对实体索引、传感器描述及可选 MIB 表的实现可能不同；适配器在缺少有效状态或真实 ifIndex 映射时 fail closed。若现场验证发现数据编码不兼容，可回滚该提交中的采集器和测试；本次没有生产部署、数据库回填或设备配置写操作。
