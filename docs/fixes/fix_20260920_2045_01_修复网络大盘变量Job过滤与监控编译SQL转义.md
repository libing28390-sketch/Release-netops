# 修复记录：修复网络大盘变量Job过滤与监控编译SQL转义

## 1. 问题现象
1. **网络大盘站点与设备显示不全、接口数 No data**：
   在 `01 网络总览` 等网络大盘中，纳管设备数显示为 14，监控站点数显示为 2，但设备下拉框中仅显示 2 台设备（`R1.eve.lab` 和 `SW6.eve.lab`），其余 12 台真实设备无法列出；同时采集接口总数等依赖变量联动的面板显示 `No data`。
2. **07 Linux 服务器监控无数据/断流**：
   在 20:30 之前历史趋势图存在数据（`192.168.204.128:9100`），但在 20:30 之后数据完全中断变平，即时卡片（受纳管主机数、运行时间、CPU 使用率等）全部显示为 0。

## 2. 根因分析
1. **网络大盘模板变量限定 Job 错误**：
   在 commit `52e18394` 中，为了避免 Linux/Windows 服务器混入网络大盘，将 `make_network_variables` 限制为了 `job="snmp"`。但实际上 vmagent 的真实抓取 Job 名称为 `network_snmp`（即指标上的标签为 `job="network_snmp"`），导致真实入库的网络设备时序全部被 `job="snmp"` 过滤排除，仅匹配到残留历史测试数据的 2 台设备。
2. **监控编译 SQL 转义在 PostgreSQL 下触发占位符误判**：
   在 `backend/api/monitoring_v1.py` 的 `_load_compile_inputs` 中，查询待采集服务器的 `server_sql` 包含了 `d.device_category LIKE '%server%'`。底层数据库适配器 `backend/database/core.py` 的 `_adapt_pg_sql` 在扫描百分号时，因判定 `next_char in {'s', '%', '('}`，将 `%server` 开头的 `%s` 误判为 psycopg2 的参数占位符 `%s`。而在执行时传入的参数为空元组 `()`，导致 psycopg2 抛出 `TypeError: not enough arguments for format string`。该异常被外层 `except Exception:` 捕获并清空了服务器列表（`servers = []`），导致每次自动同步生成的 `linux_targets.yml` 均为空列表 `[]`，vmagent 因而停止对 `192.168.204.128:9100` 的抓取。

## 3. 解决方案
1. **修复 `backend/database/core.py` 中的 `_adapt_pg_sql`**：
   优化判定逻辑：仅当 `%s` 之后的字符**非单词字符**（非字母/数字/下划线）时才保留为占位符；若紧跟字母（如 `%server`、`%status`、`%switch`），说明为普通 SQL 单词文本，统一转义为 `%%`，彻底杜绝参数占位符误判。
2. **重构 `backend/api/monitoring_v1.py` 中的 `server_sql`**：
   将 `LIKE '%server%'` 改为参数化占位符传参 `LIKE ?`，并在发生异常时记录 warning 日志，禁止静默吞没异常。
3. **在 `backend/services/monitoring_compiler.py` 中为服务器补充站点默认值**：
   对未显式关联站点的服务器资产，默认补全 `site_name: 默认站点` 标签，防止由于缺失 `site_name` 标签导致 Grafana 变量过滤落空。
4. **修复 `monitoring/grafana/generate_dashboards.py` 网络变量**：
   将 `make_network_variables` 中的 `job="snmp"` 修正为兼容正则表达式 `job=~"network_snmp|.*snmp.*"`，将大盘版本号提升至 `22` 并重新编译全部 8 个仪表盘 JSON 文件。
