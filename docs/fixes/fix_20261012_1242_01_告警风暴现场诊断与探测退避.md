# 告警风暴现场诊断与探测退避

日期：2026-10-12
关联计划：[Nexora 告警与后台任务资源隔离](../plans/plan_20261012_0825_01_告警集中负载.md)

## 现场证据

- 远端虚机为 2 vCPU、约 7.7 GiB RAM。前端仪表盘的一个采样显示 CPU 73.3%，内存 2.49/7.71 GiB；这是现场瞬时值，不是 A/B 压测。
- 告警中心曾显示 558 条待处理告警，首屏是短时间集中出现的 Device Offline/严重告警，内容为网络可达性探测未响应。数据库只读聚合快照随后看到 632、638、690、713 条未解决 Device Offline 记录，计数随监控循环继续增长；页面与 SQL 快照的查询时点不同，不应当作同一时点的精确对账。
- 一次只读 join 快照中，有 540 条未解决 Device Offline 告警引用的 device_id 已不在当前 devices 表；其 created_at 范围为 2026-10-11T10:01:42+00:00 至 2026-10-12T00:21:28+00:00。另有 204 条活动告警行关联到当前 offline 设备记录。重复快照期间设备状态还在变化。
- 告警 outbox 快照显示 critical/pending=414、normal/failed=1196。修复并启动真实 Worker 可能发送数百条既有 critical 通知，因此现场 Worker 没有被重启或放行队列消费。
- nexora-alert-redis 为 healthy，Relay 正常连接并发布。critical/normal Worker 的 RestartCount 已到 30；日志显示 Celery 启动 Mingle.send_hello 调用 Redis PUBLISH，但最小权限 ACL 拒绝该命令。没有为了消除启动报错而扩大 Redis ACL。
- 从 nexora-netops 容器对代表设备 10.255.0.14:22 做一次 TCP connect 探针，返回 errno 113（No route to host）。这证明该容器当前无法通过该管理端口到达该设备，尚未确定是宿主机路由、Docker 网络还是上游 ACL 导致。

## 根因判断

源码中的 A-Loop 每 15 秒读取所有配置了 IP 的设备，以并发 20 执行 process_device_fast。设备即使已是 offline，仍会每个周期再次进行可达性探测并写 collection result。当前有大量设备无法从 Nexora 容器到达，导致快速探测和数据库写入持续放大；从服务端流程看，Device Offline 告警只在状态转换时按设备 dedupe key 创建，不能简单把每个失败探测都算成一条重复告警。

此外，设备删除路径没有关闭该设备尚未解决的告警，所以已有 540 条找不到设备记录的活动告警残留。通知 Worker 启动失败使 critical outbox 堆积，是另一个独立故障。现场 CPU 与告警风暴同时出现，但没有基线、profile 或受控负载结果，不能据此宣称 CPU 73.3% 全由告警造成。

## 本地修改

- A-Loop 对已经标记为 offline 的设备改为每 60 秒重试一次可达性探测；在线设备仍保持原 15 秒检测周期，离线恢复最多延迟约 60 秒。该退避作用于重复失败探测和 collection result 写入，预计降低持续不可达期间的探测频率，但实际 CPU 降幅待远端验证。
- critical/normal Celery Worker 增加 --without-gossip、--without-mingle、--without-heartbeat，关闭当前不使用且触发 Redis Pub/Sub 的可选 bootsteps，继续保留 Redis 最小权限。
- scripts/deploy-docker.sh 服务选择清单加入 alert Redis、Relay、critical Worker 与 normal Worker；发布契约测试覆盖该清单。
- 活动告警残留的处理策略（设备删除时以可审计方式关闭 open alerts、并评估已有孤儿告警的安全核对/修复）仍需单独实现和验证；未直接修改远端业务数据。
