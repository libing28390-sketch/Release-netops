# Git 修复记录: CMDB & IPAM 企业级架构整改（阶段7至8）及多厂商白屏修复

## 1. 问题现象
1. **企业级监控与分布式锁缺失**：需要为后台调度任务（SNMP 轮询、设备备份等）设计分布式并发调度锁，需要建立高可用的 API Latency 性能监控接口，以及规范前后端统一关联追踪 ID（X-Request-ID）。
2. **多厂商连接与指令集对齐错误**：当华三（H3C）或华为设备其平台被错误录入为 `cisco_ios` 时，后台采集或连通性测试命令会静默回退使用思科的 `show` 命令，引发连接测试假失败或采集报错。
3. **Windows 客户端启动白屏**：在打包好的 Windows 客户端上，默认启动后端服务加载页面时显示完全的白屏，这是由于 Windows 注册表 MIME 类型污染引发的。

## 2. 根因分析
1. **分布式锁与并发**：原系统未实现分布式锁，多个后台任务并发调度可能导致冲突；API 层也未做链路追踪和指标打点统计。
2. **多厂商指令与平台对齐**：系统对物理资产（vendor）与逻辑设备的 platform 缺乏强制的同步联动校验；连通性测试中统一硬编码为思科的 `show clock`，而华三/华为不支持该指令，且遇到配置不匹配时缺乏防范静默回退思科的机制。
3. **MIME 类型污染**：部分 Windows 主机的注册表被其他编辑器（如 VS Code）污染，将 `.js` 文件类型修改为 `text/plain`。导致 FastAPI 的 StaticFiles 组件以 `text/plain` 形式返回脚本，触发了浏览器的严格 MIME 校验安全机制，直接拒绝执行 JS 并白屏。

## 3. 解决方案与实施步骤
1. **企业级整改（阶段7-8）**：
   - 实现了 [context.py](file:///d:/netops/netsops-main/backend/core/context.py) 存储协程链路 Request ID；
   - 实现了分布式锁 [scheduler_lock.py](file:///d:/netops/netsops-main/backend/core/scheduler_lock.py) 与 `@synchronized_scheduler_job` 装饰器，防止周期任务重叠；
   - 新建了监控指标体系 [metrics.py](file:///d:/netops/netsops-main/backend/core/metrics.py) 与 API [health.py](file:///d:/netops/netsops-main/backend/api/health.py)；
   - 在前端 [http.ts](file:///d:/netops/netsops-main/src/api/http.ts) 中注入错误拦截与链路 ID 显示。
2. **多厂商对齐与防静默回退**：
   - 新建了对齐模块 [platform_utils.py](file:///d:/netops/netsops-main/backend/core/platform_utils.py)，根据 `vendor` 字段强行将 empty/Cisco platform 纠正为厂商默认平台（如 `h3c_comware` / `huawei_vrp`）；
   - 在 [netmiko_driver.py](file:///d:/netops/netsops-main/backend/engine/drivers/netmiko_driver.py)、[scheduler_service.py](file:///d:/netops/netsops-main/backend/services/scheduler_service.py)、[configs.py](file:///d:/netops/netsops-main/backend/api/configs.py) 和 [devices.py](file:///d:/netops/netsops-main/backend/api/devices.py) 中全面引入该对齐，并在前端实现正确的 H3C/华为指令渲染。
3. **MIME 映射覆写**：
   - 在 [main.py](file:///d:/netops/netsops-main/backend/main.py) 入口处硬编码加入 `mimetypes.add_type('application/javascript', '.js')`，强行重写静态文件解析。
