# 配置备份单会话双配置采集与非 22 端口精准诊断修复记录

## 1. 提交目的与问题现象
- **问题 1（错误提示硬编码误导）**：非 22 端口（如 2222、8022 等）设备在备份超时或被拒绝时，界面诊断一律硬编码显示“确认防火墙是否放行 22 端口”，造成严重排障误导。
- **问题 2（批量备份凭据/端口回溯缺失）**：`run_scheduled_backup` SQL 查询遗漏 `asset_id`，导致 `resolve_device_credentials()` 无法读取物理资产中的自定义端口与特权凭证。
- **问题 3（VTY 会话冲突与二次连接风暴）**：开启启动配置采集时，系统先后发起两次独立的 SSH 连接，容易触发设备端 VTY 线路尚未释放（释放延迟 2~3 秒）而直接拒绝连接，导致批量备份超时或失败。
- **关联优化**：包含了本批次资产管理与设备清单增加“全部”卡片及全量条数分页对齐、登录页与监控大屏 UI 动效重构。

## 2. 根因分析
1. `backend/drivers/ssh_compat.py` 中的 `diagnose_ssh_failure` 与 `build_ssh_transport_guidance` 未支持动态 `port` 参数，文案直接写死“22 端口”。
2. `backend/api/configs.py` 在 `run_scheduled_backup` 中遗漏 `asset_id`，且在调用诊断函数时未透传设备解析出的管理端口。
3. 双配置采集在两个独立的协程和驱动生命周期中分别发起连接，造成短时间内对同一设备并发/重连风暴。

## 3. 解决方案
1. **动态端口诊断支持**：在 `diagnose_ssh_failure` 与 `build_ssh_transport_guidance` 中接收 `port` 参数，动态输出 `{port_str}`（如“确认防火墙是否放行 2222 端口”）。
2. **补齐查询与诊断透传**：`run_scheduled_backup` 的 `SELECT` 语句补充 `asset_id`，并在失败诊断时传入 `port=resolve_ssh_port(d)`。
3. **单会话流水线下发（Single-Session Double Collection）**：将 `commands` 组装为 `[_running_cmd, _startup_cmd]`，在单次 SSH 驱动会话内顺序下发并读取双份回显，全流程仅占用 1 条 VTY 线路，彻底杜绝 VTY 耗尽。
