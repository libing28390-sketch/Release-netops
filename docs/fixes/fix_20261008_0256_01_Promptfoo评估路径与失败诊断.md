# Promptfoo 评估路径与失败诊断修复

## 问题现象

v1.0.9 标签触发的 Promptfoo RAG 质量门禁中 50 个用例都在约两秒内报 `evaluation_error`，没有产生成功用例。隔离 PostgreSQL 语料初始化与 AI/RAG release 配置检查均通过。

## 根因

Promptfoo 0.118.0 按评估 YAML 的目录解析 Python provider 路径。配置从仓库根加载 `docs/knowledge-engine/eval/promptfoo-rag-gate.yaml`，但 `python:scripts/promptfoo_nexora_provider.py` 被解析到不存在的 `docs/knowledge-engine/eval/scripts/` 下。正确 provider 脚本在仓库根 `scripts/` 目录。

报告脚本还优先将 `failureReason` 当作错误文本；Promptfoo 0.118.0 使用数字枚举表示失败类型，数字会覆盖实际 `error` 字符串，造成全部错误都退化为泛化分类。

## 解决方案

- 将 provider 路径改为相对 YAML 目录的 `../../../scripts/promptfoo_nexora_provider.py`。
- 失败分类优先使用实际字符串错误；数值失败枚举独立映射到稳定类别，并对常见脚本文件缺失错误给出 `provider_setup_error` 分类。
- 增加配置路径存在性和 Promptfoo 0.118.0 错误结构测试，同时断言原始错误文本不写入脱敏报告。

当前本地没有 Promptfoo Node 依赖与隔离 PostgreSQL 服务，因此未在本机执行 Promptfoo 端到端评估。由 workflow 的临时 PostgreSQL 服务执行 smoke/full 评估；真实 HCL/设备不参与此门禁。

## 风险与回滚方式

如果 Promptfoo 的实际路径解析规则与固定版本预期不同，smoke 会在运行阶段直接暴露错误；新增回归测试同时固定了本仓库 YAML 目录到 provider 文件的路径关系。若需回滚，回退本记录所列配置、报告脚本、测试与文档提交即可；恢复旧错误路径会使标签评估再次在 provider 启动前失败。
