# 问题现象

项目容器数量增加后，Windows 原生桌面发行链路与 Linux/Docker 服务端发布链路混在一起，v1.0.9 的用户容易误解为仍支持 Windows 服务端部署。清理过程中还需要确保 Windows 工作站从浏览器访问 Linux 服务端时，Terminal Agent 和 Web PAM 本机浏览器能力不被误删。

# 根因

发布 workflow 同时包含 Ubuntu/Linux 与 Windows 桌面 job，仓库根目录保留 `desktop/`、Windows EXE、pgvector Windows 资源、`start.bat` 和 Windows 部署文档。前端与 API 还需要区分“服务端运行平台”和“浏览器工作站平台”，否则简单移除 Windows 会破坏远程 Windows 工作站接入。

# 解决方案

- 删除 Windows 原生服务端桌面包、打包资源、Windows pgvector 运行时和 Windows 服务端发布 job。
- 保留 Windows Workstation Agent 源码/PowerShell 自启动能力和 Web PAM 系统浏览器拉起；新增 tag-only Windows Agent 构建 job，作为独立 Release 资产发布。
- API 按 `platform` 返回 Linux installer 或从 `TERMINAL_AGENT_WINDOWS_URL` 流式返回 Windows Agent；Compose/.env 预留内网地址配置。
- 更新 release target matrix、知识门禁、部署文档和 v1.0.9 release notes，明确 v1.0.8 是最后一个 Windows 原生服务端版本。

# 实际修改文件

- 发布与配置：`.github/workflows/release.yml`、`.env.example`、`docker-compose.yml`、`Dockerfile`、`.gitignore`、`package.json`。
- 后端与前端：`backend/main.py`、`backend/api/system.py`、`backend/core/api_security.py`、前端版本 fallback 与 Terminal Agent 相关入口。
- 删除 `desktop/`、`NetOps.exe`、`NetOps.spec`、`start.bat`、Windows pgvector 资源和 Windows 服务端部署文档。
- 文档与门禁：`README.md`、`DEPLOY.md`、`docs/README_gitee.md`、`docs/deploy/*`、Knowledge Engine target/eval 文件及 `scripts/knowledge_eval_ci_gate_check.py`。

# 风险与回滚方式

- 若 v1.0.9 Workstation Agent 资产发布失败，先将 `TERMINAL_AGENT_WINDOWS_URL` 指向企业内部已验证的 EXE；服务端仍可回滚到 v1.0.8 Windows 原生包或 Linux release 前一提交。
- Windows 资产管理、WinRM、监控和工作站 Web PAM 属于运行时能力，未随服务端发行平台清理删除。
