# 设备等待中与自动化离线状态

## 问题

- 资产设备列表中新录入设备长期显示“等待中”。
- 自动化任务页面将同一设备显示为“离线”。
- 设备 SSH 端口和账号实际可用，但状态不会自动恢复。

## 根因

- 关联设备创建时 `devices.status` 默认为 `pending`。
- 15 秒快速探活循环查询时排除了 `pending`，导致新设备永远没有第一次状态探测机会。
- 自动化页面仅把 `online` 识别为在线，因而把 `pending` 显示为离线。
- 原探活只依赖 ICMP Ping，禁止 Ping 但管理端口可达的设备也可能被误判离线。

## 解决方案

- 快速探活循环纳入所有配置了 IP 的设备，包括 `pending`。
- 在线判定改为 ICMP 优先、管理 TCP 端口兜底；任一成功即视为在线。
- TCP 兜底仅检查端口可达性，不进行每 15 秒一次的 SSH 登录。

## 修改文件

- `backend/engine/orchestrator.py`
- `backend/services/background_monitor_service.py`
- `backend/tests/test_device_reachability.py`

## 数据与实机验证

- PostgreSQL 查询确认两台设备原状态均为 `pending`，凭据接入状态均为 `verified`。
- `192.168.18.201:22`、`192.168.18.202:22` TCP 可达。
- 使用普通账号对两台设备执行只读 `show clock` 均成功，旧 SSH 算法兼容正常。
- 临时启动后端后，一个探活周期内两台设备均自动更新为 `online`。
- 投产状态保持独立：`.201` 为 `staging`，`.202` 为 `production/exempt`。

## 测试

- `pytest backend/tests/test_device_reachability.py backend/tests/test_asset_production_takeover.py -q`：11 passed。
- 全量后端：372 passed，1 failed，1 warning。
- 失败项 `test_cmd_cache.py::test_send_command_caching_integration` 与本次修改无关；该测试对模拟 IP 的 SSH 端口预检未做 mock，单独复跑仍失败。

## 风险与回滚

- 管理端口开放但应用层 SSH 异常时，设备会显示在线；实际命令执行仍会返回明确的认证或协议错误。
- 回滚会重新造成 `pending` 设备无法进入首次探活的问题。
