# TextFSM 迁移编号冲突

## 问题与根因

PR #22 合入后，AI 缓存用量迁移和 H3C Comware V7 BGP VPN 实例命令迁移都使用了编号 `339`。迁移发现器拒绝重复编号，导致 PostgreSQL 初始化和依赖数据库的测试失败。PR 同时引入了使用 SQLite 的测试夹具，触发了 PostgreSQL 源码检查。

## 修改

- 保留 AI 缓存用量迁移 `339`，将 H3C Comware V7 迁移移至 `347`，并更新 `m0345_h3c_v9_bgp_vrf_route_command.py` 对共享函数的引用。
- 在 `backend/database/migrations/__init__.py` 中处理已登记 H3C 旧 `339` 的数据库。AI 字段补齐与旧记录更正同事务提交，随后按顺序应用待执行的迁移。H3C 命令修复可重复执行。
- 在 `backend/tests/database/test_db019_current_highest_upgrade.py` 加入旧记录升级的回归测试。将 `backend/tests/platform_registry/` 下 `340`、`341`、`344`、`347` 的测试切换为隔离的 PostgreSQL 数据库。

## 验证

- 用隔离数据库运行 `python -m pytest backend/tests/database/test_db019_current_highest_upgrade.py backend/tests/database/test_db020_fresh_failure_rollback.py backend/tests/platform_registry -q --tb=short`。新库初始化、旧 `339` 升级、重复执行，以及 H3C 和锐捷迁移的定向用例均通过。
- PostgreSQL 源码检查在拟提交的源码范围内报告零违规。本地被 Git 忽略的 ODF 测试仍会被全目录扫描命中。
- `git diff --cached --check` 通过。
- 远端 GitHub Actions 和部署环境待对应版本运行后核验。

## 风险与回滚

升级前按现有流程备份 PostgreSQL。升级后若需回滚，应恢复升级前的数据库备份并切回冲突合并前的已知正常版本。直接退回含重复 `339` 的版本会再次阻断迁移发现。
