# 硬件指标抓取超时

## 问题现象

生产 `/hardware-metrics` 抓取处理 3,847 条活动传感器和 144 条能力记录需 78–100 秒，vmagent 因等待响应超时而无法接收硬件指标，Grafana 设备详情的 CPU/内存/温度等面板显示无数据。

## 根因

硬件指标生成对每条传感器重复执行 LibreNMS 来源证明校验。多条传感器若来自同一 provenance，校验输入相同但仍重复扫描规则和来源文件。生产日志将瓶颈定位在传感器校验与分组阶段。

## 解决方案

为单次 `/hardware-metrics` 抓取引入完整 provenance 指纹缓存，仅对相同来源证明复用 trust 判定；传感器行仍独立执行新鲜度处理与渲染，任何来源字段冲突都会产生不同缓存键。日志新增来源校验耗时及命中/未命中数，便于生产验证。

## 验证

- `python -m pytest tests/monitoring/test_grafana_metrics_export.py tests/snmp/test_librenms_source_policy.py -q`：23 passed。
- `python -m compileall -q api/grafana_metrics.py services/librenms_source_policy.py`：通过。
- 3,847 条相同 provenance 的本地基准：重复执行验证 14.410 秒；单次验证后按 provenance 复用 0.072 秒，省去 3,846 次验证。此为来源校验微基准，不等同完整生产 HTTP 抓取耗时。

## 风险与回滚

缓存只存在于单个 scrape 请求，且键包含 trust policy 消费的全部来源字段；回归测试覆盖相同来源复用、冲突来源重新判定、拒绝不可信来源以及保留重复传感器输出。若生产验证失败，恢复部署前的 NetOps 镜像并重建该容器即可；未修改数据库 schema 或 VictoriaMetrics 数据卷。
