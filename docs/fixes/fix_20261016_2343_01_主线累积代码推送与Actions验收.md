# 主线累积代码推送与 Actions 验收

## 问题现象 / 本次提交目的

工作区累计了多个已完成任务的前后端源码、测试、数据库迁移、容器部署配置与文档修改，需要完整推送至 `main`，并验证由 main push 触发的 GitHub Actions。Actions 成功后按用户授权更新 `192.168.204.128` 上的 Docker 部署。

## 根因

改动跨多个历史任务尚未形成提交；工作区同时含大量本地构建目录与诊断日志，不能把它们误当成源码纳入提交。预检还发现 Linux 综合巡检输出的 TCP 重传兼容字段与契约断言不一致；全量前端测试在高负载下有三个交互用例的超时余量不足。

## 解决方案

- 纳入全部已跟踪源码/配置/测试修改及新增源码、迁移和测试；将本地构建输出、`dist-*` 副本和 `logs/` 排除在提交之外。
- 保留 TCP 重传率输出的 `:-0` 缺省兼容表达式；将仅在全量高负载下触顶的三个前端交互测试超时设为 20 秒，不改变其断言。
- 巡检概况通过统一 `apiRequest` 读取，使 401 响应触发全局登录失效事件。
- Docker 部署文档补充默认 Guacamole/`guacd` 的资源预算与合计上限。
- 提交前检视 GitHub Actions：main push 会运行完整 Linux/PostgreSQL 与前端门禁，并在成功后同步清理过的发布树。

## 实际修改文件

本次提交包含当前工作区所有有意保留的源码、测试、迁移、部署配置与正式部署文档修改；精确清单以提交记录为准。此提交记录同时纳入版本控制。

## 风险与回滚方式

- main push 成功后会由现有 release workflow 强制同步清理过的 Ubuntu 发布树至公开 `Release-netops` 仓库；这是工作流现有行为。
- 部署脚本会在目标机器先备份 `.env`、PostgreSQL 与配置快照，再同步发布树并重建需要更新的容器；不删除数据卷。如更新失败，先检查备份与容器日志，再使用后续回滚提交或恢复前一份发布树，不执行 `docker compose down -v`。
