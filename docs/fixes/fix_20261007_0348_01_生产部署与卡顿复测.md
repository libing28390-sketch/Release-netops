# 生产部署与卡顿复测记录

## 问题现象

用户反馈监控看板刷新、Grafana 加载和资产添加/修改表单打开与保存较慢。部署前七轮约5分钟的远端采样反复记录到后端与 Nginx API 秒级停顿，但 PostgreSQL 没有对应的持续慢查询或锁等待证据；生产精确 MIB 符号查询计划则确认对 `snmp_mib_nodes` 执行全表扫描。

## 根因与范围

- 采集路径的硬件传感器样本逐行锁定并更新，放大了数据库往返；部分同步数据库工作位于异步采集路径。
- MIB 查询使用 `LOWER(node_name)` 精确匹配，原始列索引不能支持该表达式。
- 当前生产规模为17台设备、15台绑定 SNMP、5,296个 active sensors；本次生产采样不能证明300台真实设备的承载能力。

## 解决方案与部署

- 传感器样本改为按设备批量写入；将样本持久化和采集状态同步中的阻塞数据库工作移出 async event loop。
- 增加 `LOWER(node_name)` 表达式索引迁移 m0276，并确保 fresh schema 同样创建索引。
- 为11个 Compose 服务设置 CPU、内存和 PID 上限；Nginx 默认 worker 数设为1，Uvicorn 保持1 worker。
- Actions #678（`37516754689`）完整通过，发布树 `Release-netops` 提交为 `d2c0629`。生产部署前备份位于 `/data/netops-release-backups/release-20261007-032303`；发布路径冲突的旧诊断文件保存在 `/data/nexora-preserved-untracked-20261007-032348`。部署时跳过了 Grafana dashboard 清理步骤。

## 部署后验证

- 11个容器均运行，9个具有 healthcheck 的容器均 healthy；所有11个服务的 CPU、内存和 PID 限额均非零。Nginx `nginx -t` 通过，运行中为1 worker。
- 生产已登记 m0276；对精确 `LOWER(node_name)` 查询的只读 EXPLAIN 显示使用 `idx_snmp_mib_nodes_name_lower`。
- 两轮300秒采样分别在03:31:14–03:36:14和03:38:02–03:43:02（Asia/Shanghai）。后端 live p95 分别39.8ms和266.4ms；Nginx live p95分别215.8ms和243.3ms。第一轮有一个1,326.4ms的代理请求，未超时；第二轮没有≥1秒请求或超时。
- 两轮 PostgreSQL 活动样本各299次，active query 最大224.5ms和386.9ms，无 lock wait/blocker。`snmp_mib_nodes` 顺扫及 tuple-read 增量均为0，表达式索引扫描每轮增加144次。没有观察到 cgroup throttling 或 OOM。
- 隔离 PostgreSQL/fake-SNMP 的300台、93,192样本对照中，按设备批量写入将单轮采集周期从143.799秒降到26.142秒，SQL数从186,649降到529。该结果只适用于隔离测试环境，不是生产时延承诺。

## 未验证项

资产 API 与 Grafana dashboard URL 在无登录态采样中返回401；因此真实资产新增/修改保存、已认证看板加载和 PromQL 查询没有被验证。第一轮代理尖峰尚未在第二轮复现，但应保留在观察记录中。生产仍为17台设备，本次没有进行300台生产压测。

## 风险与回滚

部署前已备份 PostgreSQL、Source Manifest、部署配置/TLS 与设备配置快照。应用级回滚可从部署前备份恢复并回退发布树版本；m0276 为新增索引，可按维护窗口评估单独删除，但删除会恢复 MIB 精确查询的全表扫描。没有更改真实网络设备配置或生产资产数据。
