# 发布 v1.0.9

## 问题现象与发布目的

今天完成的 SNMP 诊断、MIB/OID 浏览、Grafana 仪表盘、共享弹窗交互、Docker S3 默认存储及 Grafana 登录集成改动仍在工作区未提交。远端 `v1.0.9` tag 指向较早提交，GitHub Release 需要由版本 tag workflow 发布本次代码。

## 根因

工作区累积了多个面向同一版本的已授权改动；`package.json`、`package-lock.json` 与 `backend/core/version.py` 已是 `1.0.9`，但已存在的远端 `v1.0.9` tag 尚未移动到本次代码提交。

本次启动反馈另发现，Grafana 路由在导入时调用 `require_role`，但 `backend/api/users.py` 未导入该符号，导致开发后端启动失败。

## 解决方案

导入 `require_role` 并通过后端 API 模块加载验证。按用户要求，将今天确认的工作区改动提交到 `main`，再强制把源仓库和发布仓库的 `v1.0.9` tag 指向该提交。更新构建日期与 release notes；版本 tag 会运行完整发布门禁，并由 workflow 创建或更新同名 release 与发布产物。

## 验证命令与结果

- 版本核对：`package.json`、`package-lock.json`、`backend/core/version.py` 均为 `1.0.9`。
- `.env` 与备份文件状态：均被 Git ignore，不在待提交差异中。
- `git diff --check`：通过；仅见仓库 CRLF 配置对若干文件的转换提示。
- `.venv\\Scripts\\python.exe -c "import sys; sys.path.insert(0, 'backend'); import api.users"`：通过，确认缺失导入修复后 API 模块可加载。
- 发布质量门禁：由推送 `v1.0.9` 后 GitHub Actions 执行；最终结果以该 workflow 和 Release-netops 的发布状态为准。

## 未验证项

- 本地没有 Docker CLI，无法执行 `docker compose config` 或容器级启动验证。
- 按当前任务约束未在本机运行测试、前端构建；版本 tag workflow 会执行仓库定义的发布测试、lint、构建和打包门禁。
- 如果远端 workflow 尚未结束或失败，不将其描述为发布成功。

## 风险与回滚方式

- 强制覆盖 `v1.0.9` 会改变既有 tag 目标。原目标是 `ee1a368e3a9ffda466495208395f510ef1eb227d`；若需恢复，可将源仓库 `v1.0.9` 及 Release-netops 的同名 tag 恢复到旧提交。
- `main` 推送会触发发布仓库分支同步；tag 推送会触发正式发布 workflow。该流程不等同于部署生产服务，不会迁移现有本地 PAM 录像或配置备份。
