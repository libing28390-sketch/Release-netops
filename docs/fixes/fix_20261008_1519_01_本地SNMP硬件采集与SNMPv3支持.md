# 本地 SNMP 硬件采集与 SNMPv3 支持

## 问题现象

Grafana 的硬件采集视图没有设备数据，SNMP 诊断界面却提示必须先配置并启用 LibreNMS。目标架构是由 Nexora 本地采集 SNMP 硬件数据，LibreNMS 不应成为本地采集必需依赖。已保存并绑定的 SNMPv3 profile 也不能完整通过本地采集、探测和诊断链路。

## 根因

本地硬件发现、周期采样、凭据解析和 SNMP 诊断没有统一使用设备绑定的安全 profile；部分路径仍以 v2c community 是否存在来判断凭据有效。无线仪表盘的传感器筛选也只覆盖 LibreNMS 原生来源。与此同时，展示契约仍要求旧的 LibreNMS 专属面板标题，与当前生成器和仪表盘 JSON 不一致，导致仪表盘目录测试失败。

## 解决方案

- 将已绑定的 SNMPv1/v2c/v3 profile 用于本地只读 GET/WALK、硬件发现、周期采样和诊断；补充 SHA-2 认证插件，并对缺失或不支持的安全参数明确报错，不降级到空 community。
- 增加本地硬件结果归一化、轮询和探测路径；前端使用已绑定设备与版本进行诊断，不传递密钥。
- 保留 LibreNMS 为可选集成，资产纳管与诊断在实例已配置时使用对应 API；本地采集不要求在 Docker Compose 中部署 LibreNMS。
- 无线面板同时查询本地 SNMP 与可选外部来源，并同步 V2 展示契约的面板标题。
- 将资产导入、设备诊断、采集结果摘要和 SNMP WALK 的界面与测试调整到新的响应契约。

真实采集仍依赖设备可达、正确绑定的 SNMP profile 和设备实际提供的 OID。若实例配置 LibreNMS，外部纳管还依赖有效 API 地址、Token 和权限。出现回归时可回退本记录对应的代码与展示配置提交；本次不修改数据库 schema，不部署服务，也不触发设备配置变更。
