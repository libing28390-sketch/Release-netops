# 修复记录：工作区功能交付

## 问题现象

工单管理、变更审批、巡检与自动化、资产 SNMP 采集控制等多个已完成的工作区修改尚未提交到 `main`，因此没有统一的 GitHub Actions 结果。

## 根因

此前分批实现和验证了多个功能，但代码、测试和正式项目文档留在同一工作区等待整体交付；构建输出和内部协作文件也同时存在，不能直接执行全量 `git add`。

## 解决方案

- 将业务源码、测试、PostgreSQL 迁移以及对应正式计划/走查文档纳入一个原子提交。
- 排除 `.agents/`、`.codex*`、`handoff.md`、日志与构建产物。
- 推送前读取远端 `main`，只做快进推送，不改写远端历史。
- 将 GitHub Actions 成功设为关机前置条件；失败时根据具体 job 继续排查。
- 巡检指标页默认保留精简列；进入编辑状态时临时展示隐藏字段，避免单位、解析类型等字段因默认隐藏而无法修改。阈值规则与状态说明通过详情弹窗查看。

## 实际修改文件

本记录与当前工作区中已完成的工单、变更审批、巡检、自动化 UI 和设备级 SNMP 采集开关相关源码、测试及文档一并提交；最终文件清单以提交差异为准。

## 未验证项、风险与回滚方式

- 最近两次 `git fetch origin main` 和一次 `git ls-remote` 都因 HTTPS 连接重置/超时失败；稍早一次成功读取到 `origin/main=85c63b0c`。推送前继续重试，并使用普通非强制推送保护远端历史。
- `main` push 会触发仓库发布工作流，将净化后的发布树同步至 `Release-netops`；不创建 tag。
- 若 Actions 失败，保留当前提交，按失败日志追加修复提交；常规 `git revert <commit>` 可回滚代码，不使用 reset 或 force push。
