# 修复记录：修复CI环境采集器后台自动同步与测试数据库隔离竞争

## 1. 问题现象
在 GitHub Actions CI 流水线运行完整全量测试（2275个测试）时，出现 2 处断言失败报错：
1. `FAILED backend/tests/monitoring/test_network_monitoring_list.py::test_network_monitoring_list_is_server_paginated_and_server_devices_are_excluded - assert 66 == 65`
2. `FAILED backend/tests/test_rack_read_model.py::test_rack_summary_filters_search_and_pagination_use_the_same_health_contract - assert 4 == 3`

## 2. 根因分析
1. **后台异步定时器在测试环境中被意外触发**：
   - 在上一提交中引入的 `collector_sync_service.trigger_async_monitoring_sync` 使用了 2 秒防抖的 `threading.Timer`。
   - 当测试套件中涉及设备/资产增删改的用例执行时，在用例结束后 2 秒后台定时器依然在后台线程中唤醒并执行 `sync_all_monitoring_collectors`。
   - 后台线程执行数据库读写时，与正在运行的后续测试用例共享或抢占了全局数据库连接池，造成了脏数据竞态。
2. **应用启动后台自愈与调度任务未对测试环境做屏蔽**：
   - `backend/main.py` 的 `_bg_init()` 和 APScheduler 调度器在 `ENVIRONMENT=test` 或被 pytest 导入时依然执行了自动同步。
3. **conftest 中 schema template 未切回主连接**：
   - 在 `backend/tests/conftest.py` 的 `_postgres_schema_template` 夹具中，构建完 `template` 数据库后，未将 `database_core._DATABASE_URL` 切回 `source_url`，导致后续非 `isolated_db` 的用例与后台任务直接操作了 `template.url`，破坏了隔离数据库模板的洁净度。

## 3. 解决方案
1. **测试环境静默后台自动同步线程**：
   - 在 `backend/services/collector_sync_service.py` 的 `trigger_async_monitoring_sync` 中增加环境判断，在 `ENVIRONMENT == 'test'`、`PYTEST_CURRENT_TEST` 或 `pytest` 运行时直接返回，杜绝测试执行期间任何后台线程异步重入。
2. **屏蔽应用启动在测试环境下的自动抓取与调度**：
   - 在 `backend/main.py` 的 `_bg_init()` 及 `lifespan` 调度器注册处，增加非测试环境判断（`ENVIRONMENT != 'test'` 且无 `PYTEST_CURRENT_TEST`）。
3. **隔离数据库模板主连接还原**：
   - 在 `backend/tests/conftest.py` 的 `_postgres_schema_template` 完成模板数据库初始化后，立即显式调用 `switch_database(source_url, initialized=True)`，确保模板数据库仅作为只读克隆源，主连接安全归位。

## 4. 实际修改文件
- `backend/services/collector_sync_service.py`：添加测试环境短路保护，防止测试期间产生异步定时器线程
- `backend/main.py`：在启动初始化与定时调度器中跳过测试环境的采集同步
- `backend/tests/conftest.py`：在 `_postgres_schema_template` 初始化后还原 `source_url`
- `docs/fixes/fix_20260920_1205_01_修复CI环境采集器后台自动同步与测试数据库隔离竞争.md`：本修复追踪记录
