# 修复记录：移除手动 targets 文件并保持 CMDB 统一纳管机制

## 1. 问题现象与用户反馈
用户明确指出：“所有设备不都是纳管好的吗 为啥还需要单独写yml，你这次添加的targets目录是不是搞错了，没必要吧”。

## 2. 根因分析
1. **CMDB 是系统唯一的真实资产事实源**：NetOps 平台的架构规范要求所有设备（无论是交换机、路由器，还是服务器）均通过 CMDB（资产中心）统一录入和集中纳管，采集目标由后台调度与编译服务（`monitoring_compiler`）自动导出并调度，绝对不需要也不应该由运维人员在底层手工编写或维护 `.yml` targets 文件；
2. **多余文件的产生原因**：上一轮为了验证 `windows_exporter` 与 `node_exporter`，在 `monitoring/vmagent/targets/` 下创建了手动的 `linux_targets.yml` 与 `windows_targets.yml`，并修改了 `scrape.yml`。这种做法脱离了 CMDB 自动化纳管主流程，属于冗余设计；
3. **大盘无数据的实际背景**：当前系统 CMDB 资产库中纳管的 14 台设备全部为网络设备（交换机、路由器、防火墙），目前尚未在 CMDB 中录入任何 Windows 或 Linux 服务器资产，因此服务器专用大盘（07 与 08）当前显示为无数据是完全正常的业务状态，并不需要通过手动手写 yml 去强行对接。

## 3. 解决方案与实施
1. **清理冗余配置文件**：
   - 彻底删除 `monitoring/vmagent/targets/linux_targets.yml`；
   - 彻底删除 `monitoring/vmagent/targets/windows_targets.yml`；
2. **恢复采集作业原生配置**：
   - 还原 `monitoring/vmagent/scrape.yml`，移除手动追加的 `linux_nodes` 和 `windows_nodes` 外部静态抓取作业，保持系统单一数据源编译机制；
3. **保留有效成果**：
   - 维持此前已完成的 Top 接口表格名称补全（`ifDescr` + `ifName` + `ifIndex`）以及 Grafana 系列选择器语法修复（消除 Validation 报错）。

## 4. 实际修改文件
- `monitoring/vmagent/scrape.yml`
- `monitoring/vmagent/targets/linux_targets.yml` (删除)
- `monitoring/vmagent/targets/windows_targets.yml` (删除)

## 5. 验证命令与结果
- 执行 `git status -s` 确认多余 targets 文件已彻底移除；
- 运行 `python scratch/validate_dashboards.py` 确认大盘结构保持有效。

## 6. 风险与回滚方式
- 无业务风险，系统恢复纯净规范架构；
- 需回滚可执行 `git checkout HEAD~1 -- monitoring/`。
