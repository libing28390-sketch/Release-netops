# 修复记录：采集模块菜单下线与厂商覆盖解析

## 1. 问题现象
1. 用户在查看 `monitoring/snmp-exporter/snmp.yml` 后发现其已包含大量主流厂商规则，确认前端 `/monitor/modules`（模块目录）作为在线动态编排页面属于冗余低频入口，指示将其直接下线；
2. 用户询问先前 H3C 交换机部分接口状态为 `unknown` 是否由 CLI 获取，以及为何不优先使用 SNMP。

## 2. 根因与原理解析
1. **`snmp.yml` 全厂商覆盖度**：
   - 经实测分析，`monitoring/snmp-exporter/snmp.yml` 内置了 **20 套成熟模块**，完整覆盖通用接口、系统 MIB，以及思科、华为、华三、锐捷、瞻博、飞塔、中兴、迈普、迪普、山石、深信服、神州数码和 6 大无线 AC 控制器，底座已具备全厂商静态配置能力，无需普通管理员在前端二次建模。
2. **H3C 接口 `unknown` 产生根因**：
   - 来源包含两个途径：
     - **CLI 途径（TextFSM 自动化解析）**：系统在早期资产巡检中使用 `display interface brief` 命令。华三 Comware 二层 Bridge 模式端口没有三层 Protocol 状态（显示为空或 `--`），老旧解析逻辑因找不到协议状态直接兜底判定为 `unknown`；
     - **拓扑 LLDP 邻居发现**：当对端端口尚未被录入系统时，拓扑引擎临时插入占位记录时使用了 `unknown`。
3. **为什么应当且可以使用 SNMP**：
   - SNMP RFC 1213 / RFC 2863 `IF-MIB` 中的 `ifOperStatus`（`1.3.6.1.2.1.2.2.1.8`）是交换机硬件驱动层原生状态（`1=up`, `2=down`），无论是二层 Access/Trunk 还是三层路由口，只要有光/电信号即返回 UP，无信号即返回 DOWN，不受二层/三层协议是否配置 IP 的干扰；
   - 系统最初重在 SSH 自动化（设备未全部配置 SNMP community），因此遗留了 CLI 收集逻辑。当前在 Prometheus 与监控大盘中已经全面采用 SNMP `ifOperStatus` 高频采集。

## 3. 解决方案
1. 在 `src/components/AppSidebar/navConfig.ts` 中移除 `monitoring-modules` 项，实现菜单静默下线；
2. 保持路由与核心组件兼容，不影响历史 API 运行；
3. 详细向用户解答 `snmp.yml` 厂商清单与 H3C 接口状态机制。
