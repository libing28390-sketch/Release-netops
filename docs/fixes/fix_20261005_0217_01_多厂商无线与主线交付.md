# H3C/Huawei 无线监控与主线交付

## 问题现象

- Huawei AC 有 AP/射频/SSID 数据，但 Nexora 目录和探测缺少 AP Radio、VAP 行及完整 AP 身份/资源数据。
- H3C 无线适配未覆盖 Station AssociateTable 与官方 Radio 表的全部已核验列，且文本型无线属性应进入库存历史而不是数值 Prometheus 指标。
- 硬件探测中完整空 walk 的类别覆盖语义不一致；Comware transceiver 设备关联漏传 identity；UniFi 没有有效 CPU 读数时可能生成空传感器。
- `/assets/network-devices` 全部列默认开启导致横向滚动，机柜字段可能显示内部标识；专线表单曾展示无有效 ifIndex 的接口选项。

## 根因

- Huawei 无线 adapter/catalog 只覆盖 AP 数、部分 SSID 与 AP CPU/内存，未把 LibreNMS VRP Radio、VAP 与 AP 表索引接入发现、轮询和 exporter 规则。
- H3C Station/Radio 使用不同的表索引格式；字符串属性需要作为原始库存数据持久化，并且文本 measurement type 不应经过数值有限性校验。
- 类别结果需要表达成功扫描但无实例（`not_found` 且覆盖扫描完整）、不支持与部分失败之间的区别；若调用参数缺失或值为空仍创建传感器，会污染状态。
- 资产列表列默认值、表格宽度与 rack 字段展示映射不符合页面日常使用语义；WAN 候选接口没有同创建契约一样校验有效 ifIndex。

## 解决方案

- 按官方 H3C HH3C-DOT11 MIB 补齐 Station、Radio 与 AP/射频/BSS 采集。无线客户端原始属性不写入 Prometheus labels；文本值保留在库存及采样历史。Radio `.30-.35` 中无确定单位的信号值以原始单位存储，不推断 dBm。
- 按固定 LibreNMS `Vrp.php` 与 Huawei 官方 MIB 补齐 AP SN/type/name、CPU/内存、Radio type/channel/MAC/utilization/interference/EIRP、按 MAC/radio/WLAN 行索引采集 VAP 客户端数及 2.4/5 GHz SSID 客户端数；trap 节点不参与 poll。
- 为内置 H3C/Huawei 目录增加 additive、可重复执行迁移；同步硬件 exporter 和 Wireless dashboard 生成器。
- 将完整空 walk 与 unsupported/partial 状态正确区分，传递 Comware transceiver 的 identity，并避免对缺值生成 UniFi 传感器。
- 精简资产表默认列、移除强制 2200px 宽度、持久化用户列偏好；列表和导出只显示 `rack_name`。WAN 选项和表单按目标设备只读刷新有效 IF-MIB 接口。
- 推送 `main` 后按该提交 SHA 核验 GitHub Actions；只有必需工作流成功且最终状态确认后才执行用户授权的关机。

## 风险与回滚

- 不支持或未响应的列应继续显示 partial/unsupported，不补造零值；文本属性只保留在硬件库存，不暴露为高基数 label。
- migration 为 additive，撤销代码时保留 operator 配置及设备历史；如需回滚迁移应先遵循 PostgreSQL 备份流程。
- 仅提交审查后的源码、测试、仪表板与交接文档；临时 build/validation 输出留在本地，不进入版本控制。推送使用普通 fast-forward，不重写远端历史。
