## 1. 问题现象与需求背景

1. **凭据解析异常与切片重试**：
   GitHub Actions 在 Windows runner 下通过 Bash 传递多行 JSON 时存在转义损坏风险，导致凭据解析失败或进入交互模式；同时 ByPy 默认 20MB 分片上传在跨国网络下频发 `Slice MD5 mismatch` 重试。
2. **Ubuntu 发行包体积膨胀**：
   前端编译依赖 `node_modules`（>300MB）在未过滤状态下被打包进 `NetOps-Linux-Ubuntu.zip`，导致压缩包高达 120MB。
3. **多平台发布物同源一致性与 ZIP 打包**：
   用户要求百度网盘上传的内容必须与推送到公开 Release-netops 仓库的发布物 100% 同源一致，且 Windows 和 Linux 均必须提供完整的开箱即用 ZIP 压缩包。
4. **CI 终端假死感**：
   Windows 下 Python 默认开启 I/O 输出缓冲，在大文件长连接传输过程中 Actions 日志无输出。

---

## 2. 根因分析

1. **凭据解析与分片机制**：ByPy 默认采用切片分片上传（`type=tmpfile`），跨国网络高频校验易超时或 MD5 错位；同时环境变量中如果包含多行换行或 Base64 格式，直接 `json.loads` 容易因字符集问题报错。
2. **构建产物未隔离**：`npm run build` 生成 `dist/` 后未清理 `node_modules/`，普通 zip 遍历打包抓取了全部依赖文件。
3. **I/O 缓冲未刷新**：CI 环境非交互终端中 Python 的 `print` 默认开启行缓冲/块缓冲，上传期间无控制台反馈。

---

## 3. 解决方案

1. **Python 原生上传器与 Base64 自动识别**：
   在 `.github/scripts/upload_to_baidupan.py` 中实现了智能凭据解析器，同时兼容 Base64 编码字符串、单行 JSON 及标准 JSON 文件；并将脚本缓存在 `$RUNNER_TEMP`，免疫任何仓库文件清洗指令。
2. **启用单流整文件直传**：
   设置 `ByPy(slice_size=500MB)`，对 10MB~50MB 的发布包采用单 HTTP 流直传（Non-slicing Stream Upload），彻底规避分片合并接口的 MD5 校验重试。
3. **`git archive` 纯净同源归档**：
   统一采用 `git archive --format=zip HEAD` 直接基于已提交的清洗后 Release 分支生成 `NetOps-Linux-Ubuntu.zip` 和 `NetOps-Windows.zip`，确保与公开仓库内容 100% 同源一致，并将 Ubuntu 离线包体积降至 ~8MB。
4. **实时行级日志流**：
   配置 `PYTHONUNBUFFERED: "1"` 及 `print(..., flush=True)`，实现上传进度、上传耗时和返回状态的实时控制台输出。
