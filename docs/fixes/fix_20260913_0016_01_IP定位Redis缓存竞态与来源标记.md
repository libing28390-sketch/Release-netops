# 修复：IP 定位 Redis 缓存竞态与来源标记

日期：2026-09-13（Asia/Shanghai）

## 问题现象

- IP 定位页面把缺少来源字段的结果显示为“实时采集”，同一 run 实际可能混用 Redis、PostgreSQL、CLI。
- CLI 阶段收到 Redis `SET` ACK 后，紧接着的第二次定位仍从 PostgreSQL/CLI 回源；whole-result Redis 常见 miss。
- LLDP snapshot 写入能力有隔离 Redis 测试，但真实设备 complete marker 与 snapshot key 尚未填充。

## 根因

- `locator_invalidation_outbox` 的 worker 在事实写入 Redis 之后异步处理 `fact_changed`，并按 scope 宽前缀删除 route/ARP/MAC/topology 事实键。实证 run `locator-run:5ccdc46b2ee043c9b0c709b343c2fd8b` 的 Redis 写入 ACK 成功，相关 outbox 事件在 23:37:26+08 处理；23:37:41+08 的 `locator-run:f31a2800a0a0415dbc066fa11380423d` 随后回退到 PostgreSQL/CLI。两次 run 的 Redis scope、目标、VRF 与授权设备集合一致。
- route 的逻辑 freshness 是 300 秒、物理 retain 是 1800 秒；超过 5 分钟时，即便 key 仍在 Redis 也必须拒绝读取。
- 前端对没有 provenance 的旧响应默认显示“实时采集”，来源证据不足。
- 周期拓扑 worker 丢弃逐设备 gather 异常，NSOT scheduled job 可能在 LLDP/Redis publish 不完整时记录 success。

## 解决方案

- outbox 只主动清理整体结果缓存；route/ARP/MAC/LLDP 事实键保留，由 pending-outbox gate、PostgreSQL observation generation、action/parser/schema 版本和 freshness 校验决定是否可读。过期/旧版本事实仍会被拒绝，TTL 回收旧键。
- 补齐逐阶段/逐设备 `cache_provenance`，覆盖 Redis、PostgreSQL、CLI、整体结果命中/未命中及实际 SET ACK；修正 whole-result cache-hit 浅拷贝污染和 ARP targeted-positive ACK 记录。
- 页面按已记录来源展示缓存/CLI；强制刷新只标“已请求”，无来源字段标“采集来源未记录”，不再默认宣称实时。
- 周期 LLDP 汇总记录逐设备采集状态与 Redis 发布确认；只有完整采集（含合法空邻居）且 Redis 确认时才将 NSOT job 记为 success。
- 为 Redis MONITOR epoch 提供仅格式化 stdin 的时区转换脚本，不更改 Redis 协议或放宽 ACL。

## 未验证项与风险

- 当前用户服务在本轮最后修改后尚需重启并再次定位。修复上线后建议先跑一次正常定位预热，再在 5 分钟内重复一次；预期阶段来源转为 Redis，随后整体结果可写入/复用。
- 当前运行库仍无真实 LLDP complete marker / Redis topology snapshot key；未触发全网调度或手工设备采集，也未做生产灰度。
- 通过 Redis SET ACK 表示 Redis 接收了 SET，不等同于磁盘持久化或跨重启保证；真实回读仍由 opt-in Redis round-trip 测试验证。
- 回滚：恢复应用到上一提交即可；新增 PostgreSQL 表保持 additive，不应为代码回滚删除既有 locator/LLDP facts。
