# 告警通知任务资源隔离整改

日期：2026-10-12
关联计划：[Nexora 告警与后台任务资源隔离](../plans/plan_20261012_0825_01_告警集中负载.md)
实施记录：[告警集中负载 walkthrough](../walkthrough/walkthrough_20261012_0825_01_告警集中负载.md)

## 问题与证据

大量告警时，告警规则/状态持久化、事件投影和通知处理与 API 主服务共用进程和数据库。历史代码还会在 API scheduler 中周期性消费通知 outbox。静态追踪发现可能的竞争路径，但没有故障现场 CPU profile，不能将 CPU 升高唯一归因于某条 SQL 或通知发送。

更细的代码审查确认：B-loop 每分钟同步扫描 topology links，并对每条链路调用一次 `set_alert_state`；BGP/OSPF/BFD peer 也逐个写状态。原路径为每条状态更新单独开连接、提交事务，因此开销随链路/peer 数增长；每 15 秒 incident 投影还会扫描全部未解决告警。该证据确认了事务和扫描放大路径，但仍不能代替现场 profile，也不能确定本次 CPU 尖峰由哪个进程/容器占主导。主机资源告警正常最多四个键，不像数百条告警的主要放大源。

本次采用 PostgreSQL outbox + 独立 Celery Worker + 专用 Redis Broker，将通知发送和 API 分离，并给新增进程设置资源硬上限。共享 PostgreSQL 及主机仍会承受告警读写和通知状态更新的负载；CPU 配额不等于 CPU 预留，故障现场需再做同机压测校准。

## 实施内容

- PostgreSQL migration `m0283_alert_delivery_celery_dispatch` 增加投递代次、发布租约/结果、优先级和补偿索引；旧 outbox 记录和状态继续保留。
- 增加 Celery task `monitoring.alerts.deliver`，载荷仅含 delivery ID 和 generation。critical 与 normal 使用独立队列及单并发 Worker；Worker 不启动 FastAPI lifespan。
- 增加独立 Relay，从 PostgreSQL 按有界批次发布任务；发布失败退避，PG/Broker 状态窗口用 generation fencing 和一次有界补发修复。
- 事件、活动记录、通知意图在同一个 PostgreSQL 事务中提交；迁入网络告警及恢复、Grafana firing/resolved、主机资源告警、维护重新打开和定时任务失败通知。
- Grafana 重复 firing 更新当前事件但不重复创建通知；Webhook URL 只从 Worker 环境读取，不来自入站请求或任务 payload。
- Compose 新增专用 Redis，配置 AOF、`noeviction`、独立持久卷、key 前缀/受限 ACL、健康检查和资源上限。示例密码留空，启动前须生成随机值。
- Broker 只连接独立内部告警网络；API 与其他容器不能直接访问。新增告警容器设 `cpu_shares=64`，CPU 配额为硬上限、CPU share 是争用时的相对调度权重。
- 初始资源上限：Redis 0.25 CPU/384 MiB，Relay 0.10 CPU/192 MiB，critical Worker 0.25 CPU/512 MiB，normal Worker 0.25 CPU/512 MiB；告警服务总硬上限为 0.85 CPU/1.6 GiB。Worker 任务硬/软时限为 60/50 秒，停止宽限 75 秒；数据库执行租约 90 秒，Redis visibility timeout 120 秒。
- 本地开发默认 `ALERT_NOTIFICATION_CELERY_ENABLED=0`，纯进程 FastAPI 使用 PostgreSQL outbox consumer，不依赖本地 Docker/Celery/告警 Redis，但这个兼容模式不隔离本机 CPU。远端 Linux Docker Compose 显式启用独立 Relay/Worker 并关闭 API 内消费者；仅在共享测试/预发布数据库可由本地 API 通过受控网络接入时，才显式设置 `1` 交给远端 Relay 消费，API 仍无需访问内部 Broker。Celery 官方不支持 Windows，Worker 固定在远端 Linux 虚机运行。

## 剩余风险与操作

- 初始 CPU/内存上限仅约束告警容器本身，数据库、Redis 持久化和其他容器也使用主机资源。需要按实际宿主机配置测量 CPU throttling、主 API p95、PostgreSQL 压力和通知积压。
- 通知 worker 的隔离没有隔离仍运行于 FastAPI 的遥测采集/告警规则计算，也没有限制 PostgreSQL 执行告警查询时的 CPU；LLDP 状态写已按 100 项分批，协议邻居仍按 peer 事务写入。未完成现场 profile 前不能断定通知是 CPU 峰值的唯一原因或宣称主机 CPU 不受告警影响。
- 事件列表/详情/影响读取改为只读 GET 和 15 秒定时 incident 投影；没有可信持久化的 freshness 时间戳，当前不能显示精确投影延迟。
- Relay critical-first 排序没有 normal 保底份额；若 critical 长期超过发布吞吐，normal 可能饥饿。通道/租户全局限流、每秒速率和持久化聚合也未实施。
- Celery 5.6 文档说明 late-acked failed task 在 `task_acks_on_failure_or_timeout=False` 时 reject without requeue；当前保障依靠 PG Relay 对 `attempts=0` 行持续补发（60/120/240/480/960/1800/3600 秒）以及已 claim 执行的 lease recovery，而非 Redis visibility timeout 重投。真实 Broker/Worker 故障语义仍需 Docker 验证。
- 外部通知采用至少一次语义：发送成功但 worker 在写回 PostgreSQL 前崩溃，可能重复发送。
- 从 `.env.example` 新建配置后，应执行 `openssl rand -hex 32` 并设置 `ALERT_NOTIFICATION_BROKER_PASSWORD`，再验证 Compose 配置。
