# 页面卡顿与 300 台采集负载

## 问题现象

用户报告监控看板刷新、资产表单打开/保存和 Grafana 偶发卡顿。部署前七轮约 5 分钟远端采样都观察到后端请求秒级停顿；新加三轮中两轮出现直连与 Nginx 同秒约 6 秒超时。PG 活动采样未见锁等待或持续秒级 SQL，Grafana/VM health 快速，容器 cgroup 未报告 CPU throttling/OOM。

## 已确认原因与范围

- 对硬件发现 `_resolve_mib_symbol` 的生产只读 `EXPLAIN` 确认 `LOWER(node_name)` 精确匹配走 `snmp_mib_nodes` Seq Scan；七个窗口的 MIB 表顺扫计数均持续增长。该查询计划是已确认的缺口，但现有采样没有单 SQL耗时/request ID/event-loop lag 关联，不能宣称它是页面所有停顿的唯一根因。
- 代码检查确认资产表单凭据列表有 N+1 设备关联读取；采集路径的同步数据库工作和每个传感器单独写入会占用事件循环并放大 PostgreSQL 往返。
- 实际远端目前17台设备、15台有 SNMP 绑定，与300台生产规模不等价。300台容量证据来自本机隔离 PostgreSQL 和 fake SNMP。

## 解决方案

- 新增可重复的 `LOWER(node_name)` 表达式索引迁移，并与 fresh schema 一致；隔离 PostgreSQL planner 测试确认精确查询可选用该索引。
- 传感器状态按设备批量写入，为全无效/NULL批次固定 PostgreSQL 参数类型；硬件样本保存和采集结果状态写入移出 async event loop。
- 保留既有凭据关联批量查询和请求/调度/health/通知异步 I/O 修复；补充前端首页、Grafana 相关现有变更与回归。
- 为11个 Compose 服务增加 CPU、内存与 PID 上限；Nginx worker 默认1、支持1–8，受容器 PID 限制保护。Uvicorn `WORKERS=1` 不变。

## 验证

- SNMP批量写入、300台采集、遥测线程边界、Nginx worker组合：39 passed / 103.33s。
- 凭据批量读取、资产绑定、连接池、m0276 迁移、诊断和 health 资源组合：39 passed / 166.16s。
- `uv run python scripts/validate_postgresql_only.py`：0 violations；Python 编译及 `git diff --check` 通过。
- 前端 `npm run test:frontend -- --run`：115 files / 445 tests passed；`npm run lint` 和独立输出目录 production build passed。
- 后端全量曾运行95分36秒（3410 passed、1 failed、1 skipped、26 subtests）。唯一失败的 m0275 “最高版本=274”断言已修复，m0275+m0276 迁移组5 passed；修复后的完整全量由 push 触发的 Actions 复验。
- 部署前新增三轮各300秒采样：`snmp_mib_nodes` 每轮 Seq Scan +48 / tuple read +3,245,376；active SQL最大约329–513ms，无锁等待；授权部署与部署后复测待完成。

## 未验证项与风险

- 没有用户登录态，受保护业务 API 和11个 dashboard URL 返回401；真实资产保存、登录后 Grafana PromQL、浏览器交互没有验证。
- 300台数据规模的 SNMP 使用 fake driver，未包含真实网络设备 RTT、完整硬件发现和真实 Linux runtime；不能承诺生产 p95。
- 仍有少数同步服务路径未移出事件循环；部署后如同类停顿仍出现，应继续补齐 event-loop lag、连接池等待和请求 ID 观测。
- GitHub Actions、数据库备份、迁移部署及部署后五分钟采样尚待执行。

## 回滚

部署前用 release 脚本备份 PostgreSQL、Source Manifest、`.env`、TLS 与配置快照。应用不可用或资源上限触发健康失败时，停止新版本并回到部署前 Release commit / 镜像与 Compose；新增索引可以在维护窗口按 migration 版本回滚，数据表和业务行不需重写。保留 Docker volumes 和用户配置，不运行 `git clean`，不删已有 dashboard。
