# 严格对齐国产设备命令映射与可用TextFSM模板

## 问题现象
用户指出在针对国产平台（如中兴、迪普等）查询某些分类指令时，存在命令字不准确（如中兴的 `show interface brief` 与 `show ip interface brief` 混淆）及部分未实现的模板也被当作结构化数据提交的情况（如锐捷的 BFD，迪普的 NTP）。

## 根因分析
1. 之前的映射对齐仅仅补全了缺失的字段，没有写自动化校验脚本，导致 `COMMAND_CATALOG` 预告支持了部分实际上本地目录 `data/textfsm_templates/` 下并不存在的模板（例如 `dptech_ios` 的 NTP、OSPF、BGP；`ruijie_rgos` 的 BFD、日志等）。这会导致解析引擎触发 `TemplateNotFoundError`。
2. 前端的按键触发条件（`operationalCategory`）盲目跟随了后端的“假装支持”，没起到“退化为纯文本CLI”的保护作用。

## 解决方案
1. 编写专门的 Python 校验脚本，逐个模拟生成 TextFSM 文件名，核对本地 `data/textfsm_templates` 目录中是否真实存在。
2. 根据脚本结果，从后端的 `COMMAND_CATALOG` 里精准**剔除**了所有没有对应解析模板的“画大饼”指令映射（如迪普的 NTP、OSPF、BGP，锐捷的 BFD 等），让其返回纯净的未匹配状态。
3. 同步修改前端 UI 的判定逻辑（`isZte`、`isDptech` 等），确保无模板状态下，正常退化为 `CLI` 纯命令回显模式。

## 实际修改文件
- `[MODIFY] backend/services/operational_data_service.py`
- `[MODIFY] src/pages/AutomationExecute/index.tsx`

## 验证命令与结果
- 执行自定义的 python 校验脚本，确认所保留的全部映射均有对应的 `.textfsm` 模板。
- `pytest backend/tests/ -k catalog` 测试通过。

## 未验证项
- 退化为 CLI 回显后的物理设备响应报文需要真机环境验证。

## 风险与回滚方式
- **风险**: 极低。这只是针对国内四家厂商配置字典的数据清理，无任何核心逻辑重构。
- **回滚方式**: 撤销对前后端修改，恢复之前的过度映射状态。
