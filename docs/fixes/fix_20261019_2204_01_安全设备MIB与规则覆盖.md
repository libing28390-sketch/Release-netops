# 安全设备 MIB 与硬件规则覆盖

## 问题现象

资产清单包含 15 个安全设备厂商，而固定 LibreNMS bundle 仅有网络设备来源；用户需要知道哪些设备能使用现有采集链路，以及缺失部分是否只是 MIB 文件未打包。

## 根因

MIB 只定义 SNMP 对象及符号，不会单独生成设备身份识别或周期采集规则。固定 LibreNMS 提交中，部分厂商没有 OS profile，另一些产品有身份识别但没有被当前 Python parser 接受的 processor、mempool 或 sensor 定义。

## 解决方案

- 从固定 LibreNMS 提交补入 20 个有结构化硬件定义的 OS profile，覆盖 9 个资产安全厂商；添加 43 个直接及传递 MIB 文件并记录源路径和 SHA-256。
- 扩展安全厂商的 MIB 目录归一化与同步范围，使 UI 安全厂商也能导入对应的 MIB scope。
- 增加规则解析、直接 MIB 引用、MIB `IMPORTS` 闭包、来源哈希及平台 scope 测试。
- 单独搜索厂商官方文档；发现的官方 MIB/OID 资料记录在 walkthrough 与本地 `handoff.md`。非 LibreNMS 来源的产品资料没有混入固定 LibreNMS bundle，也没有据此猜测 OID。

## 实际修改文件

- `backend/vendor/librenms/resources/definitions/os_detection/`、`os_discovery/`、`mibs/`、`source-manifest.json`、`README.md`
- `backend/services/librenms_mib_service.py`、`backend/services/mib_repository_service.py`、`backend/api/devices.py`
- `backend/tests/snmp/test_librenms_bundle_manifest.py`
- `docs/architecture/SNMP采集全流程与代码索引.md`、对应 plan/walkthrough
- 根目录 `handoff.md` 仅作本地内部交接，不进入本次提交

## 验证

- `.venv\Scripts\python.exe -m pytest -q backend/tests/snmp/test_librenms_bundle_manifest.py backend/tests/snmp/test_librenms_rule_service.py backend/tests/snmp/test_librenms_source_policy.py`：39 passed。
- `.venv\Scripts\python.exe -m pytest -q backend/tests/snmp/test_mib_repository_import.py`：4 passed。
- Python `compileall`、298 条 rule 文件与 2,403 条 MIB manifest 哈希复核、代码与文档路径的 `git diff --check` 均通过。上游 YAML/MIB 按来源策略保留原始字节和空白，不对这些源文件做 whitespace 清理。
- 20 个安全 profile 的 28 个直接 MIB 模块前缀均可解析；唯一未解析文本是 FortiGate 可选描述模板中的 `InetAddress_FORTINET-FORTIGATE-MIB`，不是采集 OID。43 个新增 MIB 的 `IMPORTS` 均落在 manifest 已登记模块中。

## 未验证项、风险与回滚

- 未连接真实安全设备验证型号/固件返回值；厂商文档披露的 MIB 能力不等于已实现或已验证的 Nexora 采集规则。
- 若 bundle 测试或来源校验失败，回退本提交中的规则、MIB、manifest 与同步代码；不删除数据库已有 MIB 记录，不修改设备。
