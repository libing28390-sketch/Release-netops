# Git 修复记录: 解决数据库迁移时外键约束（ForeignKeyViolation）违规的报错

## 1. 问题现象
启动服务时，后台数据迁移报错失败，抛出类似如下的 PostgreSQL 外键违反约束：
```text
psycopg2.errors.ForeignKeyViolation: 错误: 外键约束 "arp_table_device_id_fkey" 违反
DETAIL: Key (device_id)=(cb6a48bf-67bd-409c-a24f-ec5dc7e4da40) is not present in table "devices".
```

## 2. 根因分析
在历史业务数据（如 `arp_cache`、`topology_observations`、`config_snapshots`、`alert_events` 等历史表）迁移到最新的企业级规范表（如 `arp_table`、`neighbor_table`、`config_backups`、`alarms` 等）时，系统会尝试将旧数据中的 `device_id` 或 `source_device_id` 复制到新表。
但是，由于部分物理设备在数据库历史中可能已经被物理删除（即不存在于 `devices` 核心表中），这些关联的历史缓存和状态变成了**孤立记录（Orphaned records）**。
新表的 `device_id` 列带有严格的外键约束（`REFERENCES devices(id)`），此时如果直接将已被删除设备的 ID 强行迁移插入，便会触发 PostgreSQL 的外键一致性违规限制，导致启动流程崩溃。

## 3. 解决方案与实施步骤
我们升级了 [schema.py](file:///d:/netops/netsops-main/backend/database/schema.py) 中数据迁移阶段的安全防护措施：
1. **预查有效设备**：在 Phase 5 及 Phase 6 的 `try` 段落头部，预先查询 `devices` 表并将所有在库设备的 ID 保存在内存 `valid_device_ids` 集合（Set）中；
2. **孤立数据过滤**：
   - 对于 `route_table`、`neighbor_table`、`config_backups`、`alarms` 的迁移：循环中检查设备 ID。如果不在 `valid_device_ids` 集合中，则直接 `continue` 跳过迁移该孤立行；
   - 对于 `arp_table` 迁移：如果 `dev_id` 匹配到了不存在的设备，清除当前绑定并尝试获取任意其他在库设备（`LIMIT 1`）做默认关联；如依然无法解析，则直接 `continue` 跳过，彻底防范了外键异常。
