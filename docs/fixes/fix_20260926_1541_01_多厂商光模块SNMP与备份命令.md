# 多厂商光模块 SNMP 与备份命令适配

## 问题现象

光模块查询链路仍有 CLI 默认命令/旧命令来源，无法保证所有厂商只走 SNMP；部分厂商的 DOM 指标缺少可验证的索引、单位或有效值处理。与此同时，`/config/backup` 的手动、批量和定时默认命令映射分散，厂商与设备平台字段冲突时可能错误套用其它厂商命令。关联 Grafana 面板还需要修复无数据、设备筛选、硬件汇总和长期 Down 状态的语义问题。

## 根因

- optical 查询之前复用了通用 CLI 命令目录，且历史发布档/平台静态配置可能残留 CLI fallback。
- DOM MIB 存在厂商差异：OID 根、表索引、raw 单位及哨兵值不一致，通用 scale 会导致错误读数。
- 备份命令分别在前端单设备与后端批处理分支中选择，厂商覆盖不完整，并可能依赖不匹配的平台字段。
- 部分总览面板将不具同质性的设备硬件资源做全局平均，并把长期稳定 Down 的接口持续当成链路异常。

## 解决方案

- 为 H3C、Huawei、Juniper、Ruijie、ZTE、Raisecom 实现经 MIB 核实的 SNMP DOM 采集；未确认单位、索引或端口关联的 Cisco、Arista、DPtech、Maipu、Fortinet 不添加猜测指标。所有 optical 专用入口阻断 CLI fallback。
- 以追加式 migration 扩展 OID catalog，更新 SNMP 查询 preset 和 09 接口详情统一单位的 DOM 面板。
- 共享备份命令按厂商优先选择；厂商名不会被冲突的平台/Profile 值覆盖，未知厂商 fail closed。只有未覆盖厂商可以走与设备厂商、平台均一致的已发布 Profile action。
- 按计划更新 01/04/07/09 及设备看板，并补齐备份、SNMP、迁移/compiler 和 dashboard 回归检查。

## `/config/backup` 全厂商覆盖核对

当前资产页面的平台目录共有 41 家厂商（网络设备 26 家、安全设备 15 家）。已确认的直接 vendor-first 默认命令为 11 家：Cisco、Huawei、H3C、Juniper、Arista、Ruijie、ZTE、Raisecom、DPtech、Maipu 和 Fortinet。前 10 家使用平台注册表中已有的 running/startup 命令；Fortinet 使用专用 `show full-configuration`。

另外 30 家（DCN、FiberHome、Nokia、Aruba、Extreme Networks、Ruckus、MikroTik、Ubiquiti、D-Link、TP-Link、Dell、Brocade、Ciena、Alcatel-Lucent Enterprise、Allied Telesis、Edgecore、Palo Alto、Hillstone、Sangfor、Check Point、Sophos、SonicWall、WatchGuard、F5、A10 Networks、Barracuda、Venustech、NSFOCUS、Topsec、Qi An Xin）没有厂商级默认命令。由于各厂商/系统版本的配置查看命令和启动配置语义未逐项核实，不将 Cisco/Huawei 命令套用给它们；只有设备绑定的 Profile 含已发布 `get_running_config` action 时才可走该 action，否则不列为可备份候选。

候选筛选、定时执行和定时预览已按“已知默认命令或已发布配置读取 action”判断，并排除 server/host 资产；这避免把“厂商名看起来像网络设备”误当成命令能力。未知显式厂商不会借 Cisco 平台值进入候选；Profile action 需与设备厂商和平台身份一致。设备的显式厂商仍优先于平台/Profile 字段，空值或 `Other` 才使用平台兜底。厂商层默认映射不能证明同厂商下 IOS/NX-OS/ASA、VRP/USG、DPtech switch/firewall 等不同命令方言完全通用；因此本次不扩大未经逐项核验的映射。

## 风险与回滚方式

DOM MIB 的设备实现可能受型号/固件影响；未确认组合保持不支持，避免错误读数。默认配置命令并非 41 家全覆盖：未核实的 30 家保持 fail closed，需要命令证据或已发布 Profile action。若采集器、备份命令或 dashboard 更新产生问题，可回滚本次提交；本次没有数据库回填、生产部署或设备配置写操作。迁移采用追加方式保留既有 OID 设置。
