# 修复拓扑发现 INSERT 语句参数数量不匹配 Bug

此计划旨在修复 Uvicorn 环境下，向 `topology_observations` 表中执行 `INSERT` 时，由于 SQL 占位符数量与 Python 传参元组数量不一致导致的 `TypeError: not all arguments converted during string formatting` 错误。

## 问题分析

1. **现象**：拓扑发现任务中，R1、R4 的发现状态显示为 `topology_discovery_failed`，而 R2、R3 显示为 `ssh_unreachable`，SW5、SW6 成功。
2. **根因**：
   - R2、R3 确实因 SSH 端口关闭而无法访问（符合预期）。
   - SW5、SW6 因为在数据库中已有对应的拓扑发现记录，走的是 `UPDATE` 分支（参数正常）。
   - R1、R4 因为是新发现的记录，走的是 `INSERT` 分支。
   - 在 `backend/services/topology_service.py` 的第 1133 行，`INSERT` SQL 语句的 `VALUES` 部分硬编码了 `0, 1`：
     ```sql
     VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, 'lldp', ?, 'active', ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, 0, 1)
     ```
     该 SQL 共有 23 个 `?` 占位符。
   - 但在对应的 Python 参数元组中，末尾多传了 `0, 1`：
     ```python
     now,
     now,
     source_site_id,
     evidence.get('method') or '',
     match_status,
     _safe_json(evidence.get('candidates') or []),
     now,
     now,
     0,
     1,
     ```
     导致总共传入了 25 个参数，从而引发 `TypeError: not all arguments converted during string formatting` 异常，使得拓扑保存阶段直接崩溃。

## 解决方案

在 `backend/services/topology_service.py` 的第 1166-1169 行中，移除 Python 传参元组中多余的 `0, 1`（由于在 SQL 的 `VALUES` 结尾中已经硬编码了 `0, 1`），使参数个数恢复为 23 个，与 SQL 占位符一致。
