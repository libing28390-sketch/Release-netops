# 存储用途与 S3 错误处理

## 任务目标

在对象存储管理页明确说明全局默认 Bucket 对配置备份、PAM 录像和知识库的用途范围，并复核 S3 错误处理；同时简化固定的 S3 类型显示。

## 现状与问题

页面显示存储配置和默认项，但未说明应用把不同业务对象写入哪个 Bucket 前缀；用户容易误解知识库也已使用对象存储。另一个已确认的错误分类问题是 S3 缺失 Bucket 会被当成对象不存在；Endpoint 输入也容易把 Bucket 或业务目录误填成 URL 路径。

## 影响范围

- 更新对象存储管理页的用途说明，并将固定的 S3 类型显示为静态文本。
- 修正 S3 缺失 Bucket 的错误分类；不改变 Bucket、Endpoint、默认配置或存储路由，也不改动已有对象。

## 拟修改文件

- `src/pages/StorageManagementPage.tsx`
- `backend/api/configs.py`
- `backend/services/config_snapshot_storage.py`
- `backend/services/storage_service.py`
- `backend/tests/storage/test_storage_service.py`
- `docs/walkthrough/walkthrough_20260925_2341_01_存储用途说明.md`

## 实施步骤

1. 在存储配置列表附近添加中英文用途说明。
2. 写明配置备份使用 `config/`、PAM 录像使用 `pam/`，知识库当前未接入此存储。
3. 创建/编辑弹窗中固定显示 S3，不再渲染不可操作的类型下拉框。
4. 为 Endpoint 标明 S3 API 地址用途，并提示不要把 Bucket 或业务前缀附加在地址上。
5. 将 `NoSuchBucket` 分类为存储服务配置/可用性错误；仍将 `NoSuchKey` 分类为对象不存在。
6. 为配置快照读取失败写入安全诊断日志；用户查看/下载接口将对象缺失返回 404、存储不可用返回 503，避免静默返回空配置。
7. 运行 S3 聚焦测试、Python 编译检查和前端 lint 并记录结果。

## 验证计划

- `npm run lint`
- `pytest backend/tests/storage/test_storage_service.py -q`
- `python -m py_compile backend/api/configs.py backend/services/config_snapshot_storage.py backend/services/storage_service.py`
- 检查差异，确认包含预期的文案、静态类型显示、S3 错误分类和诊断日志改动，并保留其他工作区变更。

## 风险与回滚思路

- UI 文案与错误分类修正不触发 Bucket、对象或路由变更；回滚时恢复对应前端和服务代码即可。
