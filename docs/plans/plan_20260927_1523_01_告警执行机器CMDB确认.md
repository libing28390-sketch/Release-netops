# 告警执行机器 CMDB 确认

## 任务目标

将告警规则目标选择改为“执行机器”；指定设备需通过当前租户 CMDB 搜索并勾选确认，避免手工输入 IP 后目标不明确。全局范围不展示设备匹配列表。按用户补充要求，移除表单中的“采集说明”。

## 现状与问题

- 当前规则范围标题为“作用范围”；指定 IP 是自由文本，保存时只验证格式，无法确认 CMDB 中实际命中的设备。
- 列表和运行时以 IP 字符串匹配；IP 变更会导致目标漂移，重复 IP 也可能命中多台设备。
- 编辑器仍展示“采集说明”折叠块，增加表单噪声。

## 影响范围

- 告警规则编辑器交互、范围摘要和本地化文案。
- 告警范围目录 API 支持当前租户 CMDB 设备搜索与按 ID 回查。
- 规则验证、匹配器和定向测试。
- 网络告警历史渠道归一化迁移和运行时兼容；宿主机规则仅保留健康状态阈值用途，不属于通知渠道。

## 实施步骤

1. 扩展租户范围目录接口，按关键词从 CMDB 搜索设备并可按选中 ID 查询设备摘要；遵循服务端分页上限及当前租户隔离。
2. 增加 `devices` 范围：输入设备名、管理 IP、序列号或资产标签后按 Enter 查询；候选显示可识别信息，只有明确勾选项才成为已确认执行机器。
3. 使用 JSON 设备 ID 集合保存在既有 `scope_value`，后端确认设备都属于当前租户；运行时只按设备 ID 精确匹配。
4. 规则编辑和列表用当前租户目录解析已选设备摘要；全局范围不渲染机器结果面板；旧 `ip` 范围仍按原逻辑读取。
5. 将“作用范围”改为“执行机器”，移除“采集说明”折叠内容，并完善加载、空、失败和无权限状态。
6. 将网络告警规则中的 `workspace` 及不再支持的历史通知方式规范化为 Webhook/邮件；保留已有这两种受支持方式的选择。宿主机阈值规则不进入通知投递链路，保留存量内部值但不将其描述为平台投递。通过幂等迁移更新非宿主机规则及其历史快照，并在服务读取时提供兼容规范化。
7. 补充前后端与迁移测试，运行 lint、定向 PostgreSQL 测试与生产构建。

## 风险与回滚思路

- 新的 `devices` 结构沿用现有 `scope_value`，不新增数据库列；历史 global/site/role/composite/ip/tag/interface/device 规则保持读取与运行行为。
- CMDB 查询必须限制当前租户；创建/更新时重新校验设备 ID 所属租户，避免客户端篡改候选 ID。
- 旧 `workspace` 无法表达新的明确渠道策略；归一化为 Webhook 和邮件两个当前支持渠道。迁移需使用标准数据库备份与恢复点，原有“跟随个人偏好”规则语义不会保留。
- 选中的设备如果随后从该租户 CMDB 删除或迁出，该范围不再匹配；编辑时显示不可解析 ID 并阻止保存，需用户重新选择。
- 回滚新设备集合处理代码后，历史范围结构不受影响；无需数据库回滚。

## 实施结果

- 已完成当前租户 CMDB 设备搜索、勾选确认、设备 ID 持久化和后端租户归属校验；规则运行时按设备 ID 精确匹配。旧 IP 范围读取与运行逻辑保留。
- 已将编辑器标题改为“执行机器”，全局范围不展示设备列表，并移除“采集说明”区块。
- 已为网络告警规则增加历史通知方式归一化：`workspace` 和仅含已不支持渠道的记录转换成 Webhook 与邮件；若记录已包含受支持渠道，则保留已有受支持渠道。后续运行链路审核确认宿主机规则只服务平台健康状态计算，不通过该规则发送告警通知；见 `plan_20260927_1556_01_告警设备确认与通知方式调整.md`。
- 已新增 m0259 幂等迁移；本地验证期间未对用户运行环境执行迁移。该归一化不可从新记录反推出旧的个人偏好投递语义，正式应用前需遵守数据库备份流程。
- 验证：前端 helper 测试 14 项通过；`npm run lint` 通过；生产 Vite 构建通过；Python compileall 与 PostgreSQL-only 检查通过。定向后端测试首轮 52 项通过、2 项因直接调用 FastAPI handler 未注入查询参数而失败；修正默认 `Query` 对象兼容后，2 个失败用例单独复跑通过。没有在目标浏览器环境做手工联调。
