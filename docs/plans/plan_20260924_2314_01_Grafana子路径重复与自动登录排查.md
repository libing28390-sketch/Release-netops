# Grafana 子路径重复与自动登录排查计划

## 目标

修复 Docker 部署时 Grafana 仪表盘 URL 无限叠加 `/grafana` 并返回 404 的配置回归；保留 Nexora 到 Grafana 的自动登录代理行为，并区分处理 Grafana token 轮换 401。

## 现状与证据

- 浏览器中 Nexora 生成的 iframe 初始地址仅为 `/grafana/d/nexora-network-overview/...`，但 Grafana 随后导航到重复数十次 `/grafana/grafana/...` 的地址。
- 服务器日志记录 Grafana 收到重复子路径并以 404 返回；这与用户输入路径或 Nexora iframe 初始 URL 不符。
- 当前未提交配置将 `GF_SERVER_SERVE_FROM_SUB_PATH=true` 与 Nginx 原样转发子路径组合。仓库先前的部署配置是 Nginx 剥离 `/grafana/`、Grafana 内部按根路径服务。
- `/api/user/auth-tokens/rotate` 返回 `user token not found` 是另一个 token 状态问题，现有证据不足以证明它触发了重复路径；本次不改认证逻辑。

## 影响范围

- Grafana Docker Compose 服务端子路径配置。
- Nginx `/grafana/` 反向代理 URI 处理。
- Docker 部署文档和相关 Grafana 部署契约验证。
- 不触碰 `.env`、真实服务器或 Grafana 数据卷；不重启/部署容器。

## 拟修改文件

- `docker-compose.yml`
- `nginx/nginx.conf`
- `docs/deploy/docker.md`
- `backend/tests/monitoring/test_monitoring_v1_deployment_contract.py`（补充 Nginx 与 Grafana 子路径模式组合契约）
- 本计划及对应 walkthrough

## 实施步骤

1. 恢复 Grafana `serve_from_sub_path=false`，保留正确的外部 `root_url` `/grafana/`。
2. 恢复 Nginx 通过 `proxy_pass .../` 剥离 `/grafana/` 前缀，并保留已有转发头。
3. 修正文档，明确代理剥离前缀和 Grafana 根路径模式必须成对配置。
4. 补充并运行 Grafana Compose/Nginx 子路径组合契约测试、Compose YAML/配置校验和差异检查。
5. 记录服务器部署后需验证的行为：iframe 最终 URL 不再增长、仪表盘返回 200；若 401 仍在，再独立检查 Grafana session/token 生命周期。

## 验证计划

- `pytest backend/tests/monitoring/test_monitoring_v1_deployment_contract.py`
- 若 Docker CLI 可用，检查 `docker compose config` 中 `serve_from_sub_path=false` 与 Nginx 的路径剥离配置。
- `git diff --check`。
- 浏览器只读现状已确认 iframe 的初始 URL 与最终 URL 不同；修复尚未部署到服务器，因此部署后的远端浏览器验证不在本地验证范围。

## 风险与回滚

- 若服务器实际仍加载另一份 Nginx/Grafana 配置，本地改动不会自动修复线上服务；必须将这两个配置同步并重建对应容器后验证。
- 回滚时恢复本次涉及的 Compose、Nginx 与文档差异；不要删除 Grafana 数据卷或重置账号密码。
