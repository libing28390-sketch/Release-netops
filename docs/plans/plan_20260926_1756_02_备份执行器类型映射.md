# 计划：修复配置备份执行器类型映射

## 目标

修复 `/config/backup` 在线网络设备批量备份失败的问题，并确认设备厂商对应的平台仍使用 Netmiko 支持的技术键。

## 现状与问题

线上日志显示 13 台已识别为可备份的网络设备全部在执行阶段失败，错误为 `No driver found for asset_type: network_device`。配置备份查询为区分网络设备和服务器新增了 CMDB `asset_type`；CMDB 使用 `network_device`，执行引擎注册的类别则是 `network`。驱动创建因此在使用 `vendor` 和 `platform` 选择具体 Netmiko 型号之前失败。

## 影响范围

- 计划任务与手动触发共用的 `run_scheduled_backup` 命令执行路径。
- 执行器对 CMDB 资产类型到引擎驱动类别的边界映射。
- Cisco、Huawei、H3C 的备份命令与 Netmiko 平台分派回归。

## 拟修改文件

- `backend/engine/registry.py`
- `backend/tests/configuration/test_scheduled_backup_driver_dispatch.py`
- `docs/plans/plan_20260926_1756_02_备份执行器类型映射.md`
- `docs/walkthrough/walkthrough_20260926_1756_02_备份执行器类型映射.md`
- 如需提交，增加新的 `docs/fixes/fix_*.md` 修复记录。

## 实施步骤

1. 在驱动注册边界将 CMDB `network_device` 规范为注册表使用的 `network`，保留未知类型的明确错误。
2. 保持 `platform` 独立表达 Netmiko 技术平台，由备份命令映射和 Netmiko 驱动按厂商选择，不将 `asset_type` 混作平台。
3. 补回归测试，以备份命令服务、AutomationService、真实 Netmiko 驱动构造及模拟执行验证 Cisco、Huawei、H3C；不连接真实设备。
4. 更新本计划并记录验证结果。

## 风险与回滚思路

类别别名只在驱动注册边界映射为已有注册表键；平台选择和命令目录不变。未知类别仍触发原有明确错误。若回归出现问题，可单独回滚该别名映射与新增测试，不需要数据迁移。
