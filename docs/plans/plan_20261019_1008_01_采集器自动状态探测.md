# 采集器自动状态探测实施计划

## 目标

在采集器管理页自动显示真实采集状态，识别未初始化、等待目标、等待首采、正常、部分异常、失败、无目标和服务不可用；不再把配置已应用或组件在线当作设备采集成功。

## 现状与问题

- `GET /api/monitoring/collectors` 当前检查本地 vmagent 与 SNMP Exporter 是否响应，只能证明组件存活。
- vmagent 从 file-SD 目标文件采集设备；其 `/api/v1/targets` 提供当前活动目标及最近抓取状态。
- 页面详情显示配置版本、发布状态和最近运行检查，但没有设备目标首次抓取结果，也没有自动刷新。
- `monitoring/collection-health` 的数据库记录来自设备侧采集状态表，不能单独作为 vmagent 当前活动目标的权威状态。

## 影响范围

- 后端：`GET /api/monitoring/collectors` 扩展安全的 `collection_probe` 状态字段；读取固定的本地 vmagent targets API，不回显原始 URL、凭据或错误文本。
- 前端：采集器列表和详情展示自动探测结果，并在采集器页每 30 秒刷新一次。
- 前端运维弹窗：移除与自动状态探测重复的手动检查，以及已由编译/发布覆盖的单独校验；保留编译、发布两步。
- 不修改数据库结构、采集配置、远程设备或部署流程。
- 评估“新建采集器”现状并给出建议；本轮不改变创建记录接口或该入口。

## API 合约

每个采集器返回 `collection_probe`：

- `state`: `NOT_INITIALIZED | CONFIG_PENDING | SERVICE_OFFLINE | NO_TARGETS | WAITING_FOR_TARGETS | WAITING_FIRST_SCRAPE | HEALTHY | DEGRADED | FAILED | UNKNOWN | DISABLED`
- `checked_at`, `target_count`, `healthy_count`, `failed_count`, `waiting_count`, `last_scrape_at`, `error_code`
- 仅统计 vmagent 活动目标中带有资产 `asset_id` 标签的目标；不将平台自身的 scrape target 算作设备采集。
- 目标虽然报告 `up`，但最近抓取时间超过有效采集间隔的 3 倍时按过期异常处理。按优先级读取 `discoveredLabels.nexora_scrape_interval`（file-SD 单目标间隔）、`scrapeInterval`、`discoveredLabels.__scrape_interval__`；都缺失时默认 60 秒。
- 活动目标为 0 时，按最近已应用 manifest 的目标数区分“确实无目标”和“目标尚未被 file-SD 加载”；不能用刚编译的未发布 assignments 作为活动目标数。
- `HEALTHY` 表示 vmagent 报告目标抓取成功，不表示 remote-write 已由 VictoriaMetrics 持久化；界面文案必须明确是“抓取正常”。
- 错误只返回归一化类别，不返回目标 URL 或 vmagent 的原始错误内容。

## 分工与文件边界

- Backend worker：仅修改 `backend/api/monitoring_v1.py`，从本地 vmagent `/api/v1/targets` 探测活动目标并为采集器列表返回上述合约；不改数据库和路由权限。
- Frontend worker：仅修改 `src/components/MonitoringManagementPage.tsx`，消费合约、增加状态文案/计数展示并实现采集器页面 30 秒自动刷新；不修改 API 合约或其他组件。
- Coordinator：负责本计划、集成审查、统一验证及 walkthrough。

## 实施步骤

1. 核对 vmagent active-target 响应、目标标签和当前应用配置状态；同时确认不同 vmagent 版本是否会在 `activeTargets` 返回有效采集间隔。
2. 后端将活动设备目标状态映射为稳定的初始化/采集状态；远程采集器没有心跳基础设施时保持未知。
3. 前端将采集运行状态与配置发布状态分开呈现，自动刷新探测结果，并将运维弹窗精简为编译/发布两步。
4. 审查类型、权限、错误脱敏、空目标和服务离线行为；核对新建采集器是否会实际安装或启动运行时。
5. 执行前端 lint 与 Python 语法检查；按当前工作区指令不运行测试套件。

## 后续修正：按目标实际采集间隔判定过期

- 现场 `/api/v1/targets` 的 active target 对象没有 `scrapeInterval` 字段；实际 SNMP 周期保存在 `discoveredLabels.nexora_scrape_interval`，部分非 SNMP target 则可从 `discoveredLabels.__scrape_interval__` 读取。
- 后端此前只读 `scrapeInterval`，因此回退到 60 秒默认值；300 秒周期的目标在第 180 秒后被误报异常。
- 修正后按上述优先级解析有效 interval，再应用原有 3 倍过期阈值；不改变真实 `health=down` 的失败判定。用户随后授权部署到指定机器，本次只更新 `netops` 应用镜像并备份旧镜像。

## 后续界面精简

- 采集器列表移除重复的汇总卡片，运行状态压成一个短状态和必要的目标计数，表格列随宽度展开。
- 详情弹窗只保留当前状态、启用、类型和有值的配置/采集信息；空站点或地址不显示。
- 编辑弹窗收窄为简洁表单，本地采集器不显示空的站点、管理地址和远程写入地址；编码在编辑时只读。远程字段只有已有值时才提供修改入口，避免显示空白无效项。
- 前端使用 TypeScript lint 和隔离目录构建验证后，已按既有部署授权更新指定机器上的 `netops` 前端静态资源；旧源码与镜像均留有备份，未重建其他服务。

## 风险与回滚

- vmagent API 暂时不可达或响应无法解析时，状态显示“未知/探测失败”，不能降格为“正常”。
- file-SD 刷新与首次 scrape 有延迟，因此保留“等待目标/等待首采”状态。
- 回滚只需撤销本次后端响应字段和前端展示/轮询，不涉及数据迁移或运行配置回滚。
