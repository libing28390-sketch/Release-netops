# V1.0.10 主线与公有 Release 发布计划

## 目标
整理当前 RDP/VNC 资产编辑与访问列表的小问题，统一应用版本到 1.0.10，更新公开 Release Notes，并将工作区代码推送到私有仓库 main。正式 Actions 门禁成功后，在 Ubuntu 部署验证，并通过 Actions 将 `V1.0.10` 标签、脱敏发布树和 GitHub Release 同步到公有仓库。

## 现状
- 当前分支 `main` 与私有 `origin/main` 均位于 `7a6ac2f1`，有两个未提交的前端修改；工作区另有既存临时构建目录和日志，需保留且不纳入提交。
- 当前应用版本为 1.0.9；发布工作流只触发小写 `v*` 并要求小写标签，公有发布仓库由工作流生成和同步。
- RDP/VNC 编辑器条件显示、目标端口和操作行布局已完成本地 lint 与生产构建验证。

## 影响范围
- 资产编辑和 Access Center 前端。
- 前后端版本元数据、发布标签校验及标签触发。
- Docker/Ubuntu 公共 Release Notes 与部署导航。
- GitHub Actions 正式发布、私有与公有仓库标签及 Ubuntu 实例升级。

## 拟修改文件
- `src/pages/AssetManagement/components/AssetModal.tsx`
- `src/pages/AccessCenterTab.tsx`
- `package.json`、`package-lock.json`、`backend/core/version.py`
- `.github/workflows/release.yml`
- `docs/deploy/release-notes.md`、`docs/deploy/README.md`
- 本计划、提交修复记录及完成后的 walkthrough。

## 实施步骤
1. 保留未提交用户文件，只整理本任务相关文件；把 UI 修正纳入 V1.0.10。
2. 同步版本号到 1.0.10，更新发布说明与部署导航；使发布工作流允许 `V1.0.10` 并继续支持已有小写 `v*` 标签。
3. 运行本地质量检查，检查提交清单和 Git 差异，按仓库规则添加修复记录后提交并推送私有 main。
4. 等待 main Actions release workflow 成功；在 Ubuntu 运行 `bash scripts/deploy-docker.sh update` 并核验部署健康、资产配置可见性、目标端口和同一行操作。
5. 补充实际验证记录并提交；确认最终 main 后创建并推送私有 `V1.0.10` annotated tag。等待正式 tag workflow 成功，再核验公有 main/tag/Release Note/附件。

## 验证计划
- `npm run lint`、`npm run test:frontend -- --run`、`npm run build`、`git diff --check`。
- 校验 `package.json`、lockfile 和 backend 版本一致；确认工作流可识别 `V1.0.10`。
- 检查 GitHub Actions main 与版本 tag 两次运行的最终结论均为 success。
- 远端 Docker 部署后检查容器健康和 HTTPS 页面；浏览器确认远程桌面设置只显示在 Windows server，RDP/VNC 端口使用配置端口，RDP 操作位于一行。
- 确认私有仓库 tag 指向最终发布源码提交，公有仓库 `main` 和 `V1.0.10` tag 指向本次脱敏发布树，GitHub Release 正文来自当前 Release Notes。

## 风险与回滚
- 发布工作流会更新公有 `Release-netops/main` 并创建同名 Release；在 tag 工作流成功前不宣称公有发布完成。
- 若 Actions 或远端部署失败，保留失败 run 与部署证据，先修复并重新运行；必要时将部署回退到先前成功的公有 Release 版本。不会删除或覆盖工作区中与任务无关的临时构建目录和日志。
