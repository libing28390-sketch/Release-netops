# 定时作业审批方式扩展

## 任务目标

在 `/automation/scheduled-jobs` 的安全审批流程中增加用户可选的 MFA、邮箱验证码方式，并保留现有飞书验证码方式；创建、修改、重新启用和删除作业都必须继续经过后端审批校验。

## 现状与问题

- 当前 `config_approval_service.request_approval` 只查找审批人已配置的飞书 webhook，并把 6 位验证码发送到飞书。
- 定时作业页面及删除弹窗共用这一审批请求/校验流程，前端只显示审批人选择、验证码输入，没有验证方式选择。
- 系统已有 TOTP MFA 及基于 SMTP 的邮件发送能力，但审批服务没有接入。
- `/api/config-approval/verify` 目前不要求登录态，也未把审批 token 绑定到发起该审批请求的登录用户；本次需要为安全审批校验补上操作者绑定。

## 影响范围

- 定时作业创建、编辑、重新启用、删除的审批方式选择及状态展示。
- 通用配置审批服务与 `/api/config-approval/*` 接口。未指定方式的旧调用继续默认使用飞书，避免影响其他配置审批页面。
- 不改变调度数据模型、SMTP 凭据、MFA 秘钥或飞书通知配置。

## 实施步骤

1. 在审批服务加入可用方式检查：MFA 只对已启用 TOTP 的审批人开放；邮箱只对有效邮箱且可用 SMTP 配置开放；飞书沿用已配置 webhook 的条件。
2. 增加安全的审批人可用方式查询，不返回邮箱地址、MFA 密钥或 webhook；审批请求记录所选方式和发起人，验证/消费时绑定当前登录用户。
3. 为邮箱发送短期审批码，为 MFA 方式直接验证审批人当前 TOTP；保留 5 分钟过期、最多 3 次失败和一次性消费语义。
4. 在定时作业创建/编辑和删除界面提供“飞书、邮箱、MFA”可用选项，并在方式或审批人变更时清除旧 token/code/验证状态。
5. 做后端语法检查、前端 lint/构建和差异审查，记录无法执行的验证及部署后确认项。

## 实施结果

- 已接入 MFA、邮箱、飞书三种按审批人可用能力展示的验证方式，创建/编辑/重新启用/删除仍受后端审批校验保护。
- 已补充审批人租户范围与方式能力查询、请求人和业务类型绑定，以及审批令牌的一次性消费检查。
- 已处理一次性执行计划编辑/重新启用/删除与其 `execution_plan` 类型的匹配。
- 最终检查包括 Python 语法编译、TypeScript lint、Vite 临时目录生产构建、PostgreSQL-only 策略扫描、dashboard JSON 解析和 `git diff --check`；结果记录在配套 walkthrough。
- 未运行业务测试，未连接真实 SMTP/飞书、未部署、未提交或推送。

## 验证计划

- 检查三种方式的可用条件、请求返回、验证码校验及 token actor binding。
- 运行受影响 Python 文件的语法编译、`npm run lint` 和前端构建；检查 `git diff --check`。
- 不连接真实 SMTP/飞书、不发送真实审批验证码、不在本地修改用户 MFA 设置；不部署生产环境。

## 风险与回滚思路

- 邮件方式依赖审批人账户有效邮箱及租户/共享 SMTP 配置；配置不可用时后端拒绝创建审批 token，并显示可读错误。
- MFA 方式要求审批人已启用 TOTP；未启用时不提供该选项，后端仍强制复核状态。
- 所有方式共用限时审批 token；方式切换或审批人切换后必须重新申请，不能复用旧验证码。
- 回滚时恢复前端单一飞书方式及审批服务原调用。数据库结构不变，无迁移回滚。
