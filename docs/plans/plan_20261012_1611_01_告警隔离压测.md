# 隔离告警队列压力测试

创建时间：2026-10-12 16:11（Asia/Shanghai）。

## 目标

在用户授权的 Docker 验证虚机上，以独立网络、独立测试 PostgreSQL 数据库和独立 Redis Broker，合成 500/1000/5000 条告警与 outbox 投递，验证告警列表读取和通知队列处理并行时的 CPU、内存、节流、API p95 和队列排空。测试目标不触碰现有业务数据库、真实告警、真实设备或外部通知。队列 `succeeded` 只表示自动通知已禁用时任务安全收敛，不代表通知已送达外部平台。

## 现状与问题

现有 `scripts/stress-test-docker.sh` 只对 `/api/alerts/summary` 做一般读压力，不创建告警/通知任务，也不启动 Celery 告警 Worker。其默认 11 个场景、每场景最高 50 RPS 和 2 CPU 负载生成器对 2 核主机不安全。Celery `global_webhook` 出口的 SSRF 防护拒绝内网 URL，不能为测试放宽。可在隔离库中生成 `workspace` 投递并设置 `NEXORA_AUTOMATIC_NOTIFICATIONS_ENABLED=0`，只验证数据库 outbox→专用 Redis→Celery→Worker→数据库完成路径；同时把 Docker 网络设为 internal，阻止任何外部 egress。

## 影响范围与文件边界

- `scripts/docker_capacity/main.py`、`lab.py`、`runner.py`、`metrics.py`：增加 opt-in alert-storm 模式、隔离 Broker/Relay/Worker、合成事件/outbox、告警列表负载及资源报告。
- `scripts/docker_capacity/test_main.py`、`test_metrics.py`、`test_runner.py`：覆盖隔离资源生命周期、出站通知禁用、压力门槛和 synthetic outbox 行为。
- `backend/api/grafana_metrics.py`、`backend/services/snmp_hardware_inventory_service.py`：从 `/hardware-metrics` 查询阶段排除渲染器本来就会跳过的传感器类型，避免重复拷贝未过期传感器；通过复用 FastAPI Response 已编码的 body，避免重复编码7.59MB文本并让耗时统计包含响应编码。
- `backend/services/ip_locator_service.py`：为周期 ARP 全表扫描设置独立的小并发上限，不改变实时定位与其它 SSH 工作的并发。
- `backend/services/device_health_service.py`：将设备健康快照中的逐设备接口查询改为批量查询，复用已有 PostgreSQL 批量读取器。
- `backend/core/scheduler_lock.py`：仅对运行超过 1 秒的定时任务记录锁等待、任务执行及锁清理耗时，以辨认间歇性 `max_instances` 来源。
- 对应 PostgreSQL 和监控/IP Locator 测试；本计划及 walkthrough。
- `backend/services/librenms_source_policy.py` 及对应来源校验测试：py-spy 显示硬件发现的符号解析在主事件循环重复遍历 MIB manifest，复用按 manifest 签名的候选路径索引；仍逐次验证目标文件的当前签名及 SHA-256，不缓存最终可信结论。
- Docker 验证 VM 仅用当前镜像作为底图覆盖后端文件，不执行整仓 Compose 构建；现有数据库、数据卷、通知 worker、Compose 配置保持原样。

## 实施步骤

1. 对 `alert-storm` 单独提供 opt-in CLI，默认 dry-run、默认只选 NetOps API；验证虚机 Docker 镜像中已有告警服务镜像才允许运行。
2. 使用独立随机命名网络/数据卷/数据库名/Broker 密码及现有 ownership label。克隆 API、PostgreSQL、缓存 Redis、Alert Redis、Relay 和两类 Worker；通知容器只接触克隆 PostgreSQL/Broker。测试网络为 Docker internal；Redis 密码只传给 Broker/Worker，不传给负载 runner。
3. 在克隆库事务内直接写入带 run ID 的 alert_events、`workspace` outbox 记录和必要活动记录。拒绝任何非测试 DB 名、外部 webhook channel 或未知 delivery key 前缀。通过自动通知总开关禁用渠道 dispatch。直接播种不运行规则求值、事件归并或采集入口；这些路径由现有单测和先前的调用链检查覆盖。
4. 对 500/1000/5000 条分别进行只读告警列表/API summary 请求，通知 Worker 同时排空其 outbox；每档默认 300 秒，总测量 15 分钟。记录请求 p95/error rate、outbox 任务成功/失败/积压与最老消息年龄及资源峰值。
5. 压测克隆容器总 CPU quota 上限为 0.77 核，负载 runner 上限为 0.20 核，合计不超过 0.97 核（2 vCPU VM 的一半）；创建任何测试容器前先测宿主机 CPU，3 个有效样本最大值须低于 30%。运行期间宿主机 CPU 达 80% 连续 5 个 2 秒样本即停止；保留现有低可用内存、OOM、容器重启和人工中止保护。停止后仅删除当前 run ID 所有权通过的测试资源。
6. 先跑 harness 单测、Python 编译和 PostgreSQL-only 扫描；随后 dry-run；最后在授权验证虚机运行 500 条 pilot。只有 pilot 未触发停止门槛且主机稳态留有余量，才继续完整分档。

## 风险与回滚

测试网络、volume、PG 数据库和任务均只含 run ID 隔离的合成数据，禁止用生产告警库或实际通知渠道。worker automatic notifications 明确关闭，network `--internal` 无默认路由。CPU 超过门槛 10 秒、宿主机 available RAM 低于 10%/256MiB、容器内存达上限 95%、OOM/意外退出或用户 SIGINT/SIGTERM 时立即中止并清理当前 run。CPU quota 与停止保护不能隔离共享磁盘 I/O，也不能保证宿主业务完全无短时影响；直接 SQL 播种也不能证明规则求值/事件摄取峰值的 CPU 上限，测试报告必须说明该限制。失败时只保留脱敏报告；cleanup ownership 不匹配则停止并报告，不触碰未标记资源。移除 opt-in harness 即可回滚，不更改运行中生产/验证栈服务。
