# IP 定位后台任务调度改进计划

## 任务目标

避免 IP 定位任务运行时间超过定时器间隔时，APScheduler 持续输出 `maximum number of running instances reached` 告警；保留新请求快速启动、数据库租约保护、全局并发上限与进程重启后的任务恢复。

## 现状与问题

- `/api/ip-locator/runs` 先在 PostgreSQL 创建持久任务，再通过 FastAPI `BackgroundTasks` 按 run id 立即尝试执行。
- APScheduler 每 2 秒调用 `process_pending_locator_runs`，用于拾取排队任务及恢复遗留任务。
- 当前定时函数领取一批 run 后会等待所有网络定位完成；定位可能持续数十秒，因此 APScheduler 的下一次 tick 会因 `max_instances=1` 被跳过并反复打印 WARNING。

## 影响范围

- 只调整 IP 定位持久任务 worker 的派发方式及其恢复扫描间隔。
- 不改变定位 API、任务状态契约、数据库结构、设备 CLI 流程、租约语义或全局并发配置。

## 拟修改文件

- `backend/services/ip_locator_run_worker_service.py`
- `backend/main.py`
- `docs/walkthrough/walkthrough_20261010_1118_01_IP定位后台任务调度.md`

## 实施步骤

1. 定时 worker 领取 run 后，为每个已领取任务创建有引用保留的后台 asyncio task，在线程池中继续执行定位，并立即返回给 APScheduler。
2. 完成回调移除已结束 task 并消费未处理异常，避免后台异常静默或 `Task exception was never retrieved`。
3. 将恢复扫描间隔从 2 秒调整为 5 秒；API 的即时启动路径保持不变，PostgreSQL 租约和全局活动数仍负责跨任务、跨进程并发仲裁。

## 验证计划

- 对修改的 Python 模块执行语法编译。
- 检查 `git diff --check` 与最终差异，确认只涉及本任务文件。
- 本次不运行 pytest；用户当前要求是调整逻辑，没有另行要求测试。

## 风险与回滚思路

- 后台派发依赖进程内 task 引用保持任务存活；进程退出时 PostgreSQL 租约恢复机制仍会重新排队过期 run。
- 轮询间隔增加到 5 秒后，未被 API 即时启动的排队任务最多多等约 5 秒；API 原有即时启动不受影响。
- 若出现运行时异常，可回滚 worker 派发方式和 `backend/main.py` 的间隔改动；不涉及数据库迁移。
