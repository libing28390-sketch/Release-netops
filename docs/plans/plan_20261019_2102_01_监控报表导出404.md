# 监控报表导出 404 修复计划

## 任务目标

修复 `/monitor/dashboards` 导出监控报表时返回 HTTP 404 的问题，并统一共享导出入口使用的 API URL。

## 现状与证据

- 仪表盘使用的 `ExportTableModal` 请求 `/api/monitoring/v1/export/{interfaces,devices,outbound}`。
- `backend/api/monitoring_v1.py` 的 router 前缀为 `/monitoring`，后端注册时在 `backend/main.py` 增加 `/api`，实际路径为 `/api/monitoring/export/{interfaces,devices,outbound}`。
- 对目标机匿名只读探测：错误路径返回 404；真实路由返回 401，证明线上有该路由且鉴权生效。
- `NetworkMonitoring.tsx` 的接口流量导出也使用了带多余 `/v1` 的路径。

## 影响范围与修改文件

- 新增 `src/api/monitoringReports.ts` 作为报表导出 URL 的唯一来源。
- 更新 `src/components/ExportTableModal.tsx` 与 `src/components/NetworkMonitoring.tsx`。
- 增加 URL 常量回归测试，验证三种报表地址。
- 本计划和对应 walkthrough。

## 实施步骤

1. 定义与 FastAPI 实际路由一致的三个导出 URL 常量。
2. 让仪表盘报表弹窗和接口监控导出按钮共用该常量。
3. 运行聚焦前端测试和 TypeScript lint；检查改动差异。
4. 按既有授权更新目标机前端并验证导出请求不再 404；不改数据库或监控数据。

## 验证计划

- `npm run test:frontend -- src/api/monitoringReports.test.ts`。
- `npm run lint`。
- 线上对正确导出 URL 验证路由可达，并在认证页面实际下载一份报表。

## 风险与回滚

- URL 修正后请求会进入现有报表 API，继续应用原有 Viewer 鉴权和数据范围控制。
- 若浏览器导出验证失败，恢复前端 URL 常量或回滚此次提交；不涉及数据变更。
