# 自动化备份批次历史与失败告警

## 任务目标

让 `/automation/history` 将一次批量配置备份显示为一条批次记录，并在详情中查看每台设备的成功、失败或跳过状态；备份失败时按设备产生可去重告警，并在后续备份成功后自动恢复。

## 现状与问题

- 配置备份已有 `config_backup_runs` / `config_backup_run_devices` 批次账本，记录完整最终结果。
- 备份流程在设备成功读取 running-config 后，提前调用 `_record_instant_execution` 写入 `playbook_executions`，造成 `/automation/history` 按设备拆行，并把“读到配置”误显示为“备份已完成”。
- 真正的备份结果在批次设备账本收尾时才确定；目前失败没有进入统一告警生命周期。

## 影响范围与接口约束

- 扩展当前 `/automation/history` 使用的统一执行历史查询，保留全局时间倒序分页，并纳入配置备份批次。
- 配置备份批次详情继续复用 `/api/configs/backup-runs/{run_id}` 的分页设备结果契约。
- 备份设备状态以账本最终状态为准。失败告警 key 固定为设备级，批次失败置为 active、后续成功置为 resolved；跳过结果不改变已有告警。
- 历史列表隐藏已知旧版 `Config Backup · ...` 逐设备影子记录，不删除既有审计数据。
- 前端历史页通过 `_type: config_backup` 分流详情、筛选、导出和操作，批次记录不调用 Playbook 重跑或删除接口。

## 拟修改文件

- `backend/api/inspections.py`（按当前执行历史页面的权限纳入配置备份批次）
- `backend/services/execution_history_service.py`（统一历史查询和分页）
- `backend/api/configs.py`（移除逐设备影子记录，批次完成后更新设备级失败告警）
- `backend/services/background_monitor_service.py`（告警来源可区分配置备份）
- `src/pages/alertManagementShared.ts`（配置备份告警来源标签；与 SNMP 来源标签共用）
- `src/pages/ExecutionSchedule/types.ts`
- `src/pages/ExecutionSchedule/index.tsx`
- `src/pages/ExecutionSchedule/components/HistoryList.tsx`
- `src/pages/ExecutionSchedule/components/ExecutionDetail.tsx`

## 实施步骤

1. 扩展 `/api/inspections/execution-history` 的现有统一查询，将巡检、Playbook 和配置备份批次统一过滤、计数和分页。
2. 删除配置备份流程中逐设备 `_record_instant_execution` 写入；保留已有批次和设备结果账本。
3. 在批次完成后，根据每台设备最近一次已完成备份结果更新稳定去重告警；失败通知不携带原始命令输出或未经脱敏的异常文本，并在 PostgreSQL 中按设备行串行化重叠批次的告警生命周期。
4. 在当前路由使用的历史列表中展示配置备份批次，并实现详情、设备状态过滤、分页、导出和只读操作。
5. 更新 walkthrough，执行静态语法/差异校验；按当前任务指令不运行测试。

## 验证计划

- `python -m py_compile` 检查修改过的 Python 文件。
- 前端 `npm run lint`（若仓库命令存在），检查 TypeScript/React 变更。
- `git diff --check` 检查空白与补丁格式。
- 不连接真实设备、不触发备份、不发送外部通知。

## 风险与回滚思路

- 统一历史列表查询混合多来源，需确保来源过滤后仍按时间正确分页。
- 失败告警复用现有通知 outbox；告警 key 需保持设备级稳定，跳过设备不能误清除告警。
- 告警生命周期使用现有 `alert_events` 表，无需更改 schema；设备行锁仅用于避免同一设备的并发备份批次重复打开告警。
- 回滚时可恢复旧历史读取路径并重新启用影子记录调用；新批次账本与既有记录均保留，不需删除数据或执行迁移。
