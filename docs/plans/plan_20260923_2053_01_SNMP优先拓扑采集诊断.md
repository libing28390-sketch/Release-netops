# 实施计划：SNMP 优先拓扑采集诊断

## 任务目标

修正拓扑采集结果把 SNMP 成功误记为 SSH 的问题，修复重试日志格式错误，并为 SNMP 采集与 CLI 回退补充不泄露凭据的运行日志。同步澄清未匹配拓扑节点的含义，避免把“邻居未匹配 CMDB”误说成“CMDB 中不存在”。

## 现状与问题

- 拓扑服务已按 SNMP 优先实现；只有 SNMP 无可用邻居、异常或未配置时才回退 SSH CLI。
- 用户提供的 Docker 日志出现 CLI 命令和 SSH 端口不可达，说明相关设备走到了回退路径；目前 SNMP Walk 的底层超时只记 debug，生产日志无法确认原因。
- 成功采集写入状态时 `transport` 硬编码为 `ssh`，即使 `method` 为 `snmp` 也会错误显示。
- 瞬时错误的重试日志格式有两个 `%s` 占位符，但只传了设备 ID，导致用户日志里的 `TypeError` 并遮蔽重试信息。
- 页面灰色问号节点对应已发现但未匹配 CMDB 的邻居；“未匹配”不能证明资产未登记。用户提供的实际拓扑确认 SW5/SW6 是真实交换机，R5/R6 是否与它们重复需通过管理 IP、机箱标识或 CMDB 记录判断。
- 现有邻居匹配只读 `devices.ip_address/sn`，漏掉已关联物理资产中的 `physical_assets.management_ip/serial_number`；SNMP 带回管理 IP 时可能因此仍显示成独立未匹配节点。

## 影响范围

- 后端拓扑 SNMP/CLI 采集路径的诊断日志、采集来源状态和重试日志。
- 拓扑邻居匹配使用关联物理资产的管理 IP 与序列号。
- 未匹配邻居的图标与拓扑检查器说明。
- 不改变 SNMP 无数据后的 CLI 回退行为，也不改变拓扑节点匹配规则。

## 拟修改文件

- `backend/services/topology_service.py`
- `src/components/TopologyGraph.tsx`
- `src/components/TopologyInspectorPanel.tsx`
- 本计划和对应 walkthrough 文档。

## 实施步骤

1. 为 SNMP 成功、空结果、缺少凭据和异常补充脱敏日志，并显式记录 CLI 回退原因。
2. 采集成功/失败状态按实际采集方法设置传输类型。
3. 修复拓扑重试日志缺失 `run_id` 参数。
4. 将关联资产的 `management_ip`、`serial_number` 加入已有邻居候选比对，再使用设备表字段作为回退。
5. SW5/Switch5 这类未匹配节点显示灰阶交换机图标；检查器提示“已发现、尚未匹配到资产”，引导核对主机名、管理 IP、机箱 ID。

## 验证计划

- 检查修改后的 SNMP-first 分支、fallback 分支、采集状态字段和重试日志调用参数。
- 预期可执行的专项测试：`pytest -q backend/tests/topology/test_snmp_lldp_discovery.py backend/tests/topology/test_topology_lldp_snapshot.py`。
- 前端改动的预期检查：`npm run lint`。
- 本轮按用户当前请求只实施修正与诊断，不运行测试；部署环境重建并运行后，通过 SNMP 采集日志和 `device_collection_status` 核实实际传输方式。

## 风险与回滚思路

- 新日志可能增加少量每设备的 INFO 记录；只在 SNMP 未能产生邻居时记录回退说明，并且不输出 community 或其他凭据。
- 身份匹配按现有 IP/序列号/主机名证据策略扩充关联资产字段，不按 R5/SW5 编号相似度合并设备，避免误归并。
- 仅依据 SW/Switch 主机名选择图标，不把图标类型当成设备身份匹配证据。
- 采集策略和回退语义保持不变；若日志输出造成问题，可回滚本次 `topology_service.py` 改动，不需要数据库迁移。
