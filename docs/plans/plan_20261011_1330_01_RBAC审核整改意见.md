## 1. 任务目标

基于实际代码和公开规范，审核 NetOps 的身份、角色、资源权限、作用域、变更审批和自动化执行控制。交付详细整改意见书，区分 RBAC 模型要求、项目业务约束、可选安全策略与尚待运行验证的事实；给出整改优先级、接口和数据设计建议、迁移步骤、验收矩阵与可复核证据。

## 2. 现状与待复核问题

上轮发现基础角色与资源权限依赖不一致，工单/定时作业未统一接入资源权限；Playbook 版本执行可能跳过工单要求；工单未严格绑定执行设备/版本；实施 MFA 与执行入口状态检查不一致；配置审批缺少独立审批人和实际请求内容绑定。此次重新追踪完整调用链，确认事实、正向控制和适用前提。

## 3. 影响范围和文件边界

- 只读审核：`backend/core/rbac.py`、用户/会话/资源范围、变更工单、Playbook、配置审批、定时作业及后台执行链、必要测试和迁移；前端只核对权限展示与实际 API 语义。
- 实际修改：本计划、对应意见书及必要的脱敏审计证据文件。
- 不修改业务代码、数据库设计或现有用户变更。本任务不执行真实设备操作。

## 4. 分工与共享文件归属

- 主 Agent：规范来源核验、工单/Playbook 审核、公共验证、统一意见书和交接。
- `rbac_identity_audit`（Luna backend_worker）：身份、角色、会话撤销、资源范围、前端权限一致性，只读返回证据。
- `automation_authorization_audit`（Luna backend_worker）：配置审批、定时作业实际执行器、凭据与设备范围、其他自动化执行入口，只读返回证据。
- 两个执行者不写任何文件、不运行公共测试、不创建后续 Agent。主 Agent 独占本计划、意见书和验证证据的写入。

## 5. 审核步骤

1. 核验 NIST RBAC 参考模型、公开标准目录、NIST SP 800-53 和 OWASP 授权指导；限定可访问材料，不宣称未经正式评估的认证结论。
2. 追踪登录会话→角色/动作→资源范围→审批→执行器→审计与撤权的调用链。
3. 对上轮发现复核适用入口、正向保护和绕行路径，将明确缺陷与政策选择分别标注。
4. 检查现有测试覆盖；在独立临时 PostgreSQL 数据库上运行必要的已有测试。若无法保证隔离，保留静态证据并报告限制。
5. 编制目标授权模型、权限矩阵、审批/执行不可变绑定方案、PostgreSQL 约束、迁移/回滚和验收清单。
6. 核对意见书链接、证据、优先级、事实与建议区分，交付本地文件。

## 6. 验证计划

- 所有审计结论注明代码位置、触发条件、影响和验证级别。
- 公共测试只由主 Agent 运行一次；优先查看相关安全与 Playbook 测试的 fixture 和作用范围。
- 任何触及持久化的测试必须使用共享 PostgreSQL 隔离机制；pytest 的源数据库必须是本次创建的测试专用数据库，不使用正在运行的应用数据库作为测试源。
- 不访问真实设备、不向外发送通知、不使用真实密码/Token/SNMP community 构建证据。
- 文档检查覆盖引用、编号、文件路径和必需章节。

## 7. 风险、回滚与限制

- 规范可选组件不能被写成 Core RBAC 强制要求；MFA、租户隔离和工单审批是额外项目控制，需明确其适用条件。
- 既有工作区有大量用户变更，报告以读取时的文件为基线，不能仅用 HEAD 表示所有被审计代码。
- 审核不会自动改变线上权限；建议需要按后续实施任务分批交付。
- 临时测试数据库必须使用明显测试名称并清理；文档修改可直接撤销本任务新增文件。
