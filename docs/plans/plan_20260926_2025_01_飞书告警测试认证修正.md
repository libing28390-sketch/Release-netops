# 飞书告警测试认证修正

## 任务目标

修复用户资料弹窗中的通知渠道测试请求因前端读取错误的本地令牌键而返回 401 的问题，确认飞书 webhook 本身与应用 API 认证问题相互独立。

## 现状与问题

- 后端 `/api/users/{user_id}/notify-test` 经默认 API 安全边界要求有效的 Viewer 会话令牌。
- 登录流程把应用会话令牌保存到 `localStorage.netops_token`。
- 通知测试按钮读取 `localStorage.sessionToken`，导致请求发送 `Authorization: Bearer ` 空凭证，RBAC 返回 `401 Authentication required`。
- 用户提供的直接 curl 到飞书 webhook 成功，证明 webhook 可达；该请求绕过了 Nexora API，不能替代 Nexora 会话认证。

## 影响范围

影响用户资料弹窗中的飞书、钉钉、企业微信“测试通知”请求认证头，以及 `/alerts/rules` 渠道选择器的显示和布局。后端路由、webhook 配置不在修改范围内。

## 拟修改文件

- `src/components/modals/AppModals.tsx`：从标准会话存储键 `netops_token` 读取 Authorization Bearer token。
- `src/pages/AlertRulesTab.tsx`：将飞书展示名改为 Webhook，并精简渠道选择控件；接口枚举保持 `feishu`。
- 本计划及对应 `docs/walkthrough/` 交付记录。

## 实施步骤

1. 修正通知测试请求的 token 存储键，与登录和其他 API 调用保持一致。
2. 检查最终差异，确认请求仍传递当前通知渠道的 webhook 和必要配置。
3. 检查运行中的 `Interface Down` 规则及告警历史，确认其渠道策略和可观察证据。
4. 用户在 `10.255.0.4 / Et0/3` 手动触发 DOWN 后，只读检查告警事件和投递状态。
5. 精简通知渠道选择器，将界面上的“飞书”渠道显示名改为“Webhook”，保留内部 `feishu` 标识。
6. 记录代码静态验证、实际发送证据及未完成项。

## 验证计划

- 静态检查修改前后的令牌键及后端认证链路。
- 运行 `npm run lint` 和隔离输出目录的前端生产构建；本地浏览器 UI 显示需待部署后验证。

## 风险与回滚思路

风险限于使用错误或缺失的本地令牌键导致测试通知无法发出。若修正引入问题，可单独回滚 `AppModals.tsx` 中的存储键变更；不涉及数据库、后端部署或外部 webhook 修改。
