# 数据库恢复出厂安全改造计划

## 任务目标

将桌面端现有的“清理数据”功能改造为可确认、可备份、可验证、可审计的 PostgreSQL 恢复出厂流程。操作完成后应得到一套重新初始化的业务表结构、默认基础数据和默认管理员账号，同时不误删非目标数据库或数据库外的文件。

## 现状与问题

- `desktop/desktop_tray.py` 通过内联 Python 脚本直接执行 `DROP SCHEMA public CASCADE`，操作真实且不可逆。
- 终止 PostgreSQL 连接时将数据库名写死为 `netops`，当 `DATABASE_URL` 使用其他库名时，无法正确处理并发连接。
- 危险操作只有 Yes/No 确认，没有要求输入目标数据库名、管理员口令或其他强确认信息。
- 执行前没有备份，也没有明确的备份失败阻断策略。
- 桌面端只以子进程输出中是否包含 `SUCCESS` 判断成功，没有校验子进程退出码和重建后的表结构。
- 操作后依赖“下次启动”重建表，清理、初始化、默认数据写入和健康检查没有组成一个可观测的完整流程。
- 当前只清理 PostgreSQL `public` schema，不清理附件、PAM 录像、日志、`.env` 等磁盘文件，界面文案需要明确这一边界。

## 设计原则

- PostgreSQL 是生产环境的权威实现，SQLite 仅保留现有兼容能力。
- 重置必须明确绑定当前 `DATABASE_URL` 中的主机、端口和数据库名，禁止使用写死库名。
- 在执行破坏性 SQL 前完成备份和强确认；备份失败时默认中止。
- 重置流程必须返回结构化阶段结果，不再通过模糊字符串判断成功。
- 不在日志、命令行参数或界面中输出 PostgreSQL 明文密码。
- 重置完成后必须自动执行初始化和健康校验，不将成功状态延迟到未知的下次启动。

## 影响范围

- 桌面端设置页的危险操作交互、进度展示和结果提示。
- PostgreSQL 目标库识别、连接终止、schema 重建、数据库初始化和健康检查。
- PostgreSQL 逻辑备份文件的创建、命名、存放位置和失败处理。
- 默认管理员账号和基础 seed 数据的重建验证。
- 不默认删除附件、PAM 录像、日志、环境配置和备份文件。

## 拟修改文件

- `desktop/desktop_tray.py`：改造二次确认、备份选项、阶段进度和结构化结果处理。
- `backend/database/reset.py`：新增可独立调用和测试的 PostgreSQL/SQLite 重置服务，替代桌面端内联 SQL。
- `backend/database/core.py`：如有必要，补充安全获取当前目标库元数据的 helper，不暴露密码。
- `backend/database/schema.py`：复用现有 `init_db()` 完成空库基线重建，仅在需要时增加可重入的验证辅助函数。
- `backend/main.py`：抽取或复用 seed 逻辑，保证重置后可主动执行，而非只依赖 FastAPI lifespan。
- `backend/tests/test_database_reset.py`：新增重置服务的成功、失败、目标库识别和安全边界回归测试。
- `docs/deploy/windows.md`：补充恢复出厂行为、备份位置、不清理的磁盘数据和人工恢复方法。

## 实施步骤

### 1. 抽取数据库重置服务

- 将 `desktop_tray.py` 中的内联 Python/SQL 迁移到 `backend/database/reset.py`。
- 定义明确的重置请求、阶段状态和错误类型，至少包含 `preflight`、`backup`、`disconnect`、`reset_schema`、`initialize`、`verify` 阶段。
- 子进程以 JSON 输出阶段结果，桌面端同时检查退出码和结构化状态。

### 2. 增加目标库预检查

- 从当前 `DATABASE_URL` 解析主机、端口、数据库名和当前用户，并使用 `SELECT current_database()` 二次校验实际连接目标。
- 拒绝清理 `postgres`、`template0`、`template1` 等系统库。
- 检查当前账号是否拥有终止连接、删除和创建 schema 的权限；权限不足时在破坏性操作前失败。
- 将 `pg_terminate_backend` 的 `datname` 改为实际目标库名，并记录终止连接数量。

### 3. 增加强确认交互

- 第一层展示实际数据库主机、端口、库名、清理范围和不可恢复警告。
- 第二层要求用户完整输入当前数据库名，匹配后才允许启用执行按钮。
- 明确提示默认管理员将恢复为 `admin / admin`，首次登录后必须立即修改密码。
- 如无可用的备份工具，默认禁止执行；若后续提供“无备份强制继续”，必须增加更高强度确认文字，且默认不勾选。

### 4. 执行 PostgreSQL 逻辑备份

- 优先使用与目标 PostgreSQL 主版本兼容的 `pg_dump` 生成 custom-format 备份。
- 备份文件命名包含数据库名和时间戳，默认保存到 `data/backups/database-reset/`。
- 通过环境变量传递密码，禁止将密码写入命令行、文件名或日志。
- 检查 `pg_dump` 退出码、备份文件存在性和非零大小；任一失败则中止重置。
- 界面显示备份文件路径，供用户后续使用 `pg_restore` 恢复。

### 5. 安全重建 schema

- 停止当前后端服务并等待进程退出，避免应用连接池立即重连。
- 终止目标库的其他会话，但不影响其他数据库。
- 执行 `DROP SCHEMA public CASCADE`、`CREATE SCHEMA public`，然后使用当前数据库 owner 恢复合理的 owner 和 grant，不再固定向 `public` 角色赋予宽泛权限。
- 对 SQLite 保留删除主文件、WAL 和 SHM 的兼容分支，但测试和交付以 PostgreSQL 语义为准。

### 6. 自动初始化与验证

- 重置 schema 后在同一任务中调用 `init_db()` 和 seed 逻辑，生成完整基线表结构。
- 检查关键表是否存在，至少包括 `users`、`devices`、`credentials`、`schema_migrations`。
- 检查迁移记录是否达到当前版本，默认管理员是否存在，且密码为有效 bcrypt hash。
- 启动后端并调用健康检查接口；只有建表、seed 和健康检查全部通过才向界面报告成功。
- 如果 schema 已删除但初始化失败，保留备份并在界面显示明确的 `pg_restore` 恢复指南，不误报成功。

### 7. 补充审计与文案

- 记录重置开始时间、完成时间、目标主机的脱敏信息、目标库名、阶段结果和备份路径，不记录密码。
- 明确区分“数据库恢复出厂”与“完整卸载”，列明不会自动删除的磁盘文件。
- 成功提示中显示数据库名、备份位置、初始化校验结果和修改默认密码的提醒。

## 验证计划

### 单元与集成测试

- 验证可从非 `netops` 的 `DATABASE_URL` 正确识别库名，且终止连接 SQL 使用实际库名。
- 验证系统库保护、数据库名确认不匹配、权限不足和备份失败时，不会执行 `DROP SCHEMA`。
- 验证 `pg_dump` 密码不出现在命令行、日志和错误信息中。
- 验证成功流程的阶段顺序、JSON 结果、退出码和备份文件检查。
- 验证初始化失败、健康检查失败和超时时正确报错，不显示成功。

### PostgreSQL 验证

- 使用独立的临时测试数据库，写入设备、凭据、配置快照、工单和迁移记录样本。
- 执行重置后确认样本业务数据已清空，关键表、索引、外键和迁移记录已重建。
- 验证 `admin / admin` 可首次登录，普通用户和原有会话已清除。
- 使用生成的备份对另一个临时数据库执行 `pg_restore`，验证恢复文件真实可用。
- 验证另一数据库和非 `public` schema 未被误删。

### 界面与发布验证

- 验证数据库名不匹配时执行按钮不可用，默认选择为取消。
- 验证备份、清理、初始化和健康检查的进度与错误文案。
- 运行 `python -m py_compile desktop/desktop_tray.py backend/database/reset.py`。
- 运行定向 pytest，再按风险扩展到相关数据库测试。
- 运行 `npm run lint` 和 `npm run build`。
- 重新打包 `NetOps.exe`，在 Windows 上进行真实 PostgreSQL 临时库冒烟验证。

## 风险与回滚思路

- `DROP SCHEMA public CASCADE` 是不可逆操作；实施和验证期间只允许针对明确创建的临时测试库，不对现有用户库执行真实清理。
- 备份文件是业务数据的主要回滚手段；交付前必须完成至少一次实际 `pg_restore` 验证。
- 如新流程不稳定，回滚桌面端入口并临时禁用“清理数据”按钮，不恢复旧的无备份危险实现。
- 如重建失败，保留失败日志和备份文件，按文档使用新建空库加 `pg_restore` 恢复，避免在半初始化库上继续写入。
- 保留 SQLite 现有兼容路径，但不用 SQLite 测试结果替代 PostgreSQL 真实验证。

## 完成标准

- 不再存在写死的 `netops` 数据库名。
- 破坏性操作前必须通过目标库校验、权限预检查、备份校验和数据库名强确认。
- 重置后在同一流程中完成建表、迁移、seed、默认管理员校验和后端健康检查。
- 备份文件可通过 `pg_restore` 恢复到独立临时库。
- 失败时不误报成功，界面能指明失败阶段和恢复路径。
- 相关单元测试、PostgreSQL 集成测试、TypeScript 检查、Vite 构建和 Windows exe 冒烟验证通过。
