# SNMP 自动识别迪普与山石计划

## 任务目标

让 `/assets/network-devices` 的“平台识别与绑定”入口能使用 SNMP `sysObjectID` 和 `sysDescr` 推断厂商，并为迪普、山石生成正确的平台候选；将当前资产字段留作权威数据，不在识别请求中自动改写。

## 现状/问题

- 独立 SNMP 厂商识别已有 DPtech enterprise OID `1.3.6.1.4.1.31648`，以及 Hillstone OID `1.3.6.1.4.1.24681`、`1.3.6.1.4.1.28557`。
- 资产详情页 `platform-detect` 当前只从 `sysDescr` 提取软件版本，并用设备已有 vendor/platform 查 profile；没有把 SNMP 观测到的 vendor 传给页面。
- DPtech 有系统 profile 与版本分流；Hillstone 有资产平台选项和配置备份命令，但平台注册表和平台识别映射缺少 `hillstone_stoneos` 系统 profile。

## 影响范围

SNMP-first 平台识别服务、平台系统 profile 目录、存量数据库 profile seed、资产详情页识别候选展示，以及前端厂商别名/标签。保留识别结果为建议，只有用户保存绑定时才更新平台绑定。

## 实施步骤

1. 调整资产详情页 platform-detect 的探测顺序，优先读取实时 SNMP；复用现有 SNMP 身份解析器，把 `sysObjectID`/`sysDescr` 识别结果写入响应；与已登记厂商或平台族冲突时不自动选择平台。
2. 补 Hillstone vendor 到 `hillstone_stoneos` 平台候选映射，并将 Hillstone system profile 及只读配置备份动作纳入平台目录。
3. 为现有数据库添加幂等迁移，沿用系统 profile seed 机制创建 Hillstone profile/release。
4. 前端以识别到的厂商过滤平台候选并明确展示 SNMP 厂商识别结果；不写回 vendor 字段，冲突时提示先核对资产信息。
5. 使用现有 PostgreSQL fixture 验证实时 SNMP 厂商识别、厂商冲突与探测顺序；再运行平台注册/备份覆盖测试、PostgreSQL-only 策略扫描、Python 语法检查、TypeScript lint 与 diff 检查；不连接真实设备。

## 验证计划

- `pytest backend/tests/platform_registry/test_platform_identification.py backend/tests/configuration/test_startup_config_backup.py` 检查平台识别、冲突处理与山石命令/profile 覆盖。
- `python scripts/validate_postgresql_only.py` 检查持久化路径没有新增 SQLite 专用实现。
- `python -m py_compile` 检查变更 Python 模块和迁移；`npm run lint` 检查前端类型；`git diff --check` 检查补丁格式。
- 不连接真实设备，也不对当前应用数据库执行迁移。

## 风险与回滚思路

厂商 OID 使用仓库现有映射。平台 profile 仅代表 StoneOS 家族，不推测未知版本特性。迁移采用既有幂等系统 profile helper；若映射或 profile 有问题，可撤销识别调用和候选映射，已创建的 system profile 保留，避免破坏设备外键引用。
