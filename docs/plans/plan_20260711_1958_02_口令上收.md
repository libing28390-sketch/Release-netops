# 实施计划 - 口令上收逻辑与连通性优化

## 问题分析

在资产看板页面执行“口令上收”时，提示部分上收任务启动失败且后端无日志。通过排查定位到两个根本问题：
1. **凭据表与设备表隔离验证问题**：设备在“本地凭据”模式下，口令存在独立的 `credentials` 凭据表中，而 `devices` 对应的账号密码为空。前置校验未关联 `credentials` 表，导致 422 验证报错。
2. **双密码模式轮转顺序设计缺陷**：在双密码模式下，系统在执行 takeover 时先轮转普通账号（`normal`），然后轮转特权账号（`admin`）。由于两个账号共享底层的 `credential_id` 关联，第一步普通账号改密成功后会同步更新 `credentials` 共享主密码，导致第二步特权账号连接设备时，使用了刚刚被修改更新的普通账号密码去连接还未改密的特权账号，进而引发特权账号认证失败（`Authentication failed`）。

## 解决方案

1. **改进前置校验**：在 `backend/api/assets.py` 的 `update_asset` 校验流程中引入统一凭据解析服务 `resolve_device_credentials`，支持并校验从外部凭据表获取的密码，并支持双密码空字段时的向主密码安全回退。
2. **调整改密顺序**：在单设备和批量上收逻辑中，调换改密顺序为：**先轮转特权账号密码（`admin`）**，成功后**再轮转普通账号密码（`normal`）**。这样能确保在所有阶段中用于登录的特权账号旧密码在改密完成前持续有效，完美解决了凭据冲突导致的死锁。

## 验证计划

1. 确认系统所有单元/集成测试用例均可完美跑通。
2. 重置数据库中的测试数据口令为初始状态 `123456`，在用户物理路径与虚拟机路径通畅时，执行单台/批量口令上收，验证状态是否顺利流转至 `production`（投产）。
