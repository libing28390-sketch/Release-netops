# 资产设备 OID 自动发现实施计划

## 任务目标

让资产管理中已导入的网络/安全设备在具备 SNMP 凭据时，按设备实际返回的身份信息和 SNMP 指标表自动确定可用的监控 OID，并使原生健康采集与 Monitoring V1 使用一致的选择结果。人工锁定且已验证的绑定优先；现存未验证绑定仅作为待探测候选，不直接当成正确结果。自动判断不充分时保留通用系统/接口指标并给出可查询的未匹配原因。厂商范围以资产管理实际纳管的资产为准，不同步 LibreNMS 全部厂商。

## 现状与问题

- 设备信息采集未获取 `sysObjectID.0`；版本和型号主要来自 `sysDescr` 或资产录入字段。
- LibreNMS 同步只导入 `mibs/` 符号库，没有使用 `os_detection` 规则。
- 原生健康采集的 `snmp_metric_profiles` 默认只接受显式绑定；自动候选只用于预览。
- Monitoring V1 另用 `snmp_module_variants`/采集计划编译 exporter 配置，未消费前述绑定；静态型号和版本范围会排除实际兼容设备，例如基础平台键 `h3c_comware`。
- Windows 本机 PostgreSQL 18 正在运行。使用项目 `.venv` 可只读连接：目前 `physical_assets` 中只有 2 台 `network_device`，厂商均为 Cisco；关联 `devices` 两台都是 `C2960`、`cisco_ios`、`15.4(1)T`、在线、已配 SNMP 凭据和模板绑定。
- 当前两台绑定同一份未验证的 `md-cisco-catalyst-categraf` 模板。模板 CPU 指向 CISCO-PROCESS-MIB 的 5 秒列，内存指向 Cisco Memory Pool Used/Free；尚无从设备读回的对象标识、具体 CPU 行索引或对 OID 可用性的记录。不能仅凭这些字段断言它们正确。
- 资产模板导入还存在 community 表头兼容和加密失败静默丢弃风险；这会让后续 SNMP 发现拿不到凭据，即使 OID 逻辑正确也不会生效。
- LibreNMS Cisco 逻辑会先识别 IOS 家族，然后 WALK CPU 表，优先 5 分钟新版列、其次旧版列，并按实际行索引生成 OID；内存依次尝试增强内存池、传统内存池和 CPU 内存列。当前 Nexora 的一条静态 OID 无法表达此选择过程。

## 本批范围与扩展规则

- **首批真实资产样本仍是 Cisco C2960**，但代码适配范围扩展到现有 `monitoring_oid_catalog` 中的 H3C、Huawei、Ruijie、Juniper、Fortinet、ZTE、Maipu、DPtech、Hillstone、Sangfor、DCN、Aruba、Ruckus 以及无线模块。以资产库实际出现的厂商决定运行时是否启用。
- 厂商启用集合在运行时由 `physical_assets` 中已纳管的网络/安全资产得出；目录中没有对应 OID 适配器的资产厂商只做身份和通用接口发现，不误用其他厂商 OID。
- LibreNMS 是唯一可信的 MIB/OID 来源：同步其 OS detection、OS discovery 和 MIB 规则，优先使用 LibreNMS numeric OID 候选；Nexora 内置规则只用于标准 IF-MIB/系统 MIB 的安全兜底。
- 本机是 Windows 部署且没有 Docker；本批验证限于 PostgreSQL、纯逻辑和模拟 SNMP 返回。vmagent、SNMP exporter、Grafana 的容器联调不作为本机完成标准。

## 影响范围与拟修改文件

- `backend/services/snmp_service.py`：采集并规范化标准设备身份。
- `backend/services/background_monitor_service.py`：保存身份、触发后续目标重编译。
- `backend/services/` 下的设备身份与 OID 解析服务：统一厂商、平台、型号、版本、目录变体、CPU/内存/传感器表行索引与可解释结果。
- `backend/services/snmp_vendor_registry.py`：维护资产厂商全集、适配器状态和 standard-only 安全边界。
- `backend/services/librenms_rule_service.py`：同步、解析和匹配 LibreNMS OS/OID 规则。
- `backend/services/librenms_mib_service.py`、`backend/scripts/sync_librenms_mibs.py`：同步 MIB、OS detection、OS discovery 和 OS 类定义。
- `backend/services/snmp_metric_profile_service.py`：为未锁定或未验证设备接入自动解析，保留已验证人工锁定和歧义保护。
- `backend/services/monitoring_compiler.py`、`backend/services/monitoring_oid_catalog.py`、`backend/api/monitoring_v1.py`：根据已确认的设备身份选择 exporter 模块，并将选择理由写入编译结果。
- `backend/database/schema.py`、新增 `m0242_*`/`m0243_*`/`m0244_*`：保存设备 SNMP 身份、按设备/指标发现的 OID 与索引、LibreNMS 规则来源和解析状态，并把现有目录模块注册到基线计划，兼容已部署 PostgreSQL。
- `backend/tests/snmp/`、`backend/tests/monitoring/`、`backend/tests/database/`：覆盖匹配、无匹配、歧义、绑定优先级和编译一致性。

## 实施步骤

1. **只读基线和身份边界**：固定本批 2 台 Cisco C2960 的资产、关联设备、已绑定模板和编译目标；只记录无凭据的身份/模板字段。读取资产厂商时按 `physical_assets` 的网络/安全设备类型过滤，不把服务器厂商混入 SNMP 网络设备目录。
2. **设备身份发现**：在现有 `collect_device_info` 中增加 `sysObjectID.0`；规范化数字 OID，和 `sysDescr`、资产厂商、型号、平台一起形成身份记录。Cisco 使用 IOS 家族规则，其他目录厂商使用对象标识/平台目录匹配；若 SNMP 观察与资产厂商冲突则记录冲突，不自动改写资产。
3. **指标表发现**：Cisco 使用 LibreNMS 顺序选择 CPU、内存和环境表；其他厂商从现有 OID 目录逐项探测 CPU、内存、温度、风扇、电源和无线指标，保留实际索引，过滤非数字/无效行。所有厂商接口先确认 `ifIndex`/`ifName`、64 位计数器是否可用，再决定 32 位回退。
4. **持久化与选择优先级**：新增设备身份表/字段和按设备、指标、索引的发现记录，包含数值 OID、来源、发现时间、验证状态、规则版本，不保存 community。已验证且人工锁定的绑定保持优先；历史未验证绑定和自动候选必须经过实际 SNMP 返回验证才能成为运行配置。
5. **双采集链路统一**：原生健康采集直接使用已确认的按设备 OID；Monitoring V1 以同一发现记录生成该设备的 exporter 模块/目标，不再独立凭 `C2960` 或软件版本猜 OID。没有有效结果时发布安全通用基线，标记 `pending_discovery`/`no_supported_oid`，不发布错误的厂商指标。
6. **自动触发与发布**：资产创建/更新、SNMP 身份变化、模板更新和定时重探触发发现；发现任务异步限流、失败保留上一版结果并按退避重试；只有有效配置哈希改变才生成新版本并原子发布，保留 Last Known Good 和回滚路径。
7. **可观测与人工介入**：API/UI 显示识别出的 IOS 家族、每项指标选中的 OID 与索引、选择原因、上次成功发现时间以及冲突/缺失状态；提供重新发现入口和人工锁定入口，日志与响应均不包含 SNMP 凭据。
8. **厂商扩展**：资产首次出现目录外厂商时，先添加该厂商的身份规则、指标表候选和脱敏 fixture；通过同一解析契约验证后再开启。不会同步所有 LibreNMS 厂商，也不会用其他厂商默认 OID 覆盖未知设备。

## 验证计划

- 静态检查迁移、DB 查询、事务边界和凭据脱敏；运行相关 PostgreSQL 迁移测试及仓库 PostgreSQL-only 扫描器，不触碰现有生产资产数据。
- 用模拟 SNMP WALK/GET 返回覆盖 Cisco 优先级、目录厂商的 CPU/内存/传感器发现、内存池配对、接口计数器能力、型号/版本冲突、离线、无凭据和歧义。验证原生采集与 exporter 使用同一发现结果。
- 验证两个已导入 C2960 的只读数据库投影和迁移前后兼容；未获得真实设备 SNMP 指标返回时，结果只能是 `待发现`，不得宣称具体 OID 已经通过实机验证。
- 运行 API 契约与权限检查；若前端契约变化，执行 `npm run lint`。本机无 Docker，跳过容器监控联调并写明这一限制。

## 完成判据

- 仅已导入且有目录/适配器的厂商进入自动发现；当前真实资产是 Cisco，但代码已注册现有目录厂商模块。新增未适配厂商有明确状态，不触发跨厂商 OID 回退。
- 两台 C2960 在相同模拟 SNMP 证据下产生确定且一致的 CPU、内存、接口选择；无证据时不会沿用未验证模板并宣称已成功。
- 实际选中 OID/索引、来源和原因可查询；人工锁定、发现失败、重新发现和回滚均有确定行为。
- 原生轮询与 Monitoring V1 编译所使用的选择一致；监控配置未变化时不重复发布新版本。

## 风险与回滚

- 资产厂商名可能与 SNMP 实际厂家不一致；保留证据与冲突状态，不自动改写资产厂商或平台。
- 同厂商不同硬件/软件代际的 CPU、内存等表结构可能不同；无证据时只用标准基线，专项 OID 需实机验证。
- 迁移仅新增字段，旧数据保持可读；关闭自动选择后仍可使用原有显式绑定，采集器可回滚至上一版已发布配置。
- LibreNMS GPL 数据仅作规则参考；不批量拷贝其全部厂商代码或 MIB。
