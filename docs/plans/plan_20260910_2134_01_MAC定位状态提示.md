# MAC 定位状态提示

## 任务目标

修复 IP 定位中 MAC 表查询结果语义不清的问题。后端要区分策略关闭、平台不支持、查询失败、已查询未命中和命中；前端要依据状态展示对应提示，同时保留 ARP-only 降级能力。

## 现状/问题

- `S6850-5` 的 ARP 可获得 IP→MAC，但 MAC 查询失败或未执行时，定位结果统一降级为 `ARP_DIRECT`。
- `_targeted_mac_query` 当前只返回记录列表，策略关闭、命令不支持、SSH 失败、解析为空和真实未命中都会变成 `[]`。
- 前端没有 MAC 查询状态字段，使用硬编码文案“该 MAC 未在交换机 MAC 表中发现”，容易把“不支持/未采集”误判为“已查询但不存在”。
- 设备不支持 MAC/VLAN 表时必须继续允许 ARP-only，不能通过全局开启 MAC 采集解决。

## 影响范围

- 后端 IP 定位服务响应契约及 MAC 查询状态归因。
- 前端 IP 定位结果卡片和错误/降级提示。
- 后端定位回归测试、前端类型与 lint/build 验证。

## 实施步骤

1. 为 MAC 查询增加不泄露凭据的结构化状态，覆盖策略关闭、平台/命令不支持、传输/执行异常、解析后无目标记录和成功命中；通过 list-compatible 结果包装保持现有调用方兼容。
2. 在 `locate_ip` 结果中返回 MAC 查询状态、来源设备及必要的端口/VLAN证据；ARP-only、链路未完成和终端命中行为保持兼容。
3. 更新前端 `LocateResult` 类型和结果卡片，按状态显示明确中文/英文提示；命中时显示 MAC 表端口/VLAN，ARP-only 时明确是降级而不是误报未发现。
4. 对 `PATH_TRACED` 终端结果隐藏冗长的路径推理备注，仅保留状态标签、设备、端口和 VLAN；ARP-only、链路未完成及错误提示继续保留。
5. 将用户界面中的内部枚举 `PATH_TRACED` 映射为“已定位到接入端口”，避免向用户直接展示内部状态码。
6. 增加成功、策略关闭、设备不支持/命令缺失、查询失败、未命中和 ARP 降级回归测试。
7. 运行后端定位测试、前端 lint/build，并按质量门禁检查差异、API兼容性和敏感信息。

## 验证计划

- `pytest backend/tests/vendor_audit/test_ip_locator_arp_contract.py`
- 相关前端测试（如存在）以及 `npm run lint`
- `npm run build`（使用隔离输出目录或确认不覆盖用户已有构建产物）
- 检查 PostgreSQL-only 约束扫描结果（本次不改数据库结构，但属于后端契约变更）

## 风险与回滚思路

- 新增响应字段应保持旧字段和 ARP-only 结果兼容；前端对缺失状态使用旧逻辑作为兼容回退。
- 不改变设备命令、凭据和采集策略，不下发配置；真实设备验证仅使用只读查询。
- 若状态归因影响已有调用方，可回退新增字段和前端分支，保留原有定位主流程。
