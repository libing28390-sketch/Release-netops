# 采集器运行状态与心跳判定

## 目标

让采集器列表和“状态检查”依据实际运行信号报告状态，避免把配置发布成功误报为采集器在线，也避免把本地 vmagent 状态误称为 agent 心跳。

## 现状与问题

- 当前仓库没有监控采集器的心跳写入端点或上报进程，`last_heartbeat_at` 不会被更新。
- `publish_collector()` 发布成功时把 `monitoring_collectors.status` 设为 `ONLINE`，但这只能证明配置应用成功。
- `POST /collectors/{id}/test` 只检查启用字段，却在启用时返回 `PASS`，并附带空心跳时间。
- `LOCAL` 采集由 Docker Compose 中的 vmagent 等平台组件承载；远程/边缘采集器当前没有心跳协议。

## 影响范围

- `backend/api/monitoring_v1.py`：本地运行状态探测、列表/详情的状态计算、状态检查接口、发布状态语义。
- `src/components/MonitoringManagementPage.tsx`：按采集器类型说明检查结果，停止把本地服务状态称为心跳。
- `backend/tests/monitoring/`：覆盖启用、停用、本地探测成功/失败和远程无心跳未知状态。
- 对应测试和部署记录见 walkthrough。

## 实施步骤

1. 将 `LOCAL` 采集器运行信号对接到固定内部 vmagent `/health` 和 SNMP Exporter `/metrics` 探测，并显式绕开代理。
2. 列表和详情根据探测结果呈现本地运行状态；远程/边缘在没有心跳时显示未知。
3. 状态检查接口实际探测本地 vmagent；远程/边缘无心跳时返回未知，不因“已启用”返回通过。
4. 配置发布只更新配置应用状态，不将运行状态强行写成在线。
5. 运行针对性后端测试、前端 lint、组件测试和构建；审查当前工作区全部待提交源码与对应计划/走查文档，排除生成产物和私有日志。
6. 按仓库规则创建修复记录，在 `main` 汇总提交并推送；持续检查本次提交触发的 GitHub Actions，修复本次改动造成的失败后重推并确认最终成功。
7. 备份目标环境，快进同步已验证的 `main` 提交，只重建并重启 `netops`；确认全部容器健康、API 与页面反馈正常。
8. 所有远端验证通过后关闭本机。

## 验证计划

- `pytest backend/tests/monitoring/<本次新增测试文件>`
- `npm run lint`
- `git diff --check`
- 对应提交的 GitHub Actions 全部成功完成。
- 目标容器 `nexora-netops`、`nexora-vmagent`、`nexora-db` 健康检查及 `/api/health/live`。
- `/monitor/collectors` 列表和状态检查结果；不触发编译、发布、新建或删除操作。
- `docker compose ps` 中所有容器均运行正常后再执行本机关闭。

## 风险与回滚

- 本地状态检查依赖容器网络中的 `vmagent:8429/health`；探测失败时报告离线/不可达，不改变配置发布记录。
- 该检查只证明 vmagent 进程健康，不证明目标设备已采到有效数据。
- 远程和边缘采集器仍需后续定义经过认证的心跳契约；没有心跳时保持未知。
- 如部署后服务异常，可恢复目标机备份的前端源码和应用镜像；不重建数据库或数据卷。
