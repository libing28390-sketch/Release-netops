# IP 定位缓存摘要与耗时排查

## 任务目标

精简 IP 定位用户界面，只保留本次定位是否复用了 Redis 缓存，以及所用定位证据的数据时间；同时排查 Docker Redis 时区显示和 IP 定位响应耗时的原因。

## 现状/问题

- 当前成功卡片展示 Redis 命中、PostgreSQL 复用、CLI 来源、整体结果缓存未命中、Redis 写入确认等多个不同含义的标签，用户容易把“有一项写入确认”误解为“完整结果都写入 Redis”。
- 前端结果已包含 `evidence_collected_at`，表示本次定位证据中最旧的采集时间；顶部显示的 `timestamp` 则是查询时间，不能代表数据更新时间。
- Compose 为 Redis 设置了 `TZ`。需要核对官方 `redis:7.4.2-alpine` 镜像的 tzdata 与服务时区实际生效条件。
- IP 定位通过后台 durable run 轮询；需按阶段核对前端请求超时、worker/设备查询预算、Redis socket 超时及 CLI 排队等待。

## 影响范围

- IP 定位成功卡片及可展开详情的 Redis 来源展示。
- 前端结果摘要 helper 与测试。
- Docker Redis 与定位耗时只读排查，不预先改变生产配置。

## 实施步骤

1. 用 `cache_provenance` 计算“本次是否使用 Redis”；缺少 provenance 时显示“未记录”，避免把未知误写为未使用。
2. 用 `evidence_collected_at` 显示数据时间，并明确这是本次结果最旧的证据时间，不把当前查询时间冒充缓存数据时间。
3. 移除成功卡片中的 PostgreSQL/CLI/整体 miss/SET ack 等内部徽标，并从展开详情中移除逐项 Redis 写确认，保留定位结果本身。
4. 添加摘要 helper 单测，运行前端 lint/build 和相关测试。
5. 只读核对 Redis 镜像 tzdata、Compose `.env` 时区覆盖与定位 API/Redis/SSH 等耗时边界，给出可区分瓶颈的检查方法。

## 风险与回滚思路

前端摘要只消费现有 API 字段，不改变定位流程、Redis 键或 TTL。若时间字段在兼容接口中缺失，显示“数据时间未记录”，不退回显示查询时间。若 UI 回归，可单独回滚摘要组件和 helper，不影响缓存或业务数据。
