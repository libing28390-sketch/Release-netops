# SNMP 告警链路查漏补缺实施计划

## 任务目标

审查 `/alerts/desk`、告警规则、SNMP 采集、生命周期状态机和通知出队链路，修复会导致 SNMP 告警误报、漏报或规则修改不生效的问题。保留现有个人设置中的飞书、钉钉、企业微信/API 通知能力；本批先完成 SNMP 告警闭环，邮件通知作为后续独立通道扩展。

## 现状/问题

- 采集后台只在启动时读取告警规则，规则页面更新后最多要重启服务才会进入 SNMP 采集循环。
- SNMP 模板采集器把风扇和电源状态统一规范化为 `True/False/None`，告警判断仍只识别字符串 `fail`，导致布尔型故障不会触发。
- 告警台能展示、确认、分派、备注和维护期，但列表没有展示指标类型/采集来源，排障时难以区分 SNMP 硬件、接口、SNMP 可达性和其他采集来源。
- 通知已经通过 durable outbox 调度，但用户通道分发主要读取全局通道 URL，个人设置中的非全局 webhook 可能无法真正参与自动告警分发。

## 影响范围

- SNMP 健康指标：CPU、内存、温度、风扇、电源。
- SNMP 接口指标：接口状态、利用率、错误率、震荡。
- SNMP 可达性告警和现有告警生命周期（FOR、恢复、静默、维护窗口、重复通知）。
- `/api/alerts`、`/api/alerts/{id}` 与 `/alerts/desk` 的可观测字段。
- 个人通知通道的分发优先级，不新增邮件发送实现。

## 实施步骤

1. 增加规则缓存的短 TTL/显式刷新逻辑，保证告警规则调整能在采集循环内生效，并在数据库不可用时保留上一份有效规则。
2. 统一解释 SNMP 风扇/电源状态，正确处理布尔值、字符串状态和未知值；未知值不被误判为故障或恢复。
3. 为告警 API 增加由稳定 dedupe key 推导的指标类型，完善详情时间线字段。
4. 在告警台和导出数据中展示指标类型，便于确认 SNMP 采集告警是否按预期触发。
5. 修正自动通知分发的通道选择：个人未填写独立 URL 时使用全局通道，个人填写独立 URL 时优先使用个人配置，同时遵循个人 enabled 开关；继续使用现有 outbox，不在采集协程中直接访问外部 API。
6. 对修改文件做静态编译、PostgreSQL 迁移计划检查和前端 lint/build；不在 Windows 主机上执行真实 SNMP、Docker、vmagent 或 Grafana 联调。

## 验证计划

- 静态检查 Python 编译和 `git diff --check`。
- 使用纯逻辑输入确认风扇/电源 `False` 会进入 active、`True` 会进入 recovery、`None` 不改变现有状态。
- 检查规则缓存刷新在规则更新时间变化或 TTL 到期后重新读取。
- 检查 API 响应和前端类型契约包含指标类型，且 `/alerts/desk` 能展示。
- 检查通知分发的全局回退、个人覆盖和禁用分支，不发送真实外部通知。

## 风险与回滚思路

- 本批不改变现有告警规则阈值和通知平台协议；回滚只需撤销新增逻辑及前端展示字段。
- 个人 webhook 优先策略可能改变同一平台的发送目标数量，需要保留全局配置作为无个人 URL 时的兼容回退。
- Windows 环境无法验证真实 SNMP OID 返回和外部 webhook 成功响应，部署到 Docker/采集环境后仍需做设备级验证。
