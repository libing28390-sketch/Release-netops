# 个人资料保存权限修复计划

## 任务目标

修复租户管理员在个人中心保存资料时被 `user.update` 资源范围检查拒绝的问题；同时确保自助资料保存不能修改账号角色、用户名、分组或资源范围，并让前端正确展示结构化 API 错误。

## 现状与问题

- 浏览器与日志显示，`lisan` 保存个人设置时调用 `PUT /api/users/{id}`，后端把租户内管理员按管理员代管账号的路径执行，并要求其具备 `user.update` 范围，因此返回 403。
- 该路由同时服务自助资料更新和管理员账号管理；目前以 `role == Administrator` 判断管理权限，导致管理员更新自己的资料也会进入管理账号授权路径。
- 二次复核发现，上一版仍由前端把 `currentUser.id` 传入共享路由，并依赖它与会话 `user_id` 相等。为消除前端 ID 不一致、陈旧或缺失导致误入管理分支的可能，个人中心改为调用独立自助资料接口，由服务端从登录会话确定目标用户。
- 前端把结构化 `detail` 对象直接插入 toast，显示成 `Error: [object Object]`。

## 影响范围

- 个人资料 API 的自助更新授权与字段白名单。
- 个人中心保存失败时的结构化错误展示。
- 不改变管理员代管其他账号所需的租户与资源范围校验。

## 拟修改文件

- `backend/api/users.py`
- `src/hooks/useUserProfile.ts`
- `backend/tests/security/test_audit_regressions.py`
- `docs/walkthrough/walkthrough_20261014_1644_01_个人资料保存权限修复.md`

## 实施步骤

1. 新增由会话确定目标用户的本人资料接口；只有管理员管理其他账号的接口执行 `user.update` 范围检查。
2. 自助更新时保留已有角色、角色配置、用户名、分组和资源范围，只允许更新个人资料字段与自身安全设置。
3. 限制自助保存对全局通知通道的修改：保留通道创建者和全局管理员的既有编辑权限。
4. 前端从结构化错误中提取可读消息，避免显示 `[object Object]`。

## 验证计划

- 新增回归检查，验证租户管理员可更新本人资料但不能通过个人资料表单改变角色、分组或资源范围，并验证更新其他账号仍受 `user.update` 范围保护。
- 验证本人资料请求不需要也不接受前端目标用户 ID，并始终绑定当前会话用户。
- 运行对应 pytest、`npm run lint`、Python 语法检查与 `git diff --check`。
- 在浏览器提交当前账号的未修改个人资料；若运行服务连接不可用，记录具体错误并区分本地代码验证与远端验证。

## 风险与回滚

- 风险：`PUT /api/users/{id}` 同时承担自助更新和代管更新，分支边界处理不当可能扩大权限。
- 缓解：自助分支只从数据库保留敏感管理字段；管理其他账号继续校验授权范围。
- 回滚：仅回滚 `backend/api/users.py` 与 `src/hooks/useUserProfile.ts` 本次改动及对应文档，不触碰工作区其他已有变更。
