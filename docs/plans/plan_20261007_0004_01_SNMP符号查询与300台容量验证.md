# SNMP 符号查询索引与 300 台容量验证

## 目标

基于七个约 5 分钟远端采样，核实自动硬件发现中的 MIB 符号查询是否造成重复全表扫描；若生产 SQL 计划确认为顺序扫描，则为大小写不敏感的精确匹配增加 PostgreSQL 表达式索引。再用贴近现场 SNMP 绑定比例和传感器密度的隔离 300 台负载，量化传感器样本持久化成本，并验证按设备批量写样本的候选优化。生产不导入测试设备或传感器；用户已授权对部署机执行必要备份、代码部署、索引迁移和验证。

用户最新授权要求修复完成后提交并 push 工作区相关代码、跟进 Actions、登录 Docker 部署机自主修改验证，并在所有任务完成后关机。部署时保留现有数据和自定义 Grafana dashboard；不修改真实网络设备、不用未登录生产 API 测试资产写入。

## 证据与边界

- 四个 300 秒窗口的后端 live 直连 p95 分别约为 4.18、4.02、2.20、2.75 秒；Nginx p95 分别约为 5.84、4.00、1.79、3.49 秒。前两个窗口出现 1–2 次 6 秒传输超时，后两个为 1 次及 0 次。
- 每个窗口中，Grafana 与 VictoriaMetrics health p95 保持在约 5–19 毫秒；应用容器 CPU p95 约为 85%–101%，没有 cgroup throttling 或 OOM 记录。
- 每个窗口 `snmp_mib_nodes` 累计增加 42 次顺序扫描、约 2,839,704 次 tuple read；表约 67,612 行。时间关联重复出现，但 PG activity 没有锁等待，采样到的 active SQL 年龄最高约 0.27–0.41 秒；计数没有单条 SQL 耗时，不能单独证明因果。
- 使用只读、无 `ANALYZE` 的 PostgreSQL `EXPLAIN` 对照 `snmp_hardware_probe_service._resolve_mib_symbol` 的精确 SQL，生产计划确认为 `Seq Scan` on `snmp_mib_nodes`。谓词为 `LOWER(n.node_name)=LOWER(?)`；现有索引只覆盖原始 `node_name`。
- 当前生产设备数为 17，其中 15 台有 SNMP 绑定；有 5,296 个 active hardware sensor。该规模不能代表 300 台压力。
- 隔离 PostgreSQL、fake SNMP 的密度校准基线使用300台在线设备（264台绑定、36台无绑定）和93,192个 active hardware sensor。单轮采集用时143.799秒，186,649条SQL中有93,192次行锁查询和93,192次更新；样本 SQL 合计118.712秒。本机 Windows 并发上限为2，结果不能外推为生产耗时，但明确显示逐样本 DB 往返占主导。
- 同一负载接入批量写样本后，单轮周期降至26.142秒，SQL降至529条（设备快照1条、264条传感器清单、264条批量更新），93,192个样本全部为 good。批量 UPDATE 累计执行12.464秒；相比基线，周期降低81.8%、SQL 数降低99.7%、样本 SQL 时间降低89.5%。这是本机隔离 PostgreSQL 的候选结果，不能外推为生产 Linux 的时延承诺。
- 重复请求资产表单、资产列表、Grafana auth gate 和 11 个 dashboard URL 时未提供登录态，业务路由返回 401。已测得的应用 live 延迟可复现入口停顿，但资产查询/保存和登录后 Grafana 查询耗时仍未复现；没有执行资产 POST/PUT 或 Grafana session 创建。
- 追加三轮采样窗口 02:30:17–02:35:17、02:35:33–02:40:33、02:41:18–02:46:18（Asia/Shanghai）：后端 live p95 2.33s/0.58s/2.26s，代理 p95 3.82s/0.59s/2.17s；第1、3轮各1次直连/代理同步约6s超时；每轮 MIB 顺扫+48、tuple read +3,245,376。Grafana/VM health p95 均约5.6–11.1ms；PG active query 最大约329–513ms，无 lock wait/blocker；核心容器无 cgroup throttling/OOM。认证限制仍适用。
- 保留采样输出和既有工作区修改，不清理用户文件，不更改 SNMP 周期、不重置 PostgreSQL 计数或安装扩展。

## 文件和责任边界

- 后端执行者负责新迁移、fresh schema 索引定义及对应 PostgreSQL 测试；只改迁移、`backend/database/schema.py` 对应索引区和一个新的迁移测试文件。
- 后端执行者另负责批量传感器样本持久化 helper，只改 `backend/services/snmp_hardware_inventory_service.py` 和一个新回归测试；主 Agent 负责 poller 接入和扩展300台验证。
- 主 Agent 负责诊断 helper 中精确查询计划、poller 接入、规模验证、TypeScript 输入范围修正、手册/计划/walkthrough、`handoff.md`、完整回归和集成审查。
- 合成规模验证只连接项目隔离的 PostgreSQL 测试库，SNMP 网络操作必须由 fake/mock 驱动，禁止连接真实设备和生产数据库。

## 验收标准

- PG 新 schema 与既有库迁移都能创建相同表达式索引；重复迁移安全；对精确 symbol predicate 的 PG 计划使用索引或由测试证据解释 planner 选择。
- 300 台验证在隔离 PG 和 fake SNMP 下可重复执行，且无跨测试环境数据残留；报告精确 device/sensor 数、时长、并发和脚本/测试入口。
- 批量写入与逐样本基线在相同隔离负载下语义一致；旧样本不覆盖新值，缺失设备/传感器不被插入，并量化 SQL 数及周期变化。
- 诊断 helper 不使用 `EXPLAIN ANALYZE`，不记录 SQL 参数、设备清单、凭据或响应体。
- 上述后端测试与质量门结果均有可复核命令；部署前不导入测试业务数据。授权部署允许应用幂等索引迁移与重建容器，需先备份并确认回滚方式，部署后以同一采样方案对照验证。
