# Redis 容器时区补全实施计划

## 任务目标

为独立的 Redis Compose sidecar 补齐与 Nexora 主应用一致的时区配置，同时确认 Redis 可继续单独部署，也可由现有 Docker 部署脚本与主 Compose 合并启动；本次不提交、不推送、不部署。

## 现状与问题

- `docker-compose.redis.yml` 是独立文件，部署脚本默认通过多个 `-f` 参数将其与 `docker-compose.yml` 合并。
- 主 Compose 的 PostgreSQL、Nexora 和 Nginx 服务均注入 `TZ=${TZ:-Asia/Shanghai}`。
- Redis 服务尚未注入 `TZ`，容器进程时区配置与其余服务不一致。
- Redis `MONITOR` 行内时间仍是 Unix epoch；容器时区不会改变该协议格式，已有格式化脚本负责人工查看时转换。

## 影响范围

- Redis Docker Compose 运行时环境变量。
- Docker 部署说明中的时区契约与验证记录。
- 不改变 Redis 数据、ACL、端口、缓存键、主应用接口或数据库。

## 拟修改文件

- `docker-compose.redis.yml`
- `docs/deploy/docker.md`（如需补充时区说明）
- `docs/walkthrough/walkthrough_20260913_0030_01_Redis容器时区补全.md`

## 实施步骤

1. 在 Redis 服务环境中加入 `TZ=${TZ:-Asia/Shanghai}`，沿用主 Compose 和 `.env.example` 的现有配置契约。
2. 保持 Redis Compose 独立文件及部署脚本合并方式不变。
3. 明确区分容器本地时区与 Redis `MONITOR` 的 Unix 时间戳格式。
4. 检查最终差异，确保未改动用户已有无关变更。

## 验证计划

- 使用 Docker Compose 配置解析检查 Redis 单独配置和主/Redis 合并配置（本机有 Docker CLI 时）。
- 在缺少 Docker CLI 时，使用可用 YAML 解析器验证语法，并静态核对 Compose 合并参数、环境变量展开与文档命令。
- 运行 Redis MONITOR 格式化脚本的聚焦测试，确认样例 epoch 转换及非时间戳文本透传。
- 检查 `git diff` 和 `git status`，确认无提交、无推送。

## 风险与回滚思路

- 风险较低：只新增 Redis 容器的标准 `TZ` 环境变量；自定义 `TZ` 仍由部署 `.env` 控制。
- 若目标镜像不包含某个 IANA 时区数据库，日志协议内容与 Redis 数据行为不受影响；可回退为删除该环境变量，或在后续镜像验证中补充镜像级时区数据。
- 回滚只需撤销本次 Redis Compose 与说明文档的对应行，不涉及数据卷。
