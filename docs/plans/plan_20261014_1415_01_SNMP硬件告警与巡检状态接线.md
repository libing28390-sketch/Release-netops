# SNMP 硬件告警与巡检状态接线计划

## 任务目标

继续完善 SNMP 告警和巡检：把已有的 LibreNMS 规则驱动风扇/电源状态接入巡检与后台告警；修正内存百分比计算；让接口状态巡检读取现有 IF-MIB/CLI 状态采集的最新完整快照，不为巡检再发起一轮重复 SNMP walk。

## 现状与问题

- 巡检读取本地硬件样本，但没有填充 fan/PSU 状态；fan_state、power_supply_state 已由硬件采集器映射成 0..3 状态码。
- memory_pools 同时含百分比、used bytes、total bytes；当前统一取最大值会把字节数当百分比。
- 背景监控保留 fan/PSU 告警 evaluator，但当前采集变量没有从可信的本地 SNMP 硬件库存赋值，因此路径实际不触发。
- IF-MIB 状态完整采集已由接口清单刷新流程提供，但巡检丢弃了结果；device_collection_status 已有 interface_status 的 1800 秒新鲜度契约，接口刷新流程尚未记录该采集器状态。
- IF-MIB error/discard/flap 的 OID 与规则定义存在，但没有唯一活跃的 counter/flap 采集评估闭环。本次不增加第二套 SNMP counter 轮询，避免和现有接口状态/硬件轮询争用。

## 影响范围

- 后端巡检、设备接口状态刷新、后台告警、监控状态读取。
- 不涉及数据库 schema/migration、前端页面、LibreNMS 规则包、真实设备或凭据。

## 拟修改文件

- backend/services/snmp_hardware_status_service.py（新增）：集中读取有效新鲜的风扇/电源状态并按最差状态汇总。
- backend/services/inspection_service.py：只将 memory_usage_percent 纳入内存阈值；读风扇/电源新鲜状态；读取不超过 freshness TTL 的完整 IF-MIB 状态快照。
- backend/services/interface_collection_service.py：为完整成功/失败的接口状态刷新记录 interface_status collector 状态、来源和覆盖数。
- backend/services/background_monitor_service.py：从已持久化的本地 SNMP 样本读取 fan/PSU 状态并驱动已有告警恢复/触发逻辑；缺失/陈旧/不支持数据不触发恢复或新故障。
- backend/api/monitoring.py：复用集中化硬件状态汇总，避免规则重复。

## 实施步骤

1. 将风扇/电源状态样本的可信来源、启用状态、发现状态、质量、枚举值和 freshness 检查收敛到一个 service。
2. 接线后台 fan/PSU 告警与监控 API；保留未知或陈旧数据的 no-op 语义。
3. 修正巡检内存聚合，只汇总百分比测量；把新鲜风扇/电源状态映射为 ok/warning/failed/unknown。
4. 在接口状态刷新中持久化成功/失败快照元数据；巡检只读取 fresh、完整且 IF-MIB 来源的快照，admin-down 不计入 operational down。
5. 更新 walkthrough，写明 IF-MIB counters/flap 告警尚需统一采集 owner 的原因与后续建议。

## 验证计划

- 对涉及 Python 文件运行 python -m py_compile。
- 运行 git diff --check。
- 不运行与本次纯后端改动无关的前端 TypeScript 门禁。
- 不新增或执行测试；用户本轮没有要求运行测试。

## 风险与回滚思路

- 告警只消费已有新鲜、可信的 LibreNMS SNMP 样本，不会加重设备轮询。
- 接口巡检只使用最新完整状态快照；状态采集失败、部分表、来源为 CLI、过期或状态未知时显式标记不可用，不把空数据解释为零端口故障。
- 如果状态汇总行为有误，可回滚对应 Python service/调用方；collector 元数据采用现有表结构，移除写入不需数据库迁移。
