# 资产导入 SNMP 错误提示

## 目标与现状

导入界面应明确显示 SNMP Profile 不存在、类型错误、配置缺失等原因及处理办法。目前后端 detailed import 将字符串 HTTPException 变为通用行失败消息，前端因此无法显示真实原因；未提供 Community/Profile 的成功行也没有说明主机名和型号不能自动同步。

## 范围与文件

- 主 Agent：`backend/api/assets.py` 的安全错误映射、`src/pages/AssetManagement/index.tsx` 导入结果展示、后端回归、文档与整体验证。
- Luna frontend worker：`src/pages/AssetManagement/importUtils.ts` 与 `importUtils.test.ts` 的错误格式化及缺少 SNMP 凭据行识别。双方不编辑对方文件。
- 保留已授权的 SNMP 型号与机柜同步变更，补验主机名写回先于可选型号 Walk 的顺序。

## 步骤

1. 后端为已知 SNMP 校验异常返回明确错误码与安全信息，不回传密钥、Community 或未筛选异常。
2. 前端对失败行和 HTTP 错误统一格式化，显示原因和补录位置；无 Community/Profile 的成功行显示警告，继续允许资产入库。
3. 有详细错误的提示持续显示，直到用户关闭。
4. 补聚焦回归，运行后端相关用例、前端测试、类型检查与隔离构建；检查浏览器提示。

## 验证及回滚

验证不存在/未配置 Community/错误凭据类型、缺少全部 SNMP 输入、已有 Profile/Community 的正常输入，以及型号 Walk 前 hostname 已写回。未知异常继续使用通用安全提示。变更可通过回退这次错误映射与页面格式化恢复，不涉及数据库迁移、生产部署或设备写操作。

## 排查补充（2026-10-26）

- 对比 `e810a4e3`（2026-10-25，引入 SNMP 采集开关）及导入识别调用链：默认值为开启；设备启用时继续使用原 SNMP 凭据解析与 GET；关闭时跳过。`_resolve_probe_settings`、`_read_identity`、`_sync_hostname_from_sys_name` 与 SNMP/hostname service 均与此前版本一致。
- 今天新增 ENTITY-MIB 型号读取发生在 sysName GET 和主机名写回之后。回归用例确认型号探测开始前 hostname 已写回。
- 对 192.168.56.11、.12、.14 的只读诊断：设备显示启用了 SNMPv2c/v3；用数据库绑定的 SNMPv2 Profile 单发 sysName GET 均超时。三台 H3C 的 `display snmp-agent statistics` 在请求前后均显示 unknown community 计数增加 1、已接受 GetRequest 仍为 0。当前证据将失败点定位到设备的 Community 校验，不支持将其归因于新开关、Ping、型号 ENTITY-MIB 查询或缺少凭据记录。
- 管理源 192.168.56.1 与设备目标 IP、161 端口已核对。设备端需要将实际只读 Community 与应用 `snmp-ro` Profile 对齐；本次未执行设备配置变更。

## 验收结果

- 后端 detailed import 将已知的凭据不存在、类型错误、内容缺失、解密/算法问题映射为安全错误码和中文提示。
- 前端展示失败行原因；已创建但没有 Community/Profile 的网络资产会显示主机名和型号不能自动同步的提示。只统计 API 返回的 created 行。
- 修复 hostname 顺序回归；如基础 SNMP GET 超时，型号额外查询不会先行阻塞主机名写回。
- 已执行的后端定向用例 2 项通过；前端导入工具及页面测试 31 项通过；`npm run lint`、隔离 Vite 构建、PostgreSQL-only policy scanner 和 `git diff --check` 通过。
- 真实设备只做普通凭据下的只读 SNMP GET 和 H3C `display` 查询；没有执行配置写入、提交或部署。

## 实时采集复核（2026-10-27）

- 用户确认 15 台设备应共用 `snmp-ro` Profile；数据库中 15 条设备引用和 15 条对应资产引用也一致。当前失败不是凭据中心漏绑定，而是 H3C/Cisco 设备未接受同 Profile 请求或 SNMP 路径未返回响应。
- 最新批次 `asset-import-d134612f319f`（2026-10-27 06:50 Asia/Shanghai）包含 9 行 AC_11–AC_19。`.192.168.56.11` 的输入主机名 AC_12 被 sysName 更新为 F1090-9，`.192.168.56.12` 的 AC_13 更新为 F1090-10；`.192.168.56.14` 返回 AC_11，与导入值相同，因此没有可见改名。`.10.254.0.1-.6` 六行未返回身份信息，hostname 保留为 AC_14–AC_19。更新时间也吻合：前 3 台在导入后约 7 秒更新，六台 `.10.254` 仅有导入时的更新时间。

- 后端此前未运行，按用户已授权的本机服务恢复流程启动；`/api/health` 返回 healthy，数据库 connected。前端 5400 端口仍在运行。
- 在不写回资产的脚本中，直接调用导入识别使用的 `_resolve_probe_settings`、`_read_identity` 和 ENTITY-MIB `read_chassis_model`：15 台均已绑定 `snmp-ro`、采集开关开启、端口 161；`192.168.56.11/.12/.14` 的 sysName 和型号读取成功（H3C F1060、H3C WX5540H-HCL），`.10.254.0.1-.6` 与 `.10.255.0.1-.6` 均无身份响应，故当前批次只有 3/15 可自动补齐。
- 对 `.10.254.0.1-.6` 逐台执行应用同凭据的只读 sysName GET，并前后读取 H3C SNMP 统计；六台均无响应，unknown-community 计数逐台增加 2 或 3（SNMP 重试及并行监控可能增加计数）。请求源为 `192.168.56.1`。这证明当前应用 Profile 请求到达 H3C agent，但未被接受；没有读出或输出 Community 明文，没有修改设备。
- 在用户确认 15 台应共用 `snmp-ro` 后复测 `.10.254.0.1`：绑定 Profile 的 sysName GET 无响应；仅用该设备数据库中的本地 Community 做只读 GET 时返回 `S6850_1`。同批 `.10.254.0.2-.6` 的本地字段与 Profile 相同，但仍无响应。当前数据库显示 `.1` 的本地值与共享 Profile 不同，`.2-.6` 相同；未输出任何 Community 明文。
- 为判断是否存在能覆盖全部设备的既存值，用 `.10.254.0.1` 记录中的本地 Community 作只读候选测试：可读 `.10.254.0.1-.6` 和 `.192.168.56.11/.12/.14` 共 9 台；`.10.255.0.1-.6` 均无响应。当前 `snmp-ro` 则只在 `.192.168.56.11/.12/.14` 成功。Cisco `.10.255.0.1` 使用当前 Profile 的 SNMPv1/v2c 探测、系统路由、VMware 源 `192.168.96.1` 和 VirtualBox 源 `192.168.56.1` 均无响应。所有候选值均只在进程内使用，未输出明文或改写 Profile。
- 对 `.10.254.0.1-.6` 执行只读 `display current-configuration | include snmp-agent`：六台均有一个 cipher Community 配置项，Community 配置行未引用 ACL。H3C 文档说明 `display snmp-agent community` 只显示明文保存的 Community，因此空结果不能证明设备没有配置，也无法确认其与应用 Profile 的值一致（[H3C Command Reference](https://www.h3c.com/en/Support/Resource_Center/EN/Home/Public/00-Public/Technical_Documents/Reference_Guides/Command_References/H3C_CR-29161/17/202509/2657618_294551_0.htm)）。未输出 Community 明文或 cipher 值。
- `.10.255.0.1-.6` 全部 Ping 成功但 SNMP 身份读取无响应。UDP socket 对该网段实际选中的源地址为 sing-box TUN 的 `172.18.0.1`；绑定 VMware 地址 `192.168.96.1` 后单次 SNMP GET 仍无响应。故 Cisco 侧的路由/源地址存在异常迹象，但仅凭当前测试尚不能确认它是唯一原因；SSH 只读统计连接也未能建立。
- 凭据中心“未绑定”问题已在 `credential_service.py` 和 `CmdbManagementTab.tsx` 修复，数据库的 15 条设备引用会作为 15 台关联设备呈现。该列表缺陷没有造成这 12 台的 SNMP 超时，因为设备本身已经引用 Profile。
- 整体验收仍未完成：12/15 台设备当前无法通过导入同路径 SNMP 探测，不能确认全部设备可采集；不执行交换机配置、ACL 或本机路由变更，也不关闭电脑。需核对 H3C cipher Community 与 `snmp-ro` 是否一致，并解决 Cisco 网段的源路由/agent 应答后复测。
