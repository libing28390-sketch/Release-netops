# 变更工单创建与角色校验修复计划

## 目标

修复创建变更工单时因认证依赖未执行而产生的 500；让表单和后端共同禁止实施人与协同审核人重复；确保已填写的回退方案进入工单正文、控制表和审批快照；修正责任组保存成功后弹窗不关闭，并全面检查工单管理页面的公共组件、分页和 Escape 关闭行为。

## 现状与证据

- 用户提供的 FastAPI traceback 指向 `backend/api/change_orders/core.py` 创建路由：`user=require_change_requester` 将依赖函数本身作为 `user` 传入，最终在 `authorize_resource()` 调用 `user.get()` 时触发 `AttributeError`。
- 当前表单实施人与协同审核人候选集合相同，截图中同一管理员可同时被选中；`_validate_assignment_rules()` 目前仅校验申请人/初审人/终审人的冲突，没有校验控制表中的实施人与协同审核人。
- UI 已有回退方案输入，但须核对所有提交路径是否必填、并写入主工单字段及控制表字段；模板场景不能因生成内容为空而绕过。
- 目标服务目前可连接；测试仍使用隔离 PostgreSQL，不提交测试工单或真实设备命令。

## 范围与文件

- 后端：`backend/api/change_orders/core.py`、`backend/api/change_orders/helpers.py`、新增聚焦 PostgreSQL 回归测试。
- 前端：`src/pages/ChangeOrder/`、`src/pages/Tickets/`、工单相关路由使用的公共分页/弹窗组件和相关前端测试。
- 交付文档：本计划与对应 walkthrough；追加一段 `handoff.md` 记录。

## 实施步骤

1. 将 `require_change_requester` 作为 FastAPI `Depends` 注入，检查同文件中的相同依赖误用；创建成功路径和拒绝路径都使用隔离数据库测试。
2. 前端根据实施人过滤协同审核人选项；更改实施人后若原审核人冲突则清空并提示。提交时再校验，不能只依赖下拉选项。
3. 后端规范化控制表身份后，拒绝实施人与协同审核人相同；同时确认与初审/终审及业务确认角色的分工规则一致。
4. 对所有非草稿提交要求有效回退方案；模板生成的回退内容与手工内容走同一校验，并写入主工单和控制表镜像。
5. 修复责任组保存成功后关闭弹窗；逐页检查工单列表/详情/管理对话框，统一使用现有公共分页与对话框组件，验证 Escape 关闭、遮罩/关闭按钮行为，不改页面布局和已有分页默认值。
6. 完成计划、走查和交接记录；保留用户已有工作区修改，不提交、不推送、不部署。

## 验证计划

- PostgreSQL focused tests：认证依赖正常注入、未授权拒绝、实施人与协同审核人相同被拒、合法不同人员可创建、回退方案持久化到主字段及控制表。
- 前端 focused tests：角色选项排除、实施人变化清空冲突审核人、提交校验、手工/模板回退方案序列化。
- 工单页面 tests：责任组保存成功后关闭弹窗；相关分页沿用公共组件；每个可关闭弹窗/抽屉支持 Escape，保存/取消后焦点与状态可恢复。
- `npm run lint`、受影响 TypeScript/Python 编译、隔离 Vite build、`scripts/validate_postgresql_only.py` 和 `git diff --check`。
- 对目标 URL 只做 UI/HTTP 验收；不连接设备、不执行命令、不把真实工单当测试数据。

## 风险与回退

- 后端拒绝同人配置可能影响旧草稿提交；先不改历史记录，只在新建/更新/提交路径校验，提示需重新选择责任人。
- 回退方案仅作记录和审批快照，不自动执行回退命令。
- 若目标环境或依赖服务不可用，记录为未完成的现场验证，不以本地构建替代部署证据。
