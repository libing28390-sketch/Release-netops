# AI 知识库 V2 回迁 V1 与单轨化清理任务清单

## 1. 目标

将当前知识库从“V1 检索表 + V2 治理表 + 双写/影子索引”的并行结构，收敛为一套 V1 数据模型和一条读写链路。在确认 PostgreSQL 数据迁移、检索效果和管理功能均正常后，删除 V2 运行时代码、接口、前端入口和数据库表。

本轮原则：

- PostgreSQL 是唯一数据库基线，不考虑 SQLite 兼容方案。
- 先迁移、再切流、后删除，任何阶段均不直接丢弃现有知识库内容。
- `ai_document`、`ai_document_chunk` 继续作为文档与向量检索主表。
- 官方来源目录继续以现有 YAML catalog 为配置真相源，不再保留一套重复的 V2 来源注册中心。
- 对版本追踪确有价值的数据，压缩为 V1 命名和职责清晰的修订记录；不继续保留整套 V2 表族。
- 历史迁移脚本必须保留，以支持已部署 PG 从旧版本顺序升级；“删除 V2”指删除最终运行时 schema、代码、API 和 UI，不是删除已经发布过的迁移历史。

## 2. 目标数据模型

| 数据职责 | 收敛后的归属 | 处理方式 |
| --- | --- | --- |
| 知识库与集合 | `ai_knowledge_base` | 保留 |
| 当前文档、来源、状态、语义元数据 | `ai_document` | 作为唯一文档主表，补齐必要来源字段 |
| 文档分块、向量、检索投影 | `ai_document_chunk` | 作为唯一在线检索索引 |
| 官方来源清单、厂商、状态、发现/阻断原因 | 官方来源 YAML catalog | 保留并规范校验，不在数据库重复建注册中心 |
| 抓取响应、内容哈希、解析器版本、文档历史版本 | 建议合并为单一 V1 表 `ai_document_revision` | 仅保留审计、去重、回滚真正需要的数据 |
| 导入任务、评估、检索 trace | 现有 ingestion/evaluation/trace 表 | 与 V2 解耦后保留 |
| V2 来源、文档、生命周期表族 | `kb_*` | 数据迁完且验收通过后删除 |
| 影子索引和灰度开关 | `ai_retrieval_index_*`、`ai_retrieval_rollout_flag` | 单轨切换后删除 |

## 4. 执行闸门

1. **闸门 1——允许切写：** 字段映射评审完成，目标迁移可幂等执行，备份恢复成功。
2. **闸门 2——允许停双写：** 所有导入入口已写 V1，迁移数据对账通过，V2 无新增记录。
3. **闸门 3——允许删代码/API：** V1 检索与 Agent 回归通过，前端已切换，代码中无 V2 运行时依赖。
4. **闸门 4——允许删表：** PG 全量备份可恢复，V2 独有数据为零或已归档，删表迁移已在旧库副本和空库上通过。

任何闸门不通过，只修复当前阶段，不执行后续删除。

## 5. 完成标准

- PostgreSQL 中仅保留一套知识库主数据和一套在线向量检索数据。
- 新增、更新、删除、重建和检索均只经过 V1 服务链路。
- 应用运行时不再查询或写入任何 `kb_*`、shadow generation 或 rollout flag 表。
- `/api/v2/kb` 和 `/api/knowledge-v2` 不再存在，前端无 V1/V2 切换概念。
- 文档、分块、向量、来源和必要历史数据迁移完整，无孤儿记录和静默覆盖。
- 旧 PG 可顺序升级，全新 PG 可从零初始化，两者最终 schema 一致。
- 回归测试、数据对账、安全检查和恢复演练均有可审计结果。

## 6. 建议实施顺序

按 `A → B → C → D → E → F → G → H` 顺序执行。预计拆成三个可独立验收的变更批次：

1. **批次一：** V1 schema、数据迁移和对账，不改变线上读写。
2. **批次二：** 写入、检索、API 和前端切换到单轨 V1。
3. **批次三：** 通过总闸后删除 V2 运行时代码与 PG 对象，补齐文档和交付报告。
