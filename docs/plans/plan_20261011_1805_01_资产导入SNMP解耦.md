# 资产导入与 SNMP 探测解耦计划

## 目标

表格导入时，先保存每条有效资产；SNMP、主机名识别与 LibreNMS 纳管失败不得阻止资产入库，也不得让导入请求等待整批网络探测完成。

## 现状与问题

- `POST /api/assets/import` 在一个数据库事务中处理整批资产，并在网络探测前提交。
- 提交后仍在同一请求内等待 LibreNMS 纳管、SNMP 主机名同步和设备识别全部完成；前端只在响应后刷新资产列表。
- 页面没有请求 `detailed=true`，所以单行校验错误走整批 `rollback()` 分支，无法返回部分成功结果。

## 影响范围

- 后端资产批量导入 API 的事务失败隔离与提交后任务调度。
- 资产管理前端的导入响应处理和进度提示。
- 资产导入 API 的回归测试与本计划对应的 walkthrough。

## 拟修改文件

- `backend/api/assets.py`
- `backend/tests/rackvision/test_asset_import_contract.py` 或现有资产导入测试文件
- `src/pages/AssetManagement/index.tsx`
- `docs/walkthrough/walkthrough_20261011_1805_01_资产导入SNMP解耦.md`

## 实施步骤

1. 让资产管理前端请求逐行详细结果，使坏行使用 savepoint 隔离并展示失败数量/原因。
2. 将提交后的 LibreNMS 与 SNMP 工作移到 FastAPI 响应后的后台任务；直接调用接口函数的现有单元测试仍可同步执行并验证完整结果。
3. 响应标明网络补全仍在后台进行，前端在资产写入后立即刷新列表。
4. 增加回归测试：网络设备资产先提交，后台任务被排队；单行失败不回滚同批其他成功行。

- 运行资产管理前端相关测试（如存在）及 `npm run lint`。

## 风险与回滚

- FastAPI 后台任务在应用进程重启时可能中断；本次不新增持久任务队列，网络补全失败不会回滚已保存资产，可通过重新导入/现有同步流程重试。
- 回滚时恢复旧的同步请求路径和前端导入参数；资产表结构不变，无数据库迁移。

## 执行记录

- 已实现逐行详细导入：每条有效行独立提交；失败行回滚到自己的保存点。`atomic=true` 仍保持整批事务。
- 已把 HTTP 请求内的 LibreNMS 纳管、SNMP 主机名同步和设备识别调度到响应后的 FastAPI 后台任务。
- 前端展示新增、跳过、失败数量；有后台补全时提示稍后刷新查看主机名。
- 重点回归：2 项通过；`npm run lint` 通过。
