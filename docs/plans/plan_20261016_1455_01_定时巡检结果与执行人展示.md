# 定时巡检结果与执行人展示

## 任务目标

修复 Linux 定时巡检执行详情无输出的问题，移除执行历史中的健康评分列，并将定时任务的“执行人”改为对应任务创建人。

## 现状与问题

- `script_run` 调度路径将设备巡检详情写入 `phases_json` 明文列，没有使用现有 Playbook 输出加密服务；详情接口会隔离旧明文并返回 503。
- 调度执行记录使用 `scheduler` 作为内部 author 标记；统一历史接口直接展示该标记，没有解析关联定时任务的创建人。
- 执行历史页面展示平均健康评分，用户认为该字段没有实际参考意义。
- 执行历史主表目前展示设备成功/失败等明细统计；用户希望列表只保留作业摘要，并提供开始时间、结束时间、总耗时和单一作业状态，详细设备结果在点击后查看。
- Linux 巡检脚本输出的 `ERROR` 文本会被调度器直接当作执行失败；已知 snap 的 squashfs 只读挂载会被识别为异常，需要检查并避免该类误报。

## 影响范围

- 后端调度结果存储与执行状态分类。
- 统一执行历史的数据映射。
- 定时执行历史 API 的开始/结束时间、耗时、创建人映射。
- 定时执行历史前端摘要表格与导出。
- Linux 综合巡检脚本中的只读挂载检查。

## 实施步骤

1. 复用 `protect_output` 加密保存调度器产生的设备阶段输出，明文兼容列只保存安全占位值；详情页按权限读取旧调度记录时先加密回填并清除明文，再返回结果。
2. 历史 API 通过执行记录中的定时任务 ID 获取任务 `created_by`，供 UI 展示；新执行也将创建人写入记录，避免定时任务删除后丢失归属。
3. 从历史列表及其导出、巡检详情中移除无意义的健康评分；历史表格改为开始时间、结束时间、耗时和作业状态摘要，设备级结果保留在点击详情后查看。
4. 检查 Linux 综合巡检脚本，只修正已确认的 snap 只读挂载误报；保留真实健康告警。
5. 检查最终 diff、静态差异和适用的前端构建验证；本轮不操作真实设备、不部署。

## 分工边界

- 前端子 Agent：只负责 `HistoryList.tsx`、`ExecutionSchedule/types.ts`、`ExecutionSchedule/index.tsx` 的摘要列表字段与导出。
- 主 Agent：负责调度输出加密、旧结果安全回填、历史 API 字段与创建人映射、Linux 脚本检查，以及详情页评分移除和最终集成。
- 子 Agent 完成后由主 Agent 统一检查同一工作区的集成结果并运行共享验证。

## 验证计划

- 按项目质量门禁检查相关 Python/TypeScript 改动；优先使用 `git diff --check` 与 `npm run lint`，前端集成受影响时再决定是否运行构建。
- 不运行测试，除非用户明确要求测试或验证实现。
- 旧输出只在经过现有详情权限校验后的请求中按 `protect_output` 加密回填；加密不可用时不返回旧明文。

## 风险与回滚思路

- 加密密钥不可用时，遵守现有 `protect_output` 行为：不落明文输出，保留执行状态和计数。
- 执行来源 `scheduler` 继续用于历史类型识别，展示创建人仅由历史查询计算，不改写执行审计记录。
- 如果脚本误报检查影响范围超出 snap squashfs，只回滚该检查变化，保留输出加密和创建人映射修复。
