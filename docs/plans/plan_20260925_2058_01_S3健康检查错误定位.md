# S3 健康检查错误定位计划

## 任务目标
定位 `/management/storage` 的 S3 连接测试失败原因，并在不暴露凭据或原始异常文本的前提下显示可操作的 S3 错误码与 HTTP 状态。

## 现状/问题
浏览器对现有 Environment 配置及用户给定参数的临时连接测试均显示失败。备份中心将底层结果显示为 `S3 storage check failed: ClientError`，说明 S3 端点返回了服务端错误；具体错误码未暴露。`backend/api/storage_providers.py` 又把健康检查细节覆盖成通用提示。当前工作区 `.env` 没有 `S3_REGION`；Compose 的通用 `env_file: .env` 会透传部署文件中的旧键。本次修改已移除后端该设置和 Compose 显式映射，SDK 内部继续使用 `us-east-1` 兼容默认值。服务器 `.env` 若仍有旧行，需要在部署主机手动删除，并在更新 Compose 配置后重建 `netops` 容器；这项清理本身不解决现有 `ClientError`。

## 影响范围
对象存储健康检查和管理页面测试结果，以及 S3 区域环境变量的后端/Compose 显式配置和示例；不修改数据库配置、SeaweedFS 数据卷或线上存储连接。当前本地 `.env` 不含待删字段。

## 拟修改文件
- `backend/services/storage_service.py`
- `backend/api/storage_providers.py`
- `backend/core/config.py`
- `docker-compose.yml`
- `.env.example`
- `backend/tests/storage/test_storage_service.py`
- `backend/tests/release/test_deploy_docker_storage_contract.py`
- 本计划与对应 walkthrough

## 实施步骤
1. 从 boto3/Botocore 异常中只提取经过格式校验的 S3 错误码与整数 HTTP 状态，其他情况仅显示异常类型。
2. 让对象存储测试 API 返回上述脱敏诊断文本，不返回原始异常消息或任何凭据。
3. 移除后端 `S3_REGION` 设置、Compose 显式映射和 `.env.example` 字段；Environment profile 内部固定采用 `us-east-1` 兼容默认值。服务器 `.env` 由部署维护人删除旧行，重新创建 netops 容器以更新进程环境。
4. 用本地模拟异常验证诊断脱敏，并验证部署模板不再声明 `S3_REGION`。
5. 部署后在运行页面读取具体诊断码，再据此确定线上配置/SeaweedFS 修复步骤。

## 验证计划
运行 `backend/tests/storage/test_storage_service.py` 和针对存储 Provider 测试 API 的相关测试；`git diff --check`。部署验证需要用户授权后执行。

## 风险与回滚思路
错误码/HTTP 状态属于服务端诊断信息，不含异常正文、访问密钥或 Secret。移除后端配置字段后，Compose 的通用 `env_file` 仍会传递服务器 `.env` 中未删除的旧键，但应用设置不再读取它；S3 签名仍明确使用兼容默认区域 `us-east-1`。回滚时恢复后端、Compose、示例配置的本次差异。任何远端 `.env` 修改、SeaweedFS 重建或线上部署均不在本地代码变更内。
