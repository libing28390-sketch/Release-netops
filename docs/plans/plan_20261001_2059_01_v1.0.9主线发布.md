# v1.0.9 主线发布计划

## 任务目标

将当前全部业务代码提交并推送到源仓库 main，将 v1.0.9 标签更新到同一提交，并验证 release.yml 将公有仓库标签和 Release 保持为 v1.0.9。用户已明确授权提交、推送和发布。

## 现状与问题

- 源 main 位于 a6a5ee115e80090c39dc95ef60d104413fee9a7b；旧 v1.0.9 指向 f44df30d1a8e1a215957c718078930be64c09d4f。
- 前后端版本已为 1.0.9，构建日期和 Release 说明仍为 2026-09-27。
- 工作区包含平台绑定权限、MIB 缓存、拓扑采集/身份关联/聚合链路、CMDB 主机名同步及诊断界面的业务变更。
- 当前 release.yml 动态沿用触发标签，但 main 与 tag 的同步任务可以并发写入同一公有 main。

## 影响范围与拟修改文件

- 当前 backend/ 和 src/ 下全部业务变更及对应测试。
- .github/workflows/release.yml：串行发布、版本与标签一致性检查。
- backend/core/version.py、docs/deploy/release-notes.md：日期和更新说明。
- 本次及相关计划、走查、提交修复记录，仅留在私有源仓库，现有发布过滤排除内部材料。
- 临时构建目录、旧生成的 dist/index.html、私有环境和本地日志不作为业务代码提交，保留本地文件。

## 实施步骤

1. 核对远端 main/旧标签、发布工作流、版本、工作树范围。
2. 并行完整后端和前端回归，更新发布信息及工作流一致性保护。
3. 检查工作流语法、版本契约、PostgreSQL-only、编译、敏感文件及最终暂存范围。
4. 创建本次提交记录后提交 main，正常推送 main，并用旧标签对象作为 lease 更新 v1.0.9。
5. 跟踪 GitHub Actions 全部门禁，核对公有 main/tag、Release 版本及两种附件。

## 风险与回滚

- 覆盖同名标签会使已下载旧 v1.0.9 的用户与新发布内容不同，发布说明记录本次更新日期。
- main 不强推；更新标签使用精确 lease，若远端已改变则重新检查，保留他人提交。
- 若 CI 失败，先诊断并修复对应问题，不跳过或削弱门禁；发布旧附件不视为本次成功。
- 必要时以新回滚提交恢复业务；恢复旧标签需新的用户指示。
