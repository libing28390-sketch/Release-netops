# 汇总工作区并重发 v1.0.9

## 任务目标

按用户授权将当前工作区已完成的代码和部署变更统一提交并推送到 `main`，把现有 `v1.0.9` 标签更新到该提交，并确保可选的百度网盘上传失败不会阻断公有 GitHub Release 与 Release Note 创建。

## 现状与问题

- 当前分支是 `main`，HEAD 与 `origin/main` 均为 `c70d65ed`；工作区有 SNMP、Docker、Grafana、前端和配置变更，以及对应的计划/走查记录。
- `package.json` 和 `backend/core/version.py` 的版本均为 `1.0.9`。
- 本地已存在 `v1.0.9` 注释标签，指向旧提交 `ee1a368e`；公有仓库也已有 `v1.0.9` 标签，但 Releases 页面仍缺少对应 Release。
- 发布 workflow 在百度网盘上传后才创建 GitHub Release；历史运行中网盘令牌刷新失败，后续 Release 步骤因此跳过。
- `.env`、备份文件及其他 ignored 配置不属于提交范围；`.codex` 等内部文件由发布 workflow 清理，不进入公有发布树。

## 影响范围

- 汇总提交当前工作区所有经审阅的 tracked 修改和非 ignored 新文件。
- 将百度网盘上传设为非阻断步骤，并更新 v1.0.9 Release Note 以覆盖本次用户可见功能和部署变更。
- 推送私有源仓库 `main` 并更新已有 `v1.0.9` 标签；标签事件会触发 GitHub Actions 并同步/发布到 `Release-netops`。
- 不部署目标服务器，不修改 `.env`、数据库或存储卷。

## 拟修改文件

- 当前 `git status --short` 列出的全部经审阅文件及文档记录。
- `.github/workflows/release.yml`
- `docs/deploy/release-notes.md`
- 新增 `docs/fixes/fix_20260924_2325_02_汇总工作区并重发v1.0.9.md`
- 本计划与对应 walkthrough

## 实施步骤

1. 审阅当前工作区差异、版本元数据、提交路径和忽略文件，避免将秘密或运行数据暂存。
2. 让百度网盘上传失败仅产生非阻断步骤结论，保持后续 GitHub Release 创建和 Windows Agent 发布继续执行。
3. 更新 v1.0.9 发布说明，涵盖 SNMP 厂商自动识别、LLDP 本地端口映射、Grafana 部署与 Docker 构建变更。
4. 新增提交修复记录；暂存所有经审阅的工作区变更和必要的发布文档，提交到 `main`。
5. 推送 `main`，随后将 `v1.0.9` 标签更新到新提交并推送，避免分支运行和标签运行并发覆盖公有同步结果。
6. 观察 Actions；确认 Release 与说明创建成功，或记录失败的确切步骤及当前远端 ref。

## 验证计划

- 核对版本仍为 `1.0.9`，标签指向提交 SHA，提交文件清单不含 `.env`、凭据、私钥、数据库或备份。
- `git diff --check`、工作流 YAML/结构审阅及提交前 staged diff 审核。
- 由标签触发仓库自身发布质量门禁和产物构建；本地不重复执行发布 workflow 已包含的全量测试。
- 推送后确认 `origin/main` 与发布提交相同，Actions 完成后核对公有 Release/Tag 状态。

## 风险与回滚

- 更新已存在的 `v1.0.9` 标签会改变私有源和公有仓库中该标签的目标；若发布门禁失败，保留新 `main` 提交并报告结果，不用强推掩盖失败。
- Release workflow 会对公有仓库的 `main` 和同名标签执行强制同步；先等 `main` 同步运行完成，再推标签，降低并发覆盖风险。
- 线上 Docker 服务不会因代码推送自动重建；需要另行部署并验证 Grafana 路由修复。
