## 2. 问题依据与证据等级

审查基线为任务前 main 提交 d510c59b8370efe8912fd0c508aea650eb2423e4。工作树已有先前未提交试改，这些不是现场根因证据，迁移实施时不继续沿用其 Python 适配方向。

已确认：
1. 项目 LibreNMS bundle 是精选 YAML/MIB，而非完整 PHP/composer/discovery/poller 运行时。
2. Comware 内存百分比被本地额外的正容量条件过滤；上游可保留只有百分比的内存记录。
3. 上游 PHP 中的机框私有温度发现未被原有 Python 适配完整实现。
4. CPU 首次发现过滤 0、module/正使用率内存筛选与项目固定上游一致；不能把所有空值都归为翻译缺陷。
5. 硬件库存之外还有模板/默认 CPU、内存、温度、风扇、电源路径；只删 probe 模块不能确保全量切换。
6. 设备看板读取 nexora_hw_*，无线看板同时使用硬件库存指标与 IF-MIB 接口指标；替换数据源要覆盖二者的关联契约。

尚未确认：
- 用户真实设备的 OS、私有 OID 返回结构以及实际缺失发生在哪一层。
- 所选原生引擎版本是否能够读取现场所有现有无线/光模块指标。
- 原生导出与现有 VictoriaMetrics v1.103.0 的实际互操作表现。

因此目标是消除自研硬件执行逻辑的来源差异，不能预先承诺引擎可生成设备未开放或未支持的 SNMP 数据。

**现场根因结论（当前证据等级）：尚未确认。** 已发现的 Python 适配与上游规则差异只能证明旧实现存在潜在覆盖缺口，不能单独证明它就是用户真实设备 Grafana 无数据的原因。本轮计划先对本地代码逻辑做静态/自动化核查；HCL 与真实设备的运行时对照已按用户要求延后。根因报告必须覆盖实际运行版本、LibreNMS 设备识别/发现/轮询、原生存储与导出、Nexora 身份映射以及 Grafana 查询变量，并指出第一个失败层。若原生引擎在真实设备上也没有样本，结论应明确落在设备 SNMP 可见性、凭据权限、OS/版本支持或设备未提供数据，不能称代码迁移已修复。

**P1 本地代码核查已经确认的逻辑问题（不等于现场根因）：**
1. `/monitor/snmp-walk` 的“读取 LibreNMS 结果”按钮当前仍调用 `/platform-registry/snmp-hardware-discovery-test`；该后端路由执行 `discover_device_oid_config`，再调用 `snmp_hardware_diagnostic_service.diagnose_hardware_collection`，最终会运行 Python 硬件 probe/poll。它不是只读 LibreNMS 原生结果。
2. 新建的 `librenms_diagnostic_service.diagnose_librenms_hardware` 当前没有 API/生产调用方；因此 UI 的 native 标题没有被原生 service 支撑。TypeScript result 类型描述 native binding/engine/collection，但旧 route 返回 Python discovery 字段，二者契约不匹配。
3. 当前 `librenms_runtime_client` 获取设备、全局 sensors 列表、wireless/transceiver 和 processor/mempool/storage 的健康图表元数据；健康图表接口不返回 CPU/memory 当前读数，client 也没有独立 processor/mempool 当前数据读取。按现状不能保证页面展示 CPU 和内存值。
4. sensors API 目前以全局列表查询后在客户端过滤，并受 8 MiB 响应上限约束；没有分页或按设备过滤的代码路径。大规模时可能因 payload 超限无法诊断，需后续确认受锁定版本支持的按设备/分页接口。
5. native diagnostic 顶层 `collection.observed_at` 被赋值为服务端读取时刻；只有各 sensor 的 `lastupdate` 才代表该 sensor 样本时间。若 UI 把顶层字段当采样时间，会刷新而不产生新样本年龄。
6. 当前绑定 migration 有 tenant_id/asset_id/device_id 字段，但未建立 tenant 与 asset/device 的一致性复合约束；异步 job/恢复契约也未完整落库/接线。这是实现差距，不应当作已交付的安全和可靠性能力。
7. 周期后台仍调用 `poll_hardware_inventory` 与 `collect_device_metrics(template_only=True)`；巡检、设备 SNMP 测试和光模块接口也有 Python 硬件采集路径。因此当前代码的自动硬件来源并未切为 LibreNMS，HCL 与真实设备行为差异可能受 Python adapter 覆盖/设备 SNMP配置共同影响。

以上结论由代码和现有测试夹具支持，足以说明当前 SNMP 诊断原型不能证明“使用 LibreNMS 完整引擎采集并展示 CPU/内存”。仍需 P7 HCL/真实设备逐层证据，才能确认用户部署 Grafana 无数据的第一根因层。

本次现场根因判断按下表取证，避免把“Grafana没有曲线”直接归因于设备或 Python 代码：

| 观测结果 | 根因边界 | 下一步证据 |
|---|---|---|
| 原始 SNMP 可达，但 LibreNMS 未识别 OS/型号 | 设备识别、凭据权限、版本/平台匹配或原生支持范围 | sysObjectID、LibreNMS OS 匹配结果、脱敏 discovery 日志 |
| LibreNMS 已识别设备，但无 processor/mempool/sensor 原生实体 | 原生 discovery 未发现，或设备返回/权限/上游支持不足 | discovery 时间、类别实体数、错误和设备能力；不得从 Grafana推断 |
| 原生实体存在，但 poller 没有新值/RRD点 | poller任务、设备超时、实体状态或 native polling 问题 | poller结果、实体 lastupdate、单设备只读重试证据 |
| LibreNMS 有值/RRD有点，但没有原生时序写入 | datastore 配置、字段/标签规则、写入地址或协议兼容问题 | 脱敏 line protocol、datastore日志、目标端 HTTP响应 |
| VictoriaMetrics 已有数值，但 Nexora 当前库存为空 | 原生 ID/实体标签与 Nexora 绑定或接入映射问题 | VM查询结果、绑定、projection状态和拒绝原因 |
| Nexora 当前库存有值，但 Grafana为空 | 指标名、标签、时间窗口、变量或 dashboard query 不一致 | Grafana查询表达式、变量展开值和同时间段原始series |
| HCL 成功而真实设备失败 | 型号/OS版本/配置/可见OID/权限或上游适配范围差异；仍需再定位到上述层 | 两端使用同一引擎版本的逐层证据对照 |

## 4. 目标架构与选定数据通道

主方案：

    Nexora CMDB / 凭据库
        → 受控 LibreNMS API 设备同步
        → 完整 LibreNMS discovery / 原生 poller / PHP / MIB
            ├─ MariaDB + 原生 /data（含配置、日志、RRD 等）
            ├─ REST API：设备、processor、mempool、sensor、无线与实体元数据
            └─ 原生 InfluxDB datastore：已处理数值 + 原生写入时间
                → 现有 VictoriaMetrics 的 Influx line protocol 接口
                → 原生时序结果
        → Nexora 通用结果接入：元数据 API + 原生时序样本
        → Nexora 资产身份与兼容库存投影
        → /hardware-metrics 的 nexora_hw_* 兼容输出
        → 现有 vmagent → VictoriaMetrics → Grafana

选择理由与条件：
- LibreNMS 自己执行所有硬件逻辑，并通过自带 datastore 输出处理后的数据。
- 优先使用已有 VictoriaMetrics 接收 Influx line protocol，不新增独立 InfluxDB 服务；这只是协议兼容接入。
- 保留原生时序和原生 RRD，便于和 LibreNMS 自身结果核对。
- Nexora 的兼容输出解决现有 asset_id、sensor_key、告警与设备卡片依赖，不承担设备采样。
- 原生值与兼容值必须使用不同指标名/来源空间；不可重复写同一系列，也不可将接入时间作为样本时间。
- 官方 LibreNMS InfluxDB 集成目前标记为 alpha，因此下述 POC 是实施硬门禁。不能把“双方支持协议”写成已经联调成功。

原生 exporter 初始化会检查/尝试创建 Influx 数据库。VictoriaMetrics 官方提供 SHOW DATABASES 兼容配置；POC 要验证当前版本的实际响应、dbname、precision=s、HTTP 写入及返回状态。当前方案不直接指向 vmagent 的 /write，因为 LibreNMS 的 /query 探测也必须处理；优先验证 VictoriaMetrics 单节点接口。

可靠性边界：所核对的原生 InfluxDB datastore 在批次写入异常后也会清空该批次，不能声称原生直写具备失败重放能力。VictoriaMetrics中断时，LibreNMS原生RRD可能仍有自身历史，但不等于会自动补回VictoriaMetrics。POC必须验证数据缺口与导出错误可见。如果交付要求时序库中断后自动补传，实施前须把通用接收代理纳入方案：/query 转发到 VictoriaMetrics，/write 转发到现有 vmagent 的持久队列，再remote-write；验证当前版本队列/响应语义后才启用。该代理只路由协议和实例身份，不读取SNMP或改写厂商算法；本稿不声称该备用可靠性通道已实现。

若 POC 证明上述通道不兼容：停止推进该通道并提交证据，由主 Agent修订为官方原生 Prometheus/Pushgateway 导出等通道供审核；不得改 LibreNMS 厂商代码，不得恢复 Python 硬件采集，不得静默新增 InfluxDB 或第三方 exporter。

原生 Prometheus/Pushgateway 已核实可用，但不选为当前默认：官方同样标记 alpha，且 Pushgateway 不自动删除旧序列，必须额外完成生命周期和新鲜度管理。备用通道也须单独通过验收。

**数据通道决策状态：已选定 POC 主候选，尚未选定生产实现。** 主候选为 LibreNMS 原生 Influx v1 datastore 直写现有 VictoriaMetrics Influx HTTP 接口，Nexora 通过 LibreNMS API 获取实体元数据/当前状态，并从 VM 查询已处理数值。此候选不能标记为“已兼容”：必须在锁定版本上验证设备/实体标签、值类型、时间戳、查询探测、认证、HTTP 返回、失败可见性和实例隔离。LibreNMS 官方文档将该 datastore 标注为 alpha；VictoriaMetrics 虽支持 Influx line protocol，仍需按实际 VM 版本验证 LibreNMS 会发出的具体查询/写入行为。若 P7 发现无法稳定关联原生设备/实体、时间语义不符、非数值字段被转换成数值或写入失败不可见，则候选判失败，停下提交证据并修订方案；不得直接切到另一条 exporter，更不得用 Nexora 重新采集硬件 OID 填补。

最终唯一路径必须满足：LibreNMS 是唯一自动硬件采集者；VM 接收的数值由 LibreNMS 原生 datastore 产生；LibreNMS API 只用于原生设备/实体元数据与经过验证的当前值；Nexora 只做授权、稳定身份映射、状态解释、兼容投影和产品展示。VM 查询、设备绑定或 Grafana 变量无法确定唯一 asset/native entity 时，应返回缺失/冲突状态，不得按 IP、描述相似或请求时间猜测。

## 5. 原生运行时与部署

### 5.1 组件

| 组件（建议服务名） | 职责 | 数据与要求 |
|---|---|---|
| librenms | 官方完整镜像，Web/API 与原生应用 | 固定发布标签和 digest；持久化 /data |
| librenms-dispatcher | 官方 dispatcher sidecar，执行原生发现与轮询任务 | 与主应用同版本、共享 /data 和数据库 |
| librenms-db | LibreNMS 专属 MariaDB/MySQL | 独立卷、数据库账号、备份与恢复；不迁移 Nexora 核心数据库 |
| librenms-redis | 原生任务协调/缓存 | 使用专属实例与账号；不默认复用 Nexora 受限 ACL Redis |
| 现有 VictoriaMetrics | 原生数值接收及历史存储 | 验证 Influx 接口；维持现有 remote-write |
| 现有 Nexora / vmagent / Grafana | 身份、结果投影、权限、现有产品展示 | 删除旧设备硬件轮询后接入新数据源 |

Nexora 的核心关系数据库和测试数据库继续使用 PostgreSQL。MariaDB/MySQL 是外部 LibreNMS 原生运行时自身的存储，Nexora 不新增业务 MySQL DAO。

当前工作树的 `docker-compose.yml` 与 `monitoring/librenms/image-lock.json` 已固定 LibreNMS、MariaDB、Redis 的 tag/digest；`monitoring/librenms/README.md` 记录了官方 Docker 发布 commit。该静态锁定尚未在容器中验证镜像内 LibreNMS commit/PHP/Python/RRDTool 版本、数据库兼容性或 SNMP 采集行为，不能视为镜像已拉取或运行时已验收。实施前在隔离主机核验镜像实物与锁定清单一致；不使用 latest 作为正式交付版本。

锁定清单至少记录官方镜像仓库、tag、不可变 digest、镜像内 LibreNMS commit/PHP/Python/RRDTool 版本、MariaDB 与 Redis 版本、SNMP 工具版本、Compose 文件版本、启用的 poller/discovery 模块及配置摘要。Web 与 dispatcher 必须来自同一 digest。任一版本漂移都使运行时兼容验收失效并要求重跑；`latest` 只可用于隔离探索，不能作为交付锁定值。

### 5.2 网络、持久化和启动

- 当前 monitoring_internal 为 internal:true；dispatcher 必须另有可达设备管理网的网络，不能仅加入隔离监控网后宣称已能访问设备。
- 数据库和 Redis 不对宿主公网开放；API 通过内部地址供 Nexora 使用。
- Dispatcher 启动门禁包含数据库迁移、应用初始化和 Redis 就绪，不只检查容器进程存活。
- Web 与 dispatcher 使用一致的应用配置、时区、APP_KEY 和文件权限；由原生初始化步骤完成。
- /data、MariaDB 与原生 RRD 均单独备份，恢复顺序为数据库/配置/原生数据，再恢复任务。
- API 可达性、dispatcher 在线、最近发现/采样完成、原生写入成功分别检查，不能以 Web 200 代替采集正常。
- CPU/内存资源上限、poller worker 并发和 SNMP timeout/retry 在小规模 POC 测量后确定，禁止未经测量沿用现有容量数字。
- Windows 开发通过 Linux Docker 或指定 Linux 运行时接入；Ubuntu/Docker 使用相同原生服务契约。不把完整 PHP 引擎移植进 Windows Python 进程。
- 配置示例只有占位符；读取 .env 保持 LF/CRLF 兼容，不覆盖现场 .env 或既有数据卷。

### 5.3 周期

POC 初始按原生 300 秒轮询设计，结果同步每 60 秒、元数据周期同步并在发现完成后刷新。实际使用的原生发现周期和模块设置在锁定清单记录。

兼容输出的新鲜度至少按原生实际轮询间隔的三倍计算；300 秒轮询对应下限 900 秒，不沿用固定 180 秒导致正常样本被误判过期。若最终要求 60 秒轮询，按 LibreNMS 官方一分钟轮询方式同时校正调度与 RRD 设置，并重新验收资源/时效；不通过 Python 高频重读设备满足周期。

## 6. 设备同步、身份和凭据契约

建议新增两个 Nexora PostgreSQL 集成实体（正式表名/迁移编号在实现前核对现有注册器后确定）：

| 实体 | 必需字段/约束 |
|---|---|
| LibreNMS 实例 | instance_id、受控 base_url、token credential reference、engine version/commit、enabled、连接与健康状态 |
| 资产绑定 | tenant_id、asset_id、device_id、instance_id、librenms_device_id、librenms_hostname、collector_id/poller_group、desired_state、last_sync、错误码 |

落库方案按以下逻辑模型审核，最终表名应先检查并复用项目现有租户、任务及硬件库存结构：

| 逻辑实体 | 主要字段/约束 | 生命周期用途 |
|---|---|---|
| instance | instance_id、base_url、secret_ref、enabled、pinned_version/digest、capabilities、health_state、last_health_check | 管理受控 LibreNMS 服务；凭据只存引用 |
| device_binding | binding_id、tenant_id、asset_id、device_id、instance_id、native_device_id、native_hostname、poller_group、desired_state、observed_state、last_sync、last_discovery、last_poll、error_code | Nexora 资产与原生设备的显式、唯一关联 |
| integration_job（仅在现有通用任务表不能承载时新增） | job_id、binding_id、operation、idempotency_key、state、attempt、created_at、started_at、finished_at、sanitized_error_code | 设备同步、停用、重新发现的异步审计与恢复 |
| native_entity_current（优先复用现有硬件库存） | binding_id、native_entity_id、category、measurement_type、value/unit、observed_at、presence/quality、source、updated_at | 诊断与兼容指标当前快照；不能存凭据或重新解释厂商算法 |

数据库约束或事务内服务校验必须保证：`tenant_id + asset_id` 与 `tenant_id + device_id` 不可交叉绑定；`instance_id + native_device_id` 不可重复认领；同一 Nexora 设备不能有两个 active 原生绑定。复用现有硬件库存时，应可按 `data_origin=librenms_native` 和 instance/native entity 身份隔离。历史采样保留在既有历史表/VM；当前实体退休不能级联删除历史。

- 绑定以显式映射为准；唯一约束保证同一实例设备不能同时绑定不相容资产。同 IP 不作为跨租户唯一身份。
- 主机名、管理 IP、端口、SNMP 版本变化由绑定更新处理；重命名不能新建重复设备或覆盖另一资产。
- 幂等流程：查询现有绑定 → 核对远端对象 → 创建/更新原生设备 → 回写 native ID → 请求原生发现。远端成功、本地提交失败时依靠关联标识/对账恢复，不重复创建。
- 停用先停止原生轮询并标记绑定 disabled；删除策略单独确认并记录审计，不自动删除原生历史或 Nexora 历史数据。
- SNMP v1/v2c/v3、v3 context、端口、timeout/retry 经受控服务端配置下发；不把 SSH 凭据当作 SNMP 凭据。
- API token 使用原生版本支持的鉴权方式，按版本文档核实，存于凭据库；前端无 token/community。
- 所有原生响应只允许白名单字段进入 Nexora API和日志。原生 devices 响应可能含敏感配置，不透传整个对象。
- 同步是控制面任务，与硬件采集任务独立；同步故障显示 pending/failed，不能用未关联设备的数据填补。

### 6.1 管理接口与任务契约

具体 URL 前缀须服从现有 FastAPI 路由约定；以下是需要实现的操作和语义，不要求为迁移新造另一套权限体系：

| 操作 | 请求与响应约束 | 权限与副作用 |
|---|---|---|
| 注册/更新实例 | 名称、受控 base URL、TLS 校验策略、启用状态、凭据引用；返回 instance_id、脱敏状态和能力信息 | 仅平台管理员；测试连接只访问已登记的主机 |
| 查询实例健康 | 返回 API 可达、版本、Web/dispatcher状态及最近发现/轮询/导出时间 | 管理员可查看全局；租户用户只能看到本租户绑定设备的健康摘要 |
| 绑定 Nexora 设备 | 显式传入 Nexora device/asset、LibreNMS 实例、poller group 和 SNMP 凭据引用；返回 binding_id 与异步任务 ID | 必须通过租户授权；禁止按 IP/hostname 隐式认领远端对象 |
| 同步设备 | 创建/更新/禁用为异步幂等任务；返回 desired_state、observed_state、job_id、状态时间和稳定错误码 | 不等待 discovery/poll 完成，不把 API 接受请求当作采集完成 |
| 请求重新发现 | 只允许受控 LibreNMS 原生 API/任务能力；返回 job_id 和排队状态 | 设备管理员；不接受 shell、任意命令或 SNMP OID 参数 |
| 硬件诊断快照 | 返回绑定、引擎、原生发现/轮询、当前实体快照、时序最新样本、同步/导出状态 | 按 tenant/site 过滤；不透传 LibreNMS token 或敏感设备配置 |

实例 URL 使用出站主机白名单；生产默认 HTTPS、验证证书、禁止重定向和环境代理，连接/读取超时有上限。只有配置阶段允许显式登记本地开发地址。实例凭据存入现有 secret/credential 管理机制，API 响应只返回是否已配置及凭据版本，不返回明文。

远端操作与 Nexora 本地状态分两阶段提交：先记录期望状态和幂等键，再调用 LibreNMS，最后写回远端 ID 与结果。进程中断时由对账任务按绑定键核对并恢复，不重复创建设备。错误状态至少区分 authentication_failed、host_not_allowed、api_unavailable、device_conflict、sync_timeout、native_operation_unsupported；错误上下文脱敏。

任务状态机统一为 `queued → running → succeeded | failed | canceled`；可重试故障回到 queued 并递增 attempt，终态保留错误码与结束时间。相同 `idempotency_key` 重放必须返回同一任务/同一远端效果。未经用户操作不得从 disabled 自动恢复 enabled；解绑只清本地关系或标记 retired，不擅自删除 LibreNMS 设备、RRD、原生历史或资产。

## 7. 结果接入契约与兼容投影

### 7.1 原则

结果接入层只读取原生 API 和原生输出的数值/时间。允许进行通用身份、字段和指标名称映射，不能按 vendor/os 分支选择硬件 OID、补实体、重新执行 scale/divisor/user_func、把 null/失败转成 0。

建议新增 services/librenms_runtime_client.py、librenms_asset_sync_service.py、librenms_result_sync_service.py、librenms_diagnostic_service.py，形成清晰依赖：

    API/后台业务 → 通用集成 service → 原生 API/原生时序库
    集成 service → 原有库存/业务查询接口
    禁止 集成 service → SNMP 硬件 get/walk、旧 probe、Python 硬件规则解释器

### 7.2 字段

| 字段 | 含义 |
|---|---|
| engine_instance_id / engine_version / engine_commit | 原生运行时来源 |
| native_device_id / native_entity_id / native_category | 原生设备与实体身份 |
| asset_id / device_id / tenant_id / collector_id | Nexora 稳定身份 |
| measurement_type / unit | 原生结果对应的通用展示类型与已处理单位 |
| value / observed_at | 原生输出的值和其样本时间 |
| last_poll_at / last_discovery_at | 原生任务时间，不代表每个测量成功 |
| quality / presence_status / enabled | 原生证据与时效形成的展示状态 |
| source_oid / source_index / description / group | API 可提供的原生元数据；缺失时保留缺失 |
| data_origin | 明确为 librenms_native，不能混用 librenms_adapter 等旧来源 |
| export_status / sync_status | 数值导出与 Nexora 同步的独立状态 |

- sensor_key 基于实例+原生 device ID+原生实体 ID/类别+测量类型稳定生成；不以描述或 IP 为主键。
- CPU window 只使用原生实际提供的信息；未知保留 unknown，不伪造 5s/1m。
- 同设备的多核、多主控、多内存池分别保留；最大/平均是展示汇总，不能在接入时丢掉实体。
- 原生数值和元数据必须有可核对的索引；描述相同不能作为关联理由。
- VictoriaMetrics的Influx接收会把非数值field转为0；原生datastore还可能把空tag转换为_blank_。因此数值接入必须依据选定版本的明确measurement/field类型白名单和原生实体证据，字符串属性从API读取；不能把MAC/IP/描述导出的0当作测量值，也不能猜测_blank_一定等于实体索引0。原生协议的0、空索引与字符串边界必须进入POC。
- 原生内存只有百分比时，需在 POC核实比例基数与真实容量的区别，不能将比例计算用的 100 映射为真实字节容量。
- fan/PSU 状态保留原生枚举和描述，健康展示仅使用原生状态含义；不继续现有厂商映射。

### 7.3 时间、失败与生命周期

- observed_at 来自原生数值写入时间；元数据 API请求时间、兼容输出时间、vmagent 抓取时间均不能覆盖该字段。
- 兼容导出即使周期抓取，也不能刷新 last_success；没有新的原生样本就保持样本年龄增加。
- 原生设备任务完成与单个 sensor 成功分开；若原生接口不能提供类别/实体成功证据，不伪造 coverage_complete/good，标记 evidence_unavailable 并说明。
- 原生引擎未发现某类硬件、类别采样失败、数值导出失败、元数据同步失败分别表示。
- 设备/实体禁用、删除和原生发现退休状态应停止当前数值输出；保留历史。
- 临时 API失败/发现未完成不能把已有实体全部退休；只有完整原生发现证据才能执行退休。
- 原生采样成功而导出失败时，诊断显示引擎有值但时序未到；不能把它归为设备不支持。
- 重复同步按原生身份与时间幂等，旧样本不能覆盖新样本。

### 7.4 数据分类和指标映射

采集结果分为三类，不能把它们混成一个“硬件数据”字段：

| 数据类 | 来源 | Nexora 用途 | 不允许的解释 |
|---|---|---|---|
| 实体元数据 | LibreNMS 设备、processor、mempool、sensor、无线/收发器 API | 名称、原生 ID、类别、索引、描述、阈值、端口/父实体关系 | 不把 health 图表/类别列表当作当前采样值 |
| 当前快照 | 原生 API 明确提供的当前 sensor/processor/mempool 行 | 诊断页当前状态和最近读数 | API 未提供的 CPU/memory 当前值不得由 Nexora 重新 WALK 补算 |
| 时间序列 | LibreNMS 原生 datastore 导出的数值与时间 | Grafana、历史、趋势、当前值投影及告警输入 | 不把 exporter/API 拉取时间冒充设备样本时间 |

实现前产出版本绑定的 measurement/field/tag 白名单表；每个字段记录原生含义、单位、数值类型、稳定设备/实体关联键、时间语义、Grafana目标指标及允许的聚合。只有通过原生 API 元数据能稳定关联的数值才进入 canonical series。缺少身份标签、类型不确定、字符串字段变成数值 0、空 tag 语义不明或关联仅靠描述相似时，拒绝该 series 并让 POC 判失败。

初步映射范围如下，字段/类型为方案假设；最终须以 P7 锁定版本的实际原生 API 与导出样本确认：

| 原生对象/类别 | 规范类型 | 保留粒度 | 进入现有产品的规则 |
|---|---|---|---|
| processor | CPU utilization，百分比 | 每个 native processor/entity；如原生提供 window 才保留 window | 设备最大值/平均值仅作为查询或展示聚合，不在接入时丢掉单核/主控记录 |
| mempool | memory utilization、原生提供的 used/total | 每个 native pool/entity | 百分比、字节容量分别投影；只提供百分比时不得制造字节容量 |
| temperature sensor | 温度及原生单位、阈值、状态 | 每个 sensor/index | 机框、板卡、光模块按原生类别/关联分组，不能按本地厂商规则猜测 |
| fan / PSU / voltage / current / power | 原生读数及原生状态/单位 | 每个实体 | 状态枚举保留原始值与显示文本；unknown 不映射成健康 |
| transceiver | 温度、电压、偏置电流、TX/RX 光功率等原生字段 | native entity 与明确关联的 interface | 端口名称必须有原生实体关系佐证；不能只凭 entPhysicalIndex 推断 ifIndex |
| AP / radio / SSID / BSS / client | LibreNMS 明确支持的原生字段 | 每个 native object | 逐字段映射；未覆盖项标为 unsupported，不保留旧 Python 采集器 |

标签仅保留稳定、低基数或必要身份字段。MAC、描述、序列号等高基数或敏感信息只在授权 API/元数据中展示，不默认成为时序标签。Grafana 中的 asset/site/vendor/role 标签由 Nexora 绑定关系补充，不能通过时序标签反向猜租户。

### 7.5 结果同步顺序与状态传播

1. 原生引擎完成 discovery/poll；LibreNMS 自身数据库/RRD 和选定 datastore 记录由引擎管理。
2. Nexora 定期刷新实例/设备/实体元数据，先验证 binding 仍指向同一个 native device，再更新 metadata version 和实体 presence。
3. 时序存储接收原生数值；接收端按 P7 验证过的身份标签和 measurement 白名单查询最新点。
4. 兼容投影按 native identity + observed_at 幂等更新当前库存视图；只有 observed_at 更新时才推进 last_success。
5. Grafana、资产详情、阈值评估都读取相同 source=librenms_native 的当前结果；显示值与原生点可通过 instance/native device/native entity/time 追溯。
6. 诊断将 engine poll、native export、VM ingest、Nexora projection 四段状态分别呈现；任一段失败不伪装成“不支持”或“设备健康”。

元数据刷新和时序拉取分别限流，批量设备必须使用批量 API/批量查询或受控并发；若 POC 测得只能 N+1 请求且达不到目标规模，先优化原生批量通道，不允许以高频 Python SNMP 采集绕过。所有重试有上限和退避，历史点按原时间保留，过期实体停止作为 current 输出但保留可查询历史。

## 8. 无线、光模块、接口与多实例

### 8.1 无线

旧 probe 包含 Nexora 扩展的 H3C AP/Radio/SSID/BSS/station 路径；不能假定完整 LibreNMS 已提供完全相同字段。

POC 必须列出：AC AP/client 总数、AP identity/state、Radio 指标、SSID/BSS 关系、客户端 MAC/IP/SSID/VLAN。逐项核对原生 engine/API/export 是否存在及可接入。

无法提供的字段显式标记上游未提供并列为功能差异；不得继续保留旧 Python AP/客户端读取器。若重要功能缺口影响验收，返回用户审核，不自行写新的厂商适配。

无线看板现有 AC 流量和在线状态还依赖 network_snmp 的 IF-MIB/up；本轮保留该接口链路，并在看板中明确其来源。硬件数值源仍唯一为 LibreNMS。

### 8.2 光模块

保留原有业务操作接口和记录展示，输入改为原生 transceiver/sensor/API 结果。LibreNMS 中 entPhysicalIndex 与 ifIndex 的映射证据必须保留；不能直接把物理实体索引当端口号。

缺少端口关联或实时样本时显示关联待确认/数据过期；不得恢复本地 optical probe 或 CLI/SNMP硬件兜底。

### 8.3 多采集器与实例

- 初始采用一个原生实例，按原生 poller group/dispatcher 管理设备归属。
- 远端管理网需要原生分布式 poller 的实际网络与数据库/Redis通信方案；不能把控制面 Docker DNS 地址放入远端 collector。
- 原有 collector_id 到原生 poller group 的映射明确存储，默认本地不能静默接管不可达远端设备。
- 多个独立 LibreNMS 实例时，原生指标必须携带不可冲突的实例身份；同 hostname 原生默认标签不足以隔离。实现前验证可用的接收端 extra label/独立 namespace 与路由方法。
- 多租户、站点权限在 Nexora 接入和查询层执行；原生 shared instance 的全量传感器 API不能直接暴露给普通用户。

## 10. SNMP 诊断和产品行为

/monitor/snmp-walk 保留系统信息与原始 Walk 工具。硬件诊断改用原生运行时：

1. 展示资产绑定、原生 device ID、OS、引擎版本、poller group、最近 discovery/poll时间。
2. 展示 CPU、内存、机框温度、风扇/电源及光模块的原生结果、实体索引和样本年龄。
3. 对照“引擎最近结果”“原生数值是否入时序”“Nexora兼容结果是否同步”三层。
4. 原生提供时才显示 source OID、阈值、索引、原始值；不存在不在 Python重新 Walk补齐。
5. 刷新默认刷新结果快照，不宣称即时重新采样；请求重发现通过原生支持接口排队，并跟踪 pending/running/completed/failed，完成后等待原生轮询生成新值。
6. 如需“立即采样”，先验证所选版本提供的原生任务方式与受控执行契约；禁止接受前端 shell/任意命令，禁止用 Python直接读取 OID代替。
7. 没有数据时展示具体层级：未绑定/引擎不可达/发现等待/上游未发现/采样失败/导出失败/同步失败/样本过期。
8. 复制诊断只包含白名单；保留加载、空态、权限、失败和旧响应兼容。普通用户不能通过全局原生 API读取其他站点数据。

旧硬件模板测试与自定义硬件采集入口的产品迁移必须明确：已绑定模板改为历史只读或返回清晰迁移状态，不能保留看似可配置却仍在执行旧规则的入口。接口模板和原始 Walk不受该限制。

诊断快照的分层状态使用明确枚举，不能用单一 healthy/failed 混淆设备、引擎和接入问题：

| 字段 | 建议状态 | 表示内容 |
|---|---|---|
| binding_status | unbound / pending / bound / conflict / disabled | 资产与原生设备关联状态 |
| engine_status | unknown / healthy / degraded / unreachable / disabled | 实例/API/dispatcher 总体可用性 |
| discovery_status | unknown / pending / running / succeeded / failed | 最近一次原生发现任务 |
| poll_status | unknown / pending / running / succeeded / failed | 最近一次原生轮询任务 |
| export_status | unknown / pending / succeeded / failed / unsupported | 原生时序导出状态 |
| sync_status | unknown / pending / succeeded / failed | Nexora 元数据/结果投影状态 |
| sample_status | missing / fresh / stale / unsupported / unknown | 当前实体样本的新鲜度与原生能力 |

响应至少返回 generated_at、native observed_at、last_discovered、last_polled、stale_after_seconds、实体数量及脱敏 error_code。时间缺失时标 unknown，不以接口请求时间补齐。UI 将“刷新快照”和“请求重新发现”作为不同动作；前者不触发 SNMP，后者显示异步任务状态。浏览器不直连 LibreNMS，也不接收 native token。

诊断 API 的逻辑响应至少覆盖以下结构，实际路由服从现有 FastAPI 约定；示例中的值仅表示字段语义，不代表原生 API 必然提供全部字段：

```json
{
  "device_id": "nexora-device-id",
  "binding": {"status": "bound", "instance_id": "...", "native_device_id": 123},
  "engine": {"status": "healthy", "version": "...", "dispatcher_status": "online"},
  "collection": {
    "discovery_status": "succeeded", "last_discovery_at": "...",
    "poll_status": "succeeded", "last_poll_at": "...", "poll_interval_seconds": 300
  },
  "export": {"status": "succeeded", "last_export_at": "...", "time_series_backend": "victoriametrics"},
  "sync": {"status": "succeeded", "last_success_at": "..."},
  "entities": [{"native_entity_id": "...", "category": "processor", "measurement_type": "cpu_utilization", "value": 12.5, "unit": "%", "observed_at": "...", "sample_status": "fresh"}],
  "errors": []
}
```

无法从原生证据获得的字段必须返回 `unknown`/`evidence_unavailable` 并携带可定位原因码，不能伪造成功状态或用后端请求时间补值。响应不得包含 token、community、SNMPv3 auth/privacy secret、完整原生设备对象或跨租户实体。

### 19.4 HCL 与真实设备根因判定顺序

HCL 与真实设备应尽量使用同一 LibreNMS digest、同一 poller 配置、同一 SNMP登记路径及相同查询时间窗。对照结果按“第一个失败层”分类，不跨层推断：

1. **SNMP 可达性/凭据**：真实设备连不通而 HCL 可通，先核对路由、防火墙、ACL、SNMPv3 context/read view、来源地址、超时/重试。此时不能判断 LibreNMS 处理逻辑失败。
2. **OS 与型号识别**：SNMP sysObjectID 可读但 OS 未识别/识别错，记录 LibreNMS 匹配结果与 image commit，判断版本/识别支持问题。
3. **实体发现**：OS 已匹配但无 CPU/memory/sensor 行，核对 discovery debug/模块、原始只读 OID 可见性、索引、返回类型及上游支持；真实设备不支持的数据应标 unsupported。
4. **轮询**：实体存在但 lastupdate 不前进或没有 RRD 点，检查 dispatcher/poller 工作状态、单设备任务结果、SNMP超时/重试和实体 enabled 状态。
5. **原生输出**：LibreNMS UI/API/RRD 有值而 Influx line protocol 或 VM 无值，定位 datastore配置、网络、认证、dbname、measurement/filter、时间和目标 HTTP响应。
6. **Nexora 接入**：VM有原生样本但 Nexora无 current projection，核对 binding/native ID/entity ID、查询限流、字段白名单、tenant过滤和拒绝错误。
7. **Grafana**：Nexora 或 VM有样本而目标面板为空，核对 datasource、query、标签名、dashboard revision、变量展开、时区/范围、transformations 和 stale过滤。

HCL 成功、真实设备失败时，报告必须准确指出在哪一层分叉。若证据只到代码级或模拟器，不得把现场根因写为“已解决”；如果真实设备的原生采样正常但产品展示失败，则根因在原生采集之后，并按相应层提出修复。

### 19.5 P7 验收和停点

- HCL 的 CPU 与内存至少各有一个有原生 entity 身份的有效样本，能够从 LibreNMS 原生视图/存储追到 VM，再追到 Nexora诊断/Grafana；值、单位和时间需按精度规则一致。
- 真实设备必须证明其目标硬件类别实际被原生引擎采样，或用证据确认无值属于设备权限/能力/上游 OS 支持限制。只要用户目标的 CPU/内存空白仍未定位到具体层，根因状态保持 pending。
- 原生实体不存在、任务失败、导出失败、同步失败、样本过期和不支持应显示不同状态；任何情况下不把未知/失败映射成 0 或健康。
- 现场验证失败或证据不足时停止生产切换；向用户报告第一个失败层和下一步所需证据。不得恢复 Python硬件采集作为临时 fallback。
- P8 生产切换必须另有授权、变更窗口、明确设备清单、备份与可执行回滚包；P7通过不自动授权P8。
