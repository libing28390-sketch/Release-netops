# Grafana 九个看板全量核查与接口流量修复

## 目标与范围

按用户要求，对 Grafana 全部 9 个看板进行逐页检查；重点重复验证无数据面板、04「接口流量与健康」、设备筛选器中的旧名称，并确认 01「网络总览」的 DOWN 接口含义及接口角色用语。核查包括只读 Grafana 页面和 Explore 查询，以及本地看板生成源和生成 JSON。没有保存、发布或部署 Grafana 看板。

## 核查结论

### 设备变量为什么仍显示旧名称

实时 04 的旧变量通过 label_values 从 ifOperStatus|up 指标标签提取 hostname。IF-MIB 的历史时序仍会保留已移除目标的 hostname，因此刷新页面或重生成 JSON 不会自动从变量结果中清除旧名称。刚刚直接重开 live 04 并展开设备下拉，Grafana 显示 23 个可选结果，包含 F1090-10、R10、R11、R12、R13、R14 等不在当前目标清单中的名称。

只读查询 count by (hostname) (up{job="network_snmp",...}) 重复执行返回 13 台当前 SNMP 目标，不包含 F1090-10、R10、R11、R12。当前名称为 F1090-9、R1–R4、S6850-2–6、S6850_1、SW5、SW6。使用 query_result(count by (...) (up{...})) 并由正则提取标签后，变量查询重复得到这 13 个值。查询不筛 up == 1，所以仍在 scrape target 中但当前离线的目标也会保留；已经从目标中移除的旧设备则会消失。

因此上次“已解决”只落实在仓库生成逻辑/JSON，没有反映到当前 live 实例：页面证据仍是旧变量与旧面板查询。仓库 Compose 配置把本地 dashboards 目录只读挂载到 Grafana provisioning 路径，provider 每 10 秒检查一次；若 live 使用同一挂载，通常会自动采用 JSON。当前旧内容说明该实例未读到这批文件，或 provisioning 没有成功应用。工作机没有 Docker 命令，也没有 Grafana/VM/vmagent/snmp-exporter/API 本地监听，无法查看 live 容器挂载和 provisioning 日志，因此还不能在这两个原因间定案。

## 本地修改

- monitoring/grafana/generate_dashboards.py
  - 网络、Linux、Windows 设备变量改为从当前 up 目标按标签分组，再用 query_result 和 regex 提取变量值。
  - 共享接口名称/描述 metadata join 先聚合重复时序，避免 group_left 的多对多错误。
  - 01 的关注接口条件限定为 admin UP 且 oper DOWN，补充当前状态与空闲端口语义说明。
  - 接口角色显示名改为“接口用途”，unclassified 显示“用途待确认”。
  - 移除无线面板将缺数据补成 0 的表达式回退，并解释这表示没有无线指标样本。
- monitoring/grafana/dashboards/ 下 9 个生成 JSON：使用更新后的变量、join 与面板设置重新生成。
- backend/tests/monitoring/test_domestic_and_wireless_monitoring.py：覆盖接口 join、状态条件、中文用途显示、目标变量格式及无线缺数据不伪装为零。
