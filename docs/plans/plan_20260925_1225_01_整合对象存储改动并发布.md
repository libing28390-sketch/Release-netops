# 整合对象存储改动并发布

## 任务目标

将当前仓库已完成的对象存储管理/S3 profile 代码与拓扑图合成端口标签过滤改动整理为可审查提交，推送 `main`，并按用户确认的 tag 名称发布。

## 现状 / 问题

- `main` 当前与 `origin/main` 同步，工作区包含对象存储管理页面、S3 profile/用途路由、PostgreSQL 迁移和 Docker 文档变更，以及拓扑图标签过滤。
- `v1.0.9` 已存在于 origin，指向旧提交；用户已确认覆盖现有 tag，将其移动到本次发布提交。
- Git worktree 清单中的 `netsops-main-ci-fix` 目录已不存在，其提交已包含于当前 `main`；前缀列表目录不是 Git 仓库。
- 推送 `main` 会触发仓库 release workflow 同步公开发布仓库；推送版本 tag 还会触发完整 Linux/Windows 发布流程。

## 影响范围

- 当前仓库中的 S3 profile API、存储服务、对象读写绑定、数据库迁移和管理 UI。
- `TopologyGraph` 中 `Port-数字` 合成占位标签展示过滤。
- 相关计划、走查、提交修复记录及 GitHub 发布流程。

## 拟提交文件

- 当前工作区中与对象存储管理功能对应的已修改及新增源代码、迁移、部署文档和 `20260925_1119` 计划/走查。
- 拓扑标签展示修改及 `20260925_1200` 计划/走查。
- 每个代码提交对应的 `docs/fixes/fix_*.md` 记录。

## 实施步骤

1. 核对当前改动清单、敏感文件排除项、另一个 worktree 提交包含关系、版本号、发布 workflow 和远端 tag。
2. 审查对象存储迁移/凭据加密/API/对象生命周期变更与拓扑展示过滤。
3. 核对既有静态检查结果，并对本次修改的 Python 文件执行语法编译；发布 tag 后由 GitHub Actions 执行完整 release gate。
4. 为代码变更创建修复记录，形成清晰提交；确保计划、走查和代码归属一致。
5. 将 `main` 推送至 origin，并依据用户确认的 tag 名称处理 tag；不在目标服务器上部署。
6. 检查 origin 分支/tag SHA 与远端 Actions/Release 结果并记录未完成项。

## 验证计划

- `git diff --check` 与暂存文件清单审查，排除 `.env`、部署备份、凭据、私钥和生成数据。
- 已有 `npm run lint` 和临时目录 Vite 生产构建通过；本次 Python 语法编译与 diff whitespace 检查通过。未在本机运行测试套件。
- 推送后读取 origin 分支/tag 指向并检查自动发布工作流。
- 推送后读取远端 `main`/tag 指向并检查自动发布工作流。

## 风险与回滚思路

- 迁移新增 S3 profile 与用途绑定表、并为对象记录加入 provider 关联，回滚应用时应保留数据表及已有 S3 对象，不清理存储卷。
- 远端已有 `v1.0.9`，用户已确认覆盖。重新推送此 tag 会触发完整 Linux/Windows 发布流程，并强制同步公开 `Release-netops` 仓库及现有 GitHub Release。
- 当前仅发布代码和 release artifact，不直接修改用户 Docker 主机、数据库或 S3 对象。
