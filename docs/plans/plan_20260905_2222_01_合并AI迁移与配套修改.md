# 合并 AI 迁移与配套修改

## 任务目标

将 `netsops-main-ci-fix` 工作区从 `m0204` 至 `m0208` 的数据库迁移、其配套的 AI/RAG、评测、CI、Windows/pgvector、前端和文档修改，完整纳入 `netsops-main`。合并完成后主工作区应能识别 PostgreSQL 已应用的 204–208 迁移，不再因迁移历史未知而阻止开发启动。

本次及后续仓库修改遵循单一 `main` 工作流：不新建或切换功能分支，不推送远端；已有隔离工作区只作为本次合并前的来源，合并后以 `main` 为唯一开发基线。

## 现状与问题

- PostgreSQL `netops` 数据库的 `schema_migrations` 已记录 200–208。
- `netsops-main` 的迁移发现范围只到 203，严格历史检查将 204–208 判定为 `unknown`，`npm run dev` 的后端初始化因此失败。
- `netsops-main-ci-fix` 已包含 204–208 迁移、连续修复提交以及尚未提交的配套修改；主工作区另有用户未提交文件和未合并的 `dist/index.html`，不得覆盖或清理。

## 合并范围

1. 合并 `codex/ci-contract-fixes` 从 `main` 分叉后的全部已提交提交。
2. 合并该工作区全部可追踪的后续修改和新增代码、测试、迁移、知识包、评测产物与发布配置；明显属于本机运行状态的 `.codex` 缓存和被忽略的个人笔记不纳入版本控制。
3. 在项目级 `.agents/AGENTS.md` 和架构文档中明确单一 `main` Git 流程。
4. 保留 `netsops-main` 原有用户改动，尤其是 `dist/index.html`、开发脚本、评测 manifest、`.codex` 状态、`.codex_kb_refs.txt` 和备份文件。

## 实施步骤

1. 读取两工作区状态、提交图和差异，确认 `main` 是来源提交的祖先。
2. 在来源工作区补齐计划、Git 规范和本次合并的提交记录，并提交全部后续修改。
3. 暂存主工作区既有改动（包括未跟踪文件），将 `main` 快进到来源提交。
4. 恢复主工作区改动；如生成文件发生冲突，以主工作区现有用户内容为准，并保留可审计的差异。
5. 删除临时功能分支引用（不删除用户文件），确认仓库只保留 `main` 开发分支。

## 验证计划

- 检查迁移发现/已应用集合：`unknown=()`、`pending=()`、`name_drift=()`，严格历史安全为真。
- 运行 `m0204`–`m0208` 迁移和官方模板投影相关的 PostgreSQL 回归测试。
- 运行 AI/RAG 聚焦测试、Python 编译、`git diff --check`；按改动风险运行前端 lint/测试/构建。
- 在主工作区执行开发启动的数据库初始化路径，确认不再出现 `unknown=(204, 205, 206, 207, 208)`。

## 风险与回滚思路

- 迁移写入官方模板，必须保持幂等和 PostgreSQL 事务语义；不删除或重置已有 `schema_migrations` 行。
- 主工作区的未提交文件通过 Git stash 和状态清单保护；任何恢复冲突只保留在工作区，不使用 `reset --hard`、`clean` 或覆盖式复制。
- 如合并后验证失败，可将 `main` 回退到合并前 SHA，并恢复保存的主工作区 stash；数据库迁移不执行破坏性回滚，使用现有迁移备份/恢复流程处理。
