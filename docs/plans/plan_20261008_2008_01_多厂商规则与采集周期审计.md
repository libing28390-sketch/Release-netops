# 多厂商规则与采集周期审计

## 目标

核对 192.168.204.128 Docker 部署的版本、硬件采集周期、样本完整性和 Grafana 查询；逐厂商检查实际使用的 LibreNMS 上游规则，修正自定义发现规则及误导的来源标记，清理已无用途的旧链路，并验证 SNMP 诊断页的数据来源。

## 现状

- 用户反馈 CPU/内存曲线约五分钟出现一个样本且有缺口。
- main 已推送 eee18e35，上一轮仅对 Comware 分支做过来源对齐，不能据此声称所有厂商与 LibreNMS 完全一致。
- 用户要求保留 Nexora 采集架构，不在 Compose 部署 LibreNMS 服务。
- 用户确认设备数据来自模拟器，目标是所有启用的硬件采集严格使用固定版本 LibreNMS 上游规则；无匹配官方定义时应显式不支持，不允许 Nexora 私有厂商规则回退。
- 用户已在浏览器手动接受自签名证书提示；浏览器和主机检查保持只读。
- 线上 SNMP 诊断页显示旧本地快照，Grafana 查询步长为 1 分钟，但设备样本间隔仍在 5 分钟以上；这是部署版本证据，不代表当前工作区代码。

## 影响范围与文件

按证据确定最小修改集合：硬件调度与轮询、规则执行和 vendor 来源清单、诊断 API/前端、Grafana 查询与相关测试。生产现场先执行只读命令；设备配置不在任务范围。

本轮补充核实规则包边界：运行时仅读取 `resources/definitions/os_detection/*.yaml` 与 `os_discovery/*.yaml`，不执行 vendor 包中的 PHP。将移除未被运行时调用的 PHP 参考副本，更新来源清单和说明；保留授权文件、YAML、MIB 与固定上游 commit 信息。不能把 YAML 文件存在等同于完整复现 LibreNMS PHP 行为。

## 实施步骤与分工

1. 主 Agent：只读核对 Docker 主机运行版本、数据库样本间隔、Grafana 查询和 SNMP 诊断页；区分采样间隔与查询步长。
2. 探测执行 Agent：仅负责 `snmp_hardware_probe_service.py` 与对应测试，审计 YAML OID 解释、LibreNMS PHP 方法映射、MIB 符号、来源水印和采样请求；删除私有无线/厂商采集路径。
3. 主 Agent：负责轮询器、双采集循环、Grafana 导出和诊断页/API 的来源门禁，以及其它对应测试；禁止未验证来源进入采样/导出。
4. 保留 Nexora 的 SNMP transport、持久化、诊断和 Grafana 架构；上游未定义或当前执行器未支持的规则显式标为 unsupported，不以 Nexora 私有 OID 补齐。
5. 统计固定 commit 下 OS detection/discovery YAML 覆盖；删除未执行的 PHP 快照并修正来源政策、测试和 README，避免将 PHP 参考文件误认为运行规则；审计测试夹具中的来源路径也必须与 YAML 执行链一致。
6. 聚合验证并生成同名 walkthrough 与流程图，注明支持边界、线上旧版本观察与未做的部署验证。

## 验证计划

- 对照应用调度、数据库 last_sample_at、原始时序时间戳和 Grafana query step，区分采集周期与显示粒度。
- 所有输出样本来源可校验到固定 LibreNMS commit 的官方 YAML 文件；未知函数、模板或无上游规则时 fail closed。
- 检查已打包 OS profile 文件的哈希与清单；不把“有 profile”误当作“硬件类别均有官方支持”。
- 确认检测 YAML 为 136/136、发现 YAML 为 122/136；缺失发现 YAML 的 14 个 profile 不得由本地 PHP 或 Nexora 私有 OID 回退。
- 运行受影响 SNMP/轮询/诊断/指标导出测试，后端变更运行 PostgreSQL-only 策略扫描；前端/契约变更运行 lint 和相关组件测试。
- 浏览器及 SSH 现场操作保留脱敏证据；没有验证过的厂商/设备不能宣称完成真实设备验证。
- 当前阶段不推送、不部署；生产端新逻辑须部署后才能验证实际采样间隔和 Grafana 曲线。

## 风险与回滚

提高采样频率可能增加 SNMP 请求量，需分离低频发现与短周期已发现 OID 轮询并保持有界并发。清理前核实引用与迁移路径。现有工作区的内部文档和临时构建产物保持原状；本轮不自动提交或推送。涉及运行部署的变更先完成可审阅实现与验证，再按用户授权范围执行。
