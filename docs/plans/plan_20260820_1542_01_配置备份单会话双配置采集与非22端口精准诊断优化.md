# 配置备份单会话双配置采集与非 22 端口精准诊断优化计划

## 1. 任务目标
1. **消除 SSH 错误诊断中的 22 端口硬编码**：修复 `diagnose_ssh_failure` 与 `build_ssh_transport_guidance` 中写死“22 端口”的问题，根据设备实际绑定的 `management_port`（如 2222/8022）动态输出精准的排障提示，杜绝误导。
2. **批量备份查询补齐 `asset_id`**：修复 `run_scheduled_backup` SQL 查询遗漏 `asset_id` 的问题，确保物理资产（`physical_assets`）绑定的非标准端口与凭据能 100% 透传至批量备份任务。
3. **单会话流水线采集（Single-Session Double Collection）**：将运行配置（Running-Config）与启动配置（Startup-Config）的采集重构为在**同一个 SSH 会话内连续顺序下发**，彻底避免短时间内对同一设备发起两次独立连接而导致 VTY 线路被打满、超时或被拒绝。

## 2. 现状与根因分析
1. **错误提示误导**：非 22 端口设备出现连接超时或被拒绝时，`diagnose_ssh_failure` 未接收 `port` 参数，直接提示“请确认防火墙是否放行 22 端口”，严重误导运维排障。
2. **`asset_id` 缺失**：`run_scheduled_backup` 在 `SELECT` 列中缺少 `asset_id`，导致 `resolve_device_credentials(d)` 无法回溯资产表的凭据和端口。
3. **VTY 会话冲突与二次连接风暴**：开启启动配置采集时，代码在采完 running-config 后断开连接，随即又为 startup-config 发起第二次全新 SSH 连接，极易触发网络设备的 VTY 释放延迟、并发限速与 NAT 状态冲突。

## 3. 拟修改文件与实施步骤

### 3.1 `backend/drivers/ssh_compat.py`
- 修改 `diagnose_ssh_failure(error_text: str, ip: str = "", port: int | str = 22)`：
  - 动态计算 `port_str = f"{port} 端口" if port else "SSH 端口"`；
  - “连接被拒绝”与“连接超时”排查建议中动态注入 `{port_str}`。
- 修改 `build_ssh_transport_guidance(error_text: str, port: int | str = 22)`：
  - 动态输出 `{port_str}`。

### 3.2 `backend/api/configs.py`
- **补齐 `asset_id`**：
  - 在 `run_scheduled_backup()` 的 `SELECT` 语句中加入 `asset_id`。
- **单会话双配置采集重构**：
  - 在 `_backup_one(device)` 中，若 `collect_startup_config` 开启，将 `commands` 组装为 `[_running_cmd, _startup_cmd]`；
  - `service.execute_commands(d, commands, is_config=False)` 在同一个 SSH 会话中依次执行并捕获两个回显：
    - `results[0]` 作为 running-config 输出；
    - `results[1]` 作为 startup-config 输出；
  - 避免发起第二次独立 SSH 连接，全流程仅消耗 1 条 VTY 线路。
- **诊断调用透传端口**：
  - `diagnose_ssh_failure(str(err_str), device.get('ip_address', ''), port=resolve_ssh_port(d))`。

## 5. 风险与回滚思路
- **风险**：极少数老旧设备在单会话内连续下发第二条大输出命令时可能存在命令粘连；
- **防护**：`AutomationService` 底层使用的是逐条 `send_command` 并由 `drain_paged_output` 自动清空分页与提示符，已原生支持安全流水线执行；
- **回滚**：如遇异常可直接通过 Git 还原对应修改。
