# 凭据改密同步任务与 SSH 风险治理实施计划

## 1. 任务目标

把“凭据中心修改密码”实现为可追踪、可限流、可恢复的硬件改密任务：

1. 用户输入旧密码后，系统先验证旧凭据，不允许仅凭前端输入直接覆盖中心密码。
2. 系统使用旧的特权凭据登录关联设备，在设备端修改普通账号、特权账号或 Enable 密码。
3. 每台设备使用新密码重新登录并验证成功后，才把新密码提交为凭据中心的最终值。
4. 多设备场景使用统一任务队列、全局 SSH 限流、单设备互斥、超时、重试和逐设备结果记录。
5. 任何部分成功都必须明确展示为“部分失败/需要人工处理”，不能返回伪成功。

本计划只定义实施方案，不在本次创建计划时修改业务代码或生产数据。结合前序约定，本项目可以按新模型直接实施，不设计历史数据迁移兼容层。

## 2. 当前实现核查结论

### 2.1 `.env` 与代码默认值

当前 `.env` 中涉及网络访问的非敏感配置如下；未显式配置的项目使用代码默认值：

| 配置 | 当前值 | 作用 |
| --- | ---: | --- |
| `NETWORK_SSH_GLOBAL_CONCURRENCY` | 20（默认） | 进程级 SSH/CLI 全局并发上限 |
| `NETWORK_SSH_PER_DEVICE_CONCURRENCY` | 1 | 同一设备串行访问 |
| `NETWORK_ACCESS_ACQUIRE_TIMEOUT` | 120 秒 | 获取网络访问槽位的等待上限 |
| `NETWORK_SNMP_GLOBAL_CONCURRENCY` | 30 | SNMP 全局并发上限 |
| `NETWORK_PROBE_GLOBAL_CONCURRENCY` | 50 | 探测全局并发上限 |
| `NETWORK_POOL_MAX_SIZE` | 100 | 引擎连接池最大连接数 |
| `NETWORK_POOL_IDLE_SECONDS` | 300（默认） | 引擎连接池空闲回收时间 |
| `BACKUP_CONCURRENCY` | 10 | 配置备份并发上限 |
| `CONFIG_MANAGEMENT_TIMEOUT_SECONDS` | 1 秒 | 配置管理相关短超时，不等同于 SSH 改密总超时 |
| `PASSWORD_ROTATION_ENABLED` | false（默认） | 定时密码轮换开关 |

需要区分两个概念：`backend/engine/pool.py` 的连接池用于引擎场景；凭据改密通过 `DriverFactory` 使用 `backend/drivers` 下的 Netmiko 驱动，不是从该连接池复用一条持久连接。但 `backend/drivers/base.py` 的上下文管理器会进入进程级 `NetworkAccessLimiter`，因此改密会受到 SSH 全局上限 20 和单设备上限 1 的保护。

### 2.2 底层 Driver 的实际超时

当前主 Netmiko Driver 的默认参数为：

- 建立连接 `timeout = 20` 秒；
- 会话 `session_timeout = 60` 秒；
- 阻塞读 `blocking_timeout = 30` 秒；
- 单条命令读取 `read_timeout = 120` 秒；
- 设备可以通过 `conn_timeout` 或 `timeout` 覆盖建立连接超时。

因此一次改密并不是只有 20 秒。获取 SSH 槽位最多等待 120 秒，连接、配置命令、保存配置和重新验证还会叠加。网络设备数量多、设备响应慢或认证失败时，任务耗时会明显增长。

### 2.3 当前凭据同步调用链

当前流程是：

1. `backend/api/credentials.py` 收到修改请求后，先调用 `credential_service.update_credential()` 写入 `credentials` 表。
2. 若修改了密码，API 通过 FastAPI `BackgroundTasks` 启动 `sync_hardware_device_password_for_credential()`，接口立即返回。
3. 同步函数最多创建 10 个线程，查询该凭据关联的全部设备。
4. 普通凭据关联设备按 `normal` 改密，特权凭据关联设备按 `admin` 改密；同时修改 Enable 时，同一设备还会再执行一次 `enable` 改密。
5. 每次 `rotate_password()` 会重新通过 `resolve_device_credentials()` 读取凭据中心。由于第 1 步已经写入新密码，旧密码尚未完成硬件同步时，后续登录可能已经拿新密码尝试登录设备。
6. 当前同步函数即使存在失败设备，最终返回值仍然是 `success: True`，只在结果中携带 `fail_count`，调用方没有持久化任务 ID、逐设备状态、取消和恢复能力。

## 3. 主要风险

### 3.1 一致性风险：中心密码先变，设备密码后变

凭据中心是登录解析的权威来源。先写新密码会让备份、巡检、自动化等其他请求立即读取新密码，而部分设备仍只接受旧密码，造成中心与硬件不一致。后台任务失败时，设备回滚也不能自动回滚已经提前写入中心的值。

### 3.2 并发与拥塞风险

当前单个凭据同步最多 10 个工作线程，多个同步任务可以同时各自创建线程。虽然 Driver 上下文会受全局 20、单设备 1 的限制，但线程仍可能长时间等待槽位；大量任务会在进程内堆积，并与备份、巡检、自动化争抢 SSH 资源。

单台设备同时修改登录密码和 Enable 密码时，当前实现可能产生两次独立连接。若每台设备耗时较长，批量总耗时会按“设备批次数 × 单设备多次操作耗时”增长。

### 3.3 超时与重试风险

认证失败、命令不支持、设备不可达和暂时网络抖动不能使用同一种重试策略。盲目重试可能触发设备 VTY/登录保护；没有任务级截止时间时，多个 120 秒读取超时会使后台任务长时间占用工作线程。

### 3.4 进程重启与可观测性风险

FastAPI `BackgroundTasks` 适合短任务，不适合需要跨进程重启恢复的多设备改密。当前接口没有 job ID，用户无法知道哪些设备已成功、哪些仍在排队、哪些需要回滚或人工确认。

### 3.5 权限与秘密泄露风险

这是高风险配置变更，不应仅由前端控制。旧密码、新密码、特权密码不能进入普通日志、CLI 输出、任务详情或错误堆栈；执行权限应与凭据编辑权限和设备配置变更权限分别校验。

## 4. 目标状态与不变量

### 4.1 权威顺序

目标顺序固定为：

```text
校验旧密码
  -> 创建改密任务并冻结凭据快照
  -> 全量预检查
  -> 使用旧特权凭据改设备
  -> 使用新凭据重新登录验证
  -> 汇总设备结果
  -> 全部成功后提交凭据中心
  -> 写入凭据轮换状态与审计事件
```

必须满足以下不变量：

- 设备改密未全部验证成功前，`credentials` 的当前密码不变。
- 任务执行期间不重新从中心读取待修改的当前密码，改用加密的任务快照，避免中心中途变化造成登录错配。
- 设备删除只解除绑定，不删除凭据；凭据有关联设备时禁止删除。
- 同一凭据不能同时存在两个运行中的改密任务。
- 同一设备不能被两个改密任务同时操作。
- 部分失败不得标记为成功；必须保留逐设备状态和错误分类。

### 4.2 旧密码校验

扩展 `CredentialUpdate`：

- 修改 `password` 时要求 `old_password`；新密码为空表示不修改密码。
- 修改 `enable_password` 时要求 `old_enable_password`。
- 服务端解密当前中心密码后比较旧密码；前端只负责输入和提示，不能承担校验责任。
- 修改名称、类型、用户名、账号角色等非秘密字段时不触发设备改密。
- 无设备绑定时仍执行旧密码校验，然后直接更新中心密码并写审计记录。

### 4.3 普通账号与特权账号

- 修改普通凭据：使用设备绑定的旧特权凭据登录设备，修改普通账号；不能使用已经提交的新普通密码登录。
- 修改特权凭据：使用该特权账号的旧密码登录设备，修改特权账号本身；如果设备另有管理账号，应以显式绑定的管理凭据为登录凭据。
- 修改 Enable 密码：使用旧特权登录凭据建立会话，在设备端修改 Enable 密码；设备验证时单独校验 Enable 流程。
- 设备缺少必要的特权绑定、平台无改密适配或账号角色不匹配时，预检查阶段失败，不进入硬件变更阶段。

## 5. 实施方案

### 阶段一：任务与数据模型

复用现有 `jobs`、`job_targets`、`job_steps`、`job_events` 和审计机制，新增一个明确的任务类型，例如 `credential_password_sync`，并补充任务作用域中的：

- credential ID、修改角色、请求人、目标设备快照版本；
- 加密保存的待提交新密码快照；
- 加密保存的旧密码/特权登录快照或可安全解析的版本引用；
- 是否修改 Enable、改密策略、重试策略；
- 中心提交状态、回滚状态和最终一致性状态。

任务明细应以 `job_targets` 记录设备级状态，结果 JSON 只存脱敏信息：状态、错误分类、厂商/平台、耗时、尝试次数、是否回滚成功，不存密码和原始 CLI 输出。

建议状态：`queued`、`preflight`、`running`、`rolling_back`、`succeeded`、`partially_failed`、`failed`、`manual_intervention`、`cancelled`、`timeout`。

### 阶段二：统一并发与超时策略

新增专用配置，默认保守：

- `PASSWORD_SYNC_MAX_WORKERS=5`：单任务设备并发，避免继续使用固定 10。
- `PASSWORD_SYNC_MAX_GLOBAL_WORKERS=5`：改密任务在共享 SSH 限流器中的额外预算；不能突破 `NETWORK_SSH_GLOBAL_CONCURRENCY`。
- `PASSWORD_SYNC_DEVICE_TIMEOUT_SECONDS=240`：单设备从获取任务到验证结束的总预算。
- `PASSWORD_SYNC_CONNECT_TIMEOUT_SECONDS=20`：默认沿用 Driver 连接超时。
- `PASSWORD_SYNC_COMMAND_READ_TIMEOUT_SECONDS=60`：改密命令和保存命令使用专用上限，必要时按厂商覆盖。
- `PASSWORD_SYNC_RETRY_LIMIT=1`：只对可判定为临时网络/连接超时的失败重试。

实现要求：

1. 每个设备任务通过现有 `NetworkAccessLimiter.ssh()` 获取 SSH 槽位；获取槽位的等待时间不能无限叠加到设备总预算之外。
2. 单设备任务内部串行执行所有角色变更，禁止同一设备并行开多个改密连接。
3. 多个凭据改密任务共享同一任务执行器和全局限流器，不再由每次 API 调用独立创建线程池。
4. 连接失败/读取超时可按退避重试一次；认证失败、命令语法错误、平台不支持、权限不足不自动重试。
5. 达到设备总预算后标记 `timeout`，释放网络槽位并继续处理其他设备。

### 阶段三：预检查、改密与验证

预检查至少包括：

- 目标设备仍存在且未退役；
- 设备平台有对应改密命令处理器；
- 目标普通/特权/Enable 账号和旧密码快照完整；
- 使用旧特权凭据建立登录并识别到预期提示符；
- 必要时检查配置权限、Enable 权限和保存权限；
- 同一凭据没有运行中的任务，同一设备没有其他冲突改密任务。

设备执行建议采用“一台设备一个工作单元”：

1. 取得设备锁和 SSH 全局槽位。
2. 使用旧特权凭据建立连接。
3. 在同一会话中按厂商适配修改目标账号和/或 Enable 密码。
4. 保存配置并检查 CLI 输出中的明确错误模式。
5. 断开旧会话，用新密码重新建立连接验证；Enable 改密需要额外验证特权进入。
6. 成功后写入该设备的轮换状态；此时仍不提交中心凭据。

如果设备验证失败，优先使用旧特权凭据回滚已下发配置；回滚也失败时标记 `manual_intervention`，禁止中心提交新密码。

### 阶段四：中心提交与凭据轮换同步

- 所有目标设备验证成功：单事务更新 `credentials` 当前密码/Enable 密码、版本号、更新时间，并写入轮换记录。
- 无绑定设备：旧密码校验通过后直接提交中心密码。
- 部分失败：中心维持旧密码，任务标记 `partially_failed`；允许用户只重试失败设备。
- 回滚不完整：任务标记 `manual_intervention`，界面明确列出设备和建议处理动作，不允许自动把中心改成新密码。
- 凭据轮换页面读取同一个凭据中心版本和任务结果，不再把设备表的旧兼容字段当作最终权威。

### 阶段五：API 与前端

建议接口：

- `PATCH /api/credentials/{id}`：校验旧密码；若涉及硬件同步，返回 `202` 和 `job_id`，不返回“已完成”。
- `GET /api/jobs/{job_id}`：复用现有任务查询，返回总数、成功、失败、超时、回滚和当前阶段。
- `POST /api/jobs/{job_id}/cancel`：只取消尚未开始的目标；已在设备端执行的目标必须完成验证或进入回滚流程。
- `POST /api/jobs/{job_id}/retry`：只重试符合策略的失败目标，人工介入状态需显式确认后才能重试。

前端凭据中心：

- 编辑普通/特权/Enable 密码时分别显示旧密码和新密码输入框；旧密码错误不创建任务。
- 保存后进入任务详情或抽屉，展示阶段和逐设备结果，避免用户以为接口返回即已完成。
- 密码、CLI 原文和设备返回中的敏感片段全部脱敏；错误提示保留“认证失败/连接超时/命令不支持”等分类。
- 有运行中任务时禁用同一凭据的再次改密，并展示任务链接。

## 6. 测试计划

### 单元测试

- 旧密码正确/错误、缺少旧密码、只改元数据、只改 Enable 密码。
- 普通账号、特权账号、Enable 账号的角色解析和显式绑定。
- 预检查失败时不修改任何设备和中心凭据。
- 全部成功才提交中心；部分失败保持旧中心密码。
- 回滚成功、回滚失败分别进入正确状态。
- 认证失败不重试；连接超时最多重试一次。
- 单设备锁、全局 SSH 槽位和任务级并发上限生效。
- 重复提交同一凭据被拒绝或复用同一个幂等任务。
- 日志、任务结果和审计事件不含明文密码。

### 集成测试

- Cisco、Huawei、H3C、Linux 至少各覆盖一次改密、保存和新密码验证。
- 设备数量 1、5、20、100 的任务排队、进度和超时表现。
- 多个凭据任务并发时不突破全局 SSH 上限。
- 进程重启后，已完成/运行中/排队任务可恢复或明确标记为待恢复，不出现中心先变而设备未知的状态。
- 与配置备份、巡检、自动化同时运行时验证资源争抢和错误提示。

测试必须使用模拟设备和隔离数据库，不连接真实设备、不修改生产凭据。若出现既有 fixture 或环境问题，需单独标注为基线问题，不降低断言强度。

## 7. 交付拆分与验收标准

建议按以下顺序实施：

1. 任务模型、幂等锁、设备级结果和审计事件。
2. 旧密码服务端校验及凭据中心 `202 + job_id` 契约。
3. 设备快照、预检查、共享限流、超时和分类重试。
4. 厂商改密会话复用、设备端新密码验证和回滚。
5. 中心凭据最终提交、轮换页面状态同步、前端任务详情。
6. 全量测试和用户手册/运维手册更新。

验收必须同时满足：

- 任意一台设备未验证成功时，中心不会提前显示新密码。
- 100 台设备不会创建 100 个同时执行的 SSH 连接；并发受任务上限、全局上限和单设备锁共同约束。
- 用户能看到每台设备的成功、失败、超时、重试和回滚结果。
- 网络抖动可以有限重试，认证和命令错误不会盲目重试。
- 任务取消、进程重启和部分失败不会破坏凭据中心与设备的可解释性。

## 8. 本次检查范围与未执行事项

本次只完成代码和配置核查并输出实施计划，未修改后端、前端或数据库，未启动真实设备改密任务，也未运行全量测试。进入实现阶段后，应先以模拟设备完成上述单元测试，再在少量测试设备上做分批验证，最后开放大规模任务。
