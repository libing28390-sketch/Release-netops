# 工作区代码推送与 Actions 验收

## 目标

将当前 `main` 工作区中已经实现的业务代码、测试和正式项目文档一次性提交并推送到 `origin/main`；以该提交对应的 GitHub Actions 成功作为交付条件，之后按用户要求关闭电脑。

## 现状与范围

- 当前分支为 `main`，本地 HEAD 与缓存的 `origin/main` 相同；推送前仍需成功读取最新远端引用。
- 工作区包含工单与变更流程、巡检与自动化页面、设备 SNMP 开关等已实现改动，以及对应测试和 `docs/plans` / `docs/walkthrough` 文档。
- 不提交 `.agents/`、`.codex*`、`handoff.md`、日志以及 `dist*` / `.codex-build-validation*` 生成目录。
- `.github/workflows/release.yml` 在 `main` push 时会运行完整 Linux / Docker 校验，并同步经过净化的发布树到 `Release-netops` 仓库；不创建版本标签。

## 实施步骤

1. 获取 `origin/main` 最新提交并确认本地 `main` 可快进推送；网络失败时先排查连接，不覆盖远端历史。
2. 复核源代码、迁移、测试、正式文档和生成目录边界，创建本次提交的 `docs/fixes/fix_*.md`。
3. 运行适用的 PostgreSQL、前端和仓库质量门禁，检查暂存区差异与敏感数据。
4. 在 `main` 创建单个可审查提交，正常快进推送到 `origin/main`。
5. 跟踪该提交触发的 GitHub Actions；若失败，读取具体 job/log，修复后继续提交、推送并等待新的 Actions 成功。
6. 确认成功后执行 Windows 关机。

## 验收标准

- 远端 `main` 指向本次提交且推送没有 force 更新。
- 本次提交的所有必需 Actions 运行均为成功，Release 仓库同步步骤也通过。
- 只有在 Actions 全部成功后才执行关机；失败或结果不确定时保持电脑运行并继续排查。

## 风险与回滚

- 工作区累积了多个已授权功能任务的未提交代码；只排除内部协作材料和生成物，不撤销或覆盖业务改动。
- 远端更新导致非快进时不使用 force push；先检查两侧提交图并把远端变更合入 `main`。
- Actions 失败时保留失败日志与提交，修复后追加提交，不重写远端历史。
