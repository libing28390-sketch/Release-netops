# 重复导入触发整机 SN 采集

## 目标与现状
用户使用 H3C HCL 模拟器再次导入后，资产的序列号仍为空。固定 OID `.1.3.6.1.2.1.47.1.1.1.1.11.2` 已由用户从设备侧验证可返回 SN。重复资产原先未进入 SN 队列；修复后检查本机 PostgreSQL 又发现 schema_migrations 已记录 302/303，但 `physical_assets.chassis_observed_at` 缺失，机箱持久化会失败。

## 影响范围
修复资产导入重复资产路径。精确匹配到既有网络设备的管理 IP、SNMP 端口和现有/显式相同 SNMP Profile 时，复用数据库中已有 SNMP 配置读取 H3C 机箱 SN。重复行仍按原规则跳过，不改资产身份、型号、管理配置或平台绑定。

## 拟修改文件
- `backend/api/assets.py`：为安全匹配的重复行加入 SN-only 后台任务，在两处队列筛选中保留该任务，按设备去重，并返回序列号同步状态。
- `backend/services/snmp_import_identification_service.py`：增加只同步机箱 SN 的入口，避免对已有资产重复执行可能修改身份字段的完整识别；管理 IP 读取使用导入项作为回退。
- `backend/database/migrations/m0304_asset_chassis_observed_at.py`：为已应用旧版 302 的数据库补齐采集 watermark 列。
- `src/pages/AssetManagement/index.tsx`：在导入反馈中明确显示重复设备整机 SN 正在后台采集。
- `docs/walkthrough/walkthrough_20261030_1531_01_重复导入触发整机SN采集.md`：记录实现、验证与边界。

## 实施步骤
1. 确认重复资产时旧资产 IP、端口和 SNMP 凭据；若导入行未指定凭据，则沿用旧资产当前 Profile，若显式指定则要求与旧 Profile 相同。
2. 仅把该任务标为“SN-only refresh”，使用既有设备厂商信息采集 H3C 固定索引，不触发 hostname/model/platform 自动写回。
3. 新增 304 向前迁移，修复本地数据库已记录 302 但缺少 watermark 列的历史状态，并确认迁移后 schema 到位。
4. 修正队列筛选、同设备去重和逐行 `serial_sync` 反馈，保留旧资产其余数据不变。
5. 检查静态语法、前端 lint/build 和 schema 状态；遵照本轮执行约束，不运行自动化测试、不从助手端发起 SNMP 采集、不部署。

## 验证计划
- 检查 `git diff --check`。
- 对后端改动运行 Python 编译检查。
- 如前端文件有变更，运行前端 lint/build。
- HCL/真实设备采集结果需由用户在其部署环境重新导入后确认；本地源码验证不等于设备或部署验证。

## 风险与回滚
SN-only 任务只会向已存在资产同步机箱实体和 SN，不运行重复资产导入或身份自动绑定；若目标 IP/端口不匹配或显式 Profile 不一致，则跳过 SN 刷新。回滚可移除重复分支任务入队和 SN-only helper，之前已有资产与迁移数据不需要回滚。
