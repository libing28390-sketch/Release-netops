## 实施步骤

1. 完整读取并视觉核对 PDF 任务书，记录 Git 基线和用户现有修改。
2. 阅读项目规范、Skills、构建与测试配置，扫描前后端、数据库、网络驱动、部署和文档结构。
3. 读取 8 份专题 Markdown 文档，逐条映射到当前代码、路由、API、表结构和历史实现。
4. 建立 `PROJECT_ANALYSIS.md`、`TASK_REMEDIATION.md` 与 `EXECUTION_LOG.md`，每个任务写明位置、根因、优先级、方案、验证方式和状态。
5. 按 P0 → P1 → P2 → P3 的顺序完成可执行代码整改；每组任务补充回归测试并同步任务状态与执行日志。
6. 从真实菜单、路由、API、权限和模型识别 11 个功能模块及全部子菜单，创建模块 README、功能介绍与使用手册。
7. 启动可运行环境，使用授权测试账号完成登录、菜单、查询、表单、空态、错误态、权限、网络请求和控制台检查；截图前检查并脱敏。
8. 执行后端测试、前端类型检查与构建、API 测试、Docker Compose 配置检查及可安全执行的网络能力模拟测试。
9. 校验 Markdown 路径、相对链接、截图、模块数量和文档引用，生成 `TEST_REPORT.md` 与最终走查文档。

## 验证计划

- 后端：先运行受影响测试，再执行 `pytest backend/tests`；按项目支持情况执行 Python 编译检查。
- 前端：执行 `npm run lint`、`npm run build`。
- API：验证登录、未认证、权限不足、成功、参数错误、空数据、重复提交和依赖失败路径。
- 浏览器：验证登录、11 个模块入口、各子菜单主页面、关键表单、搜索/筛选、空态、错误反馈、分页、控制台和网络错误。
- 网络自动化：优先使用 mock/fixture，覆盖 Cisco、Huawei、H3C 的厂商-平台-驱动-命令契约，不进行未授权配置下发。
- 数据库：验证迁移幂等性、fresh schema、受影响 CRUD 和 PostgreSQL 语义；不删除或覆盖用户数据库。
- 部署：执行 `docker compose config`；若本机 Docker 可用且不会影响现有环境，再执行构建/健康检查，否则明确记录限制。
- 文档：检查引用文件存在性、Markdown 相对链接、11 个模块目录和每个真实子菜单的两类文档。

## 风险与回滚思路

- 用户已有未提交部署修改：通过逐文件 diff、初始基线记录和排除重叠文件保护；任何重叠修改先以用户内容为准。
- 数据库与真实设备：不执行数据删除、重置、批量改写或设备配置命令；迁移采用幂等、向前兼容方案，设备测试默认只读。
- 凭据泄露：测试密码仅在进程级安全变量或浏览器输入中使用，不写入源码、文档、截图、日志、提交或 `.env.example`。
- 大范围文档与截图易失配：所有结论从当前路由/API/模型反查，截图来自实际页面并在交付前校验相对链接。
- 本任务不创建提交，所有变更必须通过 `git diff` 与 `EXECUTION_LOG.md` 保持可追踪；数据库变更需在迁移说明中记录兼容与恢复步骤。
