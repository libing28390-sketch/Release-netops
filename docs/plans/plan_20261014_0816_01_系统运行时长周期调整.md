# 系统运行时长采集周期调整

## 目标

将通用基础计划中 sysUpTime 的周期从 900 秒改为用户建议的 300 秒（5 分钟），同时用新迁移更新已有数据库中的内置 baseline 计划。保留用户自定义计划间隔和接口、硬件采样周期。

## 现状

- 默认计划 `plan-generic-ifmib` 中 `generic_system_std` 为 900s、timeout 30s。
- 线上 system 目标实际周期也是 900s。
- 硬件采样默认 60s；硬件发现负责列出可采的传感器，默认每设备 24 小时刷新清单。这两者是内部阶段，普通用户无需手动编排。
- 本工作只调整 system 指标周期；不调整网络接口、硬件、无线、Grafana 刷新或配置同步周期。

## 拟修改文件

- backend/database/migrations/m0287_uptime_system_poll_every_5m.py：仅修改内置 baseline 里仍为旧默认 900s 的 system 项。
- backend/services/metric_provider.py：把 sysUpTime 注释中的默认周期改为 5 分钟；保留 20 分钟查询回看窗口以容纳漏采。
- 新建本计划与配套走查文档。

## 实施与迁移

1. 新增幂等数据迁移：定位内置 `plan-generic-ifmib` 中的 `generic_system_std` 项，且仅当间隔精确为 `900s` 时改为 `300s`。
2. 不改接口间隔、硬件发现和硬件采样设置，不覆盖其他计划或用户自定义系统周期。
3. 下次部署启动时迁移更新基线；启动自动同步/发布会重新生成活动目标配置，不需要手动点编译、发布。
4. 静态检查 SQL/JSON 条件、变更差异与兼容路径。

## 验证计划

- 静态检查迁移只匹配 baseline 的目标 variant 和旧值，并可重复执行。
- 依据工作区约束，本次不运行测试、构建或部署。

## 风险与回滚

系统 SNMP 查询从每 15 分钟改成每 5 分钟，基础系统指标请求约增至原来的 3 倍；接口和硬件轮询负载不变。仅迁移内置 baseline 中仍保留 900s 的配置，不碰其他计划。若部署后负载不合适，可将 baseline 的此项调回 900s 并重新自动同步。
