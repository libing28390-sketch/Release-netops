# 修复容器启动覆盖监控目标与启动自同步实施计划

## 1. 任务背景与现状
- **问题现象**：
  1. 用户在宿主机上查看 `/app/artifacts/monitoring/runtime/vmagent/targets/linux_targets.yml`，发现内容为空的 `[]`，vmagent 未抓取 `192.168.18.139:9100`，导致 Grafana Linux 监控仪表盘无实时数据。
  2. 下拉框中显示的历史 IP `192.168.204.128` 是由于时序库中曾留存过其指标，但当前已被清空。
- **根因分析**：
  1. 在 `scripts/sync-frontend-dist.sh` 脚本的 `else` 分支中，容器每次启动都会无条件执行：
     `cp -f "$MONITORING_DEFAULTS/vmagent/targets/linux_targets.yml" "$MONITORING_RUNTIME/vmagent/targets/linux_targets.yml"`
     将代码仓库中的默认空列表 `[]` 强行覆盖用户已发布的动态目标配置！
  2. 在 `backend/main.py` 中，采集器自动同步 `monitoring_collector_auto_sync` 仅注册了 5 分钟执行一次的定时器，在服务启动初期（5分钟内）不会主动触发编译发布，导致 targets 一直停留在被覆盖的空状态。

## 2. 拟修改范围与文件
- `scripts/sync-frontend-dist.sh`：仅当目标文件不存在时才从 defaults 初始化，禁止覆盖已有的 targets 文件。
- `backend/main.py`：在启动时调度器就绪后，立即触发一次 debounced 异步同步（`trigger_async_monitoring_sync`），启动即就绪。

## 3. 实施步骤
1. 修改 `scripts/sync-frontend-dist.sh`。
2. 修改 `backend/main.py` 增加启动后即时同步触发。
3. 运行本地自动化测试验证。
4. 编写走查文档与修复记录，提交并推送到远端 `main` 分支。

## 4. 验证计划
- 运行 pytest 确保启动和监控相关测试通过。
