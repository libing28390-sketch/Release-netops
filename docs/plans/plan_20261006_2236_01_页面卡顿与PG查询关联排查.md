# 页面卡顿与 PG 查询关联排查

## 任务目标

接续 `handoff.md` 最新授权，核实后端回归，追踪监控看板请求和 PostgreSQL 查询，将后端 live 延迟与实际 SQL 活动、等待和表扫描放在同一时间轴上；修复经证据确认的问题，推送并部署后再次重复采样。保持后端 `WORKERS=1`，不修改真实网络设备，也不通过未认证生产 API 写资产数据。

## 现状与问题

- 真实 Linux Docker 旧代码复现卡顿时，直连 live 出现 1.93 秒及 5 秒超时；同窗有 MIB 和 raw 表扫描增量。
- 现有证据只有低频活动快照、累计计数增量，没有业务查询执行计划或逐秒关联，不能把扫描量等同于 SQL 耗时。
- `pg_stat_statements` 未启用。本轮不安装扩展、重启数据库或重置统计。
- 本地阻塞隔离及连接复用补丁尚未部署。完整后端 pytest 已结束，结果为 3362 passed、10 failed、1 skipped、26 subtests passed，exit code 1。失败详情和一个已修复的资产凭据绑定问题记录于 walkthrough；完整套件快照早于晚加入补丁。
- 本机 Windows 无 Docker；用户先授权 SSH 只读检查/采样，随后明确授权在 Docker 部署主机自主备份、修改、部署和验证；凭据只通过交互终端使用，没有保存到文件或输出。
- 用户确认触发操作为打开/刷新监控看板，并补充资产添加和修改也卡顿；最新更正为“还包括”，没有实际报错证据。需一并追踪资产表单加载、创建/更新及共享鉴权/连接池。
- 用户随后确认表单打开和保存都慢，Grafana 有时也慢，并提出设备数与频繁 SNMP 采集的负载疑问。
- 用户追加要求可将远端只读采样延长到约 5 分钟，并多轮调用页面相关 URL/API。本次采集脚本已按前端真实调用链增加重复 GET 探测：资产表单/列表 API 的后端直连与 Nginx 路由，以及 UI 展示的全部 Grafana dashboard URL。
- 用户明确授权 `root@192.168.204.128` 只读 SSH 排查。SSH 严格使用既有 known_hosts，诊断数据库连接强制只读、查询超时两秒；没有安装扩展、reset 统计、写数据库、改容器或操作设备。

## 本轮结果和未完成事项

- 两轮300秒远端采样反复观察到约110秒一次的后端/API同步停顿簇；轻量 live 最长约6秒。Grafana/VictoriaMetrics health 保持快速。
- 每轮 `snmp_mib_nodes` 统计增加42次 seq scan、约283.97万行读取；1秒 PG activity 最长 active 查询年龄约0.34/0.41秒、无锁等待。传感器聚合计数为5,296个 active sensor/15台设备，17台总设备中15台有 SNMP binding；native 与 VM assignment 的设备重叠未知。
- 首要疑点是 native SNMP 自动硬件发现/LibreNMS MIB 解析路径中的同步 MIB SQL 与周期性应用停顿有关；统计数据没有 SQL 单次耗时或请求 ID 关联，远端 probe/discovery 源文件也未包含在指纹名单，因此不能把相关性提升为根因结论。
- 诊断 helper 修正后为13 passed；凭据批量读取与资产 SNMP 绑定组合测试为9 passed。用户登录态浏览器复现、认证后 API/Grafana耗时、event-loop lag 与连接池等待尚未采集。工作区改动全部未部署。

## 风险与回滚

只读采样仍会增加少量查询和 HTTP 开销，需限制持续时间、采样频率、输出大小及连接数；活动快照可能漏掉短查询，不能反推未捕获的查询均快。读计划与 ANALYZE 分开；后者会实际执行查询，必须仅限固定 SELECT、只读事务及超时。删除本轮新增采集工具即可回滚，不改变服务配置、业务数据或用户原有变更。
