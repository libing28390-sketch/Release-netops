# H3C 硬件监控无数据排查

## 任务目标

排查 F1090-9 在 SNMP 硬件诊断页有传感器读数、但 Grafana「02 网络设备详情」无硬件数据的原因；修复已确认的采集发现触发缺口，不增加 H3C 隐藏规则。

## 现状与证据

- SNMP 诊断对 F1090-9 返回 LibreNMS Comware 规则结果及多个硬件类别；该诊断接口只返回实时探测结果，不写硬件传感器库存。
- 线上设备清单显示 F1090-9 在线、健康、SSH；后台 B-Loop 的在线状态门槛不是该设备当前的阻断点。
- Grafana `network_snmp` 中 F1090-9 的 `up` 为 1；硬件库存 exporter 的 scrape `up` 也为 1，但查询不到该设备的硬件传感器/能力序列。
- `/hardware-metrics` 从 `snmp_hardware_sensors` 与 `snmp_hardware_capabilities` 持久化表导出数据。
- 后台原先只在通用 SNMP 身份发现记录过期（6 小时）或不存在时重探测，没有检查硬件能力库存；较新的旧身份记录可能因此挡住首次硬件发现。
- 线上只读 SQL 已确认：F1090-9 的通用发现记录为 `matched`，设备与发现快照的 vendor/platform/model/version 完全一致，发现记录年龄为 1 小时 47 分钟；硬件发现 runs、capabilities、sensors 均为 0。结合后台 6 小时身份发现 freshness gate，可确认硬件发现没有被触发，因而没有进入持久化流程。
- 同一数据库的厂商对照显示 Cisco 有 6 台设备、30 条可导出且质量为 good 的传感器，H3C 为 0；问题并非所有厂商共同无数据。

## 影响范围

- 仅调整后台设备轮询是否需要补跑 SNMP 硬件发现的判定。
- 不按 H3C 厂商隐藏硬件信息，不修改仪表盘查询语义、SNMP 凭据、设备配置或实时 Grafana。

## 拟修改文件

- `backend/services/background_monitor_service.py`：当通用发现记录仍新鲜、但硬件能力记录不存在或版本过旧时，触发一次硬件发现并沿现有路径持久化。
- `backend/tests/monitoring/test_background_monitor_hardware_discovery.py`：覆盖硬件能力缺失、版本过旧与当前版本三种判定。
- `backend/tests/monitoring/test_background_monitor_device_label.py`：隔离既有在线设备监控测试，避免依赖新增的能力库存判定。
- 本计划及对应 walkthrough。

## 实施步骤

1. 核对诊断接口、后台发现与 Grafana 硬件指标导出的数据流。
2. 在后台轮询中同时判断硬件能力记录是否缺失或版本过期。
3. 复核只读浏览器证据和代码静态完整性；不部署到实时环境。

## 验证计划

- 检查改动 diff，确认无 H3C 隐藏条件或其他 dashboard 规则。
- 运行硬件发现判定及在线设备监控的定向 pytest。
- 用 Python AST 解析修改文件，并运行 PostgreSQL-only 策略扫描与 `git diff --check`。
- 浏览器侧现有证据仅用于证明线上当前症状；本地变更未部署，不能据此声称线上问题已修复。

## 风险与回滚思路

- 硬件能力表缺失或版本不符时会多触发一次 SNMP 探测；成功持久化后现有轮询路径将继续负责传感器采样。
- 如需回滚，仅撤销本次后台硬件发现新鲜度判定，保留其他既有工作区改动。
