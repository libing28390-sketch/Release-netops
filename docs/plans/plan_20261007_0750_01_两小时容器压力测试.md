# Nexora 两小时容器压力测试计划

## 目标

在用户指定的 Docker 部署主机 `192.168.204.128` 上进行不少于7,200秒的生产只读性能观测，并用隔离预检判断是否适合进行综合前后端压力测试；覆盖 NetOps API、Nginx、PostgreSQL、Redis、SNMP exporter、VictoriaMetrics、vmagent、Grafana、SeaweedFS、cAdvisor 和 Docker socket proxy。形成可复核报告，区分生产现象与合成预检结果。

## 现状与证据

- 远端 `/data/nexora-automation` 当前 Git HEAD 为 `ea1b192`；11个 Compose 容器均运行，9个声明 healthcheck 的容器 healthy。
- 压测前主机 `MemAvailable` 约5.3 GiB、swap空闲2 GiB；`/data` 所在卷约18 GiB可用、已用82%。主要容器当时内存：NetOps约360 MiB、PostgreSQL约274 MiB、VictoriaMetrics约174 MiB、SeaweedFS约142 MiB；未见异常高占用。
- 本机仓库容量测试工具版本为1.1.4。容量模式创建带唯一标签的隔离容器/网络/卷，不复制生产数据或凭据，使用合成数据库、缓存、时序、对象和内部模拟 SNMP；与生产共用宿主机 CPU、内存和磁盘。
- 工具默认保护线为主机可用内存10%/256 MiB、测试容器达到95%内存、测试容器 OOM/异常退出；单阶段失败会阻止更高档继续。计划将内存保护线收紧到主机可用30%、测试容器配额85%，另对 `/data` 可用空间及生产容器健康做外部监控。
- 生产观测 helper 每次最多600秒，提供只读 PG 活动/API/资源采样；会分成12个连续600秒周期覆盖两小时。它不登录、不修改业务数据，其保护路由只测未认证入口；已认证页面通过浏览器手工检查，不把鉴权门耗时当成业务查询结果。
- 预检调整：首次全场景启动因工具默认5秒登录超时而在 warmup 中止；随后单场景预检发现原工具为合成资产分配的198.18.*地址会被应用 A-Loop 当作真实目标轮询。已修正本地工具数据生成：API 合成资产不带管理 IP，SNMP 仍由独立模拟场景覆盖；默认超时提高为15秒。300条合成资产的5 RPS单场景预检通过，p95为216.6ms、150/150成功、无丢弃。
- 全场景5 RPS/场景预热（约55操作/秒）未达到阈值：测试 NetOps/Grafana/VictoriaMetrics p95约5.75/10.60/25.12秒并有排队丢弃。主机可用内存最低4.15 GiB，生产容器未重启/OOM，外部 API 保护探测未连续失败；因此将正式压力降至1和2 RPS/场景（总计约11和22操作/秒），仍各持续1小时。
- 全场景1/2 RPS/场景短预检仍未通过：warmup 阶段 Redis 场景出现5次 `redis_command_failed`，VictoriaMetrics p95约12秒且有10个排程丢弃，Grafana/NetOps p95约4.0/3.3秒；报告已记录并确认隔离栈清理完成。该结果只说明当前合成全场景负载配置无法稳定预热，不代表生产同等负载或生产 PG 慢查询。
- 生产端新增直接证据：17台设备、15台有 SNMP 绑定、5296条活动硬件传感器记录；`platform_hardware_inventory` 每60秒抓取 `/hardware-metrics`。过去30分钟该路由30次均返回200，中位耗时1.88秒、p95 4.48秒、最大5.58秒，耗时几乎全部落在 handler。源码查询返回约5296行并执行全表扫描/排序，再由 Python 解码 JSON 字段、逐设备渲染 Prometheus 文本和能力指标；表共约5322行/24 MiB。主机上的总线性扫描量不大，但该导出路径是当前确认的直接慢点，可能占用 API 处理资源并拖慢监控刷新。

- Chrome 中已打开资产列表、新增表单和编辑表单；当前17条资产能呈现，表单读取完成。未提交新增或修改；保存慢和保存报错仍未在生产做写操作验证。生产采集器对资产/Grafana API 的未认证探测返回401，只能作为鉴权门采样，不能当作真实页面请求耗时。
- 后续按用户要求启动了两次隔离 Nginx/API 长测，均触发宿主机负载保护线，未得到完整阶段报告。首次 run `2899675dee4a` 的预热和最终检查通过，1 RPS 阶段运行约14分钟；宿主机 `load1` 连续三次为3.75、4.28、5.07，且同一时段 Ubuntu `apt-daily` / `unattended-upgrade --download-only` 占用约82.8% CPU。更新任务退出后的 retry run `82d7e162c7b9` 在隔离栈初始化/预检时 `load1` 连续三次为4.85、5.34、4.29，未进入计时压力档。两份报告状态均为 `aborted`，cleanup 均完成；按 run-id 检查没有残留测试容器、网络或卷。生产容器未重启/OOM，内置 live 探针仍返回200。远端报告分别在 `/tmp/nexora-soak-20261007-0056/two-hour/report/` 与 `/tmp/nexora-soak-20261007-0056/retry-after-update/report/`。

## 影响范围与安全边界

- 压测目标为部署主机上的隔离测试栈；只对测试数据库/Redis/时序数据/对象桶进行合成写入。不得向生产数据库、资产 API、真实 SNMP 设备或设备配置发写请求。
- 浏览器仅使用用户明确提供的 NetOps 登录信息查看监控/资产页面和打开/关闭资产表单，不保存资产、不点击提交、不创建 Grafana session 或触发设备操作。
- 保留远端已有未跟踪 `docker-diagnostics-*`、`netops-cpu-*` 和 `scripts/nexora-docker-capacity-test*`；不执行 `git clean`、`docker system prune`、`docker compose down`、源容器重建或容器资源修改。
- 输出写到带唯一 run id 的 `/tmp/nexora-capacity-*` 和 `/tmp/nexora-soak-20261007-*`；记录副本下载到本机 `%TEMP%\nexora-soak-20261007`。完成后只清理本轮压测工具按唯一 label 管理的容器和卷；原始采样保留。

## 风险与停止/回滚

测试写入均局限于本次创建的隔离测试服务和卷，工具按完整随机 run id 标签回收。测试与生产共用主机资源，可能造成性能影响；资源阈值提前收紧，外部监控发现服务异常即发 SIGINT，让工具进入标签限定清理。不得通过重启/重建生产服务、删除未归属文件或 Docker prune 处理测试故障。若中断或测试时长不足两小时，报告记录实际负载秒数及停止原因，不将未完成测试表述为通过。
