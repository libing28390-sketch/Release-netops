# 资产投产上收约束与桌面样式生效计划

## 任务目标

- 确认并解决桌面端浅色危险按钮样式未生效问题。
- 保证网络设备和服务器只有在口令上收成功后才能进入“已投产”状态。
- 阻止缺少关联设备记录、凭据或连通性验证的存量资产绕过上收流程。

## 现状问题

- 当前托盘进程早于样式文件修改时间启动，双击 `NetOps.exe` 只唤醒已有进程，不会重新加载 QSS。
- 后端在异步口令上收开始前已写入 `production`，页面会提前显示“已投产”。
- 网络设备或服务器缺少关联 `devices` 记录时，单资产更新没有明确阻止投产。
- 批量上收成功后只更新托管标记，没有在成功点显式写入投产状态。

## 影响范围与拟修改文件

- `desktop/desktop_tray.py`
- `backend/api/assets.py`
- `src/pages/AssetManagement/index.tsx`
- `backend/tests/test_asset_production_takeover.py`
- `.gitignore`
- 对应 plan 与 walkthrough 文档

## 实施步骤

1. 核对运行中托盘进程的启动时间、脚本路径和源码修改时间，确认样式是否为旧进程缓存。
2. 投产请求先完成关联设备、上手状态和凭据预检，缺失关联设备时返回 422。
3. 异步上收期间保持原生命周期状态，只设置 `rotation_status=rotating`。
4. 单台或批量上收全部成功后，原子更新设备与物理资产为 `production`。
5. 上收失败时保持原生命周期并记录失败原因。
6. 前端将反馈文案调整为“上收成功后自动投产”，避免暗示提交后已立即投产。
7. 终止旧托盘进程并由当前源码重新启动，验证最新浅色 QSS 实际加载。

## 验证计划

- 新增回归测试：缺少关联设备不能投产；上收线程启动前生命周期仍为待投产；成功回调才写入已投产。
- 运行定向 pytest 与完整 `backend/tests`。
- 运行 `npm run lint` 和 `npm run build`。
- 运行桌面脚本语法检查并核对新托盘进程启动时间晚于源码修改时间。

## 风险与回滚

- 上收是异步网络操作，失败时不得留下短暂或永久的“已投产”假状态。
- 不对真实设备执行口令变更测试，使用 mock 验证状态机。
- 如新约束影响非网络类资产，只对 `network_device` 和 `server` 强制执行，其他资产保持现有生命周期编辑能力。
