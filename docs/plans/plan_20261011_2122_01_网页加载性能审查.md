## 任务目标与授权范围

对照用户粘贴的《Nexora 性能优化建议》，先审查代码并记录证据，再实施计划中已确认且边界清晰的性能改进。用户已明确授权：实现相关代码、审查并纳入工作区其他代码改动、提交到 `main`、推送并确认 GitHub Actions 成功；如 Actions 成功则关闭本机。用户提供本地测试账号用于登录验证，凭据仅限本地浏览器会话，严禁写入源码、测试日志、计划或修复记录。生产部署、真实设备变更不在授权范围内。

## 现状与问题

审查依据：用户在本聊天粘贴的完整建议，以及当前工作树源码与一次独立生产构建。用户已实施分页、按需读取和数据库索引；工作树存在大量用户未提交修改，全部保留。以下“已确认”指代码行为或构建依赖已确认，不表示已测出生产耗时或确定其为唯一卡顿根因。

### F1：首屏仍静态依赖 WebGL 与导入导出库（P1，构建已确认）

触发：任何首次打开，包括已登录后直接打开资产页；是否渲染 3D 不影响静态依赖下载/解析。

- [vite.config.ts](D:/netops/netsops-main/vite.config.ts:61) 的 manualChunks 没能保持 WebGL 的懒加载边界。构建入口实际从 react-three-vendor 导入共享 store 创建函数与 modulepreload helper，进一步引入 WebGL 依赖。

本次构建 manifest 的入口静态依赖闭包有 8 个 JS，合计 **2,354,953 bytes（约 2.35 MB），gzip 合计 692,045 bytes**。其中 three、react-three、webgl-addons、export 四块合计 1,430,334 bytes，gzip 417,578 bytes，约占初始 JS 的 61%。charts-vendor 位于动态依赖中，不能误报图表库必然随入口下载。gzip 为本地 zlib 估算，实际传输以响应头与 Network 为准；这些字节数也不是页面加载时间。

拟处理：让登录表单先可用，再加载背景动画；导入/导出库在操作时加载；调整共享 helper/store 与 WebGL 的分包归属。仅拆文件或给 chunk 命名不算完成，必须检查入口静态依赖闭包。动画保留加载失败/弱设备降级。登录动画逐帧计算的耗时另外用 Performance 验证，不凭粒子数量认定它造成输入卡顿。

### F5：主机资源 GET 随每个浏览器重复采样、写库和清理（P1，代码已确认）

## 实施结果与验收范围

本轮已完成可由代码与构建结果直接验证的改进，未把建议中的候选指标当成实测结果。没有采集 HAR、Chrome Performance trace、React Profiler、连续 API P95 或生产 `pg_stat_statements` 样本，因此尚不能声明网页已达到 1.5 秒首屏、API P95 目标或 INP 200ms。

### A + B：入口依赖与请求治理（已实施）

- 登录背景、表格导入/导出和拓扑 PNG 导出改为操作时加载；修正 Vite 手工 3D vendor 分组导致 WebGL 依赖进入入口 preload 的问题。
- 独立候选构建 manifest 的入口静态依赖闭包从 2,354,956 bytes / gzip 691,641 bytes 降至 920,886 bytes / gzip 273,128 bytes，分别减少约 60.9% / 60.5%。这比较的是同一工作区修正前后的构建产物，不是与远端 `main` 的对比，也不能代替真实下载、解析或渲染时间。
- shared lookups 按当前路由消费者加载，在同一登录身份范围复用短期完成结果并合并在途请求；用户列表只有独立认证请求来源。认证主体变化会清除旧作用域缓存。Dashboard 热任务刷新限制在 Dashboard 生命周期。
- 前端全量测试和登录、资产、拓扑页面的本地交互检查用于确认主要行为；没有录制冷/热缓存下的页面耗时。

### C：监控概览与资源读取（已实施）

- overview 的接口遥测改为每批最多 250 台设备，并按访问范围对同一在途计算做 single-flight。
- health/resource GET 使用既有调度任务写入的最近样本；GET 不再主动采样或写历史。缺少样本、只读历史和响应边界有 PostgreSQL 测试覆盖。
- 这些改动减少重复数据库/遥测工作，但本轮没有基于 100/500/1000 台设备压测，也没有算出生产路由 P95 或连接池等待分布。

### D：拓扑概览（已实施，范围有限）

- 默认全站物理视图加载站点和 links 概览，暂缓 `/api/topology/graph`；选择站点或切换非物理关系视图后再加载设备级图。保留显式全图路径和手动刷新。
- 本地拓扑页成功加载 210 个节点；该本地数据当时返回 0 条 links，因此不能据此验证跨站、LLDP 或 LAG 连边的完整性。相关前端契约测试覆盖默认不请求 graph 与选择站点后加载。

### E：Grafana 时间范围与 Nginx 上游连接（已实施，部署验证未执行）

- Grafana iframe 初次挂载不再覆盖 dashboard 自带默认时间范围；用户手动选择时间范围后仍传递所选范围。`Grafana unavailable` 是本地验证时的实际状态，Grafana 实例未运行，故未验证 iframe 查询、面板采样或慢查询。
- 普通 `/api/` Nginx 代理补充 `Connection` 清空以便使用已配置的 upstream keepalive；未改动 WebSocket、SSE 或 Grafana 认证代理。本机没有可用 Docker/Nginx 容器，因此未运行目标镜像 `nginx -t` 或连接复用测试。

### 有条件后续项（本轮未实施）

Redis 汇总缓存、前端 RUM/P95/长任务指标、React Profiler 指向的组件重渲染治理、虚拟表格、Grafana 点数/step 调优、pg_trgm/游标分页，以及按需设备诊断 async 路径里的同步 I/O 均需要各自的运行数据或独立范围；没有把它们当作已确认的页面卡顿根因。

## 风险与回滚

新增代码按模块回退，不覆盖用户已有分页/索引实现。提交前审查完整 diff 并纳入工作区其他代码改动；排除本地构建目录、dist 诊断副本、日志/运行数据、环境凭据和内部协作材料。回滚采用针对本次提交的 revert，不重置或清理工作树。

- A/B：动态库失败提供重试；延迟背景不影响登录；缓存禁用时可回到即时请求。写后失效、注销/换账号、权限变更必须先验证，不能展示另一作用域数据。
- C：批量 SQL 回滚到原查询时保持响应口径；缓存可禁用，Redis 不可用需受控回源；对资源快照回滚时恢复原采样入口与既有任务，避免双任务和告警重复。
- D：保留完整图接口/入口，摘要协议增量引入；筛选与跨站边不得静默遗漏；失败时显示错误与重试，不把不完整图当成功。
- E：只改目标 Nginx location；回滚对应配置并重新验证 WebSocket/SSE。时序分辨率调整不得损失故障峰值或改变速率/统计口径。异步诊断卸载保持连接、事务和 credential lookup 边界。
- 不因累计事务回滚数、缺虚拟表格或未显式 maxDataPoints 就直接归因；不直接增加 Worker、缓存所有 API、统一虚拟化所有表格或改全部 PromQL。所有性能收益由同一环境前后对比确认。
