# 任务目标

修正 `/automation/quick-ops` 结构化结果中的解析器来源展示：当设备有版本证据并命中对应 TextFSM 模板时，显示具体版本模板文件名，不再显示会误导用户的 `NTC Templates（旧目录）`。

# 现状/问题

- 截图中的 H3C S6850-1 为 Comware `7.1.070`，但设备尚未绑定平台 Profile，走 `collect_operational_data()` 的 legacy 兼容分支。
- 该分支实际调用 `_parse_command_output()` → `smart_parse_cli()`，却把 category 的 `parser` 硬编码为 `ntc-templates`，丢弃了 `template`、`template_source` 和版本化 parser platform。
- 前端因此把任意 legacy 结果渲染成 `NTC Templates（旧目录）`，无法区分已命中的 `h3c_comware_v7_*.textfsm`。

# 影响范围

- `backend/services/operational_data_service.py` legacy quick-query 结构化响应。
- Quick Ops 前端 parser 标签及回归测试。
- 不修改设备版本、平台绑定、命令执行权限或数据库业务数据。

# 拟修改文件

- `backend/services/operational_data_service.py`
- `backend/tests/vendor_audit/test_h3c_cisco_quick_queries.py`
- `src/pages/AutomationExecute/components/QuickQueryResultOverlay.tsx`（仅在必要时补充来源字段展示）
- 对应 `docs/walkthrough/` 完成记录。

# 实施步骤

1. 在 legacy collector 中为每条命令调用统一 `parse_device_cli_output()`，让版本证据解析出具体 `parser_platform`、`template` 和 `template_source`。
2. 保留现有类别专用 raw fallback；fallback 没有模板时返回 `platform-parser`/明确未匹配，不再伪装成旧 NTC 目录。
3. 将 parser/template/source/action 元数据回填 category 响应，使单设备和批量 Quick Ops 都能显示真实解析身份。
4. 增加 Comware V7 fixture 回归，断言 legacy 路径返回 `h3c_comware_v7_display_interface_brief.textfsm`，并覆盖无模板 fallback 标签。

# 验证计划

- `pytest backend/tests/vendor_audit/test_h3c_cisco_quick_queries.py -q`
- `pytest backend/tests -k "operational or quick_query or textfsm" -q`
- `npm run lint`
- `npm run test:frontend -- --run`（若前端组件有改动）
- 浏览器 Quick Ops：H3C V7 设备执行“接口状态”，确认显示具体版本模板；无模板时显示未匹配/平台解析。

# 风险与回滚思路

- 统一 parser 入口可能使少数 raw fallback 类别的 parser 文案更准确，但不改变原始回显和记录内容。
- 若某类 legacy 输出无法被统一 parser 命中，继续使用原类别专用 fallback，并明确标记 `platform-parser`，不会丢失查询结果。
- 回滚仅需恢复 legacy collector 的元数据回填代码；不涉及迁移或持久化数据回滚。
