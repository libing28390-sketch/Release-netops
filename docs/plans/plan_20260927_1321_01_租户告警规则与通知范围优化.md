# 租户告警规则与通知范围优化

## 任务目标

把告警规则的采集来源、适用对象、规则行为和通知收件范围整理成一致且可理解的配置流程；规则和通知组按租户隔离；保存的渠道/用户组必须进入实时告警和维护窗口重开投递。

## 现状与问题

- 告警规则表没有 `tenant_id`，不同租户共用规则；用户组和 SMTP profile 却是 tenant-local。
- “采集来源”卡片是指标元数据，不是实际采集对象选择；范围值是自由文本 matcher，UI 没解释被匹配的字段。
- `ping_unreachable` 可配置但离线监控没有解析该规则。
- `host_*` 是平台健康检查的独立路径，不读取规则范围/通知渠道；`srv_*` 可配置但未找到规则执行入口。
- 通知方式已是复选框，但规则还没有通知组字段/接口/持久化/投递过滤；SMTP profile 收件目标仍应作为管理员配置的额外边界。
- 当前表单默认展开模板 OID、持续时间、重复窗口和审批细节，主流程信息过密。

## 实施边界与契约

- 按推荐方向将告警规则做 tenant-scoping；API 从当前登录用户推导 tenant，忽略请求体中的 tenant 值。
- 为保护历史行为，迁移时为当前存在的每个 tenant 复制原全局网络规则；保留默认 tenant 下的既有 rule ID，其他 tenant 使用新 ID，并同步历史快照。
- 新增 `notification_group_names`（JSONB 字符串数组）；组目录只返回当前 tenant 中活动用户的组名和成员数，不返回用户邮箱。
- 通知组限制当前告警 tenant 内的活跃用户；SMTP profile 配置的目标继续作为额外限制，与规则选组取交集。未选规则组时维持旧行为。
- Network alert rule 的范围按同 tenant 设备上下文匹配；优先级 interface > device > site > global。维护窗口重开沿用同一规则/组。
- `host_*` 保持平台系统健康特殊路径，在 UI 明确显示其系统级行为，限制范围为全局且不显示误导性的规则组/显式渠道设置。
- 没有告警执行器的 `srv_*` 不再作为可新建规则提供；历史记录保留并标示为未接入执行器，避免假设其已生效。
- 采集来源默认显示短摘要，模板字段、说明和 OID 路径收进“采集说明”。范围按类型动态展示被匹配字段、大小写与通配符示例；接口范围提醒其当前只匹配接口名。
- 将持续时间保留为高级参数；移除或改正文案描述“重复通知窗口”，不将其宣传为周期提醒。

## 影响范围

- PostgreSQL 迁移、告警规则服务/API/历史记录与运行时规则解析。
- 设备离线告警、通知 outbox/dispatch、维护窗口重开。

- 相关后端迁移和告警规则/通知测试。

## 实施步骤

1. 检查所有规则 CRUD、历史、批量启停、运行时解析和迁移惯例，定出 tenant-scoped 查询边界。
2. 增加 PostgreSQL 幂等迁移：tenant 字段、组字段、历史租户字段，并为现有 tenant 复制规则以保留原跨租户行为。
3. 让规则列表/创建/更新/删除/批量操作/历史从认证上下文强制 tenant；按设备 tenant 选择运行时规则。
4. 增加 tenant-local 最小通知组目录；校验保存的组名来自当前 tenant 的活动用户组。
5. 将规则组字段传入网络告警 outbox、SMTP/Webhook user filtering 和维护窗口 reopen；保持 profile 目标限制。
6. 将设备离线转换映射到 `ping_unreachable`；阻止新的未实现 `srv_*` 规则并将旧数据标清；宿主机规则限制在明确的系统级语义。
7. 精简前端主表单，解释采集来源、对象范围、优先级和匹配方式；高级选项默认收起，保留审批保护。
8. 加入迁移、规则 tenant isolation、scope、离线通知、通知组过滤及表单行为的回归测试。
9. 运行针对性 backend tests、frontend lint/build，检查迁移幂等性和最终 diff。

## 验证计划

- 后端：告警规则 CRUD 租户隔离、跨 tenant 同名 group 不能串发、规则范围字段匹配与优先级、`ping_unreachable` 告警/恢复/维护重开、SMTP profile 目标与规则组交集、迁移升级与重复运行。
- 前端：组目录加载/空态/失败态、组选择序列化、动态范围说明、不可执行指标提示、表单提交和中英文文案。
- 运行相关 pytest；运行 `npm run lint` 与生产构建；使用 PostgreSQL 迁移契约，不用 SQLite 替代生产语义。

## 风险与回滚思路

- 迁移复制规则会增加规则行和历史行；按 tenant 生成新 ID 并在一个事务中提交，失败时整体回滚。回滚代码前需保留迁移执行记录，不手工删改用户规则。
- tenant-scoping 可能改变非默认租户的规则列表；复制旧规则是保持旧行为的兼容步骤，验证需覆盖多个 tenant。
- 规则组选项名称仍来自 `users.group_name` 文本，没有独立 group ID；改名后旧规则会变成无收件人，需返回明确提示。
- 多个 SMTP profile 仍会都收到同一 email channel 告警；除非用户另行要求，本次不新增规则级 profile picker。
- 宿主机健康通知是系统级路径；本次限定其规则控制，避免按 tenant 伪造设备上下文。
