# 告警规则通知渠道与邮件投递审计实施计划

## 任务目标

在现有 SNMP 告警生命周期和 durable outbox 基础上，增加“按告警规则选择通知方式”的能力，至少支持飞书和邮件，并让邮件投递失败、重试、最终失败和恢复状态都能在告警历史中被追踪。Grafana 继续作为展示和可选外部告警源，不承担本批 Nexora SNMP 告警规则。

本计划的核心验收标准是：

1. 一条规则可以选择“跟随个人设置”“飞书”“邮件”或“飞书+邮件”。
2. 告警触发、恢复和维护期重新打开时，通知方式遵循规则配置。
3. 邮件发送不阻塞 SNMP 采集协程，所有邮件投递都进入 PostgreSQL outbox。
4. SMTP 连接失败、认证失败、TLS 失败、收件人拒绝、超时和重试耗尽，都能在告警详情/历史时间线看到明确的脱敏结果。
5. 通知失败不改变告警本身的 active/resolved 状态；通知状态和告警状态可以分别判断。
6. 现有飞书、钉钉、企业微信和全局 webhook 行为保持兼容。
7. 规则变更历史必须能关联真实 `alert_rules.id`，不能被旧版 `alert_rule_settings` 外键阻断。

## 现状与问题

### 现有告警规则

- `alert_rules` 已有告警级别、阈值、作用域、FOR 持续时间、重复通知窗口、触发/恢复开关。
- 规则没有通知渠道字段，因此所有规则最终走统一的 workspace 分发路径。
- 用户个人设置保存飞书、钉钉、企业微信 webhook 偏好；系统已经支持个人配置优先、全局通道回退。
- 用户表已有 `email` 字段，但没有“邮件告警启用状态”和 SMTP 投递能力。

### 现有通知链路

- `background_monitor_service` 负责告警生命周期，并把通知写入 `alert_delivery_outbox`。
- outbox 目前支持 `workspace` 和 `global_webhook` 两类投递。
- workspace 投递会读取租户用户的通知偏好并调用现有飞书/钉钉/企业微信 provider。
- outbox 已经具备租约、重试、退避和最终失败状态，但 payload 尚未带有稳定的 `alert_id`，投递失败无法直接回写告警时间线。
- `alert_activity` 已经存在，并由告警详情接口读取；适合承载“通知排队/发送/重试/失败”审计事件，但需要增加安全的通知元数据。
- 旧的 `alert_rule_history.settings_id` 外键指向兼容表，无法承载新规则 ID；本批增加独立 `rule_id` 关联并保留旧字段。

### 需要解决的关键缺口

- 规则无法选择单一通知方式或多通知方式。
- SMTP 配置、发件人和凭据缺失。
- 邮件发送结果没有统一 provider 约定。
- outbox 失败只保留一条技术错误摘要，告警历史没有可见关联。
- 同一告警的触发通知、恢复通知和通知失败需要使用不同的幂等键，不能互相覆盖。
- SMTP 密码、用户邮箱、完整 webhook 和异常响应不能进入日志、告警正文或 outbox payload。

## 目标架构

```
SNMP 采样
  -> 规则匹配与生命周期状态机
  -> 解析规则通知策略
  -> 为每个通知渠道生成独立 outbox delivery
  -> provider（Feishu / Email / 现有 workspace）
  -> delivery attempt 状态与告警 activity 审计
  -> /alerts/desk 与告警历史时间线
```

告警状态和通知状态必须分离：

- `alert_events` 表示设备问题是否仍然 active，以及何时恢复。
- outbox/delivery 表示通知是否排队、重试、成功或失败。
- 邮件失败时，告警仍然保持 active；邮件成功或失败都不能自动关闭告警。
- 告警恢复时，恢复邮件和恢复飞书消息使用新的 delivery key，并继续关联同一个 `alert_id`。

## 数据模型设计

### 1. 规则通知策略

在 `alert_rules` 上增加通知策略字段，推荐使用 JSONB 而不是把渠道拆成多个布尔列，方便后续增加钉钉、企业微信、短信和 webhook：

- `notification_channels_json`：允许值为 `workspace`、`feishu`、`email`、`dingtalk`、`wechat`、`global_webhook` 的数组。
- 默认值为 `workspace`，兼容当前行为。
- 规则创建和更新时校验重复项、未知渠道和空数组。
- `workspace` 表示继续按个人/租户配置分发；明确选择 `feishu` 或 `email` 时只投递对应 provider。
- 现有 `notify_on_active`、`notify_on_recovery`、`notify_on_reopen_after_maintenance` 继续控制事件类型，不把这些语义复制到渠道字段中。

若后续需要复杂收件人策略，再引入独立的 `alert_notification_policies` 表。本批先把渠道选择放在规则上，避免引入无法立即使用的多级策略管理。

### 2. 邮件通道配置

新增租户/系统级邮件通道配置，建议独立于 `global_notification_channels`，因为 SMTP 字段与 webhook 结构不同：

- 通道 ID、租户 ID、名称、启用状态。
- SMTP host、port、security（SSL/STARTTLS/none）。
- username、from address、from name、reply-to。
- password 或 secret reference，只保存加密值/密钥引用，不保存明文。
- connect timeout、send timeout、最大每分钟发送数。
- created_by、updated_by、updated_at。

管理员可在系统设置中保存和测试 SMTP；普通用户只能设置自己是否接收邮件，以及使用用户表中的邮箱地址。SMTP 凭据不进入告警规则、alert_events、alert_activity 或 outbox payload。

### 3. 用户邮件偏好

在 `users.notification_channels` 兼容已有 JSON 结构，增加 `email` 节点：

- `enabled`：是否接收邮件告警。
- `active_enabled`：是否接收触发通知。
- `recovery_enabled`：是否接收恢复通知。
- 地址默认使用 `users.email`，不允许在个人设置中覆盖成未验证地址；后续如需多个地址再增加收件人表。

如果用户没有邮箱、邮箱格式非法或未启用，邮件渠道只跳过该用户，并在投递汇总中记录“无可用收件人”。

### 4. 通知投递与尝试记录

扩展 `alert_delivery_outbox`：

- `alert_id`：关联 `alert_events.id`。
- `tenant_id`：限定租户边界。
- `event_kind`：`active`、`resolved`、`reopened`。
- `channel`：`workspace`、`feishu`、`email`、`dingtalk`、`wechat`、`global_webhook`。
- `destination_key`：脱敏后的目标类别或目标组，不存完整 webhook 或邮箱列表。
- payload 只保存告警展示字段、规则 ID、渠道、收件人数量和语言，不保存 SMTP 密码、邮箱完整地址或 webhook secret。

新增 `alert_delivery_attempts` 表保存每一次 provider 调用：

- attempt ID、alert ID、delivery ID、channel、event kind。
- attempt number、状态（queued/sending/retrying/succeeded/failed/skipped）。
- safe error code、safe error summary、provider response class。
- recipient count、started_at、finished_at、created_at。

在 `delivery_key` 上继续保持唯一约束，推荐格式为：

`alert_id:event_kind:channel:destination_group`

同一渠道的重试复用同一 delivery key，不新建重复告警；每次实际调用新建一条 attempt 记录。

## 邮件 provider 设计

新增统一邮件 provider，发送纯文本和 HTML 两种内容：

- 连接支持 SMTP SSL、STARTTLS 和无加密模式；生产默认拒绝明文认证。
- 设置连接和发送超时，避免阻塞调度器。
- 将 SMTP 异常归一化为安全错误码：
  - `smtp_config_missing`
  - `smtp_dns_or_connect_failed`
  - `smtp_tls_failed`
  - `smtp_auth_failed`
  - `smtp_recipient_rejected`
  - `smtp_timeout`
  - `smtp_provider_error`
  - `smtp_invalid_recipient`
- 日志只记录错误码、attempt ID 和 alert ID，不记录密码、完整邮箱列表和 SMTP 响应中的敏感内容。
- 主题包含告警级别、告警名称和设备名称；正文包含指标、当前值、阈值、时间、持续时间和 `/alerts/desk` 链接。
- 邮件 provider 返回结构化结果，不直接修改 `alert_events`。

## 告警历史中体现邮件失败的方式

这是本任务的硬性要求，采用“双层记录”：

### 投递表记录完整尝试过程

每次 outbox worker 领取邮件任务时创建 `sending` attempt；provider 返回失败时更新为 `retrying` 或 `failed`，并保存 attempt number 和安全错误码。重试成功时保留之前的失败尝试，并新增成功结果。

### `alert_activity` 记录对用户可读的审计事件

通过现有 `alert_activity` 关联同一个 `alert_id`，增加以下事件类型：

- `NOTIFICATION_QUEUED`：告警通知已经进入 outbox。
- `NOTIFICATION_SENT`：渠道发送成功。
- `NOTIFICATION_RETRYING`：本次发送失败，将按退避策略重试。
- `NOTIFICATION_FAILED`：达到最大重试次数或发生不可重试错误。
- `NOTIFICATION_SKIPPED`：没有收件人、通道未配置或用户主动关闭该渠道。

metadata 只展示：渠道、事件类型、attempt 次数、收件人数、错误码、是否还会重试。不会展示 SMTP 密码、邮箱地址、完整 webhook 或原始异常堆栈。

### API 与前端展示

- `GET /api/alerts/{alert_id}/activity` 返回通知审计事件。
- `GET /api/alerts/{alert_id}/deliveries` 返回按渠道汇总的最新状态、最后错误码、重试次数和最后尝试时间。
- `/alerts/desk` 详情时间线用不同颜色区分设备状态变化和通知投递结果。
- `/alerts/history` 增加“通知状态”列和筛选条件：全部、已发送、重试中、最终失败、未配置/跳过。
- 告警主状态仍由 `resolved_at` 决定，通知失败不会把告警标记为恢复。

## 后端实施步骤

### 阶段一：模型与迁移

1. 新增 PostgreSQL 迁移，扩展 `alert_rules.notification_channels_json`。
2. 新增邮件通道配置表及敏感字段加密/密钥引用字段。
3. 扩展 `alert_delivery_outbox` 关联字段和渠道检查约束。
4. 新增 `alert_delivery_attempts` 表、索引和保留策略。
5. 保持旧安装默认规则自动回填为 `workspace`，不修改用户已有通道。
6. 新增规则历史 `rule_id` 关联迁移，修复规则创建/更新历史写入的外键冲突。

### 阶段二：规则 API 与服务

1. `alert_rule_service` 解析、校验和返回渠道列表。
2. 新增渠道目录接口，返回当前可用渠道、配置状态和不可用原因，但不返回密钥。
3. 规则创建/更新接口保存渠道并写入规则历史。
4. 删除或停用规则时保持历史投递记录，不删除审计数据。

### 阶段三：通知分发

1. 将 `maybe_notify_webhook` 改为按规则渠道生成多个 outbox delivery。
2. 兼容无渠道字段的旧规则，继续走 workspace。
3. 新增邮件 provider 和邮件 recipient resolver。
4. workspace provider 增加渠道过滤能力，确保规则选择飞书时不会误发钉钉/企业微信。
5. outbox worker 在领取、成功、重试、失败和跳过时写入 attempts 与 alert_activity。
6. 对不可重试错误直接记录最终失败；网络、超时和临时 SMTP 4xx 错误进入退避重试。

### 阶段四：系统设置与用户设置

1. 系统设置增加 SMTP 配置表单和测试邮件接口。
2. 测试邮件走显式用户操作，不进入告警 outbox，不写入告警历史。
3. 个人设置增加邮件接收开关和邮箱状态提示。
4. 没有邮箱或邮箱格式不合法时，前端明确提示，后端仍然做最终校验。

### 阶段五：告警台和历史

1. 告警详情展示通知渠道和最新投递状态。
2. 时间线合并设备生命周期事件与通知投递事件。
3. 告警历史支持按渠道、投递状态和错误码筛选。
4. Excel 导出增加通知渠道、最后投递状态、重试次数和最后错误码。
5. outbox 失败但告警仍 active 时，页面同时显示“告警仍在持续”和“邮件投递失败”。

## 验证计划

### 逻辑验证

- 规则选择飞书、邮件、双通道和跟随个人设置时，生成正确的 outbox 数量和渠道。
- active、resolved、reopened 各生成独立 delivery key。
- 同一 delivery key 重复入队不会生成重复投递。
- SMTP 配置缺失、无收件人和用户关闭邮件时，均进入可见的 skipped/failed 记录。
- SMTP 认证失败、TLS 失败、超时、收件人拒绝和临时网络错误分别映射为稳定错误码。
- 第一次失败进入 retrying，最终达到上限进入 failed；中间失败记录全部保留。
- 邮件失败不会改变 `alert_events.resolved_at`、workflow status 或告警 active 状态。

### 静态与数据库验证

- PostgreSQL 迁移计划安全、可重复执行、索引存在。
- 后端 Python 编译和 focused provider/outbox 检查通过。
- 前端 TypeScript 检查、lint 和生产构建通过。
- 敏感字段扫描确认 SMTP 密码、邮箱地址列表和 webhook secret 不进入日志、payload 和 API 响应。

### Docker 环境验证

- 使用测试 SMTP 服务验证成功、认证失败、TLS 失败和超时。
- 使用一条 SNMP CPU/接口告警规则验证飞书、邮件双通道发送。
- 手工制造邮件失败，确认 `/alerts/desk` 详情和 `/alerts/history` 都能看到失败事件。
- 恢复 SMTP 后确认重试成功，历史同时保留失败和成功记录。
- 验证告警恢复时恢复邮件单独发送，且不会复用 active delivery key。

## 风险与回滚思路

- SMTP 配置错误不会影响 SNMP 采集和告警入库；只会影响邮件 delivery 状态。
- 新增数据库字段和表采用追加式迁移；回滚代码时保留 outbox 与 attempts 数据，避免删除审计证据。
- 规则字段默认 `workspace`，旧版本可以继续处理已存在规则；新版本字段缺失时服务回退为 workspace。
- 邮件发送会扩大外部网络访问范围，必须使用 TLS、超时、速率限制和脱敏日志。
- Docker 联调前不在 Windows 本机发送真实邮件；本机只做静态检查和 mock provider 验证。

## 交付边界

本计划完成后，邮件通知失败可以在告警历史中被查询、筛选和追踪；Grafana 不承担本批告警规则。邮件模板国际化、短信、Teams、邮件 bounce/DSN 自动解析和复杂通知编排不纳入第一阶段。
