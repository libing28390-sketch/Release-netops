# 采集器配置版本与启用状态实施计划

## 任务目标

修复采集器编辑时取消“启用”导致 PostgreSQL 内部错误的问题；让本地采集器启停变更同步反映到实际采集配置；保留配置版本的历史递增规则。

## 现状与证据

- 线上日志确认 PATCH `/api/monitoring/collectors/collector-local` 将 Python 布尔值写入 PostgreSQL `monitoring_collectors.enabled INTEGER`，数据库报 `column "enabled" is of type integer but expression is of type boolean`。
- 该采集器当前有已发布的 v1、v2、v3 三条配置历史；截图中的“配置未变化”表示继续复用 v3，“APPLIED”表示发布成功。版本号不是默认值，不重置历史为 v1。
- 当前编译输入只包含启用的采集器；因此停用后直接编译会失败，直接发布则可能重新应用旧配置。需要让停用的本地采集器编译为空目标配置，并让后台同步在启停变化时协调运行态。

## 影响范围

- 后端采集器更新、配置编译/发布及自动同步。
- 采集器编辑成功提示，显示启停配置正在同步。
- 新增基于隔离 PostgreSQL 的回归验证；不更改线上采集器数据库或现有配置历史。

## 拟修改文件

- `backend/api/monitoring_v1.py`
- `backend/services/collector_sync_service.py`
- `backend/tests/monitoring/test_monitoring_v1_collector_runtime.py` 或新增针对更新/编译的测试模块
- `backend/tests/monitoring/` 中自动同步回归测试
- `src/components/MonitoringManagementPage.tsx`
- 本计划和对应 walkthrough

## 实施步骤

1. 将 PATCH 的 `enabled` 明确规范化为整数 0/1，并校验不支持的值。
2. 本地采集器停用时编译空 SNMP/服务器目标快照；发布操作先确保停用配置已编译，避免把旧活动配置重新发布。
3. 启停状态变化后触发自动同步；同步包含停用的本地采集器，使空配置应用到运行目录。
4. 前端提示启停变更正在同步，避免误以为保存即完成运行态切换。
5. 使用隔离 PostgreSQL 验证停用保存、空配置编译/发布及版本递增；运行相应的后端质量门禁。
6. 按用户先前授权部署到 `192.168.204.128`，备份现有部署材料并检查服务健康；不在生产数据库中实际切换采集器启用状态。

## 验证计划

- `pytest backend/tests/monitoring/test_monitoring_v1_collector_runtime.py` 及新增的采集器更新/同步测试。
- 如改动覆盖其他采集 API，再补跑相关采集器编译测试。
- 部署后确认 API/容器健康；核对生产配置版本仍保留 v1、v2、v3，启用状态未被测试改写。

## 风险与回滚

- 停用本地采集器会应用空目标配置，停止该采集器管理的设备和主机目标抓取；重新启用后自动生成并发布新版本恢复目标。
- 版本号按配置历史递增，停用/启用可能形成后续版本，不重写或删除既有版本。
- 部署前保留服务器当前应用/镜像回滚点；若同步或健康检查失败，恢复部署备份和上一镜像，不回滚数据库配置历史。
