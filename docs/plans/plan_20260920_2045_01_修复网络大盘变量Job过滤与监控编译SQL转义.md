# 修复网络大盘变量Job过滤与监控编译SQL转义实施计划

## 1. 任务背景与现状
- **问题现象 1**：用户反馈在 `01 网络总览` 等所有大盘中，纳管设备数为 14 台，但设备下拉框中仅显示 2 台（`R1.eve.lab` 和 `SW6.eve.lab`），站点和厂商筛选异常，采集接口总数显示 `No data`。
- **问题现象 2**：用户反馈更新最新代码后，`07 Linux 服务器监控` 没有任何数据，即时面板全部显示为 0，历史趋势在 20:30 之后断流。
- **根因分析**：
  1. **网络大盘变量 Job 过滤错误**：在 `monitoring/grafana/generate_dashboards.py` 的 `make_network_variables` 中，变量查询被硬编码为 `job="snmp"`。但实际上 vmagent 抓取作业在 `scrape.yml` 和 `monitoring_compiler.py` 中被命名为 `network_snmp`（时序库中标签为 `job="network_snmp"`）。导致现存 14 台网络设备的时序全部被过滤排除，仅残留历史脏数据的 2 台设备。
  2. **监控编译 SQL 转义致命 Bug 导致 Linux 采集目标清空**：`backend/api/monitoring_v1.py` 中 `server_sql` 包含 `d.device_category LIKE '%server%'`。在 PostgreSQL 环境下，`backend/database/core.py` 的 `_adapt_pg_sql` 因 `next_char == 's'` 将 `%server%` 误判为 psycopg2 的占位符 `%s`，执行时抛出 `TypeError: not enough arguments for format string`。该异常导致 `servers = []`，动态生成的 `linux_targets.yml` 变为空列表 `[]`，vmagent 停止抓取 `192.168.204.128:9100`。

## 2. 影响范围与拟修改文件
- `monitoring/grafana/generate_dashboards.py`：纠正网络设备变量的 job 过滤为 `job=~"network_snmp|snmp"`，升级大盘版本号。
- `monitoring/grafana/dashboards/nexora-*.json`：重新编译全部 8 个仪表盘文件。
- `backend/database/core.py`：修复 `_adapt_pg_sql` 的转义逻辑，防止 SQL 中的 `%s...` 被误当做参数占位符。
- `backend/api/monitoring_v1.py`：重构 `server_sql` 为健壮的参数化查询，防止异常吞没导致 targets 为空并增加错误日志记录。

## 3. 实施步骤
1. 修改 `backend/database/core.py` 中的 `_adapt_pg_sql`，编写独立单元测试验证各种含有 `%` 的 SQL 转义与 psycopg2 参数化行为。
2. 优化 `backend/api/monitoring_v1.py` 中的 `server_sql`，并增加日志记录。
3. 修改 `monitoring/grafana/generate_dashboards.py`，将 `make_network_variables` 中的 `job="snmp"` 修改为 `job=~"network_snmp|snmp"`，升级 `DASHBOARD_VERSION` 为 `22` 并重新编译全部大盘。
4. 调用远端 `192.168.204.128` 的 API 测试重新编译 `collector-local`，验证 `server_target_count` 恢复为正常值（>0），快照生成正确的 targets。
5. 运行本地自动化测试进行全量质量门禁验证。
6. 归档 walkthrough 和 fix 记录。

## 4. 验证计划
- 单元测试：验证 `_adapt_pg_sql` 正确处理 `LIKE '%server%'`、`LIKE '%switch%'` 等。
- API 联调：调用远端 Nexora 编译发布接口，验证编译结果 `server_target_count >= 1`，包含 `192.168.204.128:9100`。
- 测试套件：运行 `backend/tests/monitoring/` 下的回归测试。
