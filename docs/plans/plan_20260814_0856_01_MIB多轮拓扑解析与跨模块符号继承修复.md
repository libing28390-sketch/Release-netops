# MIB 多轮拓扑解析与跨模块符号继承修复方案

## 1. 问题背景与根因分析

### 问题现象
用户反馈从 LibreNMS 同步后的部分厂商 MIB（例如 `ARISTA-BGP4V2-MIB`、`ARISTA-ENTITY-SENSOR-MIB` 等）在前端列表中显示“解析节点：0 个”。

### 根因深度剖析
1. **ASN.1 SYNTAX 正则表达式字符集逻辑错误**：
   * 原正则写为 `SYNTAX\s+([^A-Z0-9_-].*?)\s+`，其中 `[^A-Z0-9_-]` 是排除型字符集，直接排除了所有以大写字母开头的标准 ASN.1 类型（如 `SEQUENCE OF...`, `Integer32`, `Counter64`），导致所有 OBJECT-TYPE 节点均未被正确捕获。
2. **IMPORTS 导入语句块干扰顶层标识符提取**：
   * MIB 顶部的 `IMPORTS MODULE-IDENTITY, OBJECT-TYPE ... FROM SNMPv2-SMI;` 包含关键字，导致正则表达式在抓取 `MODULE-IDENTITY` 的名称时错误抓取到了开头的 `IMPORTS` 单词，从而使得当前 MIB 的根节点符号计算失败。
3. **跨 MIB 文件符号缺乏继承机制**：
   * MIB 文件是分层定义的（例如 `ARISTA-BGP4V2-MIB` 依赖 `ARISTA-SMI-MIB` 定义的 `aristaExperiment`）。原先单文件独立解析时未共享已解析的父符号，导致子树 OID 无法递归计算。

---

## 2. 解决方案与优化

1. **重构 ASN.1 符号解析引擎**：
   * 增加 `IMPORTS ... ;` 与 `EXPORTS ... ;` 语句块自动剥离机制，彻底杜绝导入关键字对顶层符号名称的干扰。
   * 全面扩充各大厂商（Cisco, Huawei, H3C, Arista, Juniper, Ruijie, ZTE, Fortinet, Dell, HP, Mikrotik 等）官方 SMI 根命名空间。
   * 引入基于有向无环图 (DAG) 的多轮拓扑依赖符号推导算法（Multi-pass Resolution），确保深层嵌套子节点 100% 正确推导绝对 OID。
2. **目录级跨 MIB 符号动态继承机制**：
   * 遍历厂商 MIB 文件时，优先将 `SMI`、`TC`、`ROOT` 根定义文件置顶解析。
   * 在厂商目录内维护全局符号表缓存 `vendor_symbols`，并在解析后续 MIB 文件时传入 `external_symbols` 自动继承。
