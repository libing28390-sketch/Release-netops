# 告警设备确认与通知方式调整

## 任务目标

把 CMDB 搜索命中的大量设备放入独立、紧凑的确认窗口，避免挤占告警规则表单；纠正列表中“系统投递”这一不准确的展示，并明确宿主机阈值规则与告警通知渠道的区别。

## 现状与问题

- CMDB 搜索命中列表若直接放在规则表单中，设备或 IP 较多时会拉长编辑区域；选择设备应先暂存，点击确认后再写入规则。
- 旧 `workspace` 是内部兼容渠道名，不是管理员在规则中配置的通知方式，直接展示“系统投递”会让用户误以为存在额外渠道。
- 审核运行逻辑后确认，`host_cpu`、`host_memory`、`host_disk` 仅由平台健康状态计算读取阈值，不进入告警规则投递链路。因此宿主机规则不能伪装成可发送 Webhook、邮件或通知组的告警。

## 影响范围

- 告警规则编辑器中的 CMDB 搜索结果、暂存勾选、确认/取消和已确认设备摘要。
- 告警规则列表中宿主机阈值规则的通知列说明。
- 非宿主机告警规则旧通知渠道及其历史快照的兼容归一化；保留宿主机旧内部值以兼容存量数据。
- 不增加宿主机告警事件或通知投递能力，不改变 CMDB API 契约。

## 拟修改文件

- 前端：`src/pages/AlertRulesTab.tsx`、`src/pages/alertManagementShared.ts`、`src/pages/alertManagementShared.test.ts`
- 后端：`backend/services/alert_rule_service.py`、`backend/services/background_monitor_service.py`
- 迁移：`backend/database/migrations/m0259_normalize_alert_rule_notifications.py`
- 验证：告警通知迁移、通知组和宿主机规则相关 PostgreSQL 测试。
- 本计划及对应 walkthrough。

## 实施步骤

1. CMDB 搜索后自动打开受限高度的小型结果窗口，使用较小字号显示设备名、管理 IP 与资产摘要。
2. 在窗口中暂存设备选择；“确认”才一次性更新规则表单，取消或关闭丢弃本次暂存更改。主表单只保留已确认设备摘要和重新查看搜索结果的入口。
3. 宿主机指标规则编辑区说明其仅计算平台健康状态，不显示 Webhook、邮件或通知组选择；列表的通知列改为“仅用于健康状态”。
4. 非宿主机告警规则和历史快照中的旧渠道归一到当前支持的 Webhook/邮件；服务端继续拒绝不支持的旧渠道写入。迁移保留宿主机规则的内部兼容值。
5. 执行定向前端、PostgreSQL 后端和静态检查，记录未执行的浏览器联调和运行环境迁移。

## 验证计划

- 前端辅助测试、`npm run lint` 与临时输出目录下的 Vite production build。
- 告警规则渠道迁移、通知组契约和宿主机阈值读取 PostgreSQL 测试。
- `scripts/validate_postgresql_only.py` 与 `git diff --check`。

## 风险与回滚思路

- 设备选择仍以稳定设备 ID 保存；只有点击确认后才会修改表单，取消不会覆盖已确认目标。
- m0259 仅规范化非宿主机规则及对应历史快照；宿主机内部兼容值保持不变。迁移尚未在用户运行环境执行。
- 当前代码没有宿主机告警事件到通知 outbox 的执行器。如果用户需要宿主机邮件或 Webhook，需要另行实现健康状态事件评估和投递链路后再开放渠道配置。
