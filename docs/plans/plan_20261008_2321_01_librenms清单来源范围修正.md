# LibreNMS 清单来源范围修正计划

## 目标

修正 LibreNMS MIB 清单把上游来源目录与 Nexora 归档范围混为一谈的问题，并确保固定 MIB 包导入时只处理清单列出的上游文件。

## 现状与问题

- `source-manifest.json` 的 MIB 条目使用 `vendor_scope`，但该值实际表示 Nexora 的 MIB 分类范围，不一定是上游 MIB 所属厂商。
- 例如上游 `mibs/hp` 作为 `procurve` Profile 的依赖被打包到 Aruba 范围，上游 `mibs/fs` 作为 `fs-ruijie` Profile 的依赖被打包到 Ruijie 范围；原始路径虽保留，但关联原因不够明确。
- 当前固定 MIB 目录还存在 12 个不在清单中的空 `TEST-MIB-*` 文件。递归导入器目前会扫描全部文件，清单不完整时会退回全量扫描。
- 工作区已有 MIB 和清单未提交改动。本任务保留这些内容，不覆盖或删除 MIB 文件。

## 影响范围

- `backend/vendor/librenms/source-manifest.json`
- `backend/vendor/librenms/README.md`
- `backend/services/librenms_mib_service.py`
- SNMP MIB 导入相关测试
- 本计划与对应 walkthrough

## 实施步骤

1. 明确清单字段表示 Nexora 归档厂商范围，并在清单中记录 HP→Aruba、FS→Ruijie 的上游树映射与对应 OS Profile。
2. 固定 LibreNMS bundle 导入时，以 manifest `bundle_path` 清单作为文件白名单；不在清单中的工作区占位文件不进入 MIB 索引。若清单列出的文件缺失，则在连接数据库前失败，避免用不完整包索引并退役现有 MIB。外部或临时 MIB 目录仍按现有流程扫描。
3. 添加回归测试，覆盖跨目录来源映射、manifest 文件白名单、不完整清单拒绝导入和文件内容/路径完整性。
4. 更新 bundle README，说明来源厂商、Nexora 归档范围和 OS Profile 的区别。
5. 完成后更新 walkthrough；不提交、不推送、不部署。

## 验证计划

- 解析 `source-manifest.json` 并核对每条 MIB 的存在、大小和 SHA-256。
- 运行 MIB manifest 与 MIB 导入相关的后端 pytest。
- 检查 `git diff`，确认既有未提交 MIB 内容未被改写或删除。

## 风险与回滚

- manifest 白名单仅作用于固定 bundle 目录，避免改变手动上传或临时上游目录的导入行为。
- 保留原始上游 MIB 文件及其路径，不按名称推断并删除潜在 Profile 依赖。
- 若导入兼容性验证失败，可回滚本次对导入器、manifest 元数据和 README 的增量改动；预存 MIB 文件保持原样。
