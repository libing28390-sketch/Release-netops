# 修复拓扑未纳管陈旧链路与主机名匹配实施计划

## 1. 任务目标
针对用户在 Windows 环境访问 `/monitor/topology` 提出的两项核心疑问与异常现象：
1. **Windows 环境与 Docker 环境疑问**：解答“是不是我现在是 Windows 环境，只能在 Docker 环境里验证”，澄清 Windows 原生环境与网络设备通信的实际情况。
2. **刷新发现执行 CLI 的根本原因**：分析为何在 WH-DC-01 站点点击“刷新发现”会执行 `show spanning-tree` 等 CLI 命令，且明明支持 LLDP 却看似没走 SNMP。
3. **WH-DC-02 链路异常暴增至 36 条的缺陷修复**：排查并彻底解决从 19 条突增到 36 条链路的 Bug，修复未纳管链路未过滤陈旧（stale）数据以及下划线/连字符（`S6850_1` vs `S6850-1`）导致真实设备被误判为未纳管外部节点的问题。

---

## 2. 现状与根因分析

### 2.1 疑问一：是否只能在 Docker 环境验证？
**不是。Windows 原生环境完全可以验证，且当前已经验证通过。**
- 在 Windows 环境下运行脚本实测：
  - `192.168.96.101 (R1)`: SNMP (UDP 161) 在 100ms 内成功返回 2 条 LLDP 记录。
  - `192.168.96.102 (R2)`: SNMP 返回 2 条 LLDP 记录。
  - `10.255.0.3 (R3)`: SNMP 返回 2 条 LLDP 记录。
  - `10.255.0.4 (R4)`: SNMP 返回 2 条 LLDP 记录。
  - `10.255.0.5 (SW5)`: SNMP 返回 3 条 LLDP 记录。
  - `10.255.0.6 (SW6)`: SNMP 返回 3 条 LLDP 记录。
  - `WH-DC-02` 站点中的 `S6850-2`, `S6850-4`, `S6850-5`, `F1090-9`, `F1090-10` 在后台 `topology_discovery_run_devices` 表中记录的 `discovery_method` 已经是 **`snmp`**，且完全没有执行 CLI 的 `display lldp neighbor`。
- Windows 环境直接具备到目标设备的 UDP 161（SNMP）网络可达性，不需要依赖 Docker。

### 2.2 疑问二：为什么 WH-DC-01 点击刷新执行了 CLI？
存在两重原因：
1. **凭据未绑定触发设计回退**：
   - 数据库中的 `R1, R2, R3, R4, SW5, SW6` 属于历史导入资产。在导入修复生效前，数据库 `devices` 表中这 6 台设备的 `snmp_community` 和 `snmp_credential_id` 均为空字符串 `''`。
   - 拓扑引擎检测到设备未配置任何 SNMP 凭据，因此按照高可用设计安全回退到 SSH CLI。
2. **终端日志输出的是协议事实采集，而非 LLDP 邻居发现**：
   - 终端日志中打印的命令是 `show spanning-tree`、`show interfaces description` 等。
   - 这些命令是在邻居发现结束后，系统调用的 `topology_protocol_service.collect_protocol_evidence`，用于在拓扑图上标记生成树（STP）阻塞端口和路由协议链路，并非邻居发现本身的命令。

### 2.3 疑问三：为什么 WH-DC-02 链路暴增至 36 条？
经数据追溯，当前 36 条链路 = 11 条纳管内部链路 + 25 条未纳管外部链路，由两个 Bug 叠加引起：
1. **SQL 查询未过滤 Stale 陈旧数据**：
   - `backend/services/topology_service.py` 中的 `get_unmanaged_topology_nodes_and_links` 函数在查询 `topology_observations` 时，未增加 `status <> 'stale'` 与 `is_active = 1` 过滤。
   - 在此前测试阶段产生的多条已废弃陈旧观察（如 `target_port_raw='4'` 的历史错误行）被全部当作当前“未纳管外部设备”，生成了十多条虚假外部链路。
2. **主机名分隔符不一致导致无法匹配到纳管设备**：
   - 数据库中录入的主机名是 `S6850-1`（连字符），而物理交换机通过 LLDP 上报的 `lldpRemSysName` 是 `S6850_1`（下划线）。
   - `_match_target_device_with_evidence` 在计算名称相似度时，因 `s6850_1 != s6850-1` 且上报的互联 IP（`10.254.100.4`）与设备管理 IP（`10.254.0.1`）不同，导致 S6850-2/S6850-4/F1090-9 连接到 S6850-1 的所有端口均匹配失败，被误当作外部未纳管设备展开。

## 3. 拟修改文件与实施方案

### 3.1 后端服务改造 (`backend/services/topology_service.py`)
1. **未纳管链路陈旧过滤**：
   - 为 `get_unmanaged_topology_nodes_and_links(..., include_stale: bool = False)` 增加陈旧控制。
   - 当 `include_stale=False` 时，强制追加 `COALESCE(o.is_active, 1) = 1` 与 `COALESCE(o.status, 'active') <> 'stale'` 条件，阻止失效历史记录污染当前拓扑。
2. **智能宽松主机名匹配**：
   - 在 `_match_target_device_with_evidence` 中，增加分隔符归一化逻辑：去除连字符、下划线及空格后比对（`re.sub(r'[-_\s]', '', name)`）。
   - 当 `norm_clean == host_clean` 时，赋予 `0.93` 匹配置信度（方法标为 `system_name_relaxed`），使 `S6850_1` 准确识别为 `S6850-1`。

### 3.2 路由层对接 (`backend/api/topology.py`)
- 在 `get_links` 路由中，将请求参数 `include_stale` 正确传递给 `get_unmanaged_topology_nodes_and_links(include_stale=include_stale)`。

### 3.3 数据库修整与资产凭据绑定
- 将系统中已有 SNMP 凭据 `snmp-ro`（`cred-4d76c74c996e`）绑定至 `R1~R4, SW5~SW6`，并更新 `devices.snmp_community`。
- 重新计算或触发发现，使两站点的链路与设备数量恢复真实状态。
