## 1. 改造目标

把当前以变更为主的工单管理，逐步建设为统一办事入口，贯通故障、服务申请、变更、审批、自动化执行和结果确认。

第一批可交付目标：

- 用户能够快速创建变更，避免方案、控制表和回退信息重复填写。
- 待办清楚显示当前状态、负责人和下一步动作。
- 审批、实施身份、执行内容和验收结果能够对应。
- 列表、详情和错误提示简洁，默认每页 10 条并保留条数选择。

后续阶段再逐步引入故障工单、服务目录、工单 SLA，以及有范围和有效期的标准／周期授权。

## 3. 范围与实施边界

- 复用现有 React、共享组件、FastAPI、PostgreSQL 和通知通道。
- 现有变更工单和审批记录继续有效保存；新增功能采用增量数据和兼容接口。
- 每个阶段只变更已定义范围，不同时重写全部工单、监控和自动化模块。
- 前端简化不取消后端授权；现有初审、终审、MFA、快照及执行授权消费规则保留，变更必须通过专项契约与验证。
- 不自动补签历史工单，不把旧执行授权改为可重复使用，不自动关闭未验证故障。
- 本计划不修改真实设备、生产数据和部署配置。实际提交、发布和部署遵循已有授权与项目规则。

- [x] 实施人、批准命令、目标、窗口、模板、控制表及附件进入审批快照；范围改变后原授权失效并重新审核。

- [x] 使用现有状态和 JSONB 结构化记录承载验证闭环，无需增加业务表或迁移。
- [x] 记录部分失败、未知执行结果、回退和结束事实；单次授权并发消费受 PG 行锁保护。
- [x] 校验窗口起止；无时区时间按 `Asia/Shanghai` 解释，窗口为半开区间，缺失、无效或过期时拒绝实施。

### 数据与兼容

本阶段无需数据库迁移：使用现有 JSONB 结构化记录，不伪造历史责任组、验收或授权。当前缺少真实责任组目录与成员来源，纳入 M3 单独建模。

- 已结束工单保留原审批、实施和结果事实。
- 已批准未实施的旧工单按快照版本校验；旧版快照或批准范围变化时必须重新审批。
- 不重算历史快照来使旧授权自动通过，不默认放开管理员或任意实施人执行。

### 主要模块

M1 模块，以及 `backend/api/change_orders/`、`backend/services/change_order_service.py`、`backend/api/automation.py` 和关联 Playbook 执行入口。没有修改 `backend/database/schema.py` 或添加数据库迁移。

### 退出条件

非申请人可按明确指派实施；无关账号、申请人自审、终审人实施、审批内容变化和越界执行被拒绝。PG 并发初审只有一个状态转换成功；单次授权重放被拒绝。失败、回退有记录，验证未通过不能完成。责任组模型由 M3 实施。

### M2 完成结果与验证

- 责任分工 API 支持指派、接手和转派，记录实际操作者、前后实施人和原因；更换实施人或修改批准范围会作废原审批并退回审核。
- 技术验证必须由非实施人提交；配置业务验证时还要由申请人或指定业务确认人通过。完成和回退完成都检查当前审批快照下的验证结果。
- 直接配置执行与关联 Playbook 执行都校验实施人、终审分离、审批快照、窗口、MFA、目标设备及命令。管理员角色本身不自动获得设备执行权。
- 附件 SHA-256 纳入批准范围；设备操作开始后控制表与普通附件上传均返回 409，不会改写活动执行范围。
- 前端专项 6 文件 45 项通过；`npm run lint`、隔离 Vite 构建、PostgreSQL-only 扫描通过。PG 隔离套件 `backend/tests/change_orders/test_m2_authorization.py`：15 项通过，包含并发初审和附件执行中边界。
- Playbook 和设备执行使用 mock／隔离测试，没有下发真实设备命令；目标实例拒绝连接，未部署、未做现场验证。

- [x] 记录恢复证据、恢复时间和确认结论；监控事件自动 resolved 只记工单事件，不直接关闭故障单。
- [x] 配置修改通过现有变更审批路径；创建变更草稿时在同一事务内关联故障单并带入 incident、设备和摘要。
- [x] 新一轮 incident 生成新故障单；待确认期间复发时退回处理中并保留之前的恢复记录。
- [x] 建设故障工单分页、待办和访问控制；变更工单继续使用现有变更域与路由，避免重复维护状态。

### 数据与 API 方向

采用 PostgreSQL 增量表保存故障工单、追加式事件、责任组／成员和工单关联；既有变更状态仍由 `change_orders` 独立维护。使用 `backend/api/tickets/`、`backend/services/incident_ticket_service.py` 及 `src/pages/Tickets/`。

- 变更审批和执行状态继续由现有变更域管理；故障工单不复制一份可写的变更状态。M3 提供故障工单入口，并保留现有变更入口；M4 再引入跨类型列表。
- 故障工单的处理状态与监控事件状态分开保存；建立可追踪关联。
- 每个 incident 生命周期使用稳定来源键，保留现有 incident ID、变更单 URL 和 API。
- 新建变更草稿时把 `incident_ticket_id` 与 `incident_id` 一并校验，并在同一个 PG 事务中写入变更单、关系和事件。
- incident 访问沿用设备／站点／设备组范围；变更摘要必须再次验证 change_order 权限，不能仅因有权看 incident 就返回。
- 事件投影、工单状态和关联具备唯一约束、行锁和事务；失败可重试，不留下孤立链接。

### M3 完成结果与验证

- M3 增加 PostgreSQL 工单、追加式事件、责任组／成员和变更关联表；来源 incident 生命周期唯一建单，恢复和复发只更新工单事件与处理状态，不自动关闭。

- 删除／移除组或成员时阻止活动工单留下悬空责任；终态工单保留历史事实。
- 后端隔离 PostgreSQL 聚焦测试：4 个相关 suites 共 43 项通过，覆盖幂等并发、恢复/复发、变更关联范围、组与成员约束及 M2 执行授权回归。测试数据库为 `nexora_pytest_m2root_332c8fdf145d`。
- 前端聚焦测试 3 个文件、15 项通过；`npm run lint`、隔离 Vite 生产构建、Python 编译及 PostgreSQL-only 扫描通过。
- CUA 本地 mock 浏览器显示故障工单列表、负责人、下一步和 10 条/页；Mock 样例共 3 条，无真实数据连接。`192.168.56.1:5400` 拒绝连接，目标实例仍待部署验收。

### 重点复用

`backend/services/monitoring_incident_service.py`、`backend/api/monitoring.py`、`backend/api/change_orders/core.py` 及已有 incident_id 关联；导航按实际需要调整 `src/components/AppSidebar/navConfig.ts`、`src/App.tsx` 和相关路由上下文。

### 退出条件

同一 incident 并发／重放只得到同一张故障单；新一轮故障不被错误归入已关闭单；告警恢复但未确认时故障单仍未关闭；待确认复发有保留的恢复与重开事件；关联变更沿现行批准路径实施；跨租户、站点和设备组的故障或变更摘要不泄露。

## 11. PostgreSQL 迁移与历史兼容

所有涉及数据的阶段必须形成独立迁移设计：

1. 以当前 schema 和迁移注册方式核对版本，新编号在实施时分配，不预占不存在的编号。
2. 新字段、关联及索引优先采用增量方式；新安装 schema 与升级路径同步。
3. 大表回填分批、可重复、有进度与失败记录；有来源才回填，不伪造审批、验收或时限。
4. 并发状态流转、授权消费和幂等关联使用 PostgreSQL 事务、行锁及适用的唯一约束。
5. 兼容期完成后再收紧约束；状态与角色映射覆盖旧状态，禁止通过删除旧状态解决兼容问题。
6. 验证旧库升级、空库初始化、重复运行迁移和中断后恢复。
7. 回滚应用前检查数据库兼容性；优先保留新增表及已写入事实，不通过删表破坏审计。

持久化验证仅使用隔离 PostgreSQL，不引入 SQLite，也不连接生产库执行测试。
