# Grafana 加载链路排查

## 任务目标
深度定位远端 Linux Docker 的监控大盘首次进入、再次进入和切换看板加载慢的原因；按实际证据完成必要的本地修正及验证。

## 现状与问题
- 用户远端地址为已登录的 `192.168.204.128`，本机不是部署主机。此前查询语法和图例变更仅在本地完成。
- 浏览器检查器初步测到设备详情电源趋势 518 条序列、20,362 个数据点，请求耗时 2.28/2.48 秒；CPU 对照为 39 点、886 ms。不能据此直接断言 VictoriaMetrics 执行时间或整页加载时间。
- 存在未解析名称与大量重复 Slot 1 电源曲线，需要检查采集来源和身份标签。

## 影响范围与拟修改文件
- `src/pages/GrafanaDashboardPage.tsx` 及其局部启动 helper/测试：消除确认存在的重复加载和不必要的启动等待。
- `monitoring/grafana/generate_dashboards.py`、生成输出与相关静态测试：仅在证实查询/变量存在性能缺陷后修改，保持指标含义、权限和资产身份。
- 后端 Grafana 鉴权与部署代理配置：先只读追踪；如发现安全敏感设计问题，由主 Agent 决策，不添加鉴权缓存绕过权限撤销。
- 本计划和对应 walkthrough。保留所有既有未提交修改。

## 分工边界
- 主 Agent：远端浏览器耗时采样、查询/变量和采集序列审查、方案与共享文件、最终验证与记录。
- frontend_worker：只读页面启动与 iframe 生命周期审查；经明确分配后才修改页面与局部测试。
- backend_worker：只读 Grafana session、鉴权和反代配置审查；不与前端执行者写相同文件。
- 子 Agent 不运行公共验证、不访问生产数据库、不生成重复计划。

## 实施步骤
1. 通过远端 Grafana Query Inspector 采样重面板与轻面板，区分请求时间、处理时间与数据量。
2. 追踪入口路由、session bridge、health、iframe、变量依赖和数据源查询。
3. 检查资源压缩、认证子请求、数据源配置和采集高基数来源。
4. 以证据选择最小修正；未能测量的层级明确标记，不虚构改善百分比。
5. 执行局部回归、类型检查和构建，归档发现与尚需远端复测的内容。

## 排查后的实施决策
- 用户补充所有设备均为模拟器；重复功率值、占位符名称与高序列数仅视为模拟数据负荷，不修改传感器采集或删除序列。
- 用户明确允许从 Nginx 配置优化。本轮代码修改收敛到 `nginx/nginx.conf` 和现有部署契约测试，前端审查结论归档为后续项。
- 远端只进行无凭证 TLS 协商探测，浏览器侧仅协商 HTTP/1.1；本地 SSL server 未启用 HTTP/2。启用 HTTP/2，并修正 Grafana HTTP 与认证子请求的 keepalive 头部。保留权限校验和 WebSocket 升级，不缓存认证结果。
- 使用官方 Nginx 1.27 Windows 二进制做隔离语法/反代行为验证；如平台构建缺少模块则明确限制，Linux Docker 验证仍需部署后进行。
- 最终验证通过：7 项静态部署契约，官方 Nginx1.27.5 的隔离配置加载、TCP复用、h2并发请求、HTTP1.1兼容、401/403与身份隔离、Grafana/PAM WebSocket回显；临时进程全部结束。应用包与结果详见对应 walkthrough。

## 验证计划
- 前端修改：局部 Vitest、`npm run lint`，必要时隔离目录构建。
- 看板修改：无数据库的静态 pytest、生成前后契约对比、同版本 VictoriaMetrics 临时实例解析。
- 后端纯逻辑：mock/静态测试并跳过应用 DB 自动初始化；涉及持久化时仅使用隔离 PostgreSQL。
- 浏览器：保留实际面板 Stats 读数；线上不保存配置、不重新部署。

## 风险与回滚
页面 session 优化不能跨用户复用凭证、降低权限校验或将长期 cookie 当作永久可用状态。序列限制会影响可见设备部件，不能用无依据的 Top N 掩盖采集问题。远端版本可能落后于本地，最终性能须在部署后复测。变更可按文件差异回滚；本轮不清理生产序列、不改设备、不执行远端部署。
