# Docker 容器逐项压测脚本计划

## 任务目标

新增一份可在 Linux Docker 部署主机运行的脚本，对 Nexora Compose 中当前运行的容器逐个施加受控、只读的探测请求，并记录 CPU、内存、网络、块设备 I/O 和进程数。该脚本用于连通性和轻负载预检查；它没有覆盖主要业务负载，不能用于确定容量或合理的 limits。

## 现状与问题

- 当前工作区没有 Docker CLI，无法连接用户部署主机；脚本需由用户在 Docker 主机上运行。
- 根 `Dockerfile` 的 NetOps 镜像基于 `python:3.11-slim`，可用作无网络拉取的临时请求生成器。
- `docker-compose.yml` 包含 API、Nginx、PostgreSQL、Redis、VictoriaMetrics、vmagent、SNMP exporter、Grafana、cAdvisor、Docker socket proxy 和可选 SeaweedFS。
- 已有 `scripts/load_test.py` 主要压 API HTTP 路径，不能逐项覆盖 Compose 服务。
- 用户在部署主机运行初版后，HTTP 阶段出现 502/连接重置，内部网络出现不可达；代理是与这些现象相符的待验证原因。Redis 客户端触发 ACL 未授权的 `CLIENT SETNAME`，CSV 仅有压测前后样本；据此修正代理处理、Redis 客户端选项和采样循环。
- 方法审查确认 NetOps liveness 只返回固定 JSON，PostgreSQL `SELECT 1`、Redis `PING`、SNMP exporter/vmagent 自身指标、Grafana health、S3 根目录 403 都未覆盖主要业务负载。即使预检查全通过，也不能据此调整 limits。
- Nginx HTTP 根路径按配置返回 HTTPS 重定向；探测应验证 301 而不自动跟随至可能使用自签名证书的 TLS 入口。

## 影响范围

新增逐容器压测脚本和本任务计划/完成记录，不改服务镜像、Compose 限额、持久化数据或业务代码。

## 实施步骤

1. 为每个 Compose 服务选择无写入的协议探测负载；PostgreSQL 仅执行 `SELECT 1`，Redis 仅执行 `PING`，SNMP exporter 只读取自身 `/metrics`，不轮询真实设备。
2. 默认仅展示测试计划；显式传入 `--run` 后才逐容器运行，限制并发、时长和请求速率，不拉取镜像，不触碰业务数据。
3. 在每个服务负载期间采集 `docker stats` 样本并写入 CSV，同时保存请求结果日志；未运行的可选容器标记为跳过。
4. 完成脚本语法与帮助/计划模式验证；审阅部署主机初版运行报告，修复已定位的请求生成和采样问题，并记录需在部署主机复测。
5. 独立审查负载代表性，由主 Agent 统一修正脚本的结果表述和 Nginx 重定向处理；子 Agent 只读审查，不修改共享文件。记录正式容量测试所需的工作负载和指标。

## 验证计划

- `bash -n scripts/stress-test-docker.sh`
- `bash scripts/stress-test-docker.sh --help`
- `bash scripts/stress-test-docker.sh --dry-run`
- 使用 Python 3.11 解析脚本内嵌的请求生成器，并对采样循环进行后台进程冒烟检查。
- 使用本地回环 HTTP 服务验证预期 301、拒绝未预期 302、禁止自动跟随重定向及代理旁路，不访问外部服务或真实设备。
- 用户部署主机初版报告用于验证脚本行为；更新后的 `--run` 尚需在该主机重新执行，本工作区没有 Docker CLI。

## 风险与回滚思路

- 只读探测仍会增加服务 CPU 和网络请求；因此默认不执行，运行模式逐容器串行并限定并发、RPS、持续时间，支持中断时清理临时请求容器。
- 本脚本不制造 OOM 或磁盘写入压力，不能替代数据库写入/持久化基准；不触发真实 SNMP 轮询，避免给生产设备增加负载。
- 初版部署报告中除 PostgreSQL 外的阶段均失败，不能作为其他服务的容量证据；更新后仍需在部署主机复测确认代理旁路、Redis ACL 兼容性和 `during` 采样。
- 回滚只需删除新增脚本和本任务归档文档，不涉及容器或数据变更。
