# 设备版本字段兼容修正实施计划

## 任务目标

修正平台识别流程写入不存在的 `physical_assets.version` 字段，并用受跟踪的 PostgreSQL 迁移保证既有设备表具有 `devices.version`。

## 现状与证据

- 附件中 3 次 `POST /api/devices/{id}/platform-detect` 500 与 PostgreSQL `column "version" does not exist` 毫秒级对应。
- `platform_identification_service._persist_discovered_version` 在发现设备版本时更新 `devices.version`，随后还会更新 `physical_assets.version`；fresh schema 对 `physical_assets` 从未定义 `version`。
- `devices.version` 存在于 fresh CREATE TABLE，但旧表兼容补列列表和迁移中缺失；识别代码在缺列时会跳过写入，但其他设备列表 SQL 会读取该列。
- PostgreSQL 日志未包含 STATEMENT，字符位置与当前资产更新 SQL 不一致；当前根因是仓库源码中可直接确认的 schema 缺口，但日志与部署镜像版本仍需在运行时确认。
- APScheduler 的 193 次跳过表示同一进程同一 job 尚未结束，任务仍受 `max_instances=1` 保护；提高并发可能造成重复设备连接或额外数据库竞争。本次保留调度器保护与触发周期，先把该项作为已定位的 backpressure 记录，后续需结合运行时长和当前日志决策。

## 影响范围与文件边界

- `backend/services/platform_identification_service.py`：只持久化 `devices.version`，移除对不存在的资产列的同步。
- 新增 `backend/database/migrations/m0274_add_device_version_column.py`：为既有 `devices` 表幂等补齐 nullable `version TEXT`；fresh schema 已有该列，迁移应无副作用。
- 不改 APScheduler 周期、max_instances 或 CLI concurrency；不执行数据库迁移、不部署。

## 实施步骤

1. 删除 `_persist_discovered_version` 中对 `physical_assets.version` 的 UPDATE，使无效 SQL 不再回滚设备版本事务。
2. 添加 PostgreSQL-only 版本化迁移 `m0274`，使用 `ADD COLUMN IF NOT EXISTS` 补齐历史设备表。
3. 检查差异、迁移序号/发现机制与配置；记录尚待运行环境确认的 SQL 语句偏移和调度任务耗时。

## 验证计划

- 本轮上级约束不运行测试或业务构建；静态检查代码与迁移内容。
- 不连接或修改用户数据库；不执行迁移。
- 原有首页实现只降低一条重型轮询路径，是否消除了后续调度 skip 需要新的部署日志确认。

## 风险与回滚

- 迁移新增 nullable 字段且无数据回填、约束和索引；回滚代码无需清除已存在列。若 migration 尚未部署，可移除文件；一旦部署，保留该无害列。
- 当前日志缺 SQL STATEMENT，修复消除源码中确定的无效 SQL，但仍需在相同镜像版本重新观察才能最终对应日志行。
- 调度 skip 是保护机制的结果，不是队列任务丢失的直接证据；盲目提高并发或改变周期可能增加设备会话和连接池压力。
