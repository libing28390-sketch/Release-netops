# 调度锁与数据库时区修复计划

## 目标

修复 scheduler_locks 竞争时 PostgreSQL 报重复主键、任务完成后锁仍占用到 TTL 的问题；把锁时间改成 PostgreSQL `TIMESTAMPTZ`，并显式让 Docker PostgreSQL 默认按 `Asia/Shanghai` 显示。

## 现状与问题

- `scheduler_locks` 的 `locked_at` / `expires_at` 为 TEXT；部分消费者把 `locked_at` 当 UTC 时间，Reindex/Import 消费者则把它当 owner token，字段语义冲突。
- `core.scheduler_lock` 采用先删过期行再 `INSERT`，唯一键冲突被 Python 捕获，但 PostgreSQL 仍记 ERROR；同步/异步 job decorator 和动态任务完成后没有释放锁，TTL 是 55–300 秒。
- Reindex 和 Import 租约已有 owner token / heartbeat / release，但把 token 存于 `locked_at`，且 acquire 采用可能触发重复键异常的 delete + insert。
- Compose 有 OS `TZ`，但未明确 PostgreSQL session `TimeZone`；现有 TEXT 值不会被 PostgreSQL 自动转换。正确做法是 TSTZ 存绝对时刻、数据库默认时区负责显示。

## 影响范围与拟修改文件

- `backend/database/migrations/m0229_scheduler_lock_leases_timestamptz.py`：新增 `owner_token` 并将锁时间字段迁移为 TSTZ，保留旧 owner token 与 expiry。
- `docker-compose.yml`：显式设置 PostgreSQL `timezone` 与 `log_timezone` 为 `TZ`（默认 `Asia/Shanghai`）。
- `backend/core/scheduler_lock.py`：原子 acquire、owner-fenced heartbeat/release；job 生命周期通过 `finally` 释放并由 TTL/心跳保护长任务。
- `backend/services/scheduler_service.py`：动态任务包装器释放自己的锁并保证 loop 清理。
- `backend/ai/services/knowledge_reindex_service.py`、`backend/services/ingestion_job_lease_service.py`：owner token 改用独立列，时间值适配 TSTZ，竞争使用冲突安全 SQL。
- `backend/ai/services/job_observability.py`：兼容 PostgreSQL 返回 aware datetime。
- 调度锁、Reindex、Import、迁移和时区相关 pytest 文件。
- DB-022 / ING-017 / OBS-007 相关契约和 DOC-004 Reindex 运维文档（同步 owner-token 与时间列语义）。
- 对应 `docs/walkthrough/` 走查。

## 实施步骤

1. 确认所有 scheduler_locks 消费者和既有锁行语义；保留 Reindex/Import 的 owner fencing。
2. 新增 version 229 幂等 PostgreSQL migration：已有 ISO UTC 时间转 TSTZ；非时间型旧 `locked_at` 值迁入 `owner_token`；重建 expiry 索引。
3. 把核心调度锁、动态任务、Reindex 和 Import claim 统一改为 `ON CONFLICT ... WHERE expired ... RETURNING` 的原子抢锁；更新租约心跳与 owner-token 释放。
4. 设置 Compose PostgreSQL session/default `TimeZone` 为 `Asia/Shanghai`；不修改、不删除现有 PostgreSQL volume。
5. 补竞争、释放、过期接管、fencing、migration 数据保留、TSTZ 本地显示测试，并同步契约文档。
6. 运行定向 PostgreSQL pytest、PostgreSQL-only scanner、Compose/YAML 静态检查和 diff 检查；通过后按用户授权在 `main` 提交并推送，Release workflow 负责发布前全量测试；不直接操作用户服务器。

## 验证计划

- 定向测试 scheduler lock 原子竞争、TTL 接管、长任务 heartbeat、结束释放与 stale owner fencing。

## 风险与回滚思路

- 迁移必须识别旧 `locked_at` 中的 ISO 时间与 opaque token，绝不能把 token 强转为时间；变换范围仅限锁表，保留 lock_name 和 expiry。
- `TIMESTAMPTZ` 保存绝对 instant；`TimeZone=Asia/Shanghai` 只控制输入解释/查询显示，不改变已经存储的瞬时时刻。
- 原子冲突更新确保竞争失败返回 0 行而不是 PostgreSQL unique violation；owner_token 条件防止旧 worker 删除/续租新 worker 的锁。
- 若 Compose 变更导致配置问题，回滚命令行 GUC；不要删除/重建 pgdata。迁移后不将时间解释退回无时区文本，可通过应用回滚版本兼容 TSTZ 读取。
