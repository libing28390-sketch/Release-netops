# LibreNMS 自动关联与诊断反馈实施计划

## 目标

在保留 LibreNMS 原生 discovery/poller 为唯一硬件采集引擎的前提下，资产设备导入后将管理 IP 和已绑定的 SNMP 凭据 Profile 传给 LibreNMS 添加设备 API，由 LibreNMS 负责 OS 识别、Discovery 和 Poller；随后 Nexora 自动建立本地 `device_id` 关联，使 SNMP 诊断页能直接读取原生硬件快照。同时兼容 LibreNMS 已存在设备、明确报告失败原因，并修复 cAdvisor 反复读取 smaps 的配置原因。

## 现状与问题

1. LibreNMS 原生硬件结果 API 只在 `librenms_device_bindings` 中存在显式记录时读取。诊断页目前将缺少记录显示为“未绑定”，即便 LibreNMS 可能已经按自动发现收录了设备。
2. LibreNMS 设备列表 API 支持按 IPv4 查找，设备 IP API 可返回设备关联地址；当前 Nexora API 客户端未提供这两个用于精确关联的能力，绑定仅支持显式 ID。
3. 诊断服务把本地投影同步状态 `pending` 当成读取原生结果的阻断条件。投影状态不应阻止读取 LibreNMS 当前快照。
4. 绑定写入时会将空租户规范成站点租户或 `tenant-default`，但诊断查询直接依赖请求目标里的 `tenant_id`；该字段缺失时可能把已有绑定误报为“未绑定”。
5. `docker-compose.yml` 对 cAdvisor 显式指定 `--disable_metrics`，该参数列表遗漏 `referenced_memory`，使 cAdvisor 仍尝试读取进程 smaps，并周期打印告警。
6. Nexora 保存的 `snmp_credential_id` 目前用于自身采集器，不会自动出现在 LibreNMS。LibreNMS 自动发现只尝试 LibreNMS 自身全局配置的 SNMP 凭据；要按 CMDB 为单台设备确定 Profile，需调用官方 `POST /api/v0/devices` 并传入该设备凭据。
7. Nexora 资产凭据绑定入口和导入模板目前只允许 `snmpv2`；凭据中心和 exporter 编译器已有 `snmpv3` 字段，但资产无法选择/绑定 SNMPv3 Profile，需要同步扩展校验和表单筛选。
8. 新增设备 API 是远端写操作。只应在导入的网络设备具有明确管理 IP 与有效 SNMP Profile，并且存在唯一已启用、健康的 LibreNMS 实例时调用；不使用 `force_add` 或 ping-only 回退。远端失败不能回滚已保存的 CMDB 资产，也不能留下虚假的本地 binding。

## 影响范围

- 后端 LibreNMS REST 客户端、资产设备自动纳管/关联服务、硬件诊断服务和资产导入 API。
- SNMPv2/SNMPv3 资产 Profile 校验、导入模板和资产编辑表单。
- 后端 LibreNMS 客户端/诊断/自动纳管测试及对应前端测试。
- SNMP 诊断页和资产导入结果中的纳管状态说明。
- cAdvisor Compose 参数及其配置契约测试。
- 本计划和对应 walkthrough；不改数据库 schema，沿用唯一 `device_id` 与 `(instance_id, librenms_device_id)` 约束。

## 实施设计

1. 只考虑管理员已登记、健康且启用的 LibreNMS 实例。用现有加密 API-token credential 访问 LibreNMS，不记录或返回 token。已有设备可在多个实例间精确匹配；新设备仅在恰好一个健康启用实例时自动新增，多实例时拒绝猜测目标。
2. 资产导入以 CMDB management IP 作为 LibreNMS hostname/地址，SNMP 端口取资产记录；读取其 `snmp_credential_id` 指向的凭据。v2c 传 `snmpver/community`；v3 传 `snmpver/authlevel/authname/authpass/authalgo/cryptopass/cryptoalgo`。SNMPv3 secret 仅在服务端解密，并通过已校验的 HTTPS API 客户端发送。
3. 先用 LibreNMS 官方设备列表和设备 IP API 查找唯一精确地址。唯一现存候选通过官方 `PATCH /api/v0/devices/:device_id` 更新 `snmpver`、端口及版本对应的凭据字段，再建立本地 binding；切换版本时清空另一版本的旧 secret 字段。没有候选时仅当恰好一个 LibreNMS 实例可用，才调用 `POST /api/v0/devices`。两条路径都使用该资产绑定的 Profile；不使用 `force_add`、`ping_fallback` 或网段扫描。hostname/sysName/display 仅用于展示，不作为自动认领依据。
4. 新设备 POST 成功或超时后，用官方地址 API 重新查询并精确核对 IP；若唯一匹配，绑定前确认该设备已使用本次 Profile。已有设备 PATCH 成功后才持久化本地 binding。并发冲突、重复地址、多实例重复候选、凭据/API 不可用均不覆盖既有关联，返回可识别原因。
5. 远端纳管在资产导入数据库提交后执行，按行返回纳管结果；LibreNMS 不可用、权限不足或 Profile 无效不能回滚 CMDB 导入，也不能新建本地 binding。已有设备 Profile 更新通过固定字段白名单完成。每次远端纳管尝试记录审计事件但不包含 secret；重试先查远端 IP，确保幂等。
6. SNMP 诊断按数据库中的规范租户和资产身份解析已有关系；在确实缺少关系时只做精确匹配，不从只读诊断页面隐式新增远端设备。成功后读取 LibreNMS 保存的传感器、CPU、内存、无线和光模块数据。`sync_status=pending` 仅表示 Nexora 的时序/库存投影待同步，不阻止诊断 API 返回原生样本。新设备何时出现硬件样本由 LibreNMS 原生 discovery/poller 调度决定。
7. 不自动扫描设备网段，不在 Nexora 执行硬件 OID 识别或采集。OS profile、设备指纹和后续 Discovery/Poller 全由 LibreNMS 原生逻辑处理。
8. 在 cAdvisor 显式禁用列表追加 `referenced_memory`，保留 CPU、working-set memory 等当前 dashboard 依赖的指标。
9. 修正网络总览 CPU、内存和温度覆盖设备数：只统计对应的 LibreNMS 原生硬件样本，移除与 Nexora `network_snmp` exporter 在线状态的交集及其零值兜底，避免旧采集链路屏蔽原生数据。

## 验收标准

- 已自动加入 LibreNMS 且唯一 management IP 与 Nexora CMDB 完全匹配时，用户不需手工填写 LibreNMS `device_id` 即可读取 CPU/内存/硬件原生快照，并生成经过审计的本地绑定。
- 导入含唯一管理 IP 和有效设备 SNMPv2/v3 Profile 的网络资产后，新设备使用 LibreNMS add-device API 纳管；已有设备通过官方设备字段接口更新成所选 Profile。Nexora 依据唯一、精确匹配的 native device ID 自动建立绑定。
- 未被 LibreNMS 发现、实例未配置/不可用、地址重复或匹配冲突时不会创建错误绑定；诊断明确告诉用户是哪种情况以及需要检查 LibreNMS 发现配置。
- 纳管只使用设备级 LibreNMS API，不扫描网段、不使用 `force_add`/ping-only、不启动即时设备采集，也不把凭据暴露到页面、导入结果或日志。LibreNMS 失败不影响 CMDB 导入，结果可安全重试。
- 多个已启用 LibreNMS 实例时，不会把新设备猜测性地加入某一实例；已有设备仍可按唯一精确 IP 自动关联。
- binding 投影 `pending` 时仍可通过诊断读取 LibreNMS 当前保存样本。
- cAdvisor 禁用 `referenced_memory` 后不再因 smaps 指标读取路径产生该类警告；dashboard 所依赖 CPU 和 working-set memory 未被禁用。
- Grafana CPU、内存、温度覆盖设备数只由具备对应原生样本的唯一 `asset_id` 决定，不受 `network_snmp` exporter 在线状态影响；无样本时保留 No Data。
- 专项自动化验证通过；真实 LibreNMS 实例和真实设备的运行时验证单独标明，不以 mock 测试代替。

## 风险与回滚

- LibreNMS 搜索结果、Add Device API 与 IP 地址 API 可能受版本、权限或设备地址布局影响；精确复核会拒绝错误绑定。请求超时后先重新查询，不能盲目重复添加。
- 新设备添加需要 LibreNMS 创建设备权限；已有设备 Profile 更新需要设备更新权限。只读 token 会显示纳管失败，但不会影响已导入的 CMDB 资产。已有设备 PATCH 只表明配置字段已接受，实际 SNMP 可达性与硬件样本仍由后续 LibreNMS poller/discovery 结果确认。
- 一个 management IP 在多租户 CMDB 重复时不自动关联；清理重复资产或通过人工明确指定实例/设备处理。
- 自动绑定按现有唯一约束串行化/幂等；唯一键冲突不覆盖手工绑定。可停用 LibreNMS 实例立即停止新匹配与后台采集，已有绑定可按现有 API 停用。
- 若 cAdvisor 指标有其他使用方，新增禁用项会停止 `container_referenced_bytes`；仓库 Grafana 看板不依赖该指标。回滚只需移除该参数。
- HCL/生产实例的 API 行为、自动发现设置和现场数据仍须运行时验证；代码级测试不证明真实设备已被 LibreNMS 收录或提供 CPU/内存样本。
