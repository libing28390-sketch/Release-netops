## 追加范围：厂商硬件指标恢复

目标是在保持 v83 SNMP 基线目标的前提下，按仓库固定的 LibreNMS commit `6c26b4fe4a40f7b392c19c36a44257212736e38c`，补齐当前 9 台 Cisco/H3C 设备在 LibreNMS OS PHP/MIB 规则中定义的 CPU/内存发现和轮询。传感器只有在 PHP 来源和依赖 MIB 均能通过 manifest 哈希校验时才可作为 `librenms_os_rule` 信任；现有 YAML `librenms_rule` 路径保持独立。

- Cisco IOS 路由器：CPU 优先使用 CISCO-PROCESS-MIB `cpmCPUTotal5minRev`，再按 LibreNMS 顺序回退；内存依 CISCO-MEMORY-POOL-MIB used/free 计算比例。
- Cisco vIOS-L2：按 LibreNMS `avgBusy5` 回退 CPU；只有设备实际返回上游 memory pool 数据时才生成内存传感器，不猜测未提供的内存。
- H3C Comware：依 HH3C-ENTITY-EXT-MIB CPU/内存 usage，并按 ENTITY-MIB 的实体类型和名称应用 LibreNMS module/nonzero 规则。
- 更新计划轮询/指标来源筛选，让新来源可信数据可采样和导出；新发现版本触发一次重发现。
- 验证：来源篡改/缺失拒绝、索引和回退规则单测、硬件 poller、metrics/provider/API 定向测试；部署仅重建/重启 `netops` 后端，保留数据库及 v83 collector artifact。
- 生产核验按设备统计 CPU/内存新样本。Cisco vIOS-L2 若 MIB 不返回内存，作为上游来源能力限制明确报告，不以旧 adapter 历史数据冒充恢复。
- 回滚：保留本地代码和生产后端镜像/文件备份；如发现异常，仅回滚后端镜像/代码，不回滚 v83 采集目标、不清理指标或数据库卷。

## H3C AP/无线采集诊断（2026-10-09，Asia/Shanghai）

- AC_11 CLI 显示 AP_12 和 AP_13 均为 `R/M`。生产库也留有旧无线发现记录：4 条 AP、80 条 radio、9 条 controller 传感器，来源为 `h3c_wireless`；这些记录属于 `legacy_snmp`、`enabled=false`，没有当前 discovery version。旧能力状态最后成功于 2026-10-08 19:19；无线传感器最后样本为 2026-10-09 06:49。
- 当前 10:46 的新版硬件发现只产生 LibreNMS `librenms_rule` / `librenms_os_rule` 类别，不生成 wireless 类别。Grafana 无线面板按 `source_type="librenms_rule"` 过滤，因此数据库中的旧 `h3c_wireless` 记录不会显示或继续采样。
- 这不是 AC/AP 在线状态或 `network_snmp` 基线目标缺失。固定 LibreNMS commit 的 Comware OS 类实现 CPU、内存池和收发器发现，没有实现无线 AP/radio 发现；仓库中存在 `HH3C-DOT11-*` MIB 文件并不等同于存在相应 LibreNMS 采集规则。
- 按“所有采集规则都用 LibreNMS”的要求，没有重新启用旧本地 `h3c_wireless` 采集器或将其伪标为 LibreNMS。要恢复 AP 面板，需要先在固定的 LibreNMS 来源中补足 Comware wireless discovery/polling，再将其作为经过来源校验的规则接入库存和指标路径并重新部署。当前生产部署不包含这一步。
