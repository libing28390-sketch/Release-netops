# 对象存储管理页面

## 任务目标

在 Nexora 管理界面增加类似参考截图的对象存储设置页，允许管理员保存多个 S3 兼容连接配置、测试连接、编辑/删除配置并选择全局默认；同时按用途独立选择连接 profile、可选 Bucket 覆盖与 object key 前缀。配置备份和 PAM 录像可共用同一 profile，也可分别配置。

## 现状与问题

- Docker 部署通过 `.env` 提供 `STORAGE_BACKEND`、S3 endpoint、bucket 和访问凭据，目前没有管理 S3 配置的前端页面。
- 现有存储接口已经将 bucket、object key 和 provider 类型写入配置快照及 PAM 会话记录，当前后端只根据部署环境变量构建 S3 客户端。
- 配置备份与 PAM 录像使用相同的 S3-compatible 协议；用途路由决定由哪个 profile、Bucket 和 key prefix 保存。默认前缀保持 `config/` 与 `pam/`，新用途可注册到通用路由机制，不需新增 S3 Endpoint。
- 数据库凭据加密工具 `core.crypto.encrypt_credential` / `decrypt_credential` 可用于保护新存储配置中的 Access Key 与 Secret。
- 更换默认存储后，旧对象必须继续通过原有环境配置或记录中的配置 ID 读取；删除仍被对象引用的配置必须被阻止。

## 影响范围

- 后端：S3 profile CRUD/连通性检查 API、按用途的存储路由 API、对象存储服务配置选择、配置快照与 PAM 录像写入/读取、路由注册。
- 数据库：新增 S3 配置表和用途绑定表；为配置快照和 PAM 会话增加可空 provider 配置 ID。
- 前端：管理菜单、对象存储配置页面、表单/API 类型及中英文文案。

## 实施步骤

1. 增加 PostgreSQL 迁移：保存 S3 profile 元数据及加密凭据；为快照/会话增加 nullable provider config ID；新增用途绑定（`default` / `environment` / `profile`、可选 Bucket 覆盖、key prefix），并以现有 `config/`、`pam/` 作为初始前缀。
2. 扩展存储服务，使新写入按用途解析 route 并将用途 prefix 组合进 object key；对象行持久化最终 profile、Bucket、完整 key。旧记录按其 provider ID/Bucket/key 读取，无 ID 的旧 S3 记录继续使用 `.env` 兼容配置。
3. 增加管理员专用 API：profile CRUD/连接测试与通用用途路由读取/更新 API。API 不返回明文凭据；留空凭据更新时保留已保存值；阻止删除仍被对象或用途路由引用的配置。
4. 管理界面按用户参考图呈现：页面内使用简洁页签和表格列出存储配置；新增/编辑从右侧抽屉打开，按“基本设置 / S3 / 其他设置”组织字段；用途路由放在独立页签，保留 profile、Bucket、前缀、测试和对象 key 预览。当前后端没有独立的“命令存储”配置契约，因此不展示无实际功能的占位配置。
5. 复核失败上传重试继续使用首次绑定的 profile、迁移/权限/密钥脱敏/旧对象兼容性；说明知识库尚需独立对象引用和生命周期接线；编写 walkthrough。

## 验证计划

- 检查新增迁移对现存版本和全新数据库均为幂等、PostgreSQL 兼容。
- 检查 S3 配置 API 的授权边界、凭据加密/脱敏、输入校验、测试失败脱敏及被引用配置删除保护。
- 检查用途路由解析、新对象记录 provider ID/Bucket/完整 prefix key，以及未绑定 provider ID 的旧记录仍使用 `.env`。
- 检查用途切换只影响新写入、失败 spool 重试保留 route，前端路由/管理员权限/前缀预览。
- 本轮不操作用户生产部署或真实 S3 数据。

## 风险与回滚思路

- `CREDENTIAL_ENCRYPTION_KEY` 必须在部署环境中保持稳定；丢失或更换后，数据库内加密的 S3 凭据不可解密。
- 全局默认变更只影响 `provider_mode=default` 的用途后续新写入；明确绑定环境或 profile 的用途不受影响。已有对象保留 provider ID、Bucket 和完整 object key，继续指向原位置。
- 知识库目前在 `ai_document` 中保存 `original_content`、`normalized_content` 和检索 chunks；用途路由本身不会把这些内容自动迁移到 S3。将来若需把知识源文件归档到 S3，还需在文档版本/来源记录中保存 provider ID、Bucket、object key、hash/size/content type，接入下载、删除、租户授权、保留策略和既有数据迁移；检索所需的规范化文本、chunks 与向量仍按知识库当前模型处理。
- 后续增加知识库用途时，复用本次 usage API 和绑定表，添加 purpose registry/seed 与知识库 writer，不为每种业务另造 S3 Endpoint 或独立 API。映射只应用于新对象，既有对象继续按记录的 provider ID、Bucket 与完整 object key 读取。
- 删除已被对象引用的 provider 必须拒绝，避免对象无法读取。
- 回滚时保留新增表和 nullable 字段，旧应用仍按 `.env` 工作；恢复旧版本后不要删除数据库对象数据或现有 `.env` S3 参数。

## 分工

- 主 Agent：维护本计划与 walkthrough，定义 API 契约，审查整合与安全边界。
- Backend worker：独占后端迁移、存储服务、API 和后端接线文件。
- Frontend worker：独占 `src/` 页面、导航、路由与 API 类型；按本文 API 契约实现 UI。
- 两个 worker 不共同修改文件；主 Agent 在两侧完成后负责协调契约并集成。
