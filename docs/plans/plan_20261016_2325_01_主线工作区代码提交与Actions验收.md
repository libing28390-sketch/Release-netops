# 主线工作区代码提交与 Actions 验收

## 任务目标

将当前工作区所有有意保留的源码、测试、迁移、部署配置和任务文档提交并推送到 `main`；通过浏览器检查由推送触发的 GitHub Actions。若工作流失败，定位并修复原因，重新推送并验证成功。

## 现状与证据

- 当前分支为 `main`，推送前的 HEAD 与 `origin/main` 一致，基线为 `c6162768`。
- 工作区有 55 个已跟踪文件修改，以及新增迁移、测试、凭据表单策略源码和多项任务文档。
- 存在大量本地构建验证目录和 `logs/` 诊断产物；它们不是源码交付，不应随“全部代码”推送。
- `release.yml` 对 `main` 的每次 push 都运行 Linux/Docker 门禁，成功后会将清理后的 Ubuntu 发布树强制同步到 `libing28390-sketch/Release-netops`。

## 影响范围

- 当前分支上累积的前后端源码、数据库迁移、自动化及监控逻辑、测试、部署配置、跟踪文档和跟踪的 `dist/index.html`。
- 推送触发的 `Build and Sync to Release Repo` 工作流及其公开发布仓库同步步骤。

## 拟修改文件

- 不额外修改业务源码；保留当前工作区已有的全部有意代码修改。
- 新增本任务的计划、走查记录和 `docs/fixes/` 提交记录，并纳入提交。
- 不纳入 `.codex-build-*`、`dist-*` 本地构建目录或 `logs/` 诊断文件。

## 实施步骤

1. 核对 `main` 与远端提交关系、所有跟踪及未跟踪文件，审查触及部署和秘密的数据；并行只读审查后端/部署与前端/文档边界。
2. 运行与当前改动范围相符的本地检查，并确认 CI 的实际触发条件和发布副作用；修正本地测试发现的巡检脚本契约不匹配和窄超时用例。
3. 建立显式提交清单：包括所有跟踪文件修改、源码/测试/迁移新增项及正式任务文档，排除本地构建目录和诊断日志。
4. 按项目规范创建本提交的 `docs/fixes/fix_*.md` 记录，再将清单提交到 `main`。
5. 推送到 `origin/main`，在浏览器中打开本次提交对应的 Actions 运行，观察所有必需作业完成；失败时按日志修复、提交并重复验证。
6. 将最终提交、推送、Actions 结果和未验证风险写入 walkthrough。

## 验证计划

- `git status --short --branch`、提交图和 `origin/main` 对比：确认提交只含工作区目标修改且远端 main 前进到新提交。
- `git diff --check`、`npm run lint`、前端构建，以及适用的后端/前端测试。
- 使用浏览器查看 GitHub Actions 本次推送运行；确认必需工作流与发布步骤均为成功状态。
- 推送后再次检查 Git 状态，并确认发布同步来自该提交的成功运行。
- Actions 成功后通过 SSH 在 `192.168.204.128` 执行用户指定的 Docker 更新命令，并检查 Compose 容器健康状态。

## 风险与回滚思路

- `release.yml` 的 main push 路径成功后会强制更新单独的公开发布仓库；这属于该 Actions 的既有行为，应在推送前审阅并在结果中明确说明。
- 本地后端 pytest 的 autouse fixture 会在创建隔离测试模板之前对配置的源数据库调用 `database.init_db()`；本机数据库名称未标识为 test/ci/eval，已有一次测试启动触发该调用。后续本地不再运行 DB 测试，使用 GitHub Actions 的专用 PostgreSQL 测试数据库验证。
- 多日累积改动范围较大，CI 可能揭示历史遗留问题；依据失败日志修复当前改动相关问题，避免无证据扩大范围。
- 不使用 reset、clean 或覆盖式复制；若推送后的业务代码需要回滚，用后续审阅过的 revert 提交，不改写 main 历史。
