# AI 质量与 RAG 架构改造实施计划 (无幻觉落地版)

## 一、 任务背景与核心目标

当前 Nexora NetOps 经过前期单轨化治理，工程骨架与基础测试已高度稳定（底层数据库已单轨收敛至 PostgreSQL，API 契约测试通过）。然而，AI 业务层面临**“通用组件自研过重、真实回答质量欠缺评估、网络领域检索排序偶现污染（如 VLAN 查询召回 Smart Licensing）”**等现实质量痛点。

本计划旨在落实 [handoff.md](file:///D:/nexora/nexora-private/handoff.md) 与 [AI改造计划.md](file:///D:/nexora/nexora-private/AI%E6%94%B9%E9%80%A0%E8%AE%A1%E5%88%92.md) 的指导方针，遵循**“绝对不推翻现有工程骨架、零外部侵入主进程、数据驱动灰度切换、异常 100% 自动降级”**的原则，分阶段将低效自研通用组件替换为业界成熟开源方案。

---

## 二、 严格不可动边界与防 Bug 红线（Invariants）

为了确保系统稳定性，避免引入新 Bug，必须恪守以下**不可动边界**：

1. **核心自研防线严禁外部替代**：
   - `LLMGateway`：多 Provider 路由、熔断、流式输出与审计边界保持不变。
   - `Security Vault / DLP`：敏感信息识别、凭据脱敏、出向请求拦截绝对保留。
   - 租户、ACL 与网络领域模型：Tenant 隔离、设备资产、Vendor/Platform/Version/Feature 元数据为核心事实源。
   - 工具注册与高危操作审批：`ToolRegistry` 与危险命令二级确认流程必须由 Nexora 内部控制。
2. **主容器环境与资源隔离底线**：
   - 目标运行环境应为主应用与重型 sidecar 分离，并按目标环境容量评估资源；当前仓库 `docker-compose.yml` 主应用保持 `2 CPU / 2GB` 基线，禁止将 PyTorch、Docling、FlagEmbedding 或 Langfuse 写入主 `requirements.txt` 或打包入 `NetOps.exe`。
   - 重型计算组件必须作为独立 Sidecar / 独立 Docker 容器部署，主进程仅通过超时保护的 HTTP 进行通信。
3. **检索硬过滤前置原则（防止领域污染）**：
   - 任何 Reranker（如 BGE）只能在**已通过租户隔离、厂商匹配、平台校验、特性过滤**的合法候选池内进行相关性微调，绝对不能跨厂商、跨租户进行候选重排。
4. **异常 100% 降级保活原则**：
   - 任何 Sidecar 调用超时（默认 >300ms）或异常时，主检索流程立即静默回退至原有排序规则，严禁抛出 500 异常。

## 三、 分阶段实施路线（Phased Implementation）

```
阶段 0: 基线锁定与负向用例定义 (零业务代码变更)
   ↓
阶段 1: 50 条 MVP 黄金锚点集 + Promptfoo CI 门禁
   ↓
阶段 2: 检索候选池架构修正与硬过滤前置防护
   ↓
阶段 3: BGE Reranker 独立 Sidecar + 纯 Shadow 模式比对
   ↓
阶段 4: Docling 双轨文档解析验证 (PDF/DOCX)
   ↓
阶段 5: Metadata-only 可观测性旁路 (Langfuse)
```

---

### 阶段 0：基线锁定与负向防 Bug 用例定义

**目标**：固化当前代码质量指标，建立“防止常见 Bug”的负向回归用例集合，不改动任何生产业务代码。

1. **固化当前 Baseline Manifest**：
   - 记录当前单元测试通过数（`test_ret_011_020_retrieval_contract.py` 6 passed、`test_ing006_document_parser_adapters.py` 31 passed、`test_rag_retriever_v2.py` 5 passed 等）。
   - 记录当前离线检索基线准确率与 DeepSeek 样本识别率（5/8）。
2. **编写针对性防 Bug 负向测试用例（Negative Test Cases）**：
   - `TC-NEG-01`：**跨厂商污染拦截**（搜 Cisco VLAN，候选池混入华为 VLAN，校验硬过滤后华为文档绝对不能出现在前排）。
   - `TC-NEG-02`：**跨租户隔离拦截**（租户 A 检索，候选池不得出现租户 B 的私有知识库文档）。
   - `TC-NEG-03`：**高危操作安全拦截**（破坏性配置必须要求用户确认，AI 不能直接给出执行完毕指令）。
   - `TC-NEG-04`：**Reranker 超时与熔断降级**（Mock Sidecar 延迟 2 秒或返回 500，检索契约必须平滑降级到现有排序，返回结果非空）。
   - `TC-NEG-05`：**Context 展开防爆仓**（校验展开后的总 Token 数量不得超过最大上下文窗口预算）。

### 阶段 1：50 条 MVP 黄金锚点集与独立 Promptfoo CI 门禁

**目标**：不空等 400 条漫长标注，先用 50 条覆盖核心场景的黄金锚点建立自动化 CI 门禁。

1. **数据集构建**：
   - 12 条：直接采纳现有的 `eval-golden-annotations-v1.yaml` 标准答复。
   - 28 条：从 `eval-query-dataset-v1.yaml`（120条离线集）中筛选华为、Cisco、H3C、锐捷的经典配置与排障用例。
   - 10 条：故障排查与负向安全用例（包括 VLAN/Smart Licensing 污染案例文档、Prompt 注入用例）。
2. **Promptfoo 独立工作流搭建**：
   - 采用单独的 GitHub Actions / 本地测试工作流（CI 固定 Node 20.11.1 独立运行），不修改 Nexora 前端 `package.json` 依赖。
   - 设定首轮 CI 质量门禁：
     - 安全泄漏率 = 0
     - 越权工具调用 = 0
     - 核心 12 条 Golden Answer 命中率 = 100%
     - 检索召回率 Recall@5 ≥ 现网基线

---

### 阶段 2：检索链路候选池重构与硬过滤加固

**目标**：彻底修复 `backend/ai/services/rag_retriever.py` 中“先截断 `top_k` 再重排”的结构性缺陷，同时加固硬过滤。

1. **重构执行链路**：
   ```
   用户输入 Query
      │
      ▼
   1. 语义标准化与意图识别 (Query Plan)
      │
      ▼
   2. 严格硬过滤 (Tenant / ACL / Vendor / CLI Platform / Feature / 文档状态) ── [硬性阻断，不合规直接丢弃]
      │
      ▼
   3. FTS 全文检索 + pg_trgm + 向量召回 (混合检索)
      │
      ▼
   4. 文档级去重聚合，提取前 Top-N 候选池 (N=20~30)
      │
      ▼
   5. BoundedReranker 执行重排 (带 300ms 超时控制)
      │
      ▼
   6. 截取 Top-K (K=5)
      │
      ▼
   7. 受控上下文展开 (_expand_document_context，带最大 Token / 块数预算)
   ```
2. **严防回归的防护措施**：
   - 保持 `self.last_debug` 和 `build_retrieval_explanation` 返回的字典键值与结构完全兼容，避免前端或老单测报错。
   - 候选池大小 `top_n` 可通过配置动态微调（默认 20）。
   - 上下文展开增加 `max_chunks_per_doc` 保护，防止 Token 膨胀。

---

### 阶段 3：BGE Reranker 独立 Sidecar 与纯 Shadow 模式比对

**目标**：引入真正具备语义理解的重排模型，但在验证证明其明显提升且不破坏领域规则前，绝不直接切换生产返回。

1. **独立 Reranker Sidecar 服务**：
   - 编写独立轻量服务镜像（`nexora-reranker-sidecar`），搭载 `BAAI/bge-reranker-base`。
   - 暴露标准 HTTP 接口：`POST /v1/rerank`，入参为 `query` 和 `candidates: [{id, text}]`。
   - 容器与宿主机资源独立限制，只监听本地回环或 Docker 内网。
2. **实现 `BgeRerankerClient` 与 Shadow 运行机制**：
   - 在 `backend/ai/services/retrieval_contract.py` 中增加支持 Sidecar 通信的 Reranker 实现。
   - **Shadow 模式逻辑**：
     - 生产检索依然返回原有基础排序的 Top-K 给用户；
     - 异步或非阻塞调用 BGE Sidecar 计算重排顺序；
     - 将新旧排名的差异（Delta Rank）、MRR 变化、耗时记录到轻量 Shadow 观察日志中；
     - 当发生超时或错误时，静默捕获，不污染任何业务返回。
3. **切换门禁**：
   - 连续 7 天 Shadow 观测且 50 条黄金测试集上验证：Recall@5 不低于旧规则，且跨厂商污染完全消除。

---

### 阶段 4：Docling 双轨解析验证 (PDF / DOCX)

**目标**：针对复杂版面、表格和 CLI 命令手册，对比 Docling 与现有轻量自研解析器的质量差异。

1. **独立 `docling-serve` 部署**：
   - 通过独立 Docker Profile 启动 Docling 服务，禁止外部直接访问。
2. **适配器接入与对比**：
   - 在 `backend/services/document_parser_adapters.py` 的 `DocumentParserRegistry` 中注册 `DoclingParserAdapter`。
   - 采用增量对比模式：上传文档时，自研解析器生成生产 Chunk；Docling 旁路生成测试 Chunk。
   - 重点对比：CLI 代码块完整性、表格行列识别率、多栏混排连贯性。

---

### 阶段 5：Metadata-only 可观测性旁路 (Langfuse)

**目标**：补齐 Token、延迟、会话质量跟踪，但坚决杜绝敏感数据出境。

1. **数据脱敏与白名单机制**：
   - 仅导出脱敏元数据（`request_id`、`tenant_hash`、`intent`、`latency_ms`、`token_count`、`candidate_count`）。
   - 绝对禁止导出原始 Prompt、完整回答、设备 IP、凭据和配置命令。
2. **异步非阻塞 Exporter**：
   - 采用后台轻量任务推送，任何 Langfuse 服务故障绝对不影响用户正常问答响应。

## 五、 风险控制与应急回滚方案

1. **一键开关回滚**：
   - 所有改造组件均通过环境变量控制模式：
     - `AI_RERANKER_MODE=legacy | shadow | active`（默认 `legacy`）
     - `AI_PARSER_MODE=legacy | shadow | active`（默认 `legacy`）
     - `AI_OBSERVABILITY_MODE=off | metadata`（默认 `off`）
   - 一旦发现异常，通过改动环境变量或全局 Kill Switch 即可秒级切回原有状态。
2. **数据库稳定性保护**：
   - 阶段 0~3 不引入复杂的破坏性数据库迁移，仅使用既有的 V1 单轨表（`ai_document`、`ai_document_chunk`）。
   - 未来新建的实验或灰度表均作为只读/审计补充，杜绝外键级联锁死主业务表。
