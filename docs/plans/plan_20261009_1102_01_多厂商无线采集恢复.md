# 多厂商硬件与无线采集恢复计划

## 目标

修复 Python 采集链路和 Grafana 数据出口，使 LibreNMS 固定快照中可验证的硬件传感器、系统运行时长和无线 AP/客户端数据进入同一受信任库存与指标链路。无线规则以固定 LibreNMS 来源为准，由 Python 适配执行；停用重复的旧 Nexora 无线 SNMP Exporter 规则。逐厂商说明上游定义覆盖范围，未被上游规则/MIB 明确支持的指标不猜 OID、不伪称已覆盖。无线适配范围限定为 `backend/vendor/librenms/mibs` 已有的 23 个厂商桶，不引入目录外厂商或 MIB。

## 现状与问题

- 生产主机为 `192.168.204.128`，部署授权已在本任务前文明确给出；SNMP 基线目标此前已恢复。
- Python 执行器解析 LibreNMS `os_discovery` YAML 的处理器、内存池和传感器定义；Comware YAML 有风扇/电源状态与功耗，但 LibreNMS 的 Comware OS 类之外还有四个温度、dBm、voltage、current 发现源，当前 Python 规则绑定和执行器没有接入它们。
- LibreNMS 固定快照含 136 个 OS profiles、122 个硬件 discovery YAML。Wireless dispatcher 声明 20 个规则入口；Stellar 虽以空标准 OID 注册客户端传感器，但有 `apClientWlanService` 自定义轮询，Python 适配已同步该 walk 和每 SSID/总数聚合。固定 commit 中明确包含 Cisco WLC、Huawei VRP、ArubaOS 控制器的逐 AP/Radio 轮询；Aruba Instant 另有 AP 实体清单和逐 Radio 指标；Extreme EWC 有逐 AP/Radio 遥测。无线 Python 适配还覆盖现有 Cisco SAT、Ubiquiti AirFiber 三种型号和 Nokia TiMOS 射频/蜂窝规则；这些来源均属于当前已 vendored 的 Cisco、Ubiquiti、Nokia MIB 桶。
- `librenms_wireless_rule_service.py` 是执行 LibreNMS 来源规则的 Python 适配器，不是另一个上游来源，不能删除。用户要求停用旧 Nexora 无线 OID 规则并以 LibreNMS 来源规则为准。H3C Comware 类有 HH3C-DOT11 MIB，但固定快照/当前上游没有 Comware 无线采集器；H3C AP/Radio Python MIB adapter 是明确标注的项目补充，不得冒称 LibreNMS OS 无线规则。若要求 H3C 也完全来自上游，仍需 LibreNMS 上游先加入该采集器。
- `source-manifest.json` 需要纳入 ArubaOS 的固定 commit `includes/polling/aruba-controller.inc.php` 和统一入口 `LibreNMS/Modules/Wireless.php`，并核验 adapter/MIB SHA。无线来源校验须同时绑定统一 dispatcher 和厂商 OS 规则；dispatcher 存在不能替代 OS 类具体实现。
- 无线 MIB 文件数或设备识别标签不等于可执行采集规则；上游 PHP 是固定来源材料，所有新增轮询仍需由 Python 实现并通过 MIB/OID 来源校验。
- 当前硬件解析统计需分别说明：91 个 profile 有至少一项已识别定义，31 个有 YAML 但无处理器/内存/传感器定义，另 14 个没有硬件 discovery YAML；不要把“解析出 YAML”描述成“完全采集”。
- 系统运行时长的 Prometheus/API/UI 路径此前已补上，但需检查响应、页面格式和 Native/VictoriaMetrics 双后端行为，避免只在单个页面显示。
- 固定 LibreNMS commit：`6c26b4fe4a40f7b392c19c36a44257212736e38c`。生产规则执行为 Python；PHP 只作为固定上游来源材料读取，不执行。

## 实施步骤

1. 校验固定 manifest、Comware 的温度/光模块 LibreNMS 发现来源与 MIB 字段/单位；在 Python 中移植同等只读过滤、单位转换和索引语义。
2. 检查 YAML 风扇、电源状态、温度、功耗、光模块各类别从发现到 sample、Prometheus、Grafana/API/UI 的完整路径，补上缺失数据链路。
3. 核对系统运行时长的 Prometheus selector、Native/VictoriaMetrics API 和页面格式，补回归测试。
4. 对当前 MIB bundle 映射到的无线 profile 逐一分类，并将“AP/客户端”和“无线电/蜂窝信号”分开验收。覆盖固定 dispatcher 的全部 20 个上游规则入口，包括 Cisco WLC、Huawei VRP、ArubaOS、Aruba Instant、Extreme EWC、Stellar 自定义客户端轮询，以及 Cisco SAT、Ubiquiti AirFiber/AirFiber LTU/AirFiber 60、Nokia TiMOS 现有上游无线信号规则；保留 Wavence 的 YAML 规则在通用 Python 硬件采集路径执行。IOS-XE 按固定源码继承 Cisco WLC。把每个上游 Wireless 类及统一 dispatcher 固定到 manifest，来源 MIB 必须存在于当前 vendor bundle。禁用旧 Huawei/H3C/Cisco/Aruba/Ruckus/Ruijie SNMP Exporter 无线 variants 和现存 assignments，避免第二套无线规则。Comware 保留明确标记的 Nexora Python MIB adapter。核对 AP 连接数、配置数、注册数和 radio 数不被混加，不新增当前 vendor buckets 之外的供应商。
5. 检查所有硬件 measurement class 到 sample、Prometheus、诊断 API 和 Grafana 的可见性；明确保留 14 个无 YAML、31 个无已识别定义及用户函数需 adapter 的缺口。Grafana V2 mapping 必须覆盖新加的电压/电流 panels。
6. 增加来源篡改、SNMP walk 不完整、设备不支持、空表、错误索引、分类、单位转换和聚合口径测试；先跑聚焦回归，再运行相关后端回归、前端 lint/隔离构建与 PostgreSQL-only policy scanner。
7. 在已授权主机部署应用与新采集版本，等待 discovery/sample 周期后核验目标、样本、VM 指标、API 与 Grafana；保留应用镜像/artifact 回滚路径。

## 验证计划

- 校验 manifest 中 2,360 个 MIB 映射、258 个 YAML 规则文件与 29 个 adapter 文件的路径和 SHA-256；错误版本或被篡改来源必须 fail closed。
- pytest 覆盖 Comware 各传感器单位与索引、136 个硬件 profile 分类、通用 YAML state/power、uptime selector/API、仅使用现有 vendor MIB bundle 的无线 source matrix、Cisco/Huawei/ArubaOS/Aruba Instant/EWC AP/Radio 明细、Cisco SAT/AirFiber/TiMOS 信号轮询与不完整 walk、AP count 去重、旧 wireless OID variant/assignment 停用，以及 Grafana V2 和 PromQL contract。
- `npm run lint`、隔离输出目录的前端生产构建、dashboard generator、`git diff --check`、PostgreSQL-only policy scanner。
- 生产用只读 SNMP/数据库/VM 查询核验；对 AC_11 复核现有 AP 数、在线状态与指标，不写设备配置。

## 风险与回滚

- LibreNMS MIB 存在不等于 OS class 有对应发现规则；不同厂商的无线表索引和状态码不可共用一个通用假设。新增无线规则必须映射到现有 vendor MIB bundle，不扩展目录外厂商。20 个上游规则键的适配不表示每个 profile 都发现 AP 清单或逐客户端详情。
- SNMP 表扫描必须按已知 OID 和并发上限执行；任一关键 walk 不完整时不标记完整覆盖。
- 固定 vendor bundle 共 23 个桶：9 个桶在 pinned LibreNMS commit 中有无线 OS rule；另外 13 个没有上游无线规则，H3C/Comware 是额外的本地适配例外。验收以 20 个上游规则键逐一来源验证和 Python 测试为准，不把 MIB 存在误报为规则。
- 若新版本产生错误标签、单位或指标，回滚 NetOps 应用镜像/artifact 并把采集版本号回退；不重置 PostgreSQL/VM 存储卷，不重启无关服务，不触碰设备配置。

## 执行结果（2026-10-09）

- 已完成固定 LibreNMS bundle 的 profile、MIB、硬件 discovery 与无线来源盘点；运行代码为 Python，不安装/调用 PHP。Comware AP/radio 是基于固定 H3C MIB 的 Nexora Python adapter，因为固定 LibreNMS Comware OS 类没有 wireless discovery。
- 硬件执行器以 Python poll plan 执行 H3C 管理 TruthValue 映射；SNMP MacAddress 使用 OCTET STRING 原始字节格式化；硬件 metadata exporter 去除重复字段，保留 vmagent 添加的 `job`/`instance` 标签。发现版本升到 `nexora-librenms-rules-hardware-v7`，令现有设备重发现并刷新已保存 poll plan。
- 已部署到 `192.168.204.128`。collector-local v83 保持 18 assignments/9 devices；network_snmp 9/9 UP；`platform_hardware_inventory` 为 UP，最近抓取约 1.06 秒、抓取 2,770 样本，30 秒 timeout 余量充分。硬件 exporter 最近处理 602 sensor rows/9 devices/72 capabilities，render_errors=0、耗时约 1.04–1.07 秒。
- v7 当前采集样本：CPU 9 台均有好样本；内存 7 台，SW5/SW6 为 `not_found`；温度 84、光功率 96、电压 48、电流 48、功耗 238、风扇状态 3、电源状态 3，均为 good。上述机箱/光模块类别只在 SNMP 实际返回该类规则的设备出现；AC_11 的光功率/电压/电流为 `not_found`，不是空值伪装为 0。
- AC_11 的 AP_12/AP_13 均有 `run` 状态、正确 AP MAC、AP CPU 样本和 2 个 controller AP 数；controller 与 AP 客户端计数为 0。当前采集的是客户端计数，不包含逐终端 MAC/IP/SSID/RSSI 明细。4 个 radio 的信道/数值指标均可采集；MIB 当前 `hh3cDot11AdminStatus=2` 映射为关闭（0），`hh3cDot11OperStatus=2` 映射为 down。SNMP 原始值和 TruthValue 语义一致；`dis wlan ap all` 只证明 AP 注册状态，不能证明 radio 已启用或正在发射。
- `sysUpTime` 是 centisecond TimeTicks；API/Grafana 使用 20 分钟 `last_over_time` 并按采样时间外推。线上 VictoriaMetrics 对 9/9 设备均返回值：Cisco R1/R2/R3/R4/SW5/SW6 与 H3C AC_11/F1090-9/F1090-10，折算约 107,584–112,756 秒。

## v8 后的代码审查修正（2026-10-09）

- 逐项复核无线发现与轮询转换时发现 Cisco Cellular 的 RSRQ/SNR 只在发现值应用了 `0.1`，轮询计划未带倍率，导致后续样本会放大 10 倍；现已让 Python poll plan 沿用上游归一化倍率并增加原始值/样本回归断言。
- Huawei VRP 上游将同一 SSID 的 2.4 GHz 与 5 GHz 客户端数相加，并从全部 WLAN 表行统计控制器总数。Python 原执行器只读单一 OID，无法复现跨表聚合；现增加 `table_multi_sum` 计划，支持按匹配后缀或全表跨 OID 求和。不完整 walk 或完全无匹配行时不伪造样本。
- 深入核验上游 IOS AIR 的 ENTITY 描述映射时发现字符串排序会错配 ifIndex 2/10；现改为数字排序并增加乱序 walk 回归。Ruckus Hotzone 两个频段客户端传感器此前共享 identity suffix，现拆为与上游一致的 1/2 并补充逐 OID 的实际 poll sample 检查；另补 AirOS 主 profile 的负信号/距离/airtime 采样回归。
- 这两项是 v8 之后的代码收尾，不能记为已部署到生产；以本次提交和发布验证结果为准。
