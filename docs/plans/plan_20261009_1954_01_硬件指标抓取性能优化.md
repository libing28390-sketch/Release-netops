# 硬件指标抓取性能优化计划

## 目标

将 `/hardware-metrics` 的硬件来源校验与指标准备耗时降到 vmagent 抓取期限内，恢复 Grafana 硬件面板持续收到新样本，同时保持 LibreNMS 来源校验的 fail-closed 语义和现有指标格式。

## 现状与问题

生产日志显示硬件指标导出包含 3,847 条传感器、15 台设备和 144 条能力记录，响应约 9.2 MB，总耗时 78–100 秒；其中 `group_and_stale_ms` 占约 77–98 秒。vmagent 对 `/hardware-metrics` 抓取等待响应超时，硬件指标没有持续写入 VictoriaMetrics。接口流量仍正常。

代码在逐条遍历每个 sensor 时执行 `is_trusted_hardware_sensor`，而同一来源/规则的许多传感器会重复做完全相同的来源证明验证；随后也逐条检查采样新鲜度。优化将减少同一抓取批次内重复的可信来源判定，并验证结果不改变可信/不可信输入的输出语义。

## 影响范围

- `backend/api/grafana_metrics.py` 的硬件指标抓取准备路径。
- 硬件指标 API 的聚焦回归测试。
- 本次不改数据库结构、Prometheus 指标命名、LibreNMS 来源策略或设备采集逻辑。

## 拟修改文件

- `backend/api/grafana_metrics.py`
- 对应的 `backend/tests/` 硬件指标测试文件（先定位现有覆盖后再决定是否新增/更新）。

## 实施步骤

1. 检查可信来源验证需要的完整输入字段，基于当前 scrape 内的稳定 provenance 指纹缓存验证结果，避免遗漏会影响信任结论的字段。
2. 对重复的 provenance 仅执行一次校验；每条 sensor 仍需独立执行质量/新鲜度判断和指标渲染。
3. 增加回归测试，确保重复来源验证被去重，同时每条传感器数据仍被正确输出，未信任来源依然被拒绝。
4. 运行硬件指标与来源策略相关的聚焦测试，并记录测试前后可比的局部基准耗时或调用计数。
5. 按用户此前对该主机的部署授权，将只包含本次代码的可回滚镜像更新到 `192.168.204.128`；不改 vmagent/VictoriaMetrics 配置，不触碰监控数据卷。已完成，只重建 NetOps 服务。
6. 用生产日志、vmagent 抓取状态及 Grafana 设备详情页验证硬件指标恢复；已确认容器健康、接口耗时约 1.2–1.46 秒，Grafana 显示 CPU/内存/温度。vmagent 稳定后最近 3 分钟无硬件目标错误。
7. 清理未被容器使用的旧镜像，仅保留当前 NetOps 镜像和一个部署前回滚镜像；已完成。
8. 完成后更新对应 walkthrough。

## 验证计划

- 运行新增/相关的 Grafana hardware metrics API 测试。
- 运行 LibreNMS source policy 和硬件指标渲染相关测试。
- 检查 diff、测试结果及 `group_and_stale_ms` 的重复校验次数/耗时变化。
- 部署后确认 `platform_hardware_inventory` 抓取成功，`nexora_hw_*` 出现新样本，设备详情页不再显示空状态。

## 风险与回滚

- 主要风险是缓存指纹遗漏 provenance 字段而错误复用信任结果。缓存限定在单次 scrape，并以参与信任判定的完整规范化 provenance 输入为 key；仍由原有验证器作最终判断。
- 生产风险限于 NetOps 容器替换。部署前保留当前活动镜像的独立回滚标签；若健康检查或采集验证失败，只恢复该镜像并重建 NetOps 容器，不涉及数据库迁移或数据卷清理。
- 若性能提升同时改变了可信来源接受/拒绝结果或指标内容，则回退 API 中的局部缓存改动即可，不涉及数据迁移。
