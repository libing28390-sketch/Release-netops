# 手动新增设备复用导入补全流程

## 目标
让资产管理中手动新增的网络设备在提交后执行与表格导入一致的纳管补全：LibreNMS 纳管、SNMP 身份识别、监控采集目标同步；长耗时探测放在后台，避免阻塞新增接口。

## 现状与问题
`POST /api/assets` 创建并提交网络设备后只触发监控目标同步；`POST /api/assets/import` 在提交后还会排队执行 LibreNMS 纳管和 SNMP 身份识别。两种录入入口的设备补全过程不一致，可能造成手工新增设备缺少导入入口会触发的监控纳管和身份补齐。

## 影响范围
仅调整手动新增网络设备的后提交后台流程，复用导入入口已有服务；非网络资产继续使用现有监控目标同步。无需数据库迁移或前端页面改动；响应增加可选的 `enrichment_pending` 状态提示。

## 拟修改文件
- `backend/api/assets.py`
- `docs/plans/plan_20261013_0855_01_手动新增设备复用导入补全流程.md`
- 对应 `docs/walkthrough/` 执行记录

## 实施步骤
1. 对照手动创建与批量导入的提交后处理顺序、凭据解析和失败边界。
2. 在事务提交后为网络设备注册 FastAPI 后台任务，顺序执行 LibreNMS 纳管、SNMP 身份识别和监控目标同步；异常只记录安全上下文，不回滚已提交资产。
3. 保持非网络设备和现有响应字段行为不变。
4. 完成静态校验并记录结果。

## 验证计划
- `python -m py_compile backend/api/assets.py`
- 前端已有 `npm run lint` 结果为通过；如前端源文件无新增代码则引用该结果。
- `git diff --check` 检查本轮涉及的代码与文档。
- 不连接生产 Ubuntu、不访问真实网络设备、不运行 pytest。

## 风险与回滚
后台纳管/探测可能因设备离线、SNMP 凭据错误或 LibreNMS 不可用而失败；这些操作采用现有导入服务的安全失败语义，资产仍保持已提交状态，监控目标同步会在任务末尾执行。回滚时撤销手动新增路由的后台任务注册，保留原来的创建与同步逻辑。
