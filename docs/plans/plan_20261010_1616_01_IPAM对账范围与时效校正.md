# IPAM 对账范围与时效校正

## 任务目标

修正 IP 对账将范围不明的发现记录误报为未登记、将未分配/历史地址误报为离线，以及将过期端点缓存当作当前状态的问题；同步改进页面对数据来源、发现时效和刷新行为的说明。

## 对账基准

- **权威基准：IPAM 正式登记**。地址是否已分配、所属 tenant/VRF/前缀及生命周期状态以 IPAM 为准。
- **核验数据：`network_endpoints` 观测缓存**。它是从 ARP/MAC 等设备采集整理出的实际网络观测，用于比对 IP、MAC、主机名和站点；它不是完整资产名册。
- 采集数据只生成差异线索，不自动回写 IPAM。观测缺席本身不证明地址空闲；只有存在历史观测且达到 7 天未见，才列为“长期未发现”。

## 现状与问题

- `get_ipam_reconciliation()` 当前只查 `network_endpoints.is_active = 1`，不检查 `last_seen`，因此旧的活跃缓存仍可能参与对账。
- 无法解析 CMDB 设备或 VRF 的端点会得到空 scope key，但当前逻辑仍会把它们加入“未登记”列表。
- 地址状态未过滤；`available`、`released`、`reserved` 等非实际占用地址可能被列为离线 IP。
- 同 scope 地址跨站点出现时没有作为信息不一致展示，可能被当成正常匹配。
- 页面“重新对账”仅重新读取当前缓存，没有触发设备采集；“僵尸 IP”文案与立即释放动作夸大了当前证据。

## 修改范围

- 后端：`backend/services/ipam_service.py` 的对账读取和分类逻辑。
- 前端：`src/pages/IPVlan/IPReconciliationTab.tsx` 的时效说明、摘要和分类文案。
- 文档：本计划和对应 walkthrough。
- 不改采集调度、IPAM 状态模型、数据库结构或持久化 reconciliation run API。

## 规则与接口约束

- 端点“当前发现”窗口为 15 分钟（对应项目中 5 分钟端点采集周期并容忍漏跑）；窗口外的 active 缓存不得触发未登记或信息不一致。解析时间时兼容带 `+08:00` 与无时区的北京本地时间。
- “长期未发现”只针对状态为 `active` / `allocated` 的非 loopback、非 VIP 地址，且必须存在同租户、同 VRF、站点安全消歧后的历史端点记录，其 `last_seen` 至少早于 7 天。
- tenant/VRF/IP 是地址身份；同 scope 的当前活跃发现与 IPAM 登记站点不一致时，应进入“信息不一致”并提供两侧站点，不能分别误报为未登记和长期未发现。
- 当前发现命中 IPAM 中 `available` / `released` 地址时，IP 仍是已知登记对象，应报告 IPAM 生命周期状态冲突，不能当作“未登记”或正常匹配；匹配时优先选择同 scope 的非空闲有效记录。
- 没有可解析 tenant/VRF、无效 IP 或重复 IPAM scope 无法按站点消歧的端点不得当作未登记；摘要计入 `total_unscoped`。
- 保留原有三类结果字段和分页参数；信息不一致项增加 `site_mismatch`、`ipam_site`、`endpoint_site`、`status_mismatch`、`ipam_status`。扩展 `summary` 为 `total_unscoped`、端点缓存时效、15 分钟窗口和 7 天老化阈值。长期未发现条目补充 `last_seen` 与 `days_since_seen`。
- `endpoint_cache_fresh` 只表示 `network_endpoints` 全表最新一条 `last_seen` 是否落在 15 分钟内；它不能证明整轮采集成功或没有遗漏，页面不得把它解释成全量缓存完整性保证。
- 页面明确说明对账基于端点缓存，刷新不会触发设备采集；“僵尸”改为“长期未发现”。

## 实施步骤

1. 后端重新读取活跃与历史端点记录，规范化时间和地址；按 tenant/VRF/IP 归组，重复地址候选用站点安全消歧，单一 scope 的站点变化作为不一致。
2. 仅让时效窗口内且 scope 明确的当前端点产生未登记/不一致；仅让满足状态、角色与 7 天条件的历史记录产生长期未发现结果。
3. 保持现有响应形状，增加数据质量/时效摘要和长期未发现证据字段。
4. 前端使用新增摘要解释数据时效、不可判定记录及“刷新”不触发设备采集的含义，更新风险较高的“僵尸 IP”标签。
5. 检查差异、类型/查询链路与文档；按用户当前要求不运行测试或构建。

- Frontend worker：仅负责 `src/pages/IPVlan/IPReconciliationTab.tsx`，按本计划的响应字段更新呈现；不得编辑后端或 API 契约。
- 两位执行者不得继续派生 Agent；保留工作区已有改动。

- 查看前端类型与后端新增字段一致，加载/错误/空状态仍可解释。
- 不运行 pytest、lint 或构建，遵循本轮用户没有要求测试/验证的指令；在 walkthrough 记录未执行项。

## 风险与回滚

- 7 天和 15 分钟是本轮采用的保守固定阈值；如果实际采集周期不同，需要后续转为配置项。
- 新逻辑可能显著减少历史误报，也会隐藏没有任何历史端点观测的离线登记地址；它们本身不足以证明地址已失效。
- 回滚可单独还原对账函数和页面文件；不涉及迁移、批量写入或外部设备操作。
