# LibreNMS 硬件与无线监控规则对齐

## 任务目标

依据仓库固定的 LibreNMS 上游提交 `6c26b4fe4a40f7b392c19c36a44257212736e38c`，追踪并补齐 Nexora 对已适配厂商硬件与无线监控规则的发现、轮询、存储、指标暴露及 Grafana 使用链路。重点覆盖 Nexora 已适配的国产厂商和 H3C 无线 AC/AP；保留每个 LibreNMS 传感器类别/厂商的真实支持边界，不把缺少规则、无 SNMP 数据或无法由上游证明的项目伪装成 0 或“已兼容”。

## 现状与问题

- Nexora 硬件数据由 LibreNMS 规则导入、SNMP discovery/adapter、`snmp_hardware_sensors`、后台轮询和 `/hardware-metrics` 组成；原先图表为空的根因可能在发现定义执行、OS PHP 特例、持久化或指标出口的任一环节。
- 当前任务执行前工作树已包含多组无关用户未提交改动；所有实现必须在此基础上增量修改并保留它们。
- 硬件 CPU/内存执行器和 Comware/Huawei/其他注册特例正在按 pinned LibreNMS 语义适配，并由 GPT-6 LUNA MAX 子 Agent 负责。本阶段结果尚不等于所有硬件类或 OS PHP 行为完全一致。
- 无线现状是少数厂商 AP/客户端汇总 OID；没有按 AP、射频、SSID 保存的持续采集链路。LibreNMS Wireless enum 定义 25 种 sensor classes，但不同 OS 仅实现其中相应子集，不能把这些类都套到每台设备上。
- 初步核对上游 OS handler 后，确认 Nexora 当前六套无线 OID 变体只是少数汇总字段，并非 LibreNMS Wireless sensor parity。`snmp_discovery_service.py` 还按聚合类别去重候选指标，导致同类的 AP 总数/在线数可能只保留其一；H3C 当前使用的三个无线 OID 与 H3C 官方 MIB 定义不符，需要按官方 HH3C-DOT11 MIB 纠正。
- H3C 官方 HH3C-DOT11 MIB 提供 AP/射频/SSID 及 AP CPU、内存、温度、客户端数等表。固定 LibreNMS `Comware.php` 源码未声明 Wireless discovery interface；H3C 表适配必须单独标为 Nexora 官方 MIB 扩展，不能声称是上游 Comware wireless parity。
- 当前无可连接真实设备，HCL 输出可支持静态实现设计，但不能作为所有厂商/机型的 SNMP 运行验证。

## 影响范围与文件边界

- GPT-6 LUNA MAX 子 Agent：只读核查所有已导入 LibreNMS OS 的完整硬件差异（CPU、内存、sensor、storage/optics 等已纳管类型）、PHP overrides 及指标出口；不得改文件、不得运行测试。
- 主 Agent：审查并完成硬件规则集成；增加无线 sensor type / profile 规则、设备适配器和复用现有 SNMP 硬件库存/指标出口的持续发现轮询；完善 Prometheus label/series 和 Grafana 无线看板；更新本计划与 walkthrough。
- 可能涉及 `backend/services/snmp_hardware_probe_service.py`、`snmp_discovery_service.py`、`snmp_hardware_inventory_service.py`、`snmp_service.py`、`monitoring_oid_catalog.py`、`backend/api/grafana_metrics.py`、`monitoring/grafana/generate_dashboards.py` 及同目录生成输出；若确认现有 schema 无法表达无线关系，再依据 Postgres 迁移约定新增独立 migration。共享硬件执行器只由主 Agent 集成，避免与子 Agent 冲突。
- 保留用户已有前端、WAN、资产表格、迁移和测试夹具修改；不部署、不改真实设备配置、不提交代码。

## 实施步骤

1. 针对 pinned LibreNMS Wireless 模块梳理类型枚举、发现/轮询 contract、OS/PHP 实现与适配 profiles；分别记录国产及国际厂商现状，识别配置存在、上游不支持和 Nexora 未实现。对现行上游的厂商举例另标明检查日期与来源，避免和 pinned profile 混为一谈。
2. 完成 hardware executor 与 OS 特例的静态集成审查；审计国产 vendor profile 对 CPU/mempool/sensors 的覆盖以及 `MIB::symbol:0`、custom index、精度/单位、关系 OID、failure/partial 传播和 API/Prometheus 出口差异。
3. 为无线采集建立可组合的传感器类别和设备规则，正确保留 AP/radio/SSID 的原始索引、identity、名称、状态、单位、OID、发现覆盖状态及 polling plan；不得用 AP 表 index 代替可读 AP 名称。
4. 先复用现有 Postgres JSONB `snmp_hardware_sensors`、后台探测周期和 `/hardware-metrics`，仅当结构化实体/API 或时间序列语义确实无法表达时新增 migration。
5. 为目前可由固定 LibreNMS OS 实现证明的厂商补齐无线采集；为 H3C 用官方 HH3C-DOT11 MIB 实现 AP/射频/SSID 与 AP 硬件监控，且显式记录这是 Nexora 扩展。缺乏可核验上游实现或实际设备 OID 的其他厂商保持 partial/unsupported 状态，不虚报覆盖。
6. 将新指标接入 dashboard generator，显示汇总、AP 状态/基本身份、radio/SSID 可用数值，保持数据缺失与零值区别，并避免把文本枚举错误映射成百分比。
7. 逐文件审查执行者与主 Agent 改动、检查工作树差异和静态调用链；根据用户后续明确的交付要求运行影响范围内的定向测试和质量检查，并提交推送到 `main`。

## 验证计划

- 用户后续明确要求完成实现、定向验证并按目标推送，因此此处的“只做静态核验”限制已被后续指令取代。执行结果和具体命令记录在匹配的 walkthrough 与提交 fix 记录中。
- 本机无真实设备可连接；不声称验证了现场 SNMP walk、部署容器、Grafana live 数据或所有厂商的设备兼容性。
- 完成后在 walkthrough 中列出建议后续测试命令、已核对的指标类/OS、未覆盖项和现场验证步骤。

## 风险与回滚

- LibreNMS OS class 的可用 wireless sensor classes 不同；必须记录每个 OS 的真实实现集合，不能将枚举表等同于“每个厂商支持全部 26 类”。
- SNMP 表的 OctetString index 需按 MIB 编码正确关联各列；编码/解码不确定、部分 walk 或数据缺失时不建立错误关联、不将缺项标成零，并保留 partial/failed 证据。
- AP/SSID/MAC 等标签需要限制字段、转义并关注时序高基数；完整 MAC 客户端清单不默认导出为 Prometheus label。
- 若复用现有 inventory schema，确认 sensor identity 对同源多个表/索引/series variants 稳定；若新增 migration，必须是 additive、幂等、PostgreSQL JSONB 原生语义并可通过恢复前备份回滚。
- 回滚通过撤销本轮 adapter/poller/metric/dashboard 代码并恢复 discovery version；不得删除已有 Postgres 硬件历史、真实部署数据或其它用户修改。
- 本次没有设备侧和自动验证证据，因此最终交付只对确认过的规则声明完成，剩余上游代码缺口和运行验证缺口必须明确列出。
