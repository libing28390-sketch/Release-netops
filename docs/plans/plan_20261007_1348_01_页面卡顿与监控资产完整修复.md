### 阶段 4 / P2：优化硬件导出，分解 Grafana 冷加载

1. `_collect_hardware` 读取、driver JSON adaptation/decode、分组/排序、每设备 render、capability 查询和 body 大小分别计时。现有传感器导出是一条全量查询，不是传感器级 N+1；约 99.5% 行符合筛选，不能假定增加前缀索引能解决。
2. 在测试库用 `EXPLAIN (ANALYZE, BUFFERS)` 核实查询计划；生产只读观察优先现有统计，避免未经预算的重复全量 ANALYZE。
3. 优先减少重复 JSON 解析、分组复制、排序和渲染，批量读取必要定义并保持输出语义。对 5296 传感器和更大合成数据记录 CPU、内存与输出内容对比。
4. 当前没有 exporter 缓存，scrape interval 60 秒/timeout 30 秒。短于 60 秒的 TTL 缓存可能每轮 miss，不能作为主方案。只有阶段计时证明需要时才设计缓存：多进程一致性、并发只重建一次、缓存上限、失败策略、数据变更和 good→stale 时间边界必须明确。
5. 如采用版本复用，失效覆盖样本、新增/删除/停用/retired、capability、设备 hostname/vendor/platform/role/tenant/asset_id、资产/站点 label；不得单凭 sensor updated_at 判断所有输出相同。last_success 与 stale 不能被缓存冻结。凭据不作为 exporter label，更改凭据后的样本变化仍需按采集结果更新。
6. Grafana 拆测 session、HTML/JS/CSS、变量查询、ds/query、VictoriaMetrics、transform/render；“iframe 加载完”与“关键指标可读”分别计时。固定 dashboard UID、变量、时间范围与浏览器缓存条件比较。
7. 根据实际最慢阶段改 session 复用、重复检查/iframe remount 或查询；如果瓶颈在渲染/时序查询，仅优化 exporter 不能宣称 Grafana 问题解决。保留 No Data/Unknown 与 0，不能减少可见信息换取速度。

阶段通过条件：exporter 指标内容一致且达到性能目标；新鲜度和失效测试通过；Grafana 每个剩余慢阶段有量化证据与明确处理状态。

### 阶段 5：确认 SNMP 与主机竞争的贡献

1. 对齐 API 全量时间、NetOps/vmagent/SNMP exporter/PG 的 CPU 与 iowait、任务起止/队列/并发、target scrape duration/失败、PG 活动/锁等待时间轴。
2. 生产保持现有扫描周期，先分析卡顿是否与具体 poll 重叠。受控环境用模拟目标比较无采集、现有周期、正常采集并发，单变量对照。
3. 只有证明轮询集中或设备超时在占用请求资源，才做错峰、并发上限/timeout、任务隔离或批量写入；每个调整都验证采集成功率、新鲜度、告警和设备影响。不先整体降频或扩容。
4. 如资源预算不足，输出可承载范围和容量建议；先前中止的合成压力测试不计为容量认证。禁止在同一双核生产机叠加完整隔离容器栈做饱和测试。

## 5. 量化验收目标与采样口径

以下是实施目标，不是当前已达成结果；阶段 0 补齐可比全量基线后执行。不同设备、浏览器缓存、网络和负载分别分组，不将慢日志 p95 与全量 p95直接比较。

| 项目 | 目标/门禁 | 采样 |
|---|---|---|
| 监控正确性 | 已知 SQL 错误 0；租户/权限/字段回归 0 | 隔离 PG 分支全覆盖；部署后含概览/search |
| 模板列表 | 本页业务查询 ≤4（count/列表/版本/收藏）且与 N 无关；同数据受控环境全量 p95 ≤800ms；若重采全量基线>800ms，目标下降 ≥50% | 132模板/page_size200 至少100次；另测1000模板分页 |
| 页面请求 | 首次选择和后续切换模板额外 shared lookup 为0；一轮120秒polling不因callback变化重启 | mock网络生命周期测试 + 浏览器请求序列 |
| 普通页面/表单 | 热导航/列表刷新 p95 ≤2s；表单壳展示 ≤300ms、选项可用 p95 ≤1s | 相同浏览器/数据；报告请求与用户可用时间 |
| 资产保存 | 无设备网络访问的普通保存 p95 ≤1.5s；无长任务/重复提交；数据一致与错误回滚100%正确 | 合成PG至少100次；真实设备轮换另行验收，不套用普通保存阈值 |
| 硬件导出 | 5296传感器下全量 p95 ≤2s；如果有有效缓存，命中 p95 ≤500ms；零抓取超时 | 多轮覆盖至少30个60秒周期；持续变更和冷/热单独测 |
| 指标新鲜度 | 不恶化现有正常采集→exporter→scrape延迟；最大允许新增缓存滞后≤一个60秒scrape周期 | 用last_success/样本时间与数据变更验证；stale边界不冻结 |
| Grafana | 相同面板冷加载关键指标可读目标≤8s、热加载≤4s；query/变量/图表正确 | 固定UID/变量/范围；至少10冷/10热，低样本明确报告 |
| 最终稳定性 | ≥7200秒有效登录态；修复路由无非预期5xx；0新增OOM/重启；容器健康且内存/磁盘安全线通过 | 不重叠日志窗口或唯一请求明细；全程覆盖已知路径 |

若某目标不达标，记录慢阶段、前后差值和剩余问题；不能用“改善明显”代替门禁。CPU/load 是关联与停止指标，不把低 load 单独当体验验收。

## 7. 部署、复测与回滚

1. 每包先在测试/预发验收，记录脱敏 before/after、测试命令和版本；提交前按项目要求生成新的 `docs/fixes/fix_*.md`。保留现有 .env 与数据卷，内部 handoff/.agents/.codex 不进入公有发布树。
2. 获得生产部署授权后，记录当前镜像 digest/启动配置、备份必要配置；先发布 P0 SQL 修复，再模板批量化+前端，再资产与 exporter 包。可在同维护窗口顺序执行，每包有独立回滚版本和 smoke 门禁。
3. 默认只重建/替换受影响应用服务；涉及 Grafana/代理配置才更新对应服务。禁止 `down -v`、覆盖 .env、重置数据卷或随意重启全栈；首批无 schema 迁移。若新增迁移，另补幂等、锁预算、备份与前后兼容，不用代码回滚冒充数据库回滚。
4. 部署后先短 smoke：概览/search、模板列表/收藏/选择、资产表单、hardware scrape、Grafana 冷热加载。资产保存只在已明确允许的测试资产/环境提交，真实设备动作独立授权；通过后再进入长测。
5. 最终长测：两小时以上有效登录态，低频轮流覆盖 /dashboard、/monitor/telemetry、资产列表/表单和Grafana，API轮询保留。通过正常续期/重新登录维持有效会话并标注恢复；会话失效导致停止时暂停有效时长，不能把登录页停留算满7200秒。正常session/health采样副作用如实记录。
6. 长测额外负载默认每5分钟一轮用户操作，API探测单并发、平均≤1rps且避免重叠；监控scrape保持原配置。按唯一请求统计200/非预期401/499/5xx，不重叠汇总。已知报错页面必须纳入，不得为了0错误避开。
7. 安全停止线：load1>4.5连续3个一分钟样本，MemAvailable<3GiB，容器unhealthy/新增重启/OOM，或非预期5xx>10/分钟连续3分钟；发现越权、保存数据不一致或指标错误立即停止相关验证。停止线用于现场保护，不表示线以内不会卡。
8. 回滚：若非预期500、权限/数据一致性或指标新鲜度回归，停下一包并替换为该包前记录的应用镜像/前端资源；必要时回退对应Grafana/代理配置。API错误恢复只说明回滚生效，原慢问题可能回归，继续登记。合成数据清理只作用于测试库；业务写入无法靠镜像回退撤销，必须按已定义事务/补偿处理。

最终产出：修复版本/部署版本、逐问题状态、前后性能表、实际≥7200秒摘要及原始证据、未验证项/容量限制、可执行回滚信息。只有全部门禁通过才写“本轮问题已解决”。

## 8. Agent 分工、顺序与预计工作量

主 Agent 负责 scope/接口、P0 SQL、共享文件协调、根因取舍、质量门禁与最终计划/走查/handoff。每轮最多两个 Luna 6 Max 执行者；执行者不再创建子 Agent，不覆盖用户或其他执行者改动。

| 波次 | 后端执行者 | 前端/复杂执行者 | 主 Agent / 依赖 |
|---|---|---|---|
| 当前计划 | backend_worker 只读核对模板、hardware、assets | frontend_worker 只读核对lookup/表单/Grafana | 汇总方案与文件边界；不改业务代码 |
| A | backend_worker：模板批量化与局部测试 | frontend_worker：App + config状态hook请求生命周期、monitoring错误态 | 主 Agent修监控SQL；后端/前端保持现有响应契约 |
| B | backend_worker：资产PG复现与明确根因修复 | frontend_worker：资产表单loading/error/重复提交 | 不再与A同时写App；厂商平台/事务变化主Agent审查 |
| C | complex_worker：硬件导出计时与最小优化 | frontend_worker：Grafana嵌入中已证实的重复工作 | 同文件只有一个owner；跨进程缓存/schema方案返回主Agent |
| D | verification_worker：确定范围的公共检查与失败证据 | 不并行执行第二份公共回归 | 主Agent整合、发布准备、授权后部署与长测 |

每个实现工作包包含目标、已知证据、允许修改文件、skill、接口不变项、验收命令；返回修改文件、行为、验证结果、未解决项。两轮同类失败仍未定位，或需要改变架构/权限/schema/契约，执行者回传证据，由主 Agent 决策。

排期参考：基线与P0约半天；模板/前端约一天；资产复现与修复约一天；exporter/Grafana约一至两天；整合/部署/长测至少半天且两小时有效采样不可压缩。合计约4–5个工作日的范围估计，取决于资产问题能否复现和Grafana真实瓶颈；阶段门禁决定推进，不按估计时间宣告完成。

## 9. 主要风险与处理

| 风险 | 处理/停止条件 |
|---|---|
| 修SQL后暴露租户列歧义或参数错位 | 两租户真实PG覆盖全部子查询，使用明确别名，scope回归立即阻断 |
| 模板批量化改变旧版本/favorite/schema内容 | 修复前后payload契约比较；收藏按session username；错误回退该包 |
| 去重复请求后丢首次选择或刷新 | 初次/切换/删除/轮询/手动/登录变化生命周期测试；保留既有契约 |
| 资产保存后部分成功或重试重复写 | 两表事务回滚和commit后失败测试；未明确原子性不部署 |
| exporter缓存滞后、串scope或冻结stale | 优先优化计算；缓存方案单独审查与失效/跨进程测试，未通过不启用 |
| Grafana onLoad造成误判 | 以关键指标可读计时，分解session/资源/query/render，保留No Data |
| 同机压力或采样自身放大卡顿 | 单并发、低频、停止线；容量测试移到独立环境，报告采样开销 |
| 保存报错未复现、生产版本不同 | 保留未验证状态和复现条件；记录实际部署版本及脱敏错误，不用推断代替证据 |
