# 告警、自动化、工单、IPAM 与拓扑加载整改计划

## 任务目标

让告警中心四个页面、自动化中心全部子页面、工单管理和 IPAM 地址管理列表遵循同一数据加载原则：普通列表首屏、翻页和筛选只请求服务端当前页；用户明确触发导出时，才读取完整筛选结果。同时将拓扑数据改为进入页面时加载一次，此后仅由用户手动刷新；停止拓扑页的 15 秒设备全量轮询和拓扑图定时轮询。

## 现状与问题

- 部分页面可能先请求多页或较大上限的数据，再由前端分页，增加接口、内存和渲染负担。
- `fetchAllPaginatedItems` 既用于导出，也可能用于页面展示，必须逐调用点区分，不能全局截断导出。
- 页面路由在 `AppMainContent` 中按自动化子页分发；应用层共享设备数据也可能在进入自动化路由时额外加载。
- 工单列表已发现使用 `page/page_size` 请求当前页；需要纳入核验，避免误改现有正确路径。

## 影响范围

- 告警：告警工作台、告警历史、告警规则、维护窗口。
- 自动化中心：执行、脚本、NSOT、Playbook、场景、执行历史/计划历史/查询、巡检、巡检记录、计划、定时作业、指标、TextFSM 模板等全部路由子页。
- 工单管理：工单列表、筛选、分页、汇总及显式导出。
- IPAM：子网/前缀、IP 地址、地址池、VIP、DHCP 租约、冲突/对账、接口前缀候选及其矩阵/详情视图。
- 拓扑图：区分拓扑读接口刷新与 CollectorCompile 后台日志；检查 `/api/devices` 200 行兼容上限、共享设备 15 秒刷新和未知链路端点补刷之间的关系。用户确认拓扑变化不频繁，保留首屏加载及明确的“刷新拓扑”按钮，关闭定时刷新。
- 应用共享数据加载仅在确认其对当前子页产生重复或全量请求时调整。

## 拟修改文件

- `src/App.tsx`、`src/components/AppMainContent.tsx`（仅在确认有全局预取问题时）
- 告警、自动化、工单页面及其数据 hook/API 调用文件（以审计结果为准）

- `src/hooks/useTopology.ts`、拓扑页面数据来源及应用共享刷新生命周期；必要时调整拓扑读 API 或设备数据读取契约
- 必要时调整对应 FastAPI 列表接口或 service，使分页、筛选和总数由服务端完成
- 本计划及配套 walkthrough 文档

## 实施步骤

1. 按路由逐页追踪告警、自动化、工单和 IPAM 的首屏加载、翻页、筛选、详情和导出请求，记录分页契约和全量读取位置；同步核对拓扑自动刷新路径及用户日志的实际生成点。
2. 保持已实现服务端分页的页面行为；修复普通列表中的全页预取、500/1000 条上限后本地分页和共享全量数据预加载。
3. 对当前页请求同步提交搜索、筛选与排序条件，切换条件时回到第 1 页；响应保留服务端总数和页码元数据。
4. 将完整分页读取限制在显式导出回调；详情数据在打开详情后再取。
5. 静态复核所有列出的告警页、自动化子页、工单页和 IPAM 页面，确认各普通列表没有跨页循环请求；检查拓扑路由不因设备数据上限持续触发补刷。

## 验证计划

- 静态检查各页面普通列表请求均包含当前 `page/page_size`，过滤条件由接口处理。
- 检查 `fetchAllPaginatedItems` 在目标范围中的调用仅由显式导出或用户明确的完整数据动作触发。
- 检查路由加载和自动刷新没有为非当前子页预取列表数据。
- 检查 IPAM 矩阵、风险筛选和汇总使用准确的服务端总数/聚合数据，不依赖当前页近似计算全局结果。
- 检查拓扑数据没有定时轮询，进入页面仅首次加载，手动按钮可刷新；拓扑页没有 15 秒设备全量轮询，未知端点集合不会重复触发相同设备列表补刷。
- 不运行测试、lint 或构建；除非用户明确要求，遵循会话中的验证约束。

## 实施结果

状态：已完成本轮页面与刷新路径整改。

- 告警工作台、历史页保留已有服务端分页；规则和维护窗口列表改为服务端搜索/筛选、总数统计与 `LIMIT/OFFSET` 分页。
- 自动化执行历史通过统一接口合并巡检与 Playbook 记录后全局排序、分页；执行计划列表改为请求当前页。快速执行的设备列表改为服务端分页、搜索和筛选，并保留跨页已选设备信息。显式导出仍读取完整筛选结果。
- 工单列表原已使用服务端分页，保持原实现。
- IPAM 的主要列表继续使用现有服务端分页；IP 地址关联设备选择器改为打开后读取第一页、每页 50 条，并通过服务端搜索查找。显式导出仍遍历完整筛选结果。
- 停止应用层每 15 秒的共享设备全量轮询（覆盖所有依赖设备快照的路由）；路由进入时仍按需读取一次，页面自身的状态/任务轮询按各自用途保留。
- 拓扑图停用 60 秒拓扑生成状态轮询。进入拓扑页时读取一次当前数据；“刷新拓扑”按钮同时刷新图和生成状态；用户手动启动的发现任务仍轮询进度，结束后刷新一次结果。生成状态接口也改为明确报告 `manual_only`，不再错误标记不存在的自动拓扑任务为启用。

### 已知限制

- 未来执行计划接口仍需先在服务端生成查询范围内的计划，再按页切片；当前页响应已分页，但大量计划时服务端仍有全量计算成本。
- IPAM 地址/对账的组合视图需要合并手工记录与设备端点并去重，当前服务端仍在内存中整理全量候选后切片；页面不会一次返回全部行，但后端工作量尚未变为纯 SQL 分页。
- IPAM 矩阵需要完整的单个前缀地址集合来绘制网格，属于显式矩阵视图；普通表格仍按页加载。
- 维护窗口按状态筛选时，对时间字符串使用数据库文本比较；带不同 UTC 偏移的非规范时间值可能有边界差异。
- 设备选择器在打开时按需请求当前候选页，筛选首屏以外设备需使用搜索；不会预取 1000 条设备。
- TextFSM 模板列表接口只返回当前页，但服务端当前仍先构建完整模板目录再切片；模板目录规模较小时影响有限，后续可改成数据库级分页。

## 风险与回滚思路

- 混合多数据源的执行历史需要服务端统一排序和总数；仅限制前端请求数可能导致翻页遗漏或顺序错误，应在必要时提供组合分页接口。
- IPAM 子网风险排序/矩阵展示需要完整汇总时，应使用服务端聚合而非把主列表重新改为全量读取。
- 拓扑画布需要当前作用域内完整的节点和连线；应使用图数据的作用域/摘要契约解决完整性，避免依赖默认截断的共享 `/api/devices` 列表。
- 筛选摘要和分类计数不能用当前页数据推算，需继续使用服务端汇总/facets。
- 若变更后页码、总数或筛选结果不一致，回退对应页面请求映射，保留现有 API 契约，再逐接口修正分页语义。
- 导出必须继续使用当前筛选条件遍历完整结果，避免静默丢行。
