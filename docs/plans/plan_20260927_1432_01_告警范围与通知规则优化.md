# 告警范围与通知规则优化

## 任务目标

将告警规则的目标范围设计调整为接近 `/automation/scheduled-jobs` 的设备筛选语义，明确哪些资产会命中规则；通知配置只提供 Webhook 与邮件，不再向规则表单展示个人偏好；移除编辑器中的历史告警统计摘要，并提供精确/模糊匹配。

## 现状与问题

- 告警范围只有全局、站点、设备、接口四种，站点/设备均为自由文本，与定时作业的资产范围选择不一致。
- 后端运行时只支持全局、站点、设备标识和接口名匹配，页面已提交的更多匹配模式没有完整对应资产筛选能力。
- 通知表单将个人偏好与显式通知渠道混在一起；编辑器显示与保存动作无关的 24 小时告警统计。
- `scope_value` 是既有持久化字段，可承载结构化 JSON；不需增加数据库列，但必须在 API、运行时和列表展示中统一解析，并让非法或空条件安全地不匹配。

## 影响范围

- 前端告警规则表单、规则列表范围摘要和本地化帮助文本。
- 告警规则 API 的当前租户范围选项目录，以及服务端规则验证/匹配。
- 监控运行时设备上下文，使复合筛选与标签条件可以按真实设备属性命中。
- 前后端范围、通知通道回归测试和本计划/完成记录。

## 实施步骤

1. 为告警表单增加租户设备范围目录；范围支持全部、站点、角色、复合（站点/角色/设备类型/平台）、指定 IP、标签条件，并保留接口及历史设备范围。
2. 让前端与运行时共享明确的数据形状：复合条件按精确/模糊 AND 组合；IP 精确匹配；标签复用定时作业的递归 AND/OR/NOT 条件结构。
3. 后端验证并匹配这些范围，标签变更可在短缓存期限内反映；列表显示易读摘要而不直接展示 JSON。
4. 通知编辑器仅呈现 Webhook、邮件复选框；无默认个人偏好，保存前要求至少选择一个显式方式。宿主机规则继续使用系统级既有通知路径，但不在规则 UI 暴露偏好选项。
5. 移除 24 小时告警/恢复/重复键统计的表单展示与专用请求；保留必要的规则变更历史。
6. 补充成功、非法/空范围、精确/模糊、租户隔离和通知通道验证，运行定向后端 PostgreSQL 测试及前端 lint/测试/构建。

## 风险与回滚思路

- `scope_value` 结构沿用现有字符串列；旧的 `global/site/device/interface` 规则继续按旧格式读取。新增结构只在选择相应新范围类型时解释为 JSON。
- 现有保存的 `workspace` 网络规则保留原有运行行为；更新后 UI 只接受显式 Webhook/邮件，后端拒绝新写入个人偏好通道。宿主机系统告警仍保留平台的系统投递策略。
- 标签条件依赖设备标签分配；运行时读取失败或表达式损坏时 fail closed，不把告警发给更大范围设备。
- 可回滚方式是恢复前端选项和规则匹配代码；无需数据库回滚，因为不新增或重写数据库列数据。
