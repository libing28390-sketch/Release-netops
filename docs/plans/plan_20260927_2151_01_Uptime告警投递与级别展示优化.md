# Uptime 与告警运营看板展示优化

## 任务目标

- 统一所有 Grafana 看板中的 Uptime 面板格式，移除对运行时长没有诊断价值的 sparkline，并采用可读的时长显示；告警运营看板中的持续时长卡片沿用同一展示规则。
- 查明并修复“24h 告警成功率”无数据的根因，确保指标端、PromQL 查询和面板单位一致，并以“告警成功率”作为面板名称。
- 将告警运营看板中 Critical、Major、Warning、Minor 等告警级别可见文本统一为中文，保持后端 severity 值和指标标签契约不变。

## 现状与问题

- 当前在 Linux 服务器和网络设备两张看板中发现 2 个 Uptime Stat 面板，均以秒为单位并启用 area sparkline。
- 告警运营看板的 24 小时成功率查询引用 `nexora_alert_delivery_attempts_24h`，界面显示“数据暂不可用”。后端按 `sending` 后的结果另记 `succeeded`、`retrying` 或 `failed`；当前 PromQL 只计算 `succeeded` 和 `failed`，漏掉了已完成的 `retrying` 失败尝试，并在分母为零时有意返回空值。
- 告警运营看板仍将严重度写成 Critical、Major、Warning、Minor 英文标题；需要只改显示层，避免改变告警存储或指标标签。

## 影响范围

- Grafana dashboard 生成器与其输出 JSON。
- 后端监控指标导出/通知投递指标，仅在根因确认需要改动时调整。
- 相关局部验证；不改变实际告警投递行为、数据表结构或现存告警严重度编码。

## 修改文件

- `monitoring/grafana/generate_dashboards.py`
- `monitoring/grafana/dashboards/nexora-linux-metrics.json`
- `monitoring/grafana/dashboards/nexora-network-device.json`
- `monitoring/grafana/dashboards/nexora-alert-operations.json`
- `docs/plans/plan_20260927_2151_01_Uptime告警投递与级别展示优化.md`
- `docs/walkthrough/walkthrough_20260927_2151_01_Uptime告警投递与级别展示优化.md`

指标导出链路核对后确认无需修改后端：导出器在查询成功时会输出所有 allowlist channel/status 的零值序列；只有查询失败时才省略该指标族。`retrying` 是已结束的失败尝试记录，应纳入成功率分母。

## 实施步骤与结果

1. 已检查所有 dashboard JSON 与生成器，确认只有 Linux 主机和网络设备 2 个 Uptime Stat 面板；为 Stat helper 添加局部 graph mode 和 value mapping 选项，只对 Uptime 面板关闭 sparkline，单位统一为 `dtdhms`。
2. 已核对通知 outbox 每次发送的 `sending` 与完成结果记录，以及 `/metrics` 的 24 小时聚合。成功率分母现为 `succeeded + retrying + failed`；当前没有完成尝试但指标源可用时返回 sentinel 并映射为“暂无已完成投递”，指标族缺失时继续显示无数据。
3. 已将四张严重度 Stat 卡片和完整严重度分布图例本地化为中文，指标查询仍使用 exporter 的英文 severity label。
4. 已重新生成全部 dashboard JSON，并检查仅 3 个预期 dashboard JSON 发生变更；详细验证记录见配套 walkthrough。
5. 告警运营看板的“当前最久未恢复时长”和“未恢复告警时长 P95”改为 `dtdhms` 时长单位并关闭 Stat sparkline；24h 成功率面板标题简化为“24h 告警成功率”。

## 验证计划

- 运行 dashboard generator，确认只改动预期看板。
- Python 编译并解析全部生成的 dashboard JSON；检查 Uptime 与未恢复时长 Stat 面板都使用统一时长格式且无 sparkline、成功率面板名称正确、告警级别展示无英文残留、指标查询标签未被翻译。
- 对比指标 exporter 与 PromQL 状态标签/单位，做静态契约核验。
- 本轮不触发真实告警或通知，也不修改线上 Grafana；在线渲染需部署后确认。

## 风险与回滚思路

- Grafana duration unit 的显示需与输入秒数匹配；网络设备 `sysUpTime` 仍需先除以 100，Linux `node_boot_time_seconds` 差值已经是秒。
- 24 小时投递统计必须按一次实际发送尝试的最终状态计数；重试中的失败应纳入已完成尝试分母，`sending`、排队和跳过状态不代表已完成投递。零样本不应伪装成 0% 成功率。
- 严重度只翻译显示文本，不能改写存储值、PromQL label selector 或告警通知 API 契约。
- 回滚时恢复生成器的旧 Uptime Stat 配置、告警级别标题与成功率查询；若改动后端 exporter，则同步回滚对应导出逻辑，不触碰历史 outbox 数据。
