# 容器指标启动顺序实施计划

## 任务目标

修复整机启动时 cAdvisor 偶发只采集宿主机指标的问题，确保 Docker socket proxy 的 Docker API 已可用后再启动 cAdvisor。

## 现状与问题

- vmagent 的 cAdvisor scrape target 返回 `UP`，但 VictoriaMetrics 曾只有 `id="/"` 的宿主机 CPU/内存序列，Grafana 容器图因此为空。
- cAdvisor 日志记录 Docker factory 初始化时请求 `docker-socket-proxy:2375/v1.54/info` 超时；此时 Compose 仅用 `service_started` 等待 proxy 容器启动。
- 重启 proxy API 当前能正常返回容器信息；重启 cAdvisor 后 Docker factory 注册成功，VictoriaMetrics 恢复了 18 个容器的 CPU/内存序列。

## 影响范围

- Compose 中 docker-socket-proxy 健康检查及 cAdvisor 启动依赖。
- 对应的 Compose 部署契约测试。
- 部署时仅重新创建 proxy 和 cAdvisor；不改动 VictoriaMetrics 数据卷。

## 拟修改文件

- `docker-compose.yml`
- `backend/tests/monitoring/test_monitoring_v1_deployment_contract.py`
- 本计划及对应 walkthrough

## 实施步骤

1. 为 docker-socket-proxy 增加 `/info` 就绪检查；探测成功表示代理后面的 Docker API 可用。
2. 将 cAdvisor 的依赖条件从容器已启动改为代理健康。
3. 增加契约测试，锁定健康检查命令和依赖条件。
4. 跑 Compose 契约测试和 Compose 配置解析检查。
5. 在目标机备份 Compose 文件后应用该配置，检查 proxy 健康、cAdvisor Docker factory 注册和 VictoriaMetrics 容器指标。

## 验证计划

- `pytest backend/tests/monitoring/test_monitoring_v1_deployment_contract.py -q`
- `docker compose config -q`
- 目标机核对 cAdvisor target、最近采样及容器 CPU/内存序列。

## 风险与回滚

- proxy 健康检查暂时失败时，Compose 会延迟启动 cAdvisor，避免误报健康但漏采容器指标。
- 回滚只需恢复备份的 `docker-compose.yml` 并重新创建 proxy/cAdvisor；不改动数据库或时序数据卷。
