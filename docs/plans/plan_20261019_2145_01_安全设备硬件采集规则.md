# 安全设备硬件采集规则补齐计划

## 任务目标

梳理 `backend/vendor/librenms` 的硬件采集链路，在资产页面列出的 15 个安全厂商中，仅为固定 LibreNMS 上游快照实际提供 OS 识别及可执行硬件 YAML 的设备补入来源文件、MIB 与哈希清单；不猜测或自创厂商 OID。对缺少上游来源的厂商及产品规则写入 `handoff.md`。完成聚焦验证后，提交并推送本任务改动到 `main`，确认对应 GitHub Actions 成功，最后关闭电脑。

## 现状与问题

- Nexora 当前 LibreNMS bundle 固定在 `6c26b4fe4a40f7b392c19c36a44257212736e38c`，清单只覆盖 26 个网络设备厂商、136 个 OS profile；安全设备 MIB 与规则未纳入。
- 硬件链路为：`os_detection` 识别设备身份，`os_discovery` 定义 processor/mempool/sensor，Python 解析器按 YAML 执行 SNMP；采集结果需通过 `source-manifest.json` 的上游提交与 SHA-256 来源校验，MIB 符号解析依赖 bundle 导入的 MIB 索引。
- 当前资产页面安全厂商共 15 个：Fortinet、Palo Alto、Hillstone、Sangfor、Check Point、Sophos、SonicWall、WatchGuard、F5、A10 Networks、Barracuda、Venustech、NSFOCUS、Topsec、Qi An Xin。
- 固定快照解析检查已找到 20 个有结构化硬件定义的候选 OS profile，覆盖 9 个厂商。Palo Alto `panos` 有两个依赖设备硬件/版本字段的条件，需保留 partial 诊断；FortiGate 的一个描述模板引用了上游快照中不存在的 `InetAddress_FORTINET-FORTIGATE-MIB`，不得伪造该 MIB。
- 按用户后续要求补查了厂商官方资料。部分设备（Sangfor、NSFOCUS、WatchGuard、Barracuda）确有官方 MIB 或 OID 文档，但部分需要从设备管理页/安装包获取；这些材料不是 LibreNMS OS detection/discovery YAML。它们不纳入本次固定 LibreNMS 来源包，避免把 MIB 定义误报成已实现的采集规则。

## 影响范围

LibreNMS vendored OS YAML/MIB bundle、bundle 来源/平台厂商范围校验、SNMP MIB 导入路径与相关测试/文档。不会改接口采集、指标语义、外部 LibreNMS 部署或真实设备配置。

## 拟修改文件

- `backend/vendor/librenms/resources/definitions/os_detection/` 与 `os_discovery/`：固定提交中的 20 个受支持产品 profile。
- `backend/vendor/librenms/mibs/`、`source-manifest.json`、`README.md`：上游 MIB 及其来源、哈希和覆盖范围。
- `backend/services/librenms_mib_service.py`、`backend/services/mib_repository_service.py`、`backend/api/devices.py`：安全厂商 MIB 目录归属与同步范围。
- `backend/tests/snmp/`：manifest、来源信任、解析和安全厂商 MIB 作用域回归。
- `docs/architecture/SNMP采集全流程与代码索引.md`、本计划对应的 walkthrough、`docs/fixes/fix_*.md`。
- `handoff.md`：追加本次支持范围、未支持厂商及上游缺项；作为内部交接材料留在本地，不混入公开提交。

## 实施步骤

1. 以资产页面清单和固定 LibreNMS commit 为准，核对每个 OS profile 的身份匹配、hardware YAML、解析兼容级别及直接/传递 MIB 依赖。
2. 只从固定上游提交复制经过筛选的检测/采集 YAML 与 MIB 原文，保持上游文件字节和许可证头；更新 profile、MIB、文件哈希和安全厂商范围清单。
3. 让 bundle MIB 导入器可以按安全厂商选择并索引这些 MIB，同时保留缺少 MIB/硬件规则时 fail-closed 的行为。
4. 增加覆盖支持/跳过范围、MIB 来源哈希、规则来源验证和解析结果的聚焦测试；更新架构文档、vendor README 与 handoff。
5. 运行相关 pytest、源码哈希校验、Python 编译与 `git diff --check`；确认无设备真实采集被声称为已验证。
6. 检查工作树，只暂存本任务文件并创建包含新 fix 记录的提交；推送 `main`，等待该提交的 Actions 终态并确认成功。
7. 所有验证和 Actions 都成功后，按用户明确要求执行电脑关机。

## 验证计划

- `pytest backend/tests/snmp/test_librenms_bundle_manifest.py backend/tests/snmp/test_librenms_rule_service.py backend/tests/snmp/test_librenms_source_policy.py`
- `pytest backend/tests/snmp/test_mib_repository_import.py`（若本地测试 PostgreSQL 条件可用）
- 通过 Python 对每条 manifest MIB、OS rule 和 adapter source 重新计算 SHA-256；确认新增规则的 source commit 与固定提交完全一致。
- 验证每个入选 OS profile 的 identity/hardware compatibility、结构化定义数量、MIB 依赖闭包；确认未支持厂商不生成推测规则。
- `python -m compileall` 覆盖变更 Python 文件，`git diff --check`。
- 推送后核对准确提交对应的 GitHub Actions run conclusion；仅以成功终态作为 CI 完成证据。

## 风险与回滚思路

- Nexora 执行 YAML 的 Python 语义不是 LibreNMS PHP runtime 的完整镜像；仅纳入当前解析器支持的结构化定义，并保留 partial/unsupported 诊断。
- 没有安全设备 live SNMP 样本时，只能证明文件来源、解析、索引及代码路径，不能证明特定型号或固件的真实返回值。
- 若 MIB 或规则验证失败，恢复相应文件及 manifest 项到提交前版本；不删除已有 MIB 数据库记录，不触碰真实设备。
- 上游未覆盖但厂商公开 MIB 的产品，后续若要加入 Nexora 专有规则，需先取得对应产品/固件版本的原始 MIB，并建立独立、可校验的来源元数据与 OS 身份匹配；本次不以文档摘要或推测 OID 代替这些材料。
- `dist/index.html`、IPAM 菜单改动、既有验证目录和 `logs/` 属于工作区已有未提交内容，必须保持原样且不得进入本任务提交。
