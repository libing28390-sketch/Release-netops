# 资产导入 SNMP 主机名与状态展示

## 任务目标

恢复资产导入后通过 SNMP 获取 `sysName.0` 并写回设备与资产名称的能力，覆盖 SNMPv2c 和 SNMPv3；明确在线状态与 SNMP 的边界，并消除等待探测的设备被系统标签误标为“离线”的现象。

## 现状与问题

- 导入路由仅为 SNMPv2c 建立主机名同步任务；SNMPv3 被跳过，身份识别虽然读取 `sys_name`，却不写回 hostname。
- 主机名同步函数目前只读取 community，缺少 SNMPv3 GET 分支。
- 在线状态由后台周期监控维护；当前快速与慢速巡检都先做 ICMP/管理端口探测，SNMP `sysUpTime` 只在慢速路径后置兜底，导致可用 SNMP 证据未用于快速判在线，且探测顺序与期望不符。
- 远程部署页面显示 14 台“等待中”、1 台“在线”，但等待中的设备在系统标签列被标为“离线”。`tag_service` 将除 `online` 外的所有状态（包括 `pending`）映射成离线标签。

## 影响范围

- 资产导入 API 的导入后 hostname 同步，适用于新建和重复导入的网络设备。
- 系统自动状态标签，仅对明确的 `online` / `offline` 保留标签；`pending` 等未知状态不标在线或离线。
- 后台快速与慢速巡检采用 SNMP 优先、ICMP/管理端口兜底；SNMP 异常或超时本身不判离线，只有 SNMP 与兜底探测都失败才判离线。
- 不修改远程容器，不部署。

## 拟修改文件

- `backend/api/assets.py`：为 SNMPv3 配置发起 `sysName.0` GET，并移除导入队列对 SNMPv3 的排除。
- `backend/services/tag_service.py`：未知/等待状态清理在线/离线自动标签。
- `backend/services/background_monitor_service.py`：统一快速与慢速巡检的 SNMP 优先探测，复用慢速巡检探测结果并保留独立 SNMP 采集失败状态。
- 本计划及对应 walkthrough。

## 实施步骤

1. 保留现有 hostname 写回事务与响应契约，按已解析的 SNMP Profile 选择 v2c 或 v3 GET。
2. 确认新资产、重复导入均会进入 hostname 同步任务。
3. 让系统状态标签只表达确定的在线或离线状态；等待/未知时移除状态标签。
4. 快速与慢速巡检先用已配置的 SNMPv2c/v3 profile 查询 `sysUpTime.0`；成功即判在线并跳过 ICMP，失败或超时才用 ICMP/管理端口兜底。
5. SNMP 与 ICMP/TCP 均失败时才判离线；慢速巡检复用首轮 SNMP 探测结果，避免重复查询，并保留独立 SNMP 采集告警。
6. 复查 diff，记录验证与未验证项。

## 验证计划

- 代码路径审查：V2c 与 V3 凭据字段、sysName 规范化、资产/设备/拓扑同事务写回、hostname_sync 摘要。
- 在线状态路径审查：配置了 SNMP 的设备先查询 `sysUpTime.0`，SNMP 成功即在线；SNMP 失败后 ICMP/管理端口兜底，二者都失败才离线；SNMP 采集失败仍通过独立告警表达。
- 不运行测试或部署：当前请求要求分析/修复，没有提出测试或远程部署授权。

## 风险与回滚思路

- V3 探测复用当前 SNMP 服务和已解析 Profile；探测或写回失败时继续保留导入名称并在 `hostname_sync.failed_items` 中报告错误。
- 应用启动时的状态标签同步会移除 `pending` 设备错误的“离线”标签；真实在线/离线状态仍由监控探测维护。
- 若展示语义不符合预期，可分别回滚本次 `assets.py` 与 `tag_service.py` 代码改动；无数据库结构变更，也未操作远程容器。
