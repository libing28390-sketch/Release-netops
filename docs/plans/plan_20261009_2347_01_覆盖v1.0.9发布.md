# 覆盖 v1.0.9 发布计划

## 目标

将私有仓库当前 `main` 的最新功能标记为 `v1.0.9`，替换本地及私有远端已有的旧 tag，并由 tag 发布流水线同步替换公开 `Release-netops` 仓库中的同名 tag、Release 说明和发行附件。

## 现状与问题

- `package.json` 与 `backend/core/version.py` 显示版本为 `1.0.9`；发布工作流要求 tag 精确为 `v1.0.9`。
- 私有仓库的 `main` 与 `origin/main` 当前均为 `682639020d3b5efd8324046818ecbcb232039dac`，该提交对应的 main 工作流已验证成功。
- 本地和私有远端的旧 `v1.0.9` 指向 `01cec4173705c21e1822652dca837b7d9522c84d`。公开发布仓库也已有同名 release/tag。
- 现有发布说明停留在 2026-10-05；本次主线还包含 LibreNMS SNMP 硬件/无线适配、硬件采集性能改进和 PostgreSQL Grafana 性能看板，需要先补充正文。
- 用户明确要求以 `v1.0.9` 替换旧版本，并将私有仓库 `main` 也标上该版本。

## 影响范围

- 私有仓库本地 Git tag 与 `origin` 上的同名 tag。
- GitHub Actions tag 发布流水线及公开 `Release-netops` 仓库中的 v1.0.9 tag、Release 正文和资产。
- `docs/deploy/release-notes.md` 与一份提交修复记录；不修改产品代码或版本元数据，也不改动用户已有的内部协作文件。

## 实施步骤

1. 再核对分支、HEAD、版本元数据、已有 tag 目标及主分支工作流状态；记录旧 tag 的回滚提交。
2. 更新 `docs/deploy/release-notes.md`，记录旧 tag 之后的 SNMP、采集性能与 PostgreSQL 看板变化；创建同提交的修复记录。
3. 运行文档差异/空白检查，提交并推送仅包含这两份发布文档的 main commit，等待其 main 工作流成功。
4. 在该已验证的 main 提交上重建本地带注释 tag `v1.0.9`，并按用户授权强制推送至私有仓库 `origin`。
5. 等待 Linux 完整发布门禁和 Windows Agent 发布 job 结束；若失败，读取具体 job 日志并修复或报告。
6. 核验私有远端 tag、公开 Release 仓库 tag 和 `v1.0.9` Release 正文及资产均已指向/包含新版本。

## 验证计划

- 确认当前分支为 `main`，HEAD 与 `origin/main` 一致，版本字段均为 `1.0.9`。
- 对发布说明和修复记录运行 `git diff --check`，再由 main 与 tag Actions 执行发布门禁。
- 确认 tag 发布对应的 GitHub Actions run 最终成功。
- 通过 Git 远端引用和公开 Release 页面/API 检查源仓库 tag、发布仓库 tag、Release 正文及附件。

## 风险与回滚

- 这是对既有公开版本号的替换；GitHub Release 下载内容和 tag 目标会变化。
- 旧私有 tag 原目标 `01cec4173705c21e1822652dca837b7d9522c84d` 已记录，可在失败时恢复本地及私有远端 tag。公开 Release 仓库的同步 tag/附件如需回滚，应在失败后根据实际 job 状态恢复，避免在流水线运行中并发改动。
- 发布流水线会清理私有协作文件，不会将计划、交接记录或其他内部文件放入公开发行树。
