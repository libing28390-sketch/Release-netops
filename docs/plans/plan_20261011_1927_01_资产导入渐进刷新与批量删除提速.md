# 资产导入渐进刷新与批量删除提速计划

## 目标

- 表格导入过程中，及时把已经逐行提交的资产反映到资产列表，不再等完整 219 行请求结束后才刷新。
- 批量删除从“每个资产一条 HTTP 请求”改成一次批量调用，减少数据库连接、事务与重复监控同步开销。
- 为删除路径实际按设备/资产 ID 清理、且当前缺少合适索引的关联表补索引，避免大表逐资产扫描。
- 缩短资产新增和编辑的数据库工作：新增/导入每行只插入一次资产记录；编辑只校验变化的身份字段，只同步实际变化的关联数据。
- 标签与 Web 配置相同时不删除重建；编辑普通资产字段时不重写凭据、不触发不相关的监控或汇总刷新。
- 资产类型、资产编号、序列号、厂商、型号、主机名、管理 IP 和设备高度在首次录入后固定；编辑请求只携带实际变化字段。状态、生命周期、站点、机柜及安装 U 位保留可变能力，以支持运维状态调整和设备迁移。
- 保留现有逐行导入部分成功语义、逐资产删除权限校验与部分失败反馈。

## 现状与证据

- 资产导入前端 doImport 对整个表格只发一次 POST /api/assets/import?detailed=true，await r.json() 完成后才调用 fetchAssets()；后端虽逐行提交，但列表在请求期间不刷新。
- 资产管理批量删除对每个选中 ID 并发调用 DELETE /api/assets/{id}。每个后端调用会打开数据库连接、清理关联设备/机柜/IPAM/PAM记录、提交事务并触发监控同步。
- 用户提供的运行日志包含连续的 RackService Removed rack device 记录，与按资产逐个清理机柜关联的当前路径一致；日志未包含导入路由请求/完成记录，不能据此确定导入成功数量。
- 编辑接口此前对四个身份字段总是逐项做 `LOWER(TRIM(COALESCE(...)))` 查询，表达式与现有唯一索引不一致；表单全量提交还会重复解析未变化凭据、重建标签/Web 配置、同步机柜/关联设备/设备类型及触发监控同步。现在关键档案字段在创建后锁定，后端拒绝真实变更，前端编辑请求省略未变化字段。
- 新增和导入在每行主 INSERT 后又执行三条 `physical_assets` UPDATE 写入 SNMP、管理端口、WinRM 与 SSH 算法配置，形成不必要的写库往返。

## 拟修改范围

- src/pages/AssetManagement/index.tsx：导入请求未完成期间以低频、静默方式刷新资产列表；最终响应后刷新资产列表和汇总。批量删除改调新接口并显示进行中/部分失败状态。
- backend/api/assets.py：复用单资产删除的事务内清理逻辑；新增受管理员权限保护的批量删除端点，单连接、逐项 savepoint 隔离、一次提交、一次监控同步。资产新增/导入合并 INSERT；编辑按变更集合决定关联同步，并在后端锁定创建后不允许修改的档案字段。
- backend/services/tag_service.py 与 backend/services/pam_web_service.py：值未变化时避免重建手工标签及 Web 配置。
- src/pages/AssetManagement/index.tsx 与 src/pages/AssetManagement/components/AssetModal.tsx：编辑状态下锁定稳定档案字段；状态、生命周期、站点、机柜和安装 U 位仍可编辑。保存时只提交有变化的字段，未变标签和 Web 配置不进入更新请求。保存后静默刷新当前页；仅在汇总维度发生变化时刷新汇总。
- backend/database/schema.py 与 backend/database/migrations/m0282_asset_delete_lookup_indexes.py：为删除清理路径补充索引，新安装与已有数据库保持一致。
- backend/tests/rackvision/test_asset_import_contract.py：覆盖批量删除成功、缺失资产和资源范围拒绝的部分失败语义。
- backend/tests/database/test_m0282_asset_delete_lookup_indexes.py：覆盖迁移索引创建及幂等性。
- src/pages/AssetManagement/index.test.tsx：覆盖导入进行时列表会在整批请求完成前刷新、批量删除只发一个 API 请求。
- 本计划对应 walkthrough 记录验证结果。

## 实施步骤

1. 检查现有资产刷新状态与删除清理副作用，保持 API 错误信息和权限校验语义。
2. 在导入进行时每隔约 1.2 秒静默重取当前资产页；避免加载态闪烁，请求结束后执行最终列表和汇总刷新。
3. 把删除清理提取为共享事务内 helper；单资产 DELETE 保持原响应，新增 batch-delete 返回 deleted IDs 与逐项失败明细。
4. 前端批量删除只发一次请求，并在完成后刷新列表和汇总。
5. 对照删除 SQL 与现有索引，补充缺失的设备/资产关联索引并创建 PostgreSQL 迁移；身份查重 SQL 与既有唯一表达式索引保持一致。
6. 合并新增/导入的资产字段写入；编辑时锁定类型、编号、序列号、厂商、型号、主机名、管理 IP 和设备高度，只提交变化字段，保持设备状态及站点/机柜/安装 U 位可变，跳过未变凭据、标签、Web 配置以及不相关同步。
7. 补充前后端和迁移定向回归测试，运行 TypeScript 检查和相关后端测试。

## 风险与回滚

- 导入进行中静默列表读取会以约 1.2 秒间隔增加少量只读查询；每次仅读取当前页，不会扩大到全量资产导出。可通过移除轮询恢复导入完成后单次刷新。
- 批量删除仍逐项保留资源范围校验与清理；单次事务一次提交，连接或提交级故障会回滚整个批次，单项业务失败则通过 savepoint 保留其他成功项。回滚可恢复旧前端多请求路径与原单项删除实现。
- 新索引在部署迁移期间需要 PostgreSQL 扫描关联表并构建索引；大型生产表上可能短暂增加 I/O 并阻塞写入，索引不改动现有数据。
- 不修改数据库 schema；真正已删除的资产无法从应用逻辑回滚，需按现有数据库备份恢复。
