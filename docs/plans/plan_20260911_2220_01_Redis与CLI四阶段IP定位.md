## 1. 任务目标与已确定边界

以用户指定流程作为唯一主线：核心设备 → 逐跳目标路由查询 → Direct 三层终结设备 → 目标 ARP → 目标 MAC → 沿二层拓扑递归 → 有证据的最终接入接口。

- Windows Nexora 通过根目录 `.env` 指定局域网 Redis；Redis 可独立 Docker 部署，也可与容器版 Nexora 同 Compose 网络部署。
- 本功能的路由、ARP、MAC、接口和邻居采集全部使用 SSH/CLI，不调用 SNMP，不设置 SNMP 失败回退；LLDP/CDP 信息通过 CLI 获取。
- Redis 提供共享缓存；PostgreSQL 持久保存事实、任务与调度状态、历史和审计。
- 网段归属索引用于缩小范围、交叉验证和发现缺口，不替代从核心开始的三层逐跳过程。缓存命中可以复用已验证的完整过程，结果必须保留 L3/L2 路径及其来源。
- 定位请求不直接打开 SSH，由队列执行器按设备预算采集；设备配置写操作不属于此功能。
- 首轮代码、配置、迁移和部署说明已存在；Windows 应用已通过配置中的 REDIS_URL 连通 Ubuntu Docker Redis。当前审计确认仍有计划内的实现/回归缺口，不能视为整个方案已完成。真实设备采集、生产迁移和生产灰度仍需在目标环境执行。

## 3. 四阶段执行算法

### 3.1 请求上下文与起点

请求包含 `target_ip`、可选 `start_device_id`、`site_id`、`vrf`、`force_refresh`。tenant、asset/site resource scope 和授权设备集合均由服务端身份上下文计算，不能信任客户端指定的 tenant 或设备范围。

- 用户可以只输入 IP：当站点、VRF、可访问核心唯一时自动补齐。
- 自动起点使用可访问范围内 `role=core` 的设备；没有核心时返回 `needs_context`，不把所有路由设备当成核心。用户显式选择起点时只追踪该设备。
- 重叠地址、多个未明确的 VRF/入口时返回 `needs_context` 和授权候选，禁止随机取第一项。
- 多个核心候选可以在预算内探查并保留差异。
- 当前 PostgreSQL/CMDB 尚无设备到 `network_domain_id` 的权威绑定。V1 按认证用户租户、可访问站点和 VRF 限定设备；收到 `network_domain_id` 时返回 `NETWORK_DOMAIN_SCOPE_UNSUPPORTED`，不把客户端传值当成隔离证据。未来增加权威绑定关系后再开放此字段。
- V1 四阶段终端追踪以 IPv4 ARP 为验收范围。IPv6 需要 NDP 专项适配；不支持时明确返回，不能尝试 ARP，也不破坏旧入口现有能力。

### 3.2 阶段一：从核心逐跳定位 Direct

1. 在当前设备和 VRF 查询目标 IP 的精确路由，优先复用新鲜结构化缓存。
2. 按有效路由最长前缀匹配，保留所有有效等价下一跳，记录 prefix、protocol、next_hop、out_interface、VRF 和采集时间。
3. 若为有效 connected/direct 路由且覆盖目标，确认三层终结候选。Local/Receive、设备自身 /32、Loopback 应返回设备接口归属，而非继续追终端。
4. 若非 Direct，解析递归下一跳，利用已采集接口 IP 索引识别下一跳设备，再使用该设备已纳管的管理地址和凭据连接。不能直接将任意下一跳 IP 当作允许登录的管理地址。
5. 下一跳映射缺失时，在当前设备相关出口补查邻居/接口信息；只在授权网络域内消歧。未知设备、无路由、Null/Discard、不可达分别返回明确状态。
6. ECMP 保留有界分支；VRF 切换需路由泄露或配置证据，不猜测。核心到网关的结果称为控制平面推导路径，不声称是具体报文实际经过的唯一路径。

每分支维护 `(device_id, vrf, target_ip)` 访问集合，防循环；不同分支允许汇合并共享同一目标查询结果。V1 默认每分支 L3 上限 16 跳。

### 3.3 阶段二：仅在已确认网关候选查询 ARP

1. 查询该网关、该 VRF、该目标 IP 的 ARP，不扫描其他网关。
2. 提取 MAC、ARP 来源接口、VLAN/二层域、条目状态与采集时间，验证完整性。
3. VRRP/HSRP、Anycast 等多网关场景，结合冗余和路由证据补查同一网段的候选，不以响应先后决定真实来源；冲突保留为 `ambiguous`。
4. 检查 MAC 是否为本机、虚拟网关或代理 ARP 证据；无法确定时不把它当成终端 MAC。
5. ARP 未命中先返回 `arp_not_found`。V1 默认不自动 ping；如后续提供“主动探测后重查”，使用独立显式操作，限制目标、VRF、探测数与频率。

Direct 说明当前设备承载目标直连网段，不等于它必然是主机配置的唯一默认网关；结果应标记为本次路径的三层终结设备并保存证据。

### 3.4 阶段三：在网关二层入口查询目标 MAC

在目标 VLAN/bridge domain 查询精确 MAC，保留全部匹配及 local/dynamic/static/remote 类型。ARP 接口是来源证据，不直接作为物理接入口。

- 若网关支持 FDB，查询得到物理接口或聚合接口。
- 若网关为无 FDB 能力的路由器/防火墙，根据 ARP 出接口与已知链路确定相连二层设备，从该设备开始查询。
- 未能确定二层入口时返回 `l2_entry_unknown`，保留 L3 和 ARP 结果。
- VXLAN/EVPN 远端 FDB、隧道、虚拟交换或无线控制器后端，只有具备专用关系证据才能继续；V1 缺适配时返回领域边界状态，不误报为物理接入口。

### 3.5 阶段四：沿接口递归下钻

1. 规范化命中接口，匹配逻辑聚合及成员；查询已知的直接邻居，不能把可达的所有下游设备当作直接邻居。
2. 有有效邻居时，只查询该出口关联的候选设备，并带上同一 MAC 与 VLAN/二层域；有显式 VLAN 转换时记录映射。
3. 下游命中回指上游的接口不是进展证据；不能停在第一个命中分支。多分支冲突时继续有界验证，最终保留候选和理由。
4. 邻居过期/缺失时，只补查当前设备的 LLDP/CDP、相关接口和聚合信息，再重新判断。
5. 无邻居且接口有有效物理 Access/Edge/Untagged、业务 VLAN 等组合证据时，输出最末纳管接入点；不能仅因“没有 LLDP”判终端。Access 模式也不能证明后面没有未纳管交换机，UI 使用“最末纳管接入点”，不保证终端直插。
6. Trunk、Hybrid、LAG 或接口身份不完整时，缺邻居返回 `topology_incomplete`，不报定位成功。

V1 默认 L2 上限 16 跳、每跳最多 4 个候选、整任务最多查询 32 台不同设备；这些为初始可调预算。任何预算耗尽都返回 partial 和未覆盖分支，不把截断解释成未找到。

## 4. 精准采集范围与完整性

| 数据 | 常规采集范围 | 增量/按需范围 |
| --- | --- | --- |
| 接口 IP/VRF、设备能力 | 所有纳管网络设备分批维护；建议 30 分钟周期及变更触发 | 当前起点/下一跳映射相关设备 |
| LLDP/CDP、LAG、相关端口身份 | 所有支持设备错峰维护；建议 5 分钟周期 | 当前 MAC 命中出口所在设备 |
| 目标路由 | 不为定位全量拉取路由 | L3 路径设备，目标 IP 与 VRF |
| ARP | 定位功能不默认全网扫；已有网关快照可按配置复用 | 当前 Direct 网关候选，目标 IP |
| MAC | 定位功能不默认全网扫；已有明确开启的快照可复用 | 当前 L2 路径候选，目标 MAC 与二层域 |

周期基础采集经同一后台设备预算调度，增加错峰；完成不及周期时合并下一轮，不堆积重复任务。采集周期是目标，不代表实际数据年龄，超期要显示覆盖缺口。

设备能力枚举：supported / unsupported / unknown / failed。unknown 与 failed 进入能力补采，禁止按角色直接排除。设备不支持精确过滤时允许仅该设备的一次有界全表采集，按同一快照服务多个查询；限制时间、输出量和解析条数，截断结果不能证明全表未命中。平台注册绑定设备必须经过发布动作，新增精确查询动作需遵循现有发布边界。

任务缺口明确展示：起点未配置、下一跳未纳管、设备失败、VRF 不明确、拓扑缺失、预算耗尽。不承诺无法观测的设备或已老化终端绝不遗漏；验收重点是不将覆盖不足伪装为准确终点。

## 5. TTL、新鲜度与失效合同

### 5.1 初始默认值

所有时间从原始 `collected_at` 起算，单位秒。新鲜期限决定普通查询能否复用为近期证据；最长保留期限决定 Redis 键删除时间；它们不是设备协议老化时间。

| 数据 | 新鲜期限 | Redis 最长保留 | 说明 |
| --- | ---: | ---: | --- |
| 目标路由 | 300 | 1800 | 本方案增加的路由默认值，取此前讨论 5–10 分钟的下限 |
| 目标 ARP | 300 | 1800 | 成功采集的完整目标记录 |
| 目标 MAC/FDB | 120 | 900 | 保留 VLAN/二层域与来源设备 |
| 完整定位结果 | 最多 120 | 最多 900 | 受全部必要证据的更早到期时间约束 |
| 网段归属投影 | 900 | 86400 | 辅助核对；不能通过重新投影刷新采集时间 |
| 拓扑投影 | 600 | 86400 | 依赖邻居、接口、聚合证据，取必要证据最早到期 |
| 成功但无匹配的目标查询 | 15 | 15 | 失败、不支持和部分输出不可作为负缓存 |

网段归属 15 分钟新鲜期可能短于接口/IP 30 分钟周期：这是明确允许的状态。周期之间只可作为旧辅助线索；若当前定位依赖其有效性，必须按需刷新相关设备，不能提高 TTL 掩盖年龄。

### 5.2 时间与结果判定

- 事实保存 collected_at、fresh_until、retain_until、source、coverage、generation、schema_version。统一 UTC 存储，UI 转本地时区。
- `fresh_until = collected_at + fresh_seconds`；`retain_until = collected_at + retain_seconds`。
- 完整结果 `fresh_until = min(generated_at + 120, 所有必要事实 fresh_until)`；历史保留同样不超过结果上限和必要事实 retain_until。
- 从 PG 回填 Redis 使用剩余时间，读取不续期。`generated_at` 只表示计算时间，绝不能重置证据年龄。
- TTL 到期不会自动采集。普通请求/选定后台任务才触发刷新；冷门终端不周期刷新。
- 2 分钟是 MAC 近期证据窗口，不是“2 分钟内必然实时”。UI 必须显示采集年龄和来源。
- 过期结果只能展示为历史位置；依赖发生已知变更时，即使未到期限也不能展示为当前结果。

### 5.3 主动失效与一致性

ARP MAC 变化、FDB 端口/VLAN 变化、接口/拓扑 revision 变化、设备身份/VRF/资产关系变化，递增对应 generation 并使依赖结果失效；权限变化必须立即阻断访问，不依赖 TTL。

采用 PG 提交事实及 generation 后再投影 Redis；任务完成前验证读取的依赖 generation 未改变，冲突时重算或返回 inconsistent_evidence。旧任务不能覆盖更新事实。刷新时穿透已有 cmd_cache，避免 300 秒原始输出被写成新的 120 秒 MAC 事实。

full snapshot 和 targeted observation 显式区分。成功完整快照可以撤销该设备该作用域缺失条目；失败/部分快照不能清空其他设备事实；目标查询只更新/撤销该目标，不代表全表已刷新。

## 6. 队列、请求合并与 SSH 配额

### 6.1 PostgreSQL 作为协调源

- 结果任务去重键包括部署、tenant、网络域、VRF、起点、目标 IP、查询模式及有效授权范围指纹；后台共享原始事实时仍逐次校验读取权限。
- 单设备查询任务按 device、VRF、操作类型、规范化目标与解析/动作版本合并。不同 IP 任务不能互相覆盖 payload。
- 任务队列状态、优先级、租约、设备配额存 PG；Redis 不承载唯一的调度锁或唯一任务状态。
- 原子 claim 使用 PostgreSQL 行锁和 SKIP LOCKED；不能在网络 I/O 期间持有数据库事务。
- 任务租约初始 90 秒、每 20 秒续租；命令超时初始 30 秒；总任务截止时间 180 秒（含排队）。命令及连接超时均受剩余预算约束。
- 工作进程失去租约或无法续租时停止发新命令并关闭连接。用 ownership token/generation 拒绝迟到写入；故障恢复保留连接清理宽限，不能承诺网络分区下严格零重复物理会话。

### 6.2 配额与会话生命周期

- V1 定位 CLI 全局并发初始 5，单物理设备后台会话初始 1，均为部署级限制。
- 使用 canonical device ID 作为配额键；别名、多个管理 IP、不同账号不能绕过同一设备预算。
- 同一设备内命令串行；不同设备可在预算内并行。不得与 PAM 交互会话共享 shell。
- 目标：一次设备阶段内复用连接；初始空闲回收 15 秒，空闲连接仍计入配额。当前 IP 定位已按设备复用 SSH 会话并维持 locator 专属租约；定位、拓扑、巡检、备份等后台入口尚未统一到同一跨进程设备配额。
- 配额管理需覆盖定位、拓扑、巡检、备份等平台后台连接路径；变更/终端优先于定位，后台任务有等待时长上限及防饥饿机制。
- 系统外 SSH 客户端不受平台调度控制，因此每设备需配置安全后台上限和终端保留余量。无法确认容量的设备默认保守值；连接拒绝时退避，不宣称能保证外部终端永不受影响。
- 强制刷新仍排队；同目标短时间重复点击合并，不为每次点击新增会话。

### 6.3 错误、重试和背压

连接超时/暂时不可达最多一次带抖动重试，仍在任务总预算内；认证失败不即时重复尝试，失败冷却初始 300 秒，凭据修正可解除。unsupported 不重试同一命令，进入明确的能力/适配结果。

每用户活动任务初始 3、部署待处理任务初始上限 200；超限返回 429 和 retry_after，不能无限堆积。最终阈值由场景测试确定，不能把初始参数作为性能保证。

## 7. Redis 与 Windows / Docker 部署

### 7.1 配置合同

现有 `REDIS_URL` 继续作为统一连接入口。基本部署只需这一项；连接 URL 含特殊字符的用户名/密码需要 URL 编码。TTL、命名空间、连接超时和并发使用程序默认值，不要求逐项写入 `.env`。

```dotenv
# 示例地址与占位凭据，部署时替换
REDIS_URL=redis://nexora:YOUR_PASSWORD@192.168.10.20:6379/0
```

新定位流程默认使用；部署时只需设置已有的 `REDIS_URL`，TTL、命名空间、并发与超时使用代码默认值。没有 Redis 或 Redis 暂时不可用时，缓存层使用 PostgreSQL，任务仍受同一队列与设备预算约束。

程序校验默认 TTL、预算和 namespace 合法；`.env.local` 与系统环境变量仍遵循既有覆盖规则。校验 Windows CRLF/Linux LF，不改写真实 `.env`。

### 7.2 两种部署形态

- Windows Nexora → Redis 宿主机局域网 IP 与映射端口；Redis 可在同机 Docker 或局域网 Linux/Docker 主机。
- Nexora 容器 → 同网络 Redis 服务名 `redis:6379`；容器内 localhost 不代表宿主机。
- 提供独立 Redis Compose 模板和可选集成模板，固定经验证的版本标签/镜像摘要；具体版本在实施时确认。
- Redis 配置专用 ACL 用户，限制命令和 key 前缀；局域网端口只允许 Nexora 主机。跨不可信链路使用 TLS/rediss 和 CA 校验。
- Redis 仅用于可重建缓存；建议独立实例配置 maxmemory 与 allkeys-lru。初始内存预算可按 512 MiB 起做测量，不视为全网容量保证；容器总内存必须留出额外开销。
- 不将该淘汰实例兼作不可丢失任务/锁存储。不同 Redis DB 编号不能隔离实例级淘汰策略；若复用 AI 限流等业务实例，需核查其数据丢失容忍度，必要时独立实例。
- 不依赖 Redis AOF/RDB 恢复定位正确性；重启后按原始采集时间从 PG 回填，不全网同时预热。

### 7.3 故障降级

Redis 连接/命令失败采用短超时和熔断，初始熔断 30 秒后单次探测恢复；记录脱敏错误分类。回退 PG 事实读取、同一任务去重和设备预算。不能回退旧的每请求直接 SSH 扇出。

PG 不可用时暂停新采集；仅在授权仍可确认且证据有效时允许缓存读取，否则明确服务不可用。健康页只展示 Redis 主机、端口、可用性/延迟、降级状态，不展示密码或完整 URL。

## 8. 持久化和缓存模型

优先新增隔离的 V2 表及适配层，避免直接改写以 IP 为唯一键的 legacy 缓存导致重叠 IP 混淆。具体迁移序号由实施时最新版本决定。

| 拟议模型 | 必要字段/唯一性 |
| --- | --- |
| locator_runs | id、owner、tenant/scope、target、start、mode、status、deadline、result、错误与采集统计；run worker owner/token/lease 用于崩溃恢复 |
| locator_query_tasks | query_key、device、operation、target/context、priority、lease_owner/until、attempt、generation；同一 query_key 最多一个活动任务 |
| locator_run_tasks | run 与共享 query task 的订阅关系；单用户取消不取消其他订阅者任务 |
| locator_observations | scope、device、VRF、bridge_domain/VLAN、kind、target、records、coverage、原始时间、generation、schema/action version |
| network_device_access_slots | canonical device、用途、owner、lease、连接状态；任务与设备预算原子协调 |
| locator_global_access_slots | deployment-wide V2 CLI 并发槽位与 lease token；跨进程限制最大活动 run/CLI 数 |
| locator_history / invalidation outbox | 最末纳管接入点变化及事实失效事件；历史初始保留 30 天，可配置 |

PG 保存当前观察和有界最近历史，不永久保存每次完整原始 CLI 回显。任务详情初始保留 7 天，清理不得删除活动任务；观测保留至少满足缓存回填与审计需要。历史年龄不影响 fresh 判定。

Redis key 使用固定 namespace 和规范化上下文摘要，例如 `...:fact:arp:<scope_hash>:<device_id>:<vrf_hash>:<ip>`；MAC key 必须包括二层域和 VLAN。结果 key 包含起点、scope 和模式；默认 VRF 使用显式标识而非空值猜测。JSON 只存结构化脱敏事实，不存账号、密码、完整设备对象。

事实提交和失效 outbox 同事务，投影失败可重试；消费者按 generation 幂等处理。初期拒绝将 legacy 无作用域/无采集时间记录自动回填为有效 V2 证据。迁移采用新增表、补索引、逐步读写切换，fresh install 与 upgrade 保持一致。

## 9. API、UI 与兼容策略

拟议新接口：

- `POST /api/ip-locator/runs`：输入 ip、可选 start_device_id、site_id、vrf、force_refresh。用户租户、asset/site 授权和授权设备集合由服务端计算；当前 CMDB 无权威 network_domain 绑定，非空 `network_domain_id` 返回 422 `NETWORK_DOMAIN_SCOPE_UNSUPPORTED`。返回 202 queued/running，含 run_id；结果由状态接口轮询。
- `GET /api/ip-locator/runs/{id}`：返回进度与结果；每次校验任务 owner/授权范围，不能仅凭 run_id 读取他人结果。
- `POST /api/ip-locator/runs/{id}/cancel`：解除当前订阅，未被其他任务使用的查询可取消；已下发命令安全结束或超时，不把响应写入已撤销运行结果。
- `GET /api/ip-locator/health`：按现有权限体系暴露脱敏健康摘要。

run.status：queued / running / completed / partial / failed / cancelled / needs_context。与定位结论分开：managed_access_confirmed / device_interface / arp_only / ambiguous / not_found / historical。提供稳定 reason_code，例如 no_route、route_loop、next_hop_unmanaged、arp_not_found、mac_not_found、query_failed、unsupported、topology_incomplete、budget_exceeded。

响应最少包含 l3_paths、gateway_candidates、arp_evidence、l2_paths、terminal_candidates、freshness、queried_devices、coverage_gaps、cache/dependency 状态。不用一个 found 布尔值掩盖 ARP-only 与最终接入点之间的区别。

普通查询显示“近期采集位置/历史位置/正在更新”和原始年龄。强制刷新要求动态路由、ARP、MAC 证据采集不早于本次请求或可共享刷新任务的起始时间，静态拓扑仍按新鲜度与变更校验；未完成前不可标实时成功。

V2 页面和复用面板同时切换；旧 `/locate` 作为兼容适配器，不直接返回旧客户端无法识别的 202 结构。适配器走同一队列并有界等待，超时返回明确可识别错误及可选任务信息；旧错误码映射在实施时回归确认。启用 V2 后禁止旧入口绕过预算使用旧实时扇出。完整端到端诊断作为独立功能保留，后续可复用纯解析层。

## 12. 验证计划与明确验收标准

### 12.1 功能场景

- 网关在核心、汇聚、接入：均从指定核心开始，直到正确 Direct，再追至最末纳管接入点。
- 纯路由网关无 FDB、双网关、ECMP、递归下一跳、同 IP 不同 VRF/站点、设备本地 IP、黑洞路由、循环和超限。
- LAG 成员/逻辑口、Cisco/Huawei/H3C 接口别名、多个命中分支、回指上联、缺 LLDP、未纳管下游、远端 FDB、MAC 漂移。
- 未命中、不支持、命令失败、截断结果、部分覆盖状态不能混为 not_found 或最终成功。

### 12.2 TTL 与并发验收

- 100 个同作用域同目标同时请求，在同一刷新批次只生成一套可共享目标查询；不同用户分别校验授权。
- 多 worker 查询不同 IP 同设备，V1 单设备后台连接不超过配置；别名/账号不绕过限制。
- fake clock 验证 fresh/retain 边界、旧 PG 回填、缓存访问不续期、最旧证据约束、变更提前失效和迟到任务不覆盖。
- Redis 断开、恢复、淘汰、重启；冷缓存下任务仍合并且受限，不触发全网预热或直连风暴。
- worker 崩溃、取消、租约丢失、PG 不可用、队列满、认证失败退避；记录实际限制和恢复边界。
- V2 全路径测试将 SNMP 调用入口设置为失败断言，证明不会调用；验证旧定位入口也受同一预算。

## 13. 风险与回滚

- 主要风险：基础拓扑缺口、MAC/ARP 漂移、重叠地址串域、共享连接生命周期、缓存时间重置、旧入口绕过新队列。
- 新定位流程默认使用，schema 增量引入；灰度期间不删除旧事实表或重置已有 collection plan。回退通过恢复上一版应用完成，不增加 `.env` 开关。
- Redis 可降级为 PG 缓存，继续使用 V2 队列与预算；暂停采集时展示历史与不可用状态。
- 新引擎出现问题优先停新任务、排空/取消队列并关闭连接，再回退应用版本。不能以回退 Redis 故障为理由自动恢复旧的无限制查询路径。
- 数据库回滚以应用读写回退、保留新增表为主；需要删除表或迁移真实数据时必须另行制定备份和恢复步骤。
- 保留用户已配置的后台快照，但逐项纳入共享设备配额；默认不额外开启全网 ARP/MAC。
