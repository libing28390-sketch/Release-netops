# SNMP 自动绑定设备平台与修复 VLAN 生命周期

## 任务目标

1. 网络设备通过资产表格导入并具备可用 SNMP 凭据时，复用现有导入后身份探测，把唯一、安全匹配的平台注册 Profile 自动绑定到 `devices.platform_profile_id`，减少网络设备页的手工绑定。
2. 让 VLAN 的设备快照、自动发现目录和 prefix 引用拥有明确生命周期：删除设备时清理该设备快照；失去最后一个观测来源的自动发现 VLAN 不再作为陈旧记录留在 CMDB；prefix 记录保留。
3. 页面只在进入、用户刷新、筛选/分页变化或操作完成时重新加载，不增加定时自动刷新。

## 现状与根因

### 资产导入与平台绑定

- `POST /api/assets/import` 已接受 `platform`、SNMP 凭据名称/ID，并在提交资产后异步运行 `identify_imported_device`。现有探测读取 `sysObjectID/sysDescr/sysName`，使用 SNMPv2/v3 凭据和厂商/平台归一化规则，最多 5 台并发；失败不回滚已导入资产。
- 现有身份任务会更新 `devices.version`，但以已有非空值优先，可能保留旧版本；它也没有写入 `devices.platform_profile_id`。`physical_assets` 没有独立软件版本字段。表格里的平台值是技术平台代码；网络设备页手工绑定的是平台注册表中的具体 Profile。因此现有 SNMP 识别完成后，仍可能需要人工绑定。
- `platform_identification_service.identify_platforms` 已能按注册规则返回 `platform_profile_id` 候选；`bind_device` 会做 Profile/厂商/平台/版本校验，并以人工来源写入绑定及锁定状态。导入流程需要复用这些规则与校验，补上自动绑定和来源标记，不能另造一套 vendor→profile 猜测。
- 此计划的目标字段是 `platform_profile_id`，不是监控指标用的 `snmp_metric_profile_id`。

### VLAN 与设备删除

- `/api/cmdb/vlans` 合并全局 `vlans` 目录行和 CLI 快照投影。存在同站点、同 VLAN ID 的目录行时，快照合成行会被目录行覆盖。
- `sync_observed_vlans()` 会从共享接口、ARP、MAC 证据新增或更新按 `site_id + vlan_id` 归并的全局 VLAN 行，但不清理已经没有来源的自动发现行。
- m0298 创建的 `cmdb_collection_snapshots` 和 `cmdb_device_vlan_observations` 均没有 `devices` 外键；m0299 的 VLAN 端口明细只在父观测行被删除时级联。删除设备不会可靠删除这些设备快照。当前只读检查中，VLAN 快照孤儿数为 0，但采集快照状态表已有其他域孤儿记录。
- `prefixes.vlan_id` 的数据库外键是 `ON DELETE SET NULL`，但 `cmdb_service.delete_vlan()` 先因 prefix 引用主动拒绝删除。当前 VLAN 7 样例来源为 `interface_svi`，最后发现时间为 2026-10-10，当前没有 CLI/接口/ARP/MAC 来源且有 1 条 prefix 引用；说明目录项的设备来源已消失，但 IP 前缀关联仍存在。
- VLAN 页面列表没有定时轮询；接口任务状态的短间隔轮询不是 VLAN 列表刷新。

## 范围与约束

- 仅修改资产导入识别、平台注册绑定、CMDB VLAN/设备删除生命周期及相关页面/测试/数据库迁移。
- 严禁修改监控采集、SNMP 遥测/告警、监控调度与轮询策略；尤其不修改 `backend/services/snmp_service.py`。复用现有资产导入身份探测读取到的 SNMP 结果，不增加第二次探测。
- 不修改 LibreNMS 监控规则或 `snmp_metric_profile_id` 绑定语义。
- 不新增 VLAN 定时任务或页面定时刷新；Redis 按用户要求不纳入。
- 不执行真实设备 SNMP 查询或生产数据清理。存量 orphan 清理只放入可审查的 PostgreSQL 迁移，并限制为找不到 `devices` 所属记录的派生快照。

## 预计修改文件

- `backend/api/assets.py`：把导入者身份/凭据探测结果接入现有导入后处理，返回逐行平台绑定结果。
- `backend/services/snmp_import_identification_service.py`：复用现有 sysObjectID/sysDescr/sysName 结果匹配注册 Profile，不增加新的设备请求。
- `backend/services/platform_identification_service.py`：复用现有候选规则、租户范围、厂商/平台/版本兼容检查和审计；支持区分 `SNMP_AUTO` 与 `MANUAL` 绑定来源，并保持既有管理员纠错及锁定语义。
- `backend/api/devices.py`、`backend/services/vlan_discovery_service.py`、`backend/services/cmdb_service.py`：删除设备后按受影响 site/VLAN 重新核算来源，只清理无剩余来源的自动发现目录行；手工 VLAN 保留。
- 新增 `backend/database/migrations/m0300_cmdb_vlan_device_lifecycle.py`：清理设备不存在的派生快照行，并为 `cmdb_collection_snapshots.device_id`、`cmdb_device_vlan_observations.device_id` 增加 `ON DELETE CASCADE`。
- `src/pages/AssetManagement/index.tsx`：显示自动绑定、待人工选择、无凭据、未匹配、冲突和探测失败结果。
- `src/components/DeviceDetailModal.tsx`：显示绑定来源；保留现有管理员更正规则。
- `src/pages/CmdbManagementTab.tsx`：VLAN 表提供显式刷新入口；操作/导入任务完成后只触发一次 refetch，不启用周期刷新。
- `backend/tests/configuration/`、`backend/tests/vendor_audit/`、迁移测试及相应前端测试；实现阶段创建匹配的 walkthrough 和每个提交独立的 fix 记录。

## 实施步骤

### A. 资产导入自动绑定 `platform_profile_id`

1. 复用现有 `identify_imported_device` 的一次性只读 sysObjectID/sysDescr/sysName 结果，保持当前 SNMPv2/v3 Profile、社区名优先级、并发限制、超时和脱敏行为；本轮从 `sysDescr` 解析出的非空软件版本先同步到 `devices.version`，Profile 代际匹配使用同一轮观察值；未解析到版本时保留现存值。不新增监控轮询。
2. 将现有 SNMP 身份字段映射到平台注册识别规则，取得 `platform_profile_id` 候选；优先使用启用且可分配的 Profile，复用当前厂商/平台/版本兼容校验。不得仅凭型号或通用 vendor/platform 默认值绑定。
3. 仅当候选唯一、规则无同分冲突、Profile 处于可用状态且设备已有绑定为空时，写入 Profile、规范化后的 parser/driver platform、`platform_source='SNMP_AUTO'` 和对应锁定状态。手工填写的已绑定 Profile、已有锁定绑定不得覆盖。
4. 无 SNMP 凭据、SNMP 关闭、超时、v2/v3 算法不支持、厂商冲突、无候选或多候选时，资产导入仍成功；保持未绑定，返回可操作原因和候选供网络设备页人工绑定。
5. 对每行导入结果显示绑定来源与结果；后台 enrichment 继续沿用现有待处理/刷新契约，不让资产入库等待新增的第二轮 SNMP 请求。
6. 确认自动绑定遵循调用者/租户的 Profile 使用权限，不通过后台身份提升绕过 `platform.bind_device` 策略；来源记录为 `SNMP_AUTO`，审核事件可追踪。

### B. VLAN 快照和自动发现目录生命周期

1. 新迁移执行前统计 orphan 数；在 PostgreSQL 事务中仅清理 `device_id` 已不存在的 `cmdb_collection_snapshots`、`cmdb_device_vlan_observations`（端口子行随父行级联），再增加设备级级联外键。校验现有 interface observation 既有外键不重复。
2. 设备删除前保存所属站点范围；删除设备后仅重算该站点，基于仍存在设备的成功 CLI VLAN 快照及现存接口/ARP/MAC 来源重建观察集合。
3. 仅回收 `discovery_source != 'manual'` 且无其他有效来源的全局 `vlans` 行；同 VLAN 仍被其他设备报告、手工创建或存在人工覆盖的 prefix/VLAN 业务关系时保留。
4. 对无来源的自动发现行，如果仅被非手工 prefix 引用，保留 prefix 行并解除其 `vlan_id`（与现有 `ON DELETE SET NULL` 语义一致），再删除自动 VLAN 目录行。不得删除 prefix；手工覆盖关系不自动解除。
5. 调整直接 VLAN 删除服务：保留对仍有设备来源或人工维护关系的拦截；对无来源的自动发现行按同一规则处理 prefix 解绑，避免服务层“引用即永不删除”与数据库 `SET NULL` 规则冲突。
6. VLAN 页面保持无周期自动刷新：用户点击显式刷新，或本页已知的采集/删除操作成功时单次重新加载并更新列表/缓存视图。

## 验证计划

- 资产导入：PostgreSQL fixture + mock SNMP 覆盖唯一高置信 Profile 自动绑定、缺少凭据、SNMPv2/v3 成功/算法不支持、超时、厂商冲突、规则无匹配/并列冲突、已有手工锁定、部分导入失败仍保存资产、权限不足不绑定。
- Vendor/profile 合约：Cisco、Huawei、H3C 的“识别结果→Profile→规范 platform→driver/parser family”回归；不能因自动识别回退 Cisco，也不能仅凭型号猜厂商。
- VLAN migration：从 m0299 升级、重复执行迁移、fresh schema；验证 orphan 派生行清理、设备删除级联到 collection snapshot/VLAN observations/port rows。
- VLAN reconciliation：多设备共报同 VLAN 时删一台仍保留；删最后来源时只清理自动目录行；manual VLAN 保留；prefix 行保留但符合条件时解绑；人工覆盖 prefix 保留绑定；页面缓存与单次刷新更新。
- 运行受影响 pytest、`scripts/validate_postgresql_only.py`、前端测试/lint/build 和 `git diff --check`；用差异扫描确认监控代码路径、`snmp_service.py`、调度器及 metric profile 无改动。
- 完成后在授权的测试环境验证导入响应、网络设备页自动绑定状态、VLAN 页删除设备/刷新后的列表；不以本地静态或 mock 结果宣称真实设备 SNMP 已通过。

## 风险与回滚思路

- 错误 Profile 绑定会影响 SSH/自动化命令和解析模板。仅接受唯一兼容的注册 Profile；不确定时保留未绑定并提示人工处理。SNMP_AUTO 来源可追踪，管理员可按现有流程更正。
- `devices.version` 同时作为网络设备当前软件版本，并被现有 SNMP 指标 Profile 兼容性匹配读取。按用户要求同步本轮真实版本可能更新兼容性判断；本次不改监控代码、不改 `snmp_metric_profile_id`。
- 自动回收 VLAN 可能解除 prefix 与 VLAN 的关系。实施前确认保留 prefix、清空 `vlan_id` 的语义；manual override 与手工 VLAN 不自动清理。
- migration 清除的 orphan 快照属于不可见派生状态；记录各表清理数量，必要时先备份。迁移可回滚约束，但已清理快照只能通过后续重新采集恢复。
- 应用回滚不删除资产或 prefix；m0300 的 `downgrade` 保留设备级级联约束，避免回滚后重新产生孤儿快照。已清理的孤儿快照属于可重采集的派生状态，无法从迁移自动恢复。
