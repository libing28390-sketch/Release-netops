# 实施计划：Docker 部署健康检查与 S3 启动

## 任务目标
修复 Linux Docker 冷启动健康探针、SNMP Exporter 0.26 配置格式不兼容和 S3 sidecar profile 启动识别问题。

## 现状与问题证据
- 第一次启动时 `nexora-netops` 一度 unhealthy，随后恢复 healthy；依赖容器仍为 `Created`，因为 Compose 首次启动已因依赖 unhealthy 中止，当前部署脚本没有等待恢复并重试，所以需要人工再次启动。
- Dockerfile 与 Compose healthcheck 使用 `urllib` 请求 `localhost`，后端读取 `.env` 后可能继承 `HTTP_PROXY`；本地 liveness 请求应直接走 loopback 并绕过代理，并给予冷启动/迁移更长宽限。
- `nexora-snmp-exporter` 的实际日志明确报 v0.26.0 不认识 `source_indexes`、`lookup` 字段。默认模板、编译器和现有持久化 monitoring volume 均可能带旧格式；仅重启容器不能修复。
- SeaweedFS 定义为 `object-storage` profile；普通 `docker compose up` 不会启动 profile 服务。项目部署脚本按 `STORAGE_BACKEND=s3` 自动加 profile，但当前解析器对带引号的合法 `.env` 值识别不完整；示例 endpoint 还是主机回环地址，不适用于后端容器访问。
- SeaweedFS 定义为 `object-storage` profile；普通 `docker compose up` 不会启动 profile 服务。项目部署脚本按 `STORAGE_BACKEND=s3` 自动加 profile，但当前解析器对带引号的合法 `.env` 值识别不完整；示例 endpoint 还是主机回环地址，不适用于后端容器访问。

## 影响范围
Docker Compose、镜像健康检查、Docker 部署脚本、SNMP Exporter 默认配置/编译器/运行时兼容迁移、相关文档与测试。不触碰用户服务器、数据库卷或真实凭据；不改变默认 `STORAGE_BACKEND=local`。

## 实施步骤
1. 将后端 liveness probe 固定到 `127.0.0.1`、用空 ProxyHandler 绕过 `.env` 代理，并增加首次启动宽限。
2. 把 Exporter 配置里的 legacy lookup 转为 v0.26 `labels`/`labelname`/`oid`/`type` 格式；同步修复默认模板与编译器，并在启动时兼容迁移持久化 volume 中的旧配置。保持 exporter 在 netops 完成迁移并 healthy 后启动。
3. 部署脚本规范化 `STORAGE_BACKEND` 的空白、大小写和外层单/双引号，并在 S3 模式启用 profile 与服务。
4. 在在线/离线启动路径中加入有限等待与恢复重试：临时依赖 unhealthy 后等待 netops healthy，再无重建地补启动依赖服务；超时给出 health 状态。
5. 将 Docker 示例 S3 endpoint 改为 Compose 内部 DNS `seaweedfs:8333`；文档说明默认 local、启用所需凭据和直接 Compose 命令。
6. 增补部署及 Exporter schema 契约测试；运行相关 pytest、配置语法检查及 Compose YAML 校验。

## 风险与回滚
- 默认存储仍为 local；只有 `STORAGE_BACKEND=s3` 且提供凭据时部署脚本才启动 SeaweedFS，不执行数据迁移。
- 本次无法访问用户 Linux 主机的 Docker daemon；修复后需要在服务器重新运行部署脚本并读取 `docker inspect --format '{{json .State.Health}}' nexora-netops` 核验健康检查详情。
- 回滚仅恢复上述 Compose、Dockerfile、脚本、示例环境、Exporter schema 转换及文档文件；不删除任何 Docker volume 或用户数据。旧格式 exporter 配置转换为新格式是原位、原子、幂等的；回滚旧镜像前需要重新部署与其兼容的配置。
