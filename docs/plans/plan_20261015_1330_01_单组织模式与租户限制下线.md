# 单组织模式与租户限制下线

## 任务目标

停止向用户提供多租户管理和按登录用户租户隔离的访问限制，使 Nexora 按单一组织运行。`tenant_id` 字段、已有记录、审计与历史数据继续保留；用户角色权限以及显式站点/设备组资源权限继续生效。`tenant_id` 若承担业务身份/数据关联（例如 IPAM 地址空间键、拓扑复合键或通知路由），先按原语义保留，不把它误当作用户访问限制删除。

## 现状与证据

- 线上 `/cmdb/tenants` 目前仅列出 `Default Tenant`，未见其他租户记录。
- 租户管理入口位于 `src/components/AppSidebar/navConfig.ts`、`src/utils/routeContext.ts` 和 `src/pages/CmdbManagementTab.tsx`；后端 CRUD 位于 `backend/api/cmdb.py` 与 `backend/services/cmdb_service.py`。
- `src/api/cmdb.ts` 的站点初始化流程会先创建一个租户，再把该 ID 写入站点、VRF、VLAN 与网段。
- `backend/core/rbac.py` 的资源授权同时判断 role/action 与 tenant/site/device-group scope；`backend/services/access_scope_service.py` 和多个 API/Service 还各自实现租户过滤，没有统一关闭开关。工作区已开始建立中心 tenant policy，但目前只接入 RBAC/用户 scope，尚未覆盖业务查询与写入。
- 当前租户隔离并不完整：例如设备/CMDB/IPAM部分列表路由未绑定当前用户租户，租户查询条件有时只是可选过滤器。因此改造应以“统一关闭 tenant 访问边界”为目标，而非只移除导航菜单。
- PostgreSQL 多个业务表、唯一索引和历史记录包含 `tenant_id`。本次不删除列/索引、不批量回填或重写租户 ID。

## 影响范围

- CMDB 租户管理的前端路由、导航、列表和创建/编辑/删除入口。
- CMDB 租户 API 与站点初始化写入逻辑。
- 统一资源授权中租户维度的判断，以及按当前用户租户自动过滤的核心 API/Service；保留按 tenant_id 表达的业务数据身份、唯一性和外部通知路由。
- 用户/脚本/审批、设备、告警、监控、IPAM、IP 定位、变更单、拓扑和 PAM 等依赖租户的关键路径及其回归测试。
- 不修改数据库迁移历史，不改变 role/action、站点和设备组授权。

## Agent 分工与共享文件边界

- Coordinator（主 Agent）：统一定义单组织语义；负责核心 RBAC、CMDB、用户、设备/资产、IPAM、前端入口、CI 失败修正、集成审查、验证与归档文档。
- `tenant_workflow_backend`：负责 PAM 与审批、自动化/定时作业、变更单、Playbook 及平台配置注册相关后端；按固定默认 tenant 写入，保留业务对象绑定、角色/action、MFA、自审隔离和站点/设备组范围。
- `tenant_monitoring_scope`：负责 RackScope 双范围、监控/告警/LibreNMS/collection plan/配置快照/报表列表；将站点与设备组过滤推入 SQL，保持对象与聚合统计边界一致。
- `tenant_enforcement_audit`：只读审查，确认 tenant 条件下线后仍需修复监控、告警与设备组列表授权；未改文件。
- 两名实现 Agent 修改不同后端域；`backend/core/rbac.py`、`backend/services/rack_scope_service.py` 与共享测试由 Coordinator 做最终集成审查，不创建分支、不提交。

## 验证计划

- 检查 `/cmdb/tenants` 不再显示或允许维护多租户，并验证未知旧路径不会进入管理页。
- API 测试覆盖租户 CRUD 下线、内部默认组织兼容、新建记录默认租户 ID。
- PostgreSQL 回归证明 tenant_id 不再造成跨用户数据隐藏，而 Administrator/Operator/Viewer 与 site/device-group scope 仍按预期生效。
- 检查用户管理、脚本审批、告警、监控、IPAM、IP 定位、变更单、拓扑和 PAM 核心列表/对象路由不再用登录用户租户过滤。
- 运行前端 lint/build 及对应浏览器页面验证。

## 风险与回滚思路

- 关闭租户边界会使历史上不同 tenant_id 的记录进入同一组织视图，这是单组织目标要求；role/action 与显式站点/设备组权限仍是访问边界。
- 不合并租户 ID 可避免触发复合唯一索引冲突或改变审计历史；所有新业务记录固定使用 `tenant-default`。
- 若遗漏某个直接 SQL 过滤，仍可能出现某一页面看不到历史记录；以直接 SQL 检索、核心域矩阵和交叉 tenant_id 回归测试验证。
- 若前端、API 或权限回归失败，恢复相应源代码提交即可；无数据库结构或数据迁移需要回滚。
