# 设备版本识别与批量绑定一致性实施计划

## 任务目标

- 支持从锐捷、迪普、迈普、中兴 `show version` 回显中提取真实软件版本，并自动识别对应的厂商/Profile（锐捷至少 V11、V12；中兴覆盖 5900 V6 与 ZSRV2 V3）。
- 默认阻止批量平台绑定选择与设备已知实际软件主版本不一致的模板，例如 Comware 7.1.064 绑定到 V5；管理员明确确认后允许手动覆盖。
- 在前端明确区分“设备实际软件版本”和“命令/解析模板版本”，并展示可操作的错误提示。

## 现状/问题

- 设备 `version` 是资产/采集得到的真实软件版本；平台注册表 Profile 的 `version` 是自动化命令与解析模板适配版本，两者字段独立。
- 当前批量绑定只校验厂商与平台家族，没有校验已知设备版本与 Profile 版本是否一致，因此可以形成 V7 设备绑定 V5 模板的错误组合。
- 锐捷版本字符串如 `EG_RGOS 11.9(6)B13P1` 需要被规范提取并映射到 V11 Profile；其他厂商的 `Software Release`、`Version:` 等格式也不能被通用正则截断或误取。

## 影响范围

- 后端平台识别、Profile 解析与批量绑定一致性校验。
- 网络设备批量平台绑定弹窗。
- 相关后端/前端测试。

## 拟修改文件

- `backend/services/platform_identification_service.py`
- 可能涉及 `backend/core/textfsm.py`、平台注册表目录或各厂商 normalizer（以调用链检查结果为准）
- `src/components/BatchPlatformBindingModal.tsx`
- `backend/api/devices.py`、`backend/api/device_health.py`：为设备列表/详情补充独立的绑定 Profile 展示元数据，不改写设备实测版本
- `src/types.ts`、`src/store/inventoryStore.ts`、`src/components/DeviceList/DeviceTable.tsx`、`src/components/DeviceList/DeviceRowExpand.tsx`、`src/components/DeviceDetailModal.tsx`：同时展示设备软件版本与命令/解析适配版本
- 对应 `backend/tests/` 与前端组件测试文件
- `docs/walkthrough/walkthrough_20260907_2246_01_设备版本识别与批量绑定一致性.md`

## 实施步骤

1. 追踪锐捷 `show version` 从命令回显、版本提取、平台家族/版本映射到 Profile 建议的完整链路。
2. 增加 RGOS 11/12 软件版本提取和版本代际映射，并补充真实格式的脱敏 fixture 测试。
3. 提炼设备实际版本与目标 Profile 版本的兼容性判断；对已知且明确冲突的批量绑定返回稳定错误，对未知/通用版本保持兼容。
4. 前端将目标版本说明为命令/解析适配版本，并在提交前提示已知冲突；默认阻止提交，管理员明确确认后携带覆盖标记，后端继续校验角色权限并作为最终边界。
5. 运行聚焦 pytest、前端测试/类型检查、构建及 PostgreSQL-only 策略扫描。

## 验证计划

- 锐捷 `EG_RGOS 11.9(6)B13P1` → V11；RGOS 12.x → V12。
- 迪普 `Software Release S211C011D007P08` → DPtech S211；迈普 `Software Version 9.7.1.25` → MyPower V9。
- 中兴 `5900 V6.00...` → ZTE 5900 V6；`ZSRV2 V3.00...` → ZTE ZSRV2 V3。
- H3C `7.1.064` → V7；默认拒绝批量绑定到 V5，管理员明确确认后允许覆盖，正常路径绑定 V7。
- 未知版本、空版本、common Profile 不被误拒绝。
- 批量操作保持事务原子性，错误时不产生部分更新。
- `npm run lint`、相关前端测试与 `npm run build` 通过。

## 风险与回滚思路

- 风险：历史版本字符串格式复杂，过严校验可能阻止合法绑定；仅对能可靠提取主版本且双方均为明确代际时拒绝。
- 风险：已有错误绑定不会自动改写；本次默认阻止错误版本，管理员显式确认后才允许手动覆盖，并保留兼容性风险提示，避免无授权批量数据变更。
- 回滚：撤回兼容性校验与前端提示即可恢复旧行为，不涉及数据库迁移。

## Agent 分工

- 主 Agent：后端一致性规则、集成、公共验证与交付。
- 子 Agent 1：只读梳理锐捷识别链路与测试落点，不修改共享文件。
- 子 Agent 2：仅修改批量绑定前端组件及其专属测试，不修改后端文件。
