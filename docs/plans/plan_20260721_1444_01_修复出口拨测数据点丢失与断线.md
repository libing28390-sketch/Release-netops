# 修复出口拨测数据点丢失与断线 实施计划

为了解决互联网出口监控历史图表中频繁出现的数据丢失和折线断裂问题，本方案拟对前端数据聚合分桶算法进行重构。

## 问题描述与根因分析

* **现象**：虽然互联网连接完全正常，但在 `http://192.168.42.1:5150/monitor/outbound` 的 1 小时 / 1 分钟颗粒度历史图表中，折线图（延时）和状态线（可用率）出现大量空洞与数据断开。
* **根因**：
  1. 数据库中实际包含每分钟 1 次的完整探测数据，数据并未在后端或 DB 中丢失。
  2. 后端定时任务由 APScheduler 每 60 秒触发一次。由于网络延迟和任务锁竞争，真实的探测时间可能产生几秒的微调偏移（例如：12:01:05, 12:02:04, 12:03:06）。
  3. 前端以 strict-disjoint boundaries 模式进行分桶（例如 `[t, t + 60s)`）。当由于几秒的偏差导致一个桶内落入 2 个数据点时，紧接着的下一个分桶就会因为没有数据点落入而变为 `null`。
  4. Recharts 折线图在遇到 `null` 且 `connectNulls={false}` 时，会直接切断线条，导致频繁出现视觉断线和假性“数据丢失”现象。

## 拟修改文件

* [OutboundHealthPage.tsx](file:///d:/nexora/nexora-private/src/pages/OutboundHealthPage.tsx)
  - 重构 `useMemo(() => { ... }, [data?.history, ...])` 内部的分桶逻辑：
    - 将任意起点 `startTime` / `endTime` 规范化为干净的步长整分钟边界（Rounded Tick Boundaries）。
    - 从严格的分组区间 `[t, t + step)` 改为以每个整点刻度为中心的**最近邻窗格** `[t - step/2, t + step/2)`。
    - 使每个探针点都唯一地归入距离它最近的那个分钟整点。

## 验证计划

1. 前端 `npm run lint` 验证 TypeScript 编译与代码格式。
2. 前端 `npm run build` 进行生产包构建，确认无打包错误。
3. 模拟加载包含 60 个历史点（存在 1~5 秒随机偏差）的数据集，确认重构后的分桶算法输出 60 个完全连续、无 `null` 洞的数据序列。
