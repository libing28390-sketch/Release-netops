# 发布 `v1.0.9`

## 任务目标

提交并推送工作区今天累积的 Nexora 代码，将现有 `v1.0.9` tag 强制移动到新提交，并确保发布 workflow 为新提交构建并发布 `v1.0.9`。仓库中的 `package.json` 与 `backend/core/version.py` 当前均为 `1.0.9`。

## 现状与问题

- 当前分支为 `main`，远端 `origin/main` 与当前 HEAD 一致，工作区包含今天尚未提交的应用、SNMP、监控、部署与 UI 改动。
- 用户在启动开发服务时遇到 `NameError: require_role is not defined`；Grafana 路由依赖在模块加载时求值，但导入缺失。
- 远端已有 `v1.0.9` tag，指向旧提交 `ee1a368e3a9ffda466495208395f510ef1eb227d`；用户明确授权将此 tag 强制覆盖到本次发布提交。
- `.github/workflows/release.yml` 监听 `main` 和 `v*`。版本 tag 会触发完整发布门禁、同步到 Release-netops 并创建/更新同名 GitHub Release。
- `.env` 和 `.env.backup.*` 均为 Git 忽略文件，含部署私密配置，不得进入提交。

## 影响范围

- 将当前工作区今天的代码、相关计划/走查记录和必需的提交修复记录纳入一个 `main` 提交。
- 推送 `main` 并强制更新远端 `v1.0.9` tag，由 GitHub Actions 运行发布验证和产物发布。
- 不直接在目标服务器部署、不修改数据库或 S3 数据、不手动改写 Release-netops 发布资产。

## 拟执行文件

- 当前 `git status --short` 中确认属于今天任务的所有 tracked 修改和新增源码/文档。
- 新增 `docs/fixes/fix_20260924_1723_01_发布v1.0.9.md`，满足仓库提交记录要求。
- 版本元数据不应改成别的号码；确认 `package.json`、`package-lock.json`、`backend/core/version.py` 保持 `1.0.9`，并将 build date 与本次发布日保持一致。
- `.env`、`.env.backup.20260924_170021` 和其他 ignored 文件不得暂存。

## 实施步骤

1. 核对改动清单、版本源、发布 workflow 和现有远端 tag；验证敏感文件保持 ignored。
2. 修复并验证后端 `require_role` 导入问题，检查并记录今天的代码变更；不改写无关用户文件。
3. 暂存预期代码与文档，进行提交前路径和敏感信息核对后提交到 `main`。
4. 推送 `main` 并强制更新远端 `v1.0.9` 到该提交；确认远端 tag SHA。
5. 检查 GitHub Actions 发布门禁与 Release-netops 的 release/tag 状态；若 workflow 失败，记录具体失败，不声称发布成功。

## 验证计划

- 核对所有发布版本字段均为 `1.0.9`。
- 扫描待提交路径，确保 `.env`、备份、私钥、访问令牌和生成凭据未被暂存。
- 提交前运行 `git diff --check`，检查提交清单和 diff 摘要。
- 正式 tag workflow 执行仓库定义的发布质量门禁；本地不重复运行全面测试与构建。
- 推送后确认 `origin/main` 与提交 SHA 一致，`refs/tags/v1.0.9` 指向同一提交，并确认 Release-netops 发布状态。

## 风险与回滚

- 覆盖 `v1.0.9` 会改变已有 Git tag 的目标，旧目标为 `ee1a368e3a9ffda466495208395f510ef1eb227d`；如发布门禁失败且需回滚，可将远端 tag 恢复到该旧提交，再按用户决定重发。
- 推送 tag 会触发完整 release workflow；若门禁失败或发布资产不完整，保留代码提交但明确报告 release 未完成，不用强推掩盖失败。
- `main` 推送会触发分支同步 workflow；不直接部署生产容器，不迁移本地存储对象。
