# 多厂商光模块 SNMP 采集实施计划

## 任务目标

依据 LibreNMS 规范和厂商官方 MIB，梳理项目支持厂商的光模块 DOM 指标；将有可验证 MIB/OID 的厂商纳入 SNMP 采集与看板展示，并确保光模块专用查询不调用设备 CLI。没有可靠 SNMP 定义的厂商保持明确的“不支持/无数据”，不猜测 OID、不回退 CLI。用项目内 SNMP 诊断对当前 H3C 设备做只读验证。追加核对 `/config/backup` 手动与批量备份的默认命令，按全部内置厂商审计，不依赖设备当前绑定平台。

## 现状与证据

- H3C 当前设备 `S6850_1 / 10.254.0.1` 已通过项目 SNMP 诊断成功 WALK `HH3C-TRANSCEIVER-INFO-MIB` 的诊断支持、当前 Tx/Rx 功率和模块厂商字段；所有探测均为只读 SNMP，没有运行 CLI。
- IF-MIB WALK 返回 696 个接口；DOM 表索引与 `ifIndex` 对应，已看到 `.2` 映射到 `GigabitEthernet1/0/1`、`.50` 映射到 `Ten-GigabitEthernet1/0/49`、`.5121` 映射到管理口。
- 当前项目监控 OID catalog 将光模块 OID 的导出与通用接口查询分开；光模块快捷查询此前仍通过 CLI 命令目录执行，相关调用链正在改为 SNMP-only。
- `/config/backup` 手动单设备备份前端只识别 Cisco/Arista/Ruijie/Juniper，其余设备误用 Huawei `display current-configuration`；批量备份另有后端分支，命令映射不统一。
- H3C、Huawei、Ruijie、ZTE、Juniper、Raisecom 等 MIB 定义可在本地 LibreNMS MIB 副本中交叉核对。初查发现 ZTE collector 仍使用旧的、与已核实 `ZTE-AN-OPTICAL-MODULE-MIB` 不符的根 OID；Huawei power 传感器也存在正值 µW / 负值百分 dBm 的混合编码，不能用单一线性 scale 标记为 dBm。
- LibreNMS 传感器规范要求使用具名 OID、正确单位/比例、`dbm` 类别、跳过不支持哨兵值，并将传感器关联到端口。

## 本轮核实结论与实现边界

- 已实现 SNMP 光模块采集的厂商/平台：H3C、Huawei、Juniper、Ruijie、ZTE、Raisecom，以及 Cisco（IOS/IOS-XE/IOS-XR/NX-OS）、Arista EOS、Nokia 1830。Cisco 使用 ENTITY-SENSOR dBm 类型、scale/precision 及实体父子/alias 到 IF-MIB 的严格映射；Arista 使用 ENTITY-SENSOR DOM Rx/Tx 标记和精确端口映射；Nokia 1830 按 ifIndex 索引并只保留管理状态 Up 的端口。三者没有可确认映射或状态时均不编造端口/指标。
- LibreNMS 41 家厂商审计已完成：明确存在上游 DOM 传感器轮询的 5 家为 Cisco、Arista、H3C、Nokia、Edgecore；只有 MIB/模块元数据线索、未确认上游 DOM 轮询的 7 家为 Huawei、Juniper、Raisecom、ZTE、Ciena、Aruba、MikroTik；其余 29 家未发现厂商专属 DOM 证据。Nokia 本次只实现 ifIndex 可直接关联的 1830，不实现依赖机型/槽位推导的 ISAM；Edgecore OcNOS/EdgeCOS 也暂不接入，因为其模块到端口映射需要额外平台逻辑。其余未接入厂商保持不支持，不猜 OID、不回退 CLI。
- 09 接口详情新增统一 dBm 光功率表和趋势，仅接入 H3C、Ruijie、Juniper、ZTE 具有 IF-MIB `ifIndex` 映射且单位一致的 exporter 指标。Huawei 导出值是混合原始编码，Raisecom 使用多参数复合索引，未强行并入同一单位视图；二者仍由专用 SNMP 光模块操作按 MIB 解析。
- `/config/backup` 资产目录审计覆盖 41 家（网络 26、安全 15），其中 11 家已有经项目命令目录/专用映射确认的默认命令，另 30 家没有通用命令证据。受支持厂商按 vendor-first，不受旧的设备 platform/Profile 绑定影响；未支持厂商只有 vendor、platform 与已发布 Profile action 一致时才可使用该 action，未知显式 vendor 不借用平台默认命令。
- 候选列表、定时执行和定时预览统一按“已确认厂商默认命令或身份匹配的已发布 `get_running_config` action”过滤，并排除 server/host 资产。

## 影响范围

- H3C/Huawei/Cisco/ZTE 等经官方 MIB 和 LibreNMS 定义确认的厂商光模块监控。
- SNMP exporter OID catalog、模块配置与 Prometheus 指标；接口详情/设备详情 Grafana 面板。
- 光模块专用快速查询的后端 SNMP 读路径及前端结果呈现；不影响其他普通只读 CLI 查询。
- 对无官方/LibreNMS 支持或无法确认单位、索引、接口关联方式的厂商，不添加未验证指标。

## 拟修改文件

- `backend/services/monitoring_oid_catalog.py`：增加具备证据的 DOM 指标、表索引、接口名 lookup 和单位说明。
- `backend/services/snmp_md_preset_catalog.py`：补充已有光模块 OID 清单的可审计来源或语义；不把未定义 OID 猜成健康指标。
- `backend/services/operational_data_service.py` 或专用 SNMP optical service/API：使 `transceiver` 查询只通过 SNMP，并在不支持/未配置时返回明确状态。
- `src/pages/AutomationExecute/index.tsx` 及必要的结果渲染代码：光模块操作显示为 SNMP 采集，不传入 CLI 命令回退。
- `src/hooks/useConfigSnapshots.ts` 及默认命令 helper：按厂商选择 `/config/backup` 的手动默认命令，覆盖内置设备厂商并对不支持厂商明确失败。
- `backend/api/configs.py` 或专用 backup helper：对齐批量备份默认命令与厂商清单，不依赖不相符的平台字段静默挑选别家命令。
- `monitoring/grafana/generate_dashboards.py` 与被生成的目标 dashboard JSON：展示已采集的光模块 Tx/Rx/温度等数值，并保持接口变量过滤。
- 对应 SNMP/compiler/API/dashboard 测试与本任务计划、walkthrough、fix 记录。

## 风险与回滚

- 不同厂商和固件的 MIB 单位、缩放及索引可能不同；仅启用官方定义与 LibreNMS 解析均可确认的组合，按厂商/平台隔离模块。
- exporter 加入额外 WALK 会增加采集量；只加入必要 OID 并复用同一表索引。
- 若面板/采集变更导致兼容问题，可回滚本次 catalog、service/API、dashboard 和相关文档所在提交；无需设备侧回滚，因为验证和部署都不改变设备配置。
- 未获授权在此阶段把代码同步到 Linux 服务器；以 Actions 验证通过后交由用户自行更新服务器。
