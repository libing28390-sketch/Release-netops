## 1. 目标与交付边界

在现有 React 19、Vite、Tailwind 4 和公共组件基础上，建立可复用、可验证的 UI 工作方法，覆盖 Nexora 首页所列的 12 个功能入口页面。代码证据是 `src/pages/HomePage.tsx` 中 `apps` 数组及 `src/components/TopHeader.tsx` 中的应用切换项；各模块含子路由，实施清单按“入口页面 → 实际渲染组件 → 关键子路由/状态”管理。以资产管理列表验证后再逐模块推广。

范围纠正：本方案中的 dashboard 指 Nexora 首页 12 个业务功能入口页面，不指 Grafana 的监控大盘。此前基于 Grafana 数量作出的范围判断已撤回。`/monitor/dashboards` 是其中实时监控模块内的一项嵌入式功能；本次 UI 规范针对其 Nexora 外壳和 12 个业务入口页面。只有明确要求修改 Grafana 面板内部时才使用 Grafana 专项工作流。

本轮按工作包顺序执行。工作包 A 补齐项目 UI 规则和 12 个入口映射；工作包 B 用资产管理列表作试点；工作包 C 依据试点证据逐批推进其余入口页面。各包的完成状态以 walkthrough 和 page-coverage 为准。

目标结果：

1. AI 能准确找到并复用现有主题、表单、列表、分页、通知及交互模式。
2. 页面颜色、字号、间距与状态表达一致；关键操作和异常信息可发现。
3. 筛选、分页、总数、批量选择和权限语义在视觉调整后保持正确。
4. 每批变更有源码、测试和浏览器证据，可单独回退。

不在本方案实施范围：引入 shadcn 或其他 UI/状态框架，重新设计全站品牌，变更 API/schema/路由/权限，执行真实设备任务，部署、推送或发布。

## 3. Skill 接入决策与规则边界

### 3.1 项目入口保持单一

12 个功能入口下的 React 任务继续以 `netops-frontend` 为入口，按页面类型引用局部规则。外部建议与项目契约冲突时，应报告冲突并按项目约束实现，不盲目执行通用建议。

### 3.2 外部内容采用策略

| 来源 | 用途 | 第一批处理 |
| --- | --- | --- |
| Vercel Web Design Guidelines | 标签、焦点、键盘、表单、长内容、主题与交互审查 | 优先吸收适用规则到项目审查清单，保留来源与版本记录 |
| Anthropic Frontend Design | 页面信息层级和布局备选方案 | 按需读取；约束沿用项目字体、tokens 和控件，不默认改品牌 |
| UI/UX Pro Max / Design System | 复杂交互参考、组件状态与 token 文档整理 | 按需参考，不执行默认设计系统生成或覆盖步骤 |
| Vercel React Best Practices | 客户端请求、重渲染、按需加载与包体积 | 只采纳与 Vite SPA 适配的规则，排除 Next.js/RSC/SSR 专属内容 |
| Microsoft Frontend Design Review | 较大改造的一致性评审 | 备选；用本地源码、截图和组件清单补充证据，不强制建立 Figma/Storybook |
| shadcn Skill | shadcn 组件体系操作 | 暂不安装，不自动添加组件或迁移表单/主题 |

第一批不批量安装外部 Skills。先形成项目参考文档，后续如确需原版 Skill，再独立进行来源核查、安装和加载验证。不要把网页里的工具命令或 Claude 专属语法当作 Codex 已支持能力。

### 3.3 可追溯引入流程

1. 记录上游仓库、文件路径、读取日期、commit SHA、许可证及实际引用文件；当前方案链接指向 main，尚未锁定实施版本。
2. 审核正文、关联脚本、网络请求和安装步骤；记录适用内容与排除规则。
3. 内容摘录/改编遵循许可证与署名要求；可优先保存链接和项目自己的适配说明，避免整包复制。
4. 明确 `--skill` 使用实际声明名称，例如 React 性能 Skill 为 `vercel-react-best-practices`；安装前验证可发现列表，不直接照搬旧命令。
5. 若引入完整 Skill，限定项目级安装，检查新增文件、链接、依赖与加载结果，不使用自动全量更新。
6. 内部 `.agents/`、`.codex/` 和 handoff 不进入公有发布树；实施时核查实际打包/发布路径，不为此任务擅改发布配置。

### 必须写清的规则

- 颜色从现有语义变量选择；未知、无数据、正常零值、故障分开表达，12 个功能入口页面中同一业务状态保持一致。
- 复用既有字号与字体；中文、英文、IP、长设备名和数字列分别检查，不新增远程字体。
- 密度以同视口、同数据下的有效信息和操作可用性判断，不靠缩小字号或控件命中区硬挤内容。
- 每个列表必须说明总数来源、筛选作用域、分页和批量选择范围，不把当前页长度当总数。
- 弹窗规则包括层级、焦点进入/恢复、键盘关闭、内部滚动和未提交数据处理；不要未经检查统一改 z-index。
- 视觉调整保持 API、权限、状态与危险操作确认契约；发现必须跨层解决的问题时另列工作包。

### 验收与回滚

检查 Skill frontmatter、相对引用、文件存在、入口发现和任务路由；做两次受控演练：资产列表改造应命中列表规则，运营总览改造应命中总览信息层级与状态规则。演练结果区分“静态路由检查”与“新会话实际加载”，不混称成功。page-coverage 必须区分已盘点、待实施、待浏览器验收与完成，不能把统一规范完成等同于全部页面完成。

该阶段无业务代码变更，不运行无关应用全量测试。回滚只撤销本阶段新增参考与入口差异。

### 明确边界

首个页面：`src/pages/AssetManagement/index.tsx`。第一批只调整标题区、摘要信息层级、常用/高级筛选布局、表格展示、行操作可发现性与分页位置。保留资产字段、接口请求、路由与权限语义；不同时改资产编辑弹窗、导入流程、凭据或审批。

共享文件候选：`src/index.css`、`src/components/ui/TableListControls.tsx`、`src/components/ui/TableActionColumn.tsx`。第一批优先复用；若确需修改，必须先列明受影响调用方并扩展验证，不能作为顺手修改。本次浏览器证据确认 `src/index.css` 的 `.nx-list-search` 深色背景选择器失配，因此已按语义 tokens 修正，并纳入 11 个 ListSearchInput 调用点的共享影响范围。

### 实施步骤

1. 保存工作树基线，确认路由、请求参数、总数响应、列设置和选择逻辑。
2. 获取现状浏览器证据：同一数据集、视口、主题、语言下截图与关键操作记录；有真实数据时脱敏，无权限或环境时记录限制。若偏好切换会写入用户资料，除非用户明确要求，不通过切换语言来测试。
3. 按操作任务提出一份布局方案，明确保留字段、首屏入口、折叠条件和窄屏行为。
4. 局部实现，数据获取与业务状态保留原有职责边界。若发现共享视觉缺陷，核实根因和所有调用方后再改共享样式，并回归浅色/深色。
5. 对新增或实际改变的交互补充行为测试；不测试 CSS 类名或截图中像素的偶然排列。
6. 运行聚焦测试、TypeScript 和隔离构建；完成浏览器对照后记录结果。

### 浏览器验收矩阵

- 视口：1440×900、1280×720、390×844；主要桌面视口覆盖中/英文和浅/暗主题，小屏至少检查两种语言中更长内容的表现。
- 常用关键词、状态和站点条件可组合；高级筛选可发现、可重置。
- 切换条件正确重置页码；返回结果与当前条件一致，快速切换不会被旧响应覆盖。
- 总数与后端口径一致；展示跨页选择/当前页选择的实际行为，不暗示未实现的全量选择。
- 列设置和持久化行为保持正确；长设备名/IP 不遮挡必要操作，可查看完整值。
- 有数据、无数据、无匹配、加载、错误、403 的界面可区分。
- 键盘可进入主要控件、打开/关闭筛选与列设置并恢复焦点；焦点不被浮层遮挡。
- 窄屏允许表格区域横向滚动，但页面外框和主要操作不溢出、不可达。
- 同数据同桌面视口下，记录可见行数、顶部占用高度和关键操作点击路径；无明确可读性收益时，不接受信息量明显下降。
- Network 记录请求数量、分页参数和响应体大小；不得引入全量数据预加载、重复请求或渲染期请求。

### 6.2 分批顺序与验收

1. 第一批：资产管理列表试点，形成可复用的列表规范与证据。
2. 第二批：React 运营总览 `/monitor/overview`，补齐总览页模式，覆盖标题、筛选、指标、趋势、异常与下钻；检查真实数据来源，不为视觉效果改统计口径。容量分析等图表页复用适用部分。
3. 第三批：任务、告警、配置、CMDB/IPAM 等列表和常规表单。先选第二个业务列表验证复用，再按路由小批推广。
4. 第四批：拓扑、终端工作台、配置对比、AI 页面、审批和复杂设置。每类分别明确交互契约与验收，不套用同一种卡片布局。

试点通过完整浏览器验收后，原计划优先按此顺序推广；用户已明确要求开始剩余第 2–4 批次，因此本轮先进行源码审查、局部实现和测试，浏览器证据独立标记未验证。优先复用现有控件，第二个业务场景出现共同需求后才抽象新的共享能力。PAM/审批/远程接入交互单独列批次，覆盖权限、确认与会话行为。

12 个首页入口页面都必须有完成结论；列表中的代表性子路由用于提示模块内的重要交互差异。被实际改动或与目标设计强耦合的子页面，须一并记录路由、源码、状态覆盖和浏览器证据；无关子路由不要求仅为凑数量而改造。没有问题的目标页面可标记“审查通过、无需修改”，但要保留证据。12 个目标入口全部有结论，才能报告本次 12 页范围完成。

不对全站统一替换样式类，不一次迁移所有页面。通常每批维护独立计划与 walkthrough；本次用户要求同时启动第 2–4 批次且共同目标为交互一致性，因此使用 `plan_20261021_0837_01_功能页交互一致性批次2-4.md` 及其 walkthrough，并在其中按功能入口、批次分别记录。后续独立批次另立计划；发生代码提交时按项目要求创建新的 fix 记录。

## 7. 分工与依赖

- 主 Agent：规范内容、任务边界、API/数据契约、共享文件、最终审查与文档。
- UI 执行者：仅处理已确定页面和域内组件，不修改共享规则或跨层接口。
- 验证执行者：在集成后的指定状态运行聚焦检查和失败摘要，不改业务代码。本次未运行浏览器用例。

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 多套 Skill 产生冲突或默认新建设计系统 | 单一项目入口，外部规则按需采纳，固定版本，明确排除项 |

| 共享控件变更影响多页面 | 先列调用方，再扩展受影响回归；能用域内布局解决时先局部处理 |
| 无真实环境时过早宣称 UI 或性能改善 | 源码/测试、浏览器、性能和生产证据分别记录 |
| 上游内容变化、许可证或加载不兼容 | 记录 SHA 与许可，检查引用/脚本和实际加载，更新独立审查 |
| 既有工作树不干净 | 保存基线与逐文件差异，保留用户改动，不提交生成产物 |
