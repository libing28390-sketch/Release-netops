# NSOT 操作关联与定时作业预览计划

## 任务目标

形成完整 NSOT 采集闭环：Automation「操作管理」中按设备采集模板关联 Quick Ops 的 collection categories/actions，显示采集事实/指标、每台设备当前软件版本的已发布 Platform Registry action 命令及对应 TextFSM 解析模板；该版本没有绑定 action 时，按同 parser platform/version 查找该操作类别关联的 TextFSM command template 作为只读 fallback。NSOT 定时作业详情再按当前在线目标设备及其有效模板展示解析后的预计命令。EIGRP/RIP 不纳入 NSOT 采集模板、预览或统一定时流程，但保留其他 Quick Ops 场景的通用能力。目录、预览和真实采集不得各自维护重复命令表。预览不得运行作业、登录设备或更改策略。

## 现状 / 问题

- `JobDetailModal` 对 NSOT 仅显示一段固定说明，没有指标列表、模板分布或命令。
- Automation「操作管理」目前是脚本生命周期页面；NSOT device templates 位于 NSOT policy service，操作管理中看不到模板关联的 Quick Ops category、设备版本 action、命令和 TextFSM 解析规则。
- NSOT 作业创建/更新不会保存 `commands` 或 `script_id`。实际采集通过 `run_unified_nsot_sync`，各阶段再读取每台设备的模板、平台和能力；因此从定时作业记录无法静态列出唯一命令表。
- Quick Ops 的 `interfaces/arp/mac_table/vlan/neighbors/routing_table/...` category 是实际操作语义；`operational_data_service` 对已绑定 profile 的设备调用当前 published release action，对未绑定 profile 的设备使用平台命令目录并按 platform/version/command 选择 TextFSM。已绑定 profile 缺少单项 action 时目前显式 unsupported，需补充严格同版本 TextFSM fallback。
- Platform Registry 已提供设备平台 profile 与当前发布 software release 的 action mappings；TextFSM 文件名包含 parser platform/version/command，文件注释可带 `action_code`。缺少已发布 action 时需同版本精确 fallback，不能跨版本或跨厂商猜命令。
- 目标范围只作用于当前在线设备；作业预览应与调度器共用同一个目标解析逻辑，不能只按作业筛选文本估算。
- 全量设备规模可能增长；详情需通过按需接口读取，并以模板/平台/有效指标组合分组，避免前端加载全设备和 N+1 请求。

## 影响范围

- Backend：新增只读 NSOT operation resolver/catalog/preview service/API；模板 collector keys 映射到 Quick Ops/Platform Registry action_code；优先解析每台设备当前发布软件版本的 action，若 action 缺失再选 exact platform/version/action_code 对应的 TextFSM 命令模板。
- Frontend：Automation「操作管理」增加 NSOT 模板/action/TextFSM 命令视图；定时作业详情按需读取当前目标预览，展示目标数量、指标/事实类别、传输方式、设备软件版本、action 来源、TextFSM parser、只读命令、条件性和加载/空态/错误态。
- 不改计划调度、采集模板、设备策略、作业范围和周期；不触发实际设备命令；不新增数据库字段/迁移。

## API / UI 契约

- 增加只读 `GET /api/collection-plans/operation-catalog?platform_profile_id=...`，返回 collection template→Quick Ops category→该 profile/release action 或 TextFSM command/parser 的对照，供 Automation「操作管理」消费；排除 NSOT 不需要的 EIGRP/RIP。
- 增加 `GET /api/scheduled-jobs/{job_id}/nsot-preview`，仅对 `action_type=nsot` 返回当前 job scope 的在线目标采集计划。
- Preview 使用当前时刻的在线目标；scope resolution 调用调度器已有 `_resolve_nsot_target_device_ids`，之后按当前用户 asset:view tenant/site 范围收窄。响应不得泄露当前用户无权查看的设备信息。
- 按平台 profile/current published release、模板和有效指标集合聚合目标，返回目标数量、设备软件版本、模板、指标 label/key、transport、action code、CLI 命令和 TextFSM parser 绑定。
- 命令来源严格优先级：设备绑定 profile 当前 published release 中同一 Quick Ops operation 的 action；没有 action 才按该设备 parser platform/software version 与该 operation category 的 TextFSM command template 查找。`action_code` 存在时必须一致；缺失时只允许通过正式 catalog 的 category-command 关联。无匹配时返回 unsupported 状态，不得 fallback 到其他版本或默认 Cisco 命令。
- 明确区分 CLI、SNMP、ICMP 和数据库派生指标；只把 CLI 项标成命令。对协议发现、VRF/多命令 fallback 标“条件性/运行时决定”，不承诺设备认证、能力或命令成功。
- Operation Management 中展示的 action/template/commands 来自同一 resolver，不另存自由文本副本；命令/解析器的发布仍走 Quick Ops/Platform Registry 与 TextFSM 管理的审批流程。
- 详情文案标注“预览，不连接设备；设备离线、策略变更或运行时发现会改变最终结果”。

## 拟修改文件与分工

- Backend worker：仅更新 `backend/services/operational_data_service.py`，共享真实执行 resolver 并实现 bound-profile 缺 action 时的同版本 TextFSM fallback；新增 PostgreSQL 隔离的 runtime fallback tests。不得改 API 或前端。
- Frontend worker：更新 `src/pages/ScriptManagementTab.tsx`（并新建 `src/pages/NSOTCollectionOperations.tsx`），在操作管理中展示 NSOT 模板与 versioned action/TextFSM command 链；不编辑 backend 或作业详情 modal。
- 主 Agent：新增 `backend/services/nsot_collection_preview_service.py` 并更新 `backend/api/collection_plans.py`、`backend/api/scheduled_jobs.py`，实现操作目录和 scoped job preview；更新 `src/pages/ScheduledJobs/types.ts`、`src/pages/ScheduledJobs/index.tsx`、`src/pages/ScheduledJobs/components/JobDetailModal.tsx`；集成与统一验证。
- 不触碰当前工作区与该功能无关的用户改动。

## 实施步骤

1. 审核 unified NSOT collector、Quick Ops collection categories、Platform Registry published release action、TextFSM versioned command lookup及 action_code 元数据契约。
2. 建立 collection template operation mapping：每个 collector 关联 Quick Ops category/可用稳定 action_code、数据指标和 transport；真实采集与目录共用 resolver。
3. 对绑定 software profile 的设备先解析当前发布版本对应 action；缺失时只允许同 parser platform、同软件版本、同操作类别的 TextFSM command fallback（存在 action_code 时必须相同）；无匹配则 unsupported，不连接设备。
4. Automation「操作管理」增加 NSOT 模板/action catalog，展示平台/版本命令、TextFSM parser/source 和支持状态；命令/解析器编辑由现有管理页面负责，catalog 不创建自由文本副本。
5. 定时作业详情按需读取共享 preview service，按在线 scope、权限、设备版本和 effective template 展示采集指标与预计命令。
6. 增加成功、空目标、权限范围、非 NSOT 作业、action 命令优先、TextFSM fallback、跨版本拒绝、unsupported 和条件项测试；运行前端 lint/build、相关 PostgreSQL 测试和质量扫描。
7. 浏览器只读打开操作目录和现有 NSOT 作业详情验证；不执行真实 action、不运行立即同步、不保存作业。

## 验证计划

- `backend/tests/vendor_audit/test_nsot_collection_preview_api.py`（新增，隔离 PostgreSQL）；复用调度器 scope 与 collection policy 测试合同。
- 覆盖在线筛选、scope 一致、不同设备模板和软件版本聚合、tenant/site 授权、设备策略关闭指标后不展示、published action 优先、同类别同版本 TextFSM fallback（含未标 action_code 的模板）、跨版本拒绝、无 parser/action unsupported、动态 VRF/协议标记、NSOT 不采 EIGRP/RIP、非 NSOT 作业拒绝、空目标。
- TextFSM tests 确认 fallback 的 platform/version/action_code/command/parser 来源完全符合当前模板解析优先级；绑定已发布 Registry profile 的设备仍以当前 release action 为准。
- `npm run lint`、`npm run build`（隔离输出目录）、`git diff --check`；必要时运行 `scripts/validate_postgresql_only.py`。
- 不连接设备、不运行定时作业、不部署或推送。

## 风险与回滚

- collection workflow 跨多个服务，实际命令可能受平台 registry 发布版本、VRF、协议发现、命令回退和设备能力影响。Preview 必须标明“预计/条件性”，不得把模板目录误报成必定执行的精确命令。
- 当前在线设备与策略会变化；预览只代表打开时刻，不持久化、不构成作业运行快照。
- API 为只读且无迁移；如结果不准确，可回滚预览 endpoint/service/UI，不影响已存作业和采集执行。

## 最终集成与提交

- 已实现目录、作业预览、按命令来源区分 Registry/TextFSM/legacy、设备软件版本与 Registry 发布号分离、数据库派生项状态。
- 前端子 Agent 负责目录和预览展示收尾；后端子 Agent 负责隔离 PostgreSQL 回归；主 Agent 负责集成、浏览器只读检查和 Git 提交。
- 用户已明确授权验证通过后 push 到现有 origin/main，由现有 release 流程处理后续发布。
- 提交包含此前 NSOT 模板、批量策略和调度范围的必要依赖；不包含工作区独立的知识库或 Redis 缓存摘要改动。
