# Implementation Plan - 修复路由协议邻居不显示

本计划旨在解决用户在前端“实时交互测试”页面点击“BGP邻居”或“OSPF邻居”时，无法显示任何数据的故障。

## 现状/问题
1. **API 自动过滤掉 bgp 和 ospf 分类**：后台任务采集默认策略中，由于动态路由协议配置消耗资源较多，其默认采集开关为关闭（`bgp: False`, `ospf: False`）。前端在触发单机即时操作数据查询（POST `/api/devices/{device_id}/operational-data`）时，后端 API 仅传递了 categories 字段而未提供 `policy_override_categories` 重置标志。由于未提供该标志，在 categories 校验链（`_resolve_categories`）中，bgp/ospf 分类因为不满足设备默认收集计划而被静默剔除。所以最终只返回了空的分类结果，前端展示为“没有返回可展示的数据”。
2. **华三 OSPF 模板解析 State Error 崩溃**：华三设备的 OSPF 邻居模板 `h3c_comware_display_ospf_peer.textfsm` 存在三个格式匹配错误：
   - 华三 OSPF 流程标头行含有前导空白/制表符，导致 `^OSPF\s+Process` 正则失配。
   - 华三 OSPF 输出的列表列顺序为 `Router ID | Address | Pri | Dead-Time | State | Interface`（`State` 在 `Interface` 前面），而原模板的字段排序错误。
   - OSPF 邻居的 `STATE` 字段（如 `Full/ -`）包含空格，原有 `\S+` 匹配失败。
   - 模板最后包含极为严苛的 `^. -> Error` 规则，导致不匹配时直接抛出 `State Error`。

## 实施步骤
1. **修复 API 过滤**：
   - 修改 `backend/api/devices.py` 中的 `collect_device_operational_data` 路由处理器。
   - 在调用 `collect_operational_data` 时，附加传递参数 `policy_override_categories=set(categories)`，使得由用户手动即时触发的请求能彻底跳过背景采集策略过滤。
2. **修复 OSPF 模板**：
   - 修改 `data/textfsm_templates/h3c_comware_display_ospf_peer.textfsm` 模板文件，放宽前导匹配、修正列名顺序、使 `STATE` 能正确匹配含有空格的模式，并将 `^. -> Error` 降级为 `^.*` 避免崩溃。

## 验证计划
1. 运行测试验证脚本，确认 OSPF 交互式收集能在 H3C 设备成功获取并结构化解析邻居表项。
2. 运行整体 API 后端测试，确保无退化发生。
