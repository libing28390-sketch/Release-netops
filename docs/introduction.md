## 前言：从 Python 脚本满天飞，到构建网络知识图谱

做网络运维这些年，我写过不少自动化脚本。

最开始，那只是一些简单的 Python 程序。批量登录设备、备份配置、采集接口状态、生成巡检报告……
随着需求增多，我的 `scripts/` 目录下多出了一堆文件：

```text
scripts/
├── backup.py          # 备份配置
├── monitor.py         # 监控
├── lldp.py            # 拓扑发现
├── arp_scan.py        # IP 扫描
└── interface_check.py # 接口检查
```

每个脚本都能解决一个具体的问题，但随着时间推移，新的问题越来越明显：**这些脚本之间没有任何关系。** 它们各自维护着一套设备列表，各自连接着不同的数据库，修改一个设备的登录密码，我得去改好几个脚本。

慢慢地，我发现：**真正缺少的，不是脚本，而是一套统一的数据平台。**

---

### 1. 为什么重新设计，而不是继续写脚本？

很多网络工程师都会写 Python，利用 Netmiko 或 Paramiko，一个晚上就能写出一个批量执行命令的工具：

> **工作流：** 登录 100 台设备 ──> 执行 display cpu-usage ──> 保存结果 ──> 结束

这个工具能用。但第二天，需求变了，需要采集接口信息，于是写了脚本 B；第三天需要备份，写了脚本 C……

它们解决的是**“动作”**（跑一次命令），而不是**“数据”**（把状态沉淀下来）。这也是导致很多网络自动化项目最后维护越来越困难的原因。

**真正的问题，是数据没有沉淀。**

实际上，网络运维中的绝大多数功能，依赖的都是同一套底层数据。
*   **要生成网络拓扑**：需要知道设备有哪些接口？接口连到哪里？哪些是聚合口？哪些接口已经 Down？哪些接口属于哪个 VLAN？
*   **要分析故障排障**：需要知道源 IP 路由的下一跳是谁？ACL 是否拦截？路由是否改变？
*   **要做容量预测**：需要知道接口的历史流量、丢包率、错误包。

它们看起来是完全不同的功能，但底层的数据模型是完全相通的。所以，与其去写各种杂乱的功能脚本，不如**先把底层的数据模型建立起来**。

---

### 2. 重新思考：为什么从 CMDB 和 IPAM 开始？

在决定重新设计 Nexora 平台前，我研究了 NetBox、Zabbix、SolarWinds 等优秀的产品。我发现了一个共同点：我更希望**整个网络的数据只保存一份，所有功能都建立在这份数据之上。**

很多人问我：为什么不先做炫酷的自动化、监控或拓扑，而是先做枯燥的 CMDB？

答案很简单：**没有资产，就没有后面的一切。**

*   **第一步：CMDB** —— 负责描述整个网络里“有什么”（设备、厂商、角色），建立基础账本。
*   **第二步：IPAM** —— 把 IP 地址从“一个字符串”变成“整个网络资源的一部分”，关联 VLAN、VRF、子网 and 网关，防止 IP 冲突和浪费。

---

### 3. 架构的关键转折点：Interface（接口）才是灵魂

在设计平台时，我遇到了最大的设计转折。
起初，我设计的数据结构是：设备 A 连着设备 B。

后来我发现这完全行不通。**因为真正连接网络、承载状态的，不是设备，而是接口。**

> **物理连接示例：**
> Core-SW (接口 GigabitEthernet1/0/1) <──────> Access-SW (接口 GigabitEthernet1/0/24)

接口拥有自己独立的属性：MAC 地址、双工、速率、MTU、错误包、流量、光衰…… 真正的网络链路（Link），实际上建立在两个物理接口之间。

于是，项目进行了第一次大的架构调整：**以后所有的网络关系，全部围绕 Interface（接口）建立。**

至于大家最喜欢的**网络拓扑图**，它并不是下一步。因为拓扑只是一种**展示结果**。只要我们把设备发现、LLDP 邻居、MAC 表、ARP 表和路由表的数据全部采集并关联准确，拓扑图的画出只是顺理成章的事情。如果底层数据是错的，拓扑画得再漂亮也毫无意义。

---

### 4. 我们的终极目标：网络知识图谱

Nexora 并不想做成一个功能的简单堆叠，而是希望沿着一条清晰的数据演进路线，构建一张真正的网络知识图谱。

为了保证在手机端（知乎 App）阅读时不会因为排版过宽导致换行错乱，我们使用最直观的**树状结构**展示这套演进路径（各阶段水平均等对齐，防手机端折行）：

```text
CMDB (资产账本)
  ├── IPAM (子网与 IP 管理)
  ├── Interface Inventory (接口明细)
  ├── LLDP/CDP Discovery (物理邻居发现)
  ├── Network Topology (网络拓扑呈现)
  ├── Endpoint Tracker (终端接入追踪)
  ├── Route Intelligence (智能路由发现)
  ├── Smart Path Trace (业务路径分析)
  ├── Configuration Center (配置与合规审计)
  └── AI Root Cause Analysis (AI 根因分析)
```

每一个模块，都依赖前一个模块提供的数据沉淀。

---

### 写在最后

网络自动化真正困难的地方，从来不是怎么用 Python 敲几行 SSH 命令，或者解析几段命令行回显。

真正困难的是，**如何让来自不同厂商、不同协议、不同维度的数据，最终汇聚成一套统一、可扩展、可持续演进的数据模型**。

这也就是 Nexora NetOps 想要探索的方向。我们不求一开始功能最多，但求把基础的数据模型打得最牢。

下一篇文章，我会聊聊一个很多人容易忽略的话题：**为什么一个真正的 NetOps 平台，必须先做好 CMDB，而不是先画网络拓扑。** 敬请期待！
