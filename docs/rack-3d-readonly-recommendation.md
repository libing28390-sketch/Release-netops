# Nexora 机柜只读 3D 查看器与多机柜总览建议书

**审查日期：** 2026-08-27  
**审查对象：** `http://192.168.56.1:5400/cmdb/racks`、前端机柜管理模块、机柜/设备/健康/拓扑后端接口  
**审查性质：** 方案审查与匹配度评估；本轮未修改业务代码

## 1. 结论先行

建议把 3D 机柜定义为 **2D 机柜数据的只读投影**，而不是第二套机柜编辑器：

```text
2D 机柜管理（唯一写入入口）
        │
        ├── 机柜摘要 / 布局 / 健康 / 拓扑只读数据
        │
        ├── 多机柜 3D 总览（轻量、可定位）
        │
        └── 单机柜 3D 详情（精确到 U 位、设备、端口和链路）
```

当前项目并不需要更换 Three.js 技术栈。React 19、`@react-three/fiber`、`@react-three/drei`、Three.js 和现有 `RackVM` 适合继续使用，单机柜静态展示也已有基础实现。

但当前 3D 还不能直接扩展成“很多机柜的只读查看器”。主要原因不是建模能力，而是产品边界、数据请求方式和数据真实性还没有收拢：

1. 3D 页面外层仍有“安装”写操作入口。
2. 3D 只接收一个 `rackVM`，场景中也只创建一个机柜。
3. 进入页面时会并发请求所有机柜的完整布局，机柜数量增长后会形成请求风暴。
4. 拓扑渲染存在按设备名称和设备顺序推断链路的兜底逻辑，会把“未建模”显示成“已连线”。
5. 后端有机柜、U 位和设备数据，但还没有机柜在房间中的三维位置、方向、PDU/传感器、设备端口锚点和设备视觉模型等契约。
6. 全屏目前只包住 3D 画布容器，右侧设备清单和详情抽屉不在全屏工作区内。

因此，推荐采用 **渐进式只读 3D 工作台**：先把单机柜体验和数据可信度做好，再增加多机柜总览，最后按实际需求增加机房空间坐标、热力和气流。

以下评分是基于当前代码的工程判断，不是最终产品评分。

| 能力 | 当前证据 | 匹配度 | 判断 |

## 3. 已审查的现有实现

### 3.1 前端数据流

`src/pages/RackManagement/index.tsx` 当前负责列表、2D 编辑、3D 切换、设备详情和写操作，职责比较集中：

- `loadRacks()` 先调用 `/racks`，随后对每个机柜调用 `/racks/{id}/layout`，并用 `Promise.all` 等待全部结果。
- 当前选中机柜再通过 `loadLayout()` 加载或读取缓存。
- 布局通过 `normalizeRackToVM()` 转成 3D 和 2D 共用的 ViewModel。
- 2D 将 `onDeviceMove` 和 `onEmptySlotClick` 传入编辑器；3D 只接收 `rackVM`、设备选择和回退 2D 的回调。

这说明“2D 与 3D 共用数据源”的方向是对的，但初始化阶段仍然把所有机柜当作详情页面加载。建议将数据拆成：

```text
RackSummary[]       首屏、列表、总览使用
RackLayout          选中机柜详情使用
HealthSnapshot      按站点/机柜/设备范围使用
TopologyLink[]      按站点或机柜范围使用
```

### 3.2 当前 3D 组件

`src/pages/RackManagement/Rack3D/` 已经具备：

- 正面、背面、等轴、俯视、顶部/底部聚焦和缩放控制。
- 开关门、U 位标尺、健康/角色/功耗显示模式。
- 设备选择、悬浮提示、双击聚焦、WebGL 检测和异常回退到 2D。
- 拓扑线、选中链路高亮、全屏调用。

这些能力可以保留，但需要调整语义和组织方式：

- “抽出检修”属于展示动画，不应让用户误以为可以在 3D 中发起检修或改变资产状态；第一版建议改为“拉出观察”，并明确显示“只读”。
- 设备搜索现在只改变选中设备，不会把相机移动到设备；列表、搜索和 3D 点击应统一调用“选中 + 聚焦 + 打开只读详情”。
- 相机距离按固定比例计算，42U 设备在不同屏幕和全屏尺寸下可能出现过远、过近或内容裁切；建议增加基于包围盒的 `fitToView`。
- 现有全屏只作用于 `Rack3DContainer` 内部。建议全屏根节点包含 3D、工具栏、图例、设备列表和只读详情面板。
- 机柜卡片外层是 `<button>`，内部又嵌套编辑、删除按钮；运行页面时已观察到嵌套按钮 hydration 错误，应优先修复为外层非按钮容器或拆成独立按钮区域。

### 3.3 设备与机柜几何

当前 `rackViewModel` 能从 `total_u`、`start_u`、`u_height`、`position` 和 `is_full_depth` 计算设备的 U 位、前后面和深度。它还会识别越界、重叠、未知面向，并把异常设备从 `validDevices` 中排除。这是非常适合只读场景的基础。

当前模型仍缺少以下信息：

- 机柜在房间中的 `x/y/z`、旋转角、行方向和相邻机柜关系。
- 设备真实宽度、深度、前后面安装偏移。
- 型号级别的面板、端口布局、端口锚点和电源入口。
- PDU、电源回路、温度传感器、冷通道/热通道和气流方向。
- 3D 数据的更新时间、来源和版本号。

因此，现阶段不应承诺“物理级数字孪生”；应先把产品定位成“可导航、可核验、数据来源明确的 3D 机柜视图”。

### 3.4 拓扑连线风险

`RackCableLayer` 当前有三类问题：

1. 当接口返回链路后仍会增加基于设备名称的 `F1090-9`、`F1090-10` 特殊链路。
2. 对其他设备会按设备顺序自动创建级联链路，并生成端口号、速率和线缆类型。
3. 端口坐标通过通用字符串解析和固定列数估算，而不是来自设备型号的端口布局。

在监控类产品中，错误的链路比不显示链路更危险。建议调整为：

- 只有后端明确返回的链路才绘制为真实链路。
- 未匹配设备、未匹配端口或缺少端口坐标时，显示“拓扑数据不完整”，不自行补线。
- “示意连接”如果保留，必须是显式的演示模式，不能和真实拓扑使用同一颜色、状态和图例。
- 默认只显示选中设备的链路；“全部链路”作为临时诊断开关，并在链路数量过大时提示范围。

### 3.5 后端接口与数据能力

后端已提供只读接口：

- `GET /racks`
- `GET /racks/{rack_id}`
- `GET /racks/{rack_id}/layout`
- `GET /racks/{rack_id}/devices`
- `GET /rack-types`、`GET /device-types`
- `GET /device-health/overview`
- `GET /topology/links`

写接口使用更高角色：

- 机柜新增、修改、删除为 Operator/Admin。
- 设备上架、移动、移除为 Operator。

这套权限划分足以支撑“3D 只读、2D 写入”。第一阶段不需要新增 3D 专用写接口，也不应让 3D 直接调用任何 POST、PUT、DELETE。

当前后端能满足单机柜基础详情：布局接口返回机柜尺寸、U 高度、设备型号/厂商、设备角色、U 高度、前后面、满深度和额定功耗等信息。

多机柜和高保真 3D 仍缺：

- `/racks` 没有分页或按房间/行的完整范围过滤，服务层返回整表机柜。
- 页面全局调用 `/device-health/overview`，3D 只需要当前范围。
- 3D 无 `site_id` 过滤地调用 `/topology/links?limit=500`，会把全局拓扑拉到浏览器再筛选。
- `GET /racks/stats` 在服务层读取并在 Python 中汇总全部机柜，规模扩大后应改为范围化或数据库聚合。
- 没有机柜空间布局、真实设备端口锚点、PDU/传感器和设备视觉资产引用。

## 4. 推荐产品形态

### 4.1 三层视图

#### A. 多机柜总览

面向“我想知道机房里有哪些机柜、哪里有问题”：

- 以轻量化机柜体显示站点、楼层、房间和行。
- 只显示机柜摘要：机柜名、设备数、U 利用率、功率利用率、健康状态、数据质量。
- 点击机柜后相机平滑定位；双击或“打开详情”进入单机柜模式。
- 机柜数量较多时使用实例化几何、LOD 和聚合标签，不渲染每台设备和每根线。

#### B. 单机柜详情

面向“我想核对这个机柜的设备和链路”：

- 机柜正面/背面/等轴/俯视。
- U 位标尺、设备选中、高亮和只读详情。
- 健康、角色、功耗是显示图层，不改变数据。
- 设备搜索、右侧设备列表和 3D 点击共享同一个选中状态。
- 默认不显示全量线缆；选中设备后显示真实拓扑。

#### C. 只读检查面板

统一展示：

- 来源：2D 机柜布局、健康接口或拓扑接口。
- 更新时间和是否可能过期。
- 设备 U 位、面向、型号、序列号、资产关联、状态、健康、功耗。
- 数据质量问题：越界、重叠、未知面向、未匹配拓扑、缺少端口锚点。
- “在 2D 中查看”跳转到原有编辑页面；不在 3D 中提供编辑按钮。

### 4.2 全屏设计

全屏不应只是放大 Canvas，而应进入完整的 3D 工作台：

```text
┌────────────────────────────────────────────────────┐
│ 站点 / 房间 / 行 / 机柜   只读   数据时间   退出全屏 │
├──────────────┬───────────────────────┬─────────────┤
│ 场景/筛选/图例 │       3D 场景          │ 设备详情    │
│ 多机柜/单机柜  │ 机柜、设备、真实链路   │ 健康/功耗    │
│ 状态过滤      │                       │ 数据质量    │
└──────────────┴───────────────────────┴─────────────┘
```

建议：

- 全屏根节点监听 `fullscreenchange`，并在尺寸变化时调用 R3F resize。
- `Esc` 退出全屏，保留用户当前的机柜、选中设备和相机状态。
- 全屏仍保留“回到 2D”和“关闭只读详情”的明确入口。
- 工具栏采用“常用按钮 + 更多”分层，避免把相机、门、U 标尺、线缆、图层、功耗、全屏全部挤在一条线上。

## 5. 推荐技术架构

```text
RackManagementPage
├── RackReadModelProvider / useRackReadModel
│   ├── rack summaries（列表与多机柜总览）
│   ├── selected rack layout（按需）
│   ├── health snapshot（按范围）
│   └── topology links（按站点/机柜范围）
├── RackOverview3D
│   ├── RackInstances
│   ├── status / utilization aggregation
│   └── selection + camera fit
├── RackDetail3D
│   ├── RackFrame
│   ├── RackDeviceItem
│   ├── verified topology layer
│   └── camera / focus / display layers
└── ReadonlyRackInspector
```

实施上建议把读取请求从超大页面组件中抽到 `useRackReadModel` 或同等的查询层，但继续复用现有 `fetchJson`、鉴权头和 API 响应解包规则。2D 的写操作可以继续留在现有页面；3D 只消费查询结果和回调。

### 5.1 数据加载策略

首屏只加载机柜摘要：

```text
GET /racks?site_id=...&room=...&row=...&q=...
          │
          └── 只返回摘要或列表页

用户选择机柜
          │
          └── GET /racks/{id}/layout

用户查看链路/健康
          │
          └── 按站点、机柜或设备范围获取
```

不建议再使用“所有机柜一进入页面就请求完整 layout”的方式。选中的机柜可以用缓存；缓存应有上限、失效时间或版本判断，避免长期保留过期布局。

### 5.2 多机柜的空间定位策略

建议分两步：

**第一步：逻辑行布局。** 使用站点、房间、行、机柜编号和排序生成规则化排列。它不需要立刻修改数据库，适合先完成多机柜导航和筛选。

**第二步：真实机房布局。** 当用户确实需要按现场位置核对时，再增加可选的空间布局数据：

```ts
interface RackSpatialPlacement {
  rackId: string;
  x: number;
  y: number;
  z: number;
  rotationY: number;
  zone?: string;
  source: 'configured' | 'inferred';
}
```

空间位置建议放在独立的布局表或空间布局资源中，不要为了 3D 直接把大量渲染字段塞进基础 `racks` 表。没有真实坐标的机柜必须标记为 `inferred`，不能伪装成现场坐标。

### 5.3 型号与端口视觉模型

第一版可继续使用程序化机箱，但要把硬编码从渲染组件移到型号配置：

```ts
interface DeviceVisualProfile {
  deviceTypeId: string;
  widthMm: number;
  depthMm: number;
  frontProfile?: string;
  rearProfile?: string;
  portAnchors?: Array<{
    interfacePattern: string;
    x: number;
    y: number;
    face: 'front' | 'rear';
  }>;
  assetUrl?: string;
  assetLicense?: string;
}
```

真实图片或 GLTF 资产必须记录来源和许可证。没有型号级配置时，显示“通用设备外观”，而不是假装是准确的真实面板。

## 6. 性能和可维护性要求

### 必须调整

- 去掉初始化时对所有机柜完整 layout 的 `Promise.all`。
- 多机柜总览使用 `InstancedMesh`、LOD、视锥裁剪和按需标签。
- 只对选中机柜创建设备细节和线缆几何。
- `TubeGeometry` 不要在每次渲染映射中重新创建；需要缓存、复用并在链路变化时释放旧 geometry/material。
- 交通粒子动画只在选中链路或用户明确开启时运行。
- 生产模式不应默认 `preserveDrawingBuffer: true`；仅在导出截图时启用专用导出路径。
- 多机柜场景中的地面网格只创建一次，不要每个机柜复制一套。
- 设备标签默认只显示选中、悬浮或告警设备，避免大量 `Html` 节点。

### 建议的性能分层

| 层级 | 渲染内容 | 数据内容 |
|---|---|---|
| L0 房间/行 | 机柜实例、颜色、编号 | 机柜摘要 |
| L1 机柜聚焦 | 机柜外框、设备色块、告警标记 | 选中机柜 layout |
| L2 详情 | 设备面板、U 标尺、真实链路、只读提示 | layout + 健康 + 拓扑 |

性能验收应在目标部署机器上用 50、100、500 个机柜摘要数据做基准，记录首屏请求数、详情请求数、帧率、内存和切换延迟；不建议只以开发机上的主观流畅度作为上线标准。

## 7. 分阶段实施建议

### Phase 0：只读边界和稳定性

目标：让现有 3D 先成为可信的只读视图。

- 3D 模式隐藏“安装”、移动、删除等写操作入口。
- `Rack3DContainer` 不接触任何写接口；增加“只读”标识。
- “抽出检修”改为“拉出观察”或暂时从 MVP 移除。
- 修复机柜卡片嵌套按钮 hydration 错误。
- 全屏根节点覆盖工具栏、设备列表和只读详情。
- 设备列表/搜索与相机聚焦联动。
- 增加基于场景包围盒的默认 fit-to-view。
- 删除拓扑硬编码和自动级联造线；没有真实链路就显示缺失提示。

这一阶段不需要新增数据库字段，风险最低，应该优先完成。

### Phase 1：单机柜体验

目标：把一个机柜做成日常可用的查看工作台。

- 正面、背面、等轴视图和设备级聚焦。
- 设备健康、功耗、角色图层统一图例。
- U 位、数据质量、更新时间和来源清晰可见。
- 真实拓扑按选中设备显示，缺失数据可解释。
- 3D 与 2D 之间可以快速跳转，且不会出现两个独立状态。
- 增加 Rack3D 交互测试和浏览器测试。

### Phase 2：多机柜逻辑总览

目标：支持一个房间/一排/一个站点的机柜导航。

- 首屏使用机柜摘要，不预加载所有布局。
- 增加站点、楼层、房间、行、状态和健康筛选。
- 先使用逻辑行布局，不强行要求真实房间坐标。
- 机柜点击定位，选中后切入单机柜详情。
- 拓扑和健康按范围获取，避免全局数据下发。

### Phase 3：真实空间和高保真模型

仅在现场确实需要时实施：

- 机柜空间坐标、方向、区域和布局版本。
- PDU、电源回路、温度传感器、冷/热通道。

### 当前基线

本轮执行结果：

### Phase 0/1 验收

- 3D 页面没有“安装”“移动”“删除”等写入入口，也不发起机柜/设备写请求。
- 2D 修改机柜或设备后，重新进入 3D 或刷新可以看到同一份数据。
- 42U、24U、48U 机柜在默认视角下完整可见，不裁切、不漂移。
- 点击列表、搜索结果、3D 设备都能定位同一设备，并能打开只读详情。
- 全屏包含 3D 场景、工具栏、图例、设备清单和详情面板；退出后状态保留。
- 空 U 位可以查看“空闲 U 位”信息，但不会打开安装流程。
- 没有真实拓扑时不显示伪造的线；链路缺失有明确提示。
- 异常 U 位和冲突设备不会导致 3D 崩溃，且能在数据质量面板中解释。

### Phase 2 验收

- 首屏只请求当前筛选范围内的机柜摘要。
- 选中一个机柜后才请求该机柜的完整布局。
- 机柜数量扩大时，不创建与机柜数量线性增长的完整设备/线缆细节。
- 机柜筛选、定位、切换和返回列表不会遗留旧的设备详情或链路。
- 在目标机器上完成 50/100/500 个机柜摘要场景性能基准。

## 10. 开源项目参考

建议借鉴产品结构和数据表达，不直接复制未经确认的模型或代码：

- [NetBox Thermal View](https://github.com/tak-labo/netbox-thermal-view)：Apache-2.0，提供楼层/机柜热力视图、按 U 位显示和只读 3D 机柜，是“总览 → 机柜详情 → 设备/热力”的有价值参考。
- [Rackula](https://github.com/RackulaLives/Rackula)：MIT，重点是机柜布局、真实设备图片、多机柜/成组机柜和导出体验。它主要是 2D/SVG，不是 Three.js 引擎，但很适合作为 2D/3D 共用数据和设备目录体验的参考。
- [openDCIM](https://opendcim.org/features.html)：成熟的 DCIM 领域参考，覆盖容量、功率、温度、重量、PDU 和网络连接等概念；其 GPLv3 许可证意味着不能在未评估许可证策略的情况下直接复用代码。
- [thingraph/server-room](https://github.com/thingraph/server-room)：可作为 Three.js/WebGL 机房视觉交互参考；当前未把它作为可直接引入的依赖，使用前必须独立确认许可证和资产来源。
- [NetBox Visual Explorer](https://netboxlabs.com/docs/visual-explorer/)：可参考“同一数据源、站点/机柜范围、点击打开详情、URL 状态可分享”的产品交互模式；它是产品参考，不是本项目的开源依赖。

## 11. 最终建议与决策点

建议批准以下决策：

1. **2D 是唯一写入和事实来源，3D 永久只读。**
2. **先做单机柜可信详情，再做多机柜轻量总览。** 不先做“所有机柜都按真实物理细节渲染”。
3. **真实拓扑优先于视觉炫技。** 删除自动造线，缺数据就诚实提示。
4. **第一阶段不新增空间坐标表。** 先用现有机柜字段做逻辑行布局，确认用户确实需要现场级空间还原后再建模。
5. **不更换 Three.js。** 现有技术栈足够，工作重点是只读边界、数据查询、场景分层、性能和测试。

下一步应先实施 Phase 0，再以单机柜为验收样板；Phase 0/1 稳定后再开始多机柜 API 和场景层。这样既能解决当前“功能不齐、体验差”的直接问题，也能避免把现有 2D 机柜编辑能力复制成一套难以维护的 3D 编辑器。
