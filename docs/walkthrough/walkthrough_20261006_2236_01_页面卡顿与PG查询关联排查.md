# 页面卡顿与 PostgreSQL 关联排查：执行结果

## 完成摘要

在远端运行中的 Nexora 服务上完成了两轮各 5 分钟的只读采样，并对第三轮做了 60 秒 SNMP 设备/传感器聚合统计。两轮都捕获到后端 live 与多个 API 路径约每 110 秒同步变慢的簇，部分请求达到 6 秒超时。Grafana 和 VictoriaMetrics 的独立健康探测同期仍快速返回。

PostgreSQL 1 秒活动采样没有记录到锁等待、阻塞或持续秒级 active SQL，但 `snmp_mib_nodes` 每轮有 42 次全表扫描。数据库没有启用 `pg_stat_statements`，现有计数没有单条查询的耗时。结合约110秒重复节律和工作区中自动 SNMP 硬件发现的同步 MIB SQL 路径，SNMP 发现工作是目前最值得继续验证的疑点，尚不能称为已证实根因。

## PostgreSQL、SNMP 和容器证据

- 300 秒窗口的 PG activity 采样为 298 和 299 次；最长 active query 年龄分别约 341ms 和 412ms。没有采样到 lock wait 或 blocked activity。1 秒采样可能漏掉短 SQL。
- `snmp_mib_nodes` 两轮各增加 42 次 seq scan，共读取 2,839,704 行；该表约有 67,612 行。扫描增量以约 110 秒周期聚集。`interface_telemetry_raw` 两轮的 seq scan 增量均为 0，主要为索引访问；`interface_telemetry_1m` 在两个采样窗没有扫描增量。
- 两轮 PostgreSQL 的 commit/rollback、读块和临时文件都在变化，但这些是全服务合计，不能归给单次 API 或某个 SQL。数据库未启用 `pg_stat_statements`；没有重置统计、安装扩展或重启数据库。
- NetOps 容器 CPU p95 两轮分别约 92.46% 和 100.62%，峰值 103.26% 和 106.09%；容器 quota 是 2 CPU。cgroup 记录没有 CPU throttling 或 OOM，故不能解释为已触及容器 CPU 上限。其他监控组件没有同期持续满载迹象。
- 60 秒 fleet 计数窗口记录17台设备、15台存在 SNMP 绑定；A-loop/B-loop 候选均为17台。active hardware sensor 共5,296条、涉及15台设备。VM V1 assignment 按间隔计数为30秒15台、120秒1台、900秒15台。两组资产是否重叠未知；`explicit_snmp_profiles=0` 不表示没有 SNMP。这些是负载规模线索，不表示有5,296个独立 SNMP 包。
- 工作区调用链显示 B-loop await 每台设备的 `process_device_slow`。在 `backend/services/background_monitor_service.py:1810-1845`，过期或缺失的硬件发现会触发自动 `discover_device_oid_config`；`backend/services/snmp_discovery_service.py:1106-1163` 将 LibreNMS 规则探测接到 `probe_librenms_hardware`，其中 `backend/services/snmp_hardware_probe_service.py:210-244` 的 `_resolve_mib_symbol` 同步查询 MIB 表，计划含 `Seq Scan snmp_mib_nodes`。常规 active sensor 轮询走另一条路径：同步读取传感器清单，再 await SNMP walks。B-loop 每轮收集后休眠60秒，采集耗时再加约50秒与观测到的约110秒周期相容，但不能单凭节律证明是同一任务造成。
- 远端 fingerprint 确认 `background_monitor_service.py` 与工作区一致；`orchestrator.py` 与当前工作区不同（旧容器与本地 HEAD 的关系见 `handoff.md` 旧采样审查）。本轮 fingerprint 未覆盖 `snmp_discovery_service.py` 和 `snmp_hardware_probe_service.py`。因此上述是可解释现象的代码候选，但该探测/发现模块在线版本、具体触发设备及每次 SQL 耗时仍未确认；也没有将扫描与 HTTP request ID、event-loop lag 做时间关联。

## 代码改动

- `scripts/diagnostics/nexora_pg_latency.py` 增加真实前端 API 与全部 Grafana dashboard URL 的重复 GET 探测，以及只返回数量的 SNMP 绑定/硬件传感器统计。`scripts/diagnostics/README.md` 说明路由频率、超时和认证边界。
- `backend/tests/release/test_pg_latency_diagnostics.py` 覆盖目标路由、无响应体读取、未伪造用户授权头、聚合数据不暴露设备明细和脱敏行为。
- `backend/services/credential_service.py` 把凭据列表中的设备关联查找由每条 credential 一次改为单条 `ANY(array)` 查询，保留安全输出、角色、排序和最多五条设备预览。对应隔离 PG 测试位于 `backend/tests/configuration/test_credential_list_batching.py`。
- `backend/api/assets.py` 修正独立 SNMP 凭据中的 community 不应误建 SSH credential binding；该文件还包含此前已有的资产首页统计变更，本次只涉及凭据绑定判断。
- 本 walkthrough、对应 plan 和 `handoff.md` 记录完整证据及限制。工作区改动没有部署到远端。

## 后续验证

要最终确认用户所见页面卡顿的来源，需要在用户已登录的浏览器里同步刷新 dashboard、打开资产添加/编辑表单并保存，同时关联前后端 request ID、数据库连接池等待、SQL 执行时长和 asyncio event-loop lag。若同步出现周期性 MIB 扫描，应继续量化 MIB lookup 的调用数和持续时间，再决定是否做缓存/索引或将同步查询移出事件循环。没有这组关联数据前，不调整远端采集频率、不启用扩展、不部署本地改动。
