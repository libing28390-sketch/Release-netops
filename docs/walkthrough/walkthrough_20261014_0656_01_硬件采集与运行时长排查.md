# 硬件采集与运行时长排查结果

## 完成摘要

1. 首次硬件数据延迟与 LibreNMS 规则初始化链中的全量 MIB 导入有关。首批硬件发现已在手动编译之前入库，不能将点击编译/发布认定为本次数据出现的触发原因。
2. “都是 60 秒”不符合实际配置：硬件采样为 60 秒，运行时长所属 generic_system_std 目标为 900 秒。
3. 系统模块曾发生 SNMP 请求超时。后续正常周期自动恢复；2026-10-14 06:54:53 检查时，15/15 system 目标 UP，20 分钟查询范围内 15 台设备均有 sysUpTime。
4. 浏览器选择有线交换机 S6850_1 后已显示系统运行时长。该字段没有仅限无线设备的规则。

## 编译和发布的作用

- 编译入口：backend/api/monitoring_v1.py:1318，读取采集计划、设备和凭据，生成 assignments、快照及版本。
- 发布入口：backend/api/monitoring_v1.py:1491，调用 collector_artifact_service 发布版本并重载 snmp-exporter 配置。
- 源码没有从这两个入口调用 LibreNMS 硬件发现或 MIB 初始化的路径。
- 编译器确实生成 /hardware-metrics 的 60 秒抓取任务，见 backend/services/monitoring_compiler.py:1136。因此编译/发布可以影响硬件指标是否进入时序库；本次日志证明该任务在手动操作前已持续抓取，且首批传感器已先入库。
- 部署容器与本地五个关键文件经换行统一后哈希一致：monitoring_v1.py、collector_artifact_service.py、orchestrator.py、snmp_hardware_poller_service.py、snmp_hardware_probe_service.py。

## 系统运行时长空值

默认采集计划中 generic_system_std 的间隔为 900 秒、整次 scrape timeout 为 30 秒，见 backend/database/migrations/m0232_monitoring_v1_control_plane.py:289。后续迁移只补缺失项，不覆盖已有频率。编译器把计划间隔传给目标级 vmagent scrape interval，线上 discoveredLabels.nexora_scrape_interval 同样为 900s。

该模块采用标准 sysUpTime OID 1.3.6.1.2.1.1.3，不按无线/有线筛选。此前 S6850-4、S6850-5、F1090-9 等 system 目标返回 HTTP 500，exporter 错误为 request timeout after 2 retries，失败次样本数为 0；接口抓取当时仍正常。

少量只读 sysUpTime 标量 GET 均成功：

| S6850-4 | 0.074 秒 |

这验证了抽查的有线和无线设备均支持该 OID。后续正常周期恢复：S6850-4 最近成功抓取 06:49:32，F1090-9 为 06:51:00。没有修改配置或手动编译/发布。

## 剩余问题与建议

- 已定位到失败表现为 SNMP request timeout，但未证明具体是网络抖动、设备响应、启动负载或哪个 OID 请求造成；不能把整个 system walk 配置直接认定为根因。
- system 配置同时 walk 整个 system 子树和 GET 六个标量，OID 范围有重叠；是否实际重复请求取决于 exporter 行为，未据此下因果结论。
- 建议后续评估将运行时长独立为 60 秒标量 GET，以及让页面呈现首次 MIB 初始化/发现进度；本次没有实施。
- 当前业务代码和运行时配置无待集成变更、无阻塞事项；后续实施方案由主 Agent 统一设计。
