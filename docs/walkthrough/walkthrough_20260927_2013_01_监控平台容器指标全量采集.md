# 监控平台容器指标全量采集验收记录

日期：2026-09-27

对应计划：`docs/plans/plan_20260927_2013_01_监控平台容器指标全量采集.md`

状态：本地实现与静态验证完成；目标主机运行时验收待部署

## 1. 诊断结论

- 大盘中的六行是六个 `platform_*` Prometheus 指标端点，并非 Docker 容器清单。平台 API、VictoriaMetrics、vmagent、SNMP Exporter、Grafana 和 cAdvisor 各是一个 scrape job。
- 已打开的 Grafana 页面与 Grafana `/metrics` scrape 健康不是同一检查。用户提供的 vmagent `wget` 输出显示 `grafana:3000/metrics` 被发往 HTTP 代理 `192.168.31.253:10808` 并返回 502；清除采集容器代理环境并设置 Docker 内网 `NO_PROXY`。
- Docker 列表显示 cAdvisor 容器处于 `Restarting (2)`。用户提供的日志尾部是 cAdvisor 参数帮助；Compose 的 `--disable_metrics` 含 `accelerator`，但上游 cAdvisor v0.60.6 允许值列表不包含该项，因此移除它。需在部署后再确认容器实际启动。
- CPU、内存和容器磁盘面板空白与 cAdvisor 未提供有效采集数据相符。VictoriaMetrics 存储占用率面板则另有版本原因：Compose 使用 v1.103.0，而 `vm_total_disk_space_bytes` 在 v1.124.0 引入；改用该版本支持的 `vm_data_size_bytes` 显示已用数据量，不再伪称文件系统占用率。

## 2. 本地改动

- `docker-compose.yml`：为 vmagent 与 cAdvisor 清空大小写 HTTP/HTTPS/ALL proxy 环境；设置分别访问内部服务 DNS 与 Docker socket proxy 的 `NO_PROXY`；移除 cAdvisor 不支持的 `accelerator` 分类。
- `backend/tests/monitoring/test_monitoring_v1_deployment_contract.py`：增加代理绕行和 cAdvisor 参数契约断言。
- `monitoring/grafana/generate_dashboards.py`、`monitoring/grafana/dashboards/nexora-platform-health.json`：六个采集端点保留在独立健康状态表；CPU、内存、磁盘查询去掉九容器静态白名单，按非空 `name` 聚合；新增基于 `container_last_seen` 的容器观测数与清单。
- VictoriaMetrics 可用空间面板保留，原存储占用百分比改为 `sum(vm_data_size_bytes)` 已用数据量。

## 4. 部署后验收

将本次 Compose 与 dashboard 生成物更新到目标主机后，需确认 vmagent 对 `grafana:3000/metrics` 不再走宿主代理，`platform_grafana` 与 `platform_cadvisor` 恢复 UP，cAdvisor 的 `/metrics` 包含全部 Docker 容器的 CPU、内存和磁盘样本，并确认动态清单数量与目标机容器情况相符。若 cAdvisor 仍重启，应读取从启动开始的完整首条错误日志；若容器已 UP 但资源指标仍缺失，再检查目标机 cgroup、Docker API 权限与宿主挂载。
