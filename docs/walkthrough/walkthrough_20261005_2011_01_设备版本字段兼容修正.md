## 关键实现

- 平台识别仅在 `devices.version` 为空时更新该字段；移除了对 schema 不存在的 `physical_assets.version` 的 SQL。此前后续 UPDATE 失败会使当前事务中的设备版本更新无法正常提交。
- 新迁移 `274 / add_device_version_column` 使用 `ALTER TABLE devices ADD COLUMN IF NOT EXISTS version TEXT`。新建表已有此列；迁移只为旧表补列，不回填、不设约束和索引。
- 日志中 3 次 `platform-detect` HTTP 500 与 PostgreSQL `UndefinedColumn` 毫秒级对应，强烈指向该路径；但 DB 日志没有 STATEMENT，字符位置 140/146 与当前工作树 SQL 的版本列位置不一致，因此尚不能证明运行容器执行的就是该语句。需要同版本部署后观察，或启用受控 SQL statement 记录以完成最终对应。

## 调度器警告排查

- 193 条 APScheduler warning 的时间为 16:49:36–17:28:58，包含 locator runs 102、locator invalidations 45、health snapshot 40、alert delivery outbox 6。
- `max_instances=1` 的 warning 表示同一进程内上一实例仍运行，新 tick 被跳过。它不能证明队列任务丢失。locator 两任务每 2 秒触发，run worker 每轮最多认领 5 个工作并等待 SSH trace；单条 trace deadline 可到 180 秒。health snapshot 每分钟执行并逐设备加载接口数据，outbox 每 5 秒最多串行投递 20 条。
- 保留 `max_instances=1` 和触发周期，避免通过并发运行同一工作造成重复设备 CLI、额外数据库竞争或连接池压力。之前首页改为聚合并取消重型明细轮询可能降低后台压力，但尚未部署，因此不能声称已消除这些 warning。后续需要查看新版本的 job 实际运行时长和数据库连接池记录，再决定是否批量化 health snapshot 或调整队列执行模型。
