# 验证报告与走查记录 - 口令上收逻辑与连通性优化

## 变更内容

1. **改进前置校验**：在 `backend/api/assets.py` 中的 `update_asset` 校验函数中，使用 `resolve_device_credentials` 来加载本地和外部凭据表中的用户和口令数据，并实现了双密码模式下特定密码为空时向主密码的安全回退。
2. **调整改密执行顺序**：在 `backend/api/assets.py` 的单设备和批量设备 takeover 逻辑中，将改密执行顺序调整为**特权账号（`admin`）优先改密，成功后再对普通账号（`normal`）改密**。

## 验证结果

### 自动化测试
运行 pytest 后端单元与集成测试用例，所有 **353 个测试用例全部一次性通过**，无任何 Regression 问题。

```bash
================= 353 passed, 1 warning in 207.34s (0:03:27) ==================
```

### 业务场景走查（手动测试）
1. **测试环境调试**：
   * 在调整宿主机去往 `172.16.255.0/24` 网段的网关路由至核心交换机 `192.168.96.220` 后，物理/虚拟机链路连通性恢复正常。
   * 编写脚本重置了 `credentials` 表中的设备密码为初始状态 `123456`。
2. **单设备/批量设备 takeover 测试**：
   * 先后对 `ACC-SW1` 与其他双密码设备发起了口令上收。
   * **特权账号改密（Admin Role）**：首先使用旧的特权密码 `admin/123456`（成功从凭据表中读取并降级回退）进行登录，下发改密命令，将设备上的特权口令修改为生成的 20 位新密码，同时更新数据库的 `devices.*` 和 `credentials.*`。
   * **普通账号改密（Normal Role）**：接着使用刚刚改密成功的特权账户（`admin` 和生成的 20 位新密码）重新登录设备，执行配置命令成功将普通账号修改为 20 位新密码，写入数据库。
   * **投产转变**：在两个账号轮转改密均完毕后，设备顺利投产，`onboarding_status` 成功转变为 `active`，状态变为 `online`，`is_managed` 变为 `1`。

## 结论
修改彻底解决了口令上收因为凭据共享覆写死锁导致的 `Authentication failed` 认证报错，以及由于数据库隔离没有读取到密码的 422 报错，且业务拓扑网关配置匹配。
