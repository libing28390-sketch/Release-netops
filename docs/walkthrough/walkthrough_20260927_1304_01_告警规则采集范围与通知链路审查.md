# 告警规则采集范围与通知链路审查

## 审查范围

- 告警指标与采集源/模板的绑定。
- 规则范围的保存、匹配和优先级。
- 网络设备、平台宿主机、服务器指标三类告警的执行入口。
- 通知渠道、SMTP 收件组、租户隔离和维护窗口重开通知。
- 前端可配置项与运行时行为是否一致。

## 结论

代码里已有采集源元数据、规则匹配和通知 outbox，但它们目前不是一条对所有指标一致的链路。规则表单展示的“采集源”是由指标类型推导出的说明，不是告警对象/设备选择器；范围则是自由文本匹配器。网络告警规则多数会参与执行，但离线告警绕过规则。宿主机和服务器类别的规则执行能力不同，界面目前没有表达这种差别。

## 重点发现

1. **采集源和告警对象是两件事。** `snmp_metric_profile_service` 按 `metric_type` 返回采集源、模板字段和说明；`alert_rule_service` 将其只读地附加到规则响应。它不选择某台设备，也不保存某台设备的模板。设备实际使用匹配型号的已验证模板；模板未验证时可能改用 SNMP 自动发现结果。规则表单目前把这段元数据展开成模板路径列表，容易被误认为对象选择。

2. **网络设备范围是匹配器，不是对象选择器。** `global` 命中全部；`site` 比对设备行里的站点文本；`device` 分别比对设备 ID、主机名、IP；`interface` 只比对接口名。值和候选字段都转小写，因此匹配不区分大小写。优先级为 interface > device > site > global；同一优先级命中多条时，最近更新的规则胜出。当前没有租户、标签、设备多选，也没有设备与接口组合条件，所以“接口 Gi1/0/1”会匹配所有设备上的同名接口，不能唯一指定某台设备的某个端口。

3. **设备离线规则目前没有接入规则引擎。** 表单/API允许配置 `ping_unreachable`，但后台离线切换使用 `dev_offline` 键并硬编码 `critical`，没有调用 `resolve_alert_rule`，也没有把规则传给通知器。因此这类规则的启停、级别、渠道和范围不会影响设备离线告警。维护窗口重新通知也把 `dev_offline` 映射成未定义的 `device_offline`，无法重选 `ping_unreachable` 规则。

4. **平台宿主机指标走独立路径。** `host_cpu`、`host_memory`、`host_disk` 的阈值和 severity 确实由 `/api/health` 读取，但读取时只按指标取最近两条规则，不匹配站点/设备范围；通知通过 `dispatch_to_all_users`，不使用规则渠道或通知组。该路径查询活动用户时没有 tenant 条件，因此多租户部署会面向所有租户用户发送系统宿主机通知。

5. **服务器类规则暂未找到执行入口。** `srv_*` 类型出现在规则类型校验、前端选项、种子监控指标和采集源描述中；仓库中未发现它们进入 `select_rule` 或另一条 alert-rule 阈值执行链路的路径。能保存不等于会触发告警。

6. **网络规则通知已存在 outbox 链路，但没有规则级组。** 网络告警将 `notification_channels` 放进 outbox，并按租户派发；SMTP 通道可按 profile 里的组/用户目标过滤。规则只存渠道，不存用户组。重开通知会重读渠道，但 payload 也没有规则级组。

7. **规则与用户组的租户边界未对齐。** `alert_rules` 没有 `tenant_id`，规则读写按全局 `rule_id` 处理；而用户组与 SMTP profile 都按 tenant 读取。仅增加一个 `group_name` 字符串前，需要明确组名如何绑定租户。当前运行时可安全实现的最小语义是：使用规则选择的组名，在告警对象所属 tenant 内展开活动成员；这要求不同 tenant 的同名组被视为同一规则意图。若规则应由各 tenant 独立管理，则需先对规则做 tenant-scoping 和 CRUD 授权隔离。

8. **重复通知窗口的名字会让用户误解。** 规则重复窗口只在一次新的通知调用时做短期节流；当前正常网络规则只在告警开启/恢复时调用，不会按窗口定时重复发送，所以它不是持续告警的周期提醒。

9. **渠道选项不选择 SMTP profile。** 告警规则勾选 `email` 后，outbox 会向该 tenant 的所有已启用 SMTP profile 分别建立投递。如果配置多个启用 profile，同一规则邮件会送到所有 profile 的收件范围。

## 子 Agent 审查摘要

- 前端审查确认表单只保存 `notification_channels`，现有 SMTP 收件人目录接口是 Administrator 权限；规则编辑允许 Operator，不能直接复用该目录接口，也不能只加前端字段。
- 后端审查确认规则全局存储、profile 目标按租户解析；新增规则级收件组需要同步数据库、API/服务、告警 payload、outbox 投递和维护窗口重开路径。
- 后端审查关于“静态列表中缺少 host/srv collection binding”的判断由代码中的动态循环补齐；运行时模块会为这些类型添加采集源元数据。但这不代表 `srv_*` 已接入告警规则执行器。

## 建议的实施顺序

1. 先明确全局规则与 tenant-local 用户组的关系；在此之前不要把组名伪装成规则级稳定 ID。
2. 修正表单对象/范围说明，将模板路径收进可展开帮助；高级字段默认收起。
3. 为确实由网络规则引擎执行的指标接入规则级组过滤，并同步覆盖维护窗口重开投递。
4. 将 `ping_unreachable` 纳入网络规则解析；宿主机独立路径和未实现的 `srv_*` 指标分别决定是接入还是从可配置入口移除。
5. 明确 SMTP 多 profile 的规则级选择语义，再决定是否需增加 profile selector。
