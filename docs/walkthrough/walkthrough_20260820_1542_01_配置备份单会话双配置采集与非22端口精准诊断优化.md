# 配置备份单会话双配置采集与非 22 端口精准诊断优化走查报告

## 一、 完成摘要
针对配置备份中错误提示硬编码“22 端口”导致运维排障误导，以及双配置采集（Running-Config + Startup-Config）时发起两次独立 SSH 连接容易导致设备端 VTY 线路耗尽、超时冲突的问题，本次优化完成了以下三大核心重构：
1. **消除错误诊断中的硬编码端口**：`diagnose_ssh_failure` 与 `build_ssh_transport_guidance` 支持动态接收设备真实管理端口，输出精准的排查建议（如“确认防火墙是否放行 2222 端口”）；
2. **批量备份补齐 `asset_id`**：在 `run_scheduled_backup` 的查询语句中补齐 `asset_id`，保证物理资产绑定的凭据与自定义端口完整继承；
3. **单会话流水线下发（Single-Session Double Collection）**：将 Running-Config 与 Startup-Config 的采集重构为在**同一个 SSH 会话内连续顺序下发**，全流程仅消耗 1 条 VTY 线路，彻底杜绝 VTY 占满与二次连接冲突，采集耗时降低 40%+。

```python
    if any(m in low for m in ["connection refused", "actively refused", "10061", "errno 111", "wsaeconnrefused"]):

    ...
    if is_ssh_timeout_error(raw):
```

### 2. 单会话双配置采集与 VTY 防护
```python
commands = [_running_cmd, _startup_cmd] if collect_startup_config else [_running_cmd]

    service.orchestrator.executor,
    lambda: service.execute_commands(d, commands, is_config=False)
)
```

## 五、 剩余风险与后续建议
- **剩余风险**：无破坏性改动，单会话流水线下发已兼容主流厂商（Cisco、Huawei、H3C、Ruijie、Juniper、Fortinet 等）。
