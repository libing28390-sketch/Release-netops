# 多厂商硬件与无线采集恢复 Walkthrough

## 完成摘要

已在 `192.168.204.128` 部署 Python 采集修复。生产环境不执行 PHP：容器内 `shutil.which("php")` 返回 `None`。应用使用 Python 解析固定 LibreNMS 来源定义并执行 SNMP 发现和轮询；这不是运行 LibreNMS PHP 程序。固定上游版本为 `6c26b4fe4a40f7b392c19c36a44257212736e38c`。

普通硬件规则来自固定 LibreNMS 快照中的 OS 类/YAML 和 MIB 定义，按 Python 执行路径实现来源校验、字段/单位处理和轮询计划。需要如实区分的唯一设备适配例外是 H3C Comware AP/无线：LibreNMS 固定 Comware OS 类没有 Wireless discovery，因此本项目按同一快照中的 H3C MIB 符号编写了显式标注的 Nexora Python MIB adapter。它没有被伪称为 LibreNMS 上游 wireless rule。

## LibreNMS 来源覆盖范围

- 固定 manifest 涵盖 136 个 OS profile、2,360 个 MIB 映射、258 个 hardware discovery YAML 文件和 28 个 adapter 文件。人工复核入口：[source-manifest.json](../../backend/vendor/librenms/source-manifest.json)；来源说明在 [README.md](../../backend/vendor/librenms/README.md)。
- 硬件定义盘点：91/136 个 profile 至少有一项可识别的处理器、内存或传感器定义；31 个有 YAML，但没有本执行器识别的处理器/内存/传感器定义；14 个没有 hardware discovery YAML。这是上游定义覆盖分类，不能解释为 136 个 profile 都有完整硬件支持。
- 无线来源盘点限定在当前 `backend/vendor/librenms/mibs` 的 23 个厂商桶，没有引入目录外厂商。固定 dispatcher 声明 20 个上游 rule key，Python 适配器全部实现并逐项来源校验；Stellar 的传感器虽没有标准 OID，但由 LibreNMS `pollWirelessClients()` 对 `apClientWlanService` 做自定义 walk，Python 已同步该轮询及每 SSID/总客户端聚合。IOS-XE 的 pinned `Iosxe` 类继承 `Ciscowlc`，因此共用 Cisco WLC 规则是源码确定的。
- 5 个非 AP 清单的上游无线类规则现在也由 Python 读取现有 MIB：Cisco SAT 错误/RSSI/SNR，Ubiquiti AirFiber/AirFiber LTU/AirFiber 60 的频率、距离、功率、质量、速率和信号，以及 Nokia TiMOS 蜂窝信号。Nokia Wavence 射频功率由既有 LibreNMS YAML Python 执行器处理；Yunshan YAML 仅提供 WLAN 控制器冗余状态。
- 23 个现有 vendor 桶中，9 个在固定 LibreNMS 快照里有无线 OS rule，20 个 rule key 已由 Python 适配；其余 13 个桶在该快照中没有上游 wireless OS rule，不能因为存在 MIB 就宣称有采集规则。Comware 的 AP/radio 使用明确标记的 H3C MIB adapter，因为固定上游 Comware 类没有 Wireless interface。聚合计数、AP/Radio 行与射频/蜂窝信号不混作同一能力。

### 多厂商硬件能力边界

- 生产目标共 9 台：Cisco R1/R2/R3/R4/SW5/SW6，H3C AC_11/F1090-9/F1090-10。CPU 全覆盖；内存缺少 SW5、SW6；机箱温度、功耗、风扇/电源状态和光模块数据按上表列出的设备生效。
