# 告警隔离压测工具实现与验证

创建时间：2026-10-12（Asia/Shanghai）。

## 完成摘要

新增 opt-in `--alert-storm` 压测流程，用 run ID 隔离的 PostgreSQL、Redis Broker、NetOps API、Relay 和 critical/normal Celery Worker，分档写入 500/1000/5000 条合成活动告警及 `workspace` outbox。每档默认持续 300 秒，以 2 RPS、最多 2 个并发客户端读取告警列表与摘要，同时观察 outbox 排空、API p95、错误率、容器资源和宿主机 CPU。

测试数据直接写入隔离测试数据库，不触碰现有告警库或数据卷。Docker 网络设为 `internal`，清除代理环境；worker 的自动通知总开关关闭，所以 outbox `succeeded` 表示任务已安全收敛，不表示真实外部通知送达。不同告警档位使用不同 delivery ID，防止 Redis 中迟到的 Celery 重投与后续档位复用同一任务身份。

告警模式的测试容器 CPU quota 合计最多约 0.77 核，runner 最多 0.20 核；负载启动前要求宿主机 CPU 至少有 3 个有效样本且最大值低于 30%。运行期间宿主机 CPU 达 80% 连续 5 个 2 秒样本会停止，另保留宿主机可用内存 10%/256MiB、容器内存 95%、OOM、异常退出及人工终止保护。高负载预检失败时不会创建测试容器。

## 已确认的问题

告警页面卡顿的直接原因已经有线上请求证据：修复前 `GET /api/alerts` 约 2.34 秒，其中约 2.32 秒耗在认证等待；会话认证与设备探测竞争 asyncio 默认线程池，RBAC 又重复查询同一个会话。为认证改用独立有界线程池并复用请求态认证结果后，认证约 27 毫秒；部署复测的告警列表没有持续出现超过 500 毫秒的慢请求。该问题解释了网页响应卡顿。

虚机基线证明 CPU 高峰在合成告警测试开始前已经存在：主机 2 vCPU 的 30 秒窗口峰值为 81.02%，NetOps 峰值 83.27%，PostgreSQL 峰值 48.97%，通知 Worker 基本空闲。因此本次不能把峰值归因于 Celery 告警 Worker，也没有证据证明 500/1000/5000 条告警的负载曲线。

进一步取得 `/hardware-metrics` 内部阶段日志后，确认此路由每分钟取回 3902 个传感器行、渲染约 7.59 MB；总耗时 1.27–3.89 秒，其中传感器查询 0.34–1.60 秒、JSON 解码 0.10–0.56 秒、来源校验 0.18–1.46 秒、分组/新鲜度检查 0.26–2.00 秒、逐设备渲染 0.34–1.23 秒。数据库中 378 个 `voltage_volts`、378 个 `current_amperes` 和 12 个 `sensor_value` 行在渲染器中无条件跳过，约占 19.7%。这是可证实的高成本路径，但不能单独解释整个 81% 宿主峰值；ARP sweep 的 5 路并发与一处峰值样本重合。Locator invalidation outbox 当时没有待处理行，因此没有据警告日志猜测性调整它的批量或频率。
