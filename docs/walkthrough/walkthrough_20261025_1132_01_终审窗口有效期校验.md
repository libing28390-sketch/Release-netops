# 终审窗口有效期校验

## 完成摘要

最终审批现在要求实施窗口完整、有效且尚未结束。允许在窗口开始前批准，也允许窗口已开始、尚未结束时批准；开始实施仍要求当前时间位于 `[scheduled_start, scheduled_end)`。

截图中的窗口为 2026-10-25 09:32 至 2026-10-30 09:32。审批发生在开始时间之后但结束时间之前，因此应可进入“审批完成”，实施人可在当前窗口内开始实施。

## 关键实现

- 新增 `assert_change_order_window_approvable()`：校验计划窗口字段完整、时间有效且未过期；窗口开始在未来时允许审批等待窗口。
- 最终审批阶段调用该校验。窗口已结束返回 409，提示调整实施时间并重新提交审批，避免出现“审批完成但无法实施”的单据。
- 实际开始实施继续使用原 `assert_change_order_window_open()`，仍会拒绝窗口开始前或窗口结束后的实施。
- 没有为变更工单新增 SLA 计时或默认目标。当前 `ticket_sla_clocks`/SLA 策略实现用于故障工单与服务申请；变更工单有审批、实施时间戳及实施窗口，但没有独立审批 SLA deadline、暂停时钟或超时升级。

## SLA 设计边界与剩余风险

- 推荐把审批 SLA 和实施窗口分开：初审、终审各自从进入待办节点计时，超时提醒并升级责任人，不自动批准或取消。
- 实施窗口仍作为硬性执行边界；窗口结束后调整计划并重新审批。
- SLA 目标分钟数、工作日历和升级对象尚未配置，不在本次臆造默认承诺。
- 开发后端启动时，既有采集器自动同步遇到 SNMP Exporter reload pending / DNS 解析失败；API 健康检查仍为 200。该独立采集问题未在本次变更中处理。服务包含正常只读采集循环，本次未下发设备配置命令、未创建或修改现场工单。
