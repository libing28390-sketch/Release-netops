## 缓存摘要语义

- “本次使用 Redis 缓存”按本次 `cache_provenance` 中至少一个实际 Redis 命中判断。若旧响应没有来源记录，则显示“Redis 使用情况未记录”，不会错误地宣称命中或未命中。
- “数据更新时间”优先用后端 `evidence_collected_at`。该字段在追踪过程中取本次结果证据中最旧的采集时间，作为保守的数据时效基准；不再把当前查询时间当成数据更新时间。只在旧响应没有该字段时，回退到已提供的缓存记录时间。
- 该值是底层证据采集时间，不是 Redis 键物理执行 `SET` 的时间；现有 Redis payload 没有单独保存写入时刻。
- Redis/PostgreSQL/CLI 分阶段来源和 Redis SET 确认仍用于内部计算，但用户卡片不再逐项展示。
- 较早的成功查询详情显示：`S6850-2` 路由为 Redis 命中；`S6850-1/S6850-5` 路由及 `S6850-5` 的 ARP/MAC 有阶段级 Redis SET 确认；整体结果仍是缓存 miss。后续 12:09/12:10 两个 run 没有 Redis read hit，但阶段 SET 获确认，说明“写入成功”不等于本次定位“读取了 Redis 缓存”。
- 12:10 run 的 trace scope 与前一个 run 一致、最终状态为 `completed`、queue 时间为 0；阶段记录显示 route/MAC 从 PostgreSQL 复用、ARP 执行 CLI，SET 回执确认。随后在工作区当前 `.env` 对应的 Redis 查询到 route/ARP keys 且 backend PING 健康，但这是运行结束后的观测，不能证明这些 keys 在 12:10 查询启动前已经存在。整体结果缓存仍未写入确认。

## Redis 时区排查结论

- 主 Compose 的 Redis 服务设置 `TZ: ${TZ:-Asia/Shanghai}`；`.env.example` 也默认 `TZ=Asia/Shanghai`。
- Docker Hub 上 `redis:7.4.2-alpine` 的镜像层记录显示最终镜像安装了 `tzdata`，因此该固定镜像配合 `TZ=Asia/Shanghai` 应能让容器内 `date` 显示上海时间；这不是缺少时区包造成的静态配置问题。[镜像层记录](https://hub.docker.com/layers/library/redis/7.4.2-alpine/images/sha256-54bb38301796028b6c13f560125fe9de3a6c7344af8fa19d80c298f22b84bf78?tab=layers)
- 仍不能据此确认目标服务器当前容器实际时区：目标环境 `.env` 可覆盖 `TZ`，运行中的容器只有 recreate 后才会采用最新配置。
- `redis-cli MONITOR` 的时间是 Unix epoch；`docker logs --timestamps` 由 Docker 加入 RFC3339Nano UTC 时间，两者都不会因容器内 `TZ` 显示为上海时间。
- Redis `TIME` 命令返回 Unix 秒和微秒，不是带时区的本地时间。[Redis TIME 文档](https://redis.io/docs/latest/commands/time/)，[Redis MONITOR 示例](https://redis.io/docs/latest/develop/tools/cli/)，[Docker 日志时间戳格式](https://docs.docker.com/reference/cli/docker/container/logs/)。
- 所以仓库配置目前看不出时区包缺失；实际原因还需检查目标容器的 `TZ`、时区文件和 `date` 输出，才能区分 `.env` 覆盖/容器未重建与对 UTC/epoch 时间的误读。
- 用户随后在 Docker 容器里验证 `TZ=Asia/Shanghai`、`tzdata` 和 zoneinfo 均存在，容器 `date` 输出 `CST +0800`；时区已经确认正确。

## 定位耗时排查结论

- 页面先 POST `/api/ip-locator/runs`，随后每 800 ms 轮询后台任务；后端定位任务默认总预算为 180 秒，页面超时设为 190 秒。页面在排队或执行时目前只显示“正在定位”，不显示当前设备/阶段。
- Redis 连接与 socket 超时默认各 1 秒，失败后打开 30 秒熔断。因此单独 Redis 故障通常不能解释数分钟等待。
- 后台定位会顺序尝试路由、ARP、MAC、拓扑 CLI，并共享每设备/全局 SSH 配额；单次 CLI 等待上限通常为 30 秒，但 Netmiko 兼容配置把连接/认证传输超时下限设为 60 秒、已建立会话超时下限设为 120 秒。设备不可达、认证协商慢、配额排队或同目标 single-flight 等待均可能拖长查询。
- 本次先前确认过设备密码错误、改正后定位成功；这能解释那一次 SSH 认证阶段拖长/失败，但不能单凭它推断后续每次慢查的原因。
- Locator 默认 freshness 为 route/ARP 300 秒、MAC 120 秒、整体结果 120 秒；6 分钟间隔后重新走设备查询符合这些 freshness 设定。较新的两个 run scope hash 相同，但 12:10 run 仍使用 PostgreSQL/ARP CLI 而非 Redis，当前证据不能确定它的先前 Redis key 为何未命中。
- 浏览器侧一次查询先显示 `queued`，约 8.4 秒后得到成功结果；紧接着的第二次约 3.4 秒显示完成，而后台 run 记录实际耗时 1 秒。两次都显示“未使用 Redis 缓存”，所以这个样本里的查询等待不由 Redis 缓存读取耗时解释。
- `/ipam/locate` 当前浏览器 URL 是 `:5400`；仓库 Vite 默认将 `/api` 代理至 `127.0.0.1:5310` (`VITE_API_TARGET` 可覆盖)，当时本机 5310 与 5400 都有监听进程。因此测试精确测到用户给定 URL 的响应，但除非 Vite 运行时 `VITE_API_TARGET` 指向 Docker API，否则不能把后台耗时归因于 Docker `nexora-netops` 容器。
- 工作区 backend `.env` 配置的 Redis health probe 返回 `healthy`、约 `0.29 ms`；这只代表该工作区配置所指向的 Redis，不证明它就是 Linux Docker 主机内 `nexora-redis`。DevTools 的页面域名是 Vite 地址，当前工作区 API proxy 目标默认是本机 backend，因此本次 API timing 不能直接当作 Docker 容器内的耗时。
- 前端 190 秒超时只在 POST/GET 返回后检查；若一个 HTTP 请求本身一直不返回，页面可能继续转圈。
- 仅凭已完成查询截图不能判定目标部署当时处于 queued、running、single-flight 等哪一类，也不能把时区显示问题当作查询慢的根因。

## 建议的只读现场核验

目标机 Redis 容器：

```bash
grep '^TZ=' .env || true
docker exec nexora-redis sh -c '
  printf "TZ=%s\\n" "${TZ-<unset>}"
  apk info -e tzdata >/dev/null 2>&1 && echo tzdata=installed || echo tzdata=missing
  test -r /usr/share/zoneinfo/Asia/Shanghai && echo shanghai_zoneinfo=present || echo shanghai_zoneinfo=missing
  date "+local=%Y-%m-%d %H:%M:%S %Z %z"
  TZ=UTC date "+utc=%Y-%m-%d %H:%M:%S %Z %z"
'
```

定位慢查询可在浏览器 Network 查看 POST `/api/ip-locator/runs` 和后续 GET `/api/ip-locator/runs/{id}`：`queued` 持续时间指向 worker 容量/认领，`running` 且 GET 正常返回则指向追踪/SSH 阶段；如能取得 run ID，再查对应 `locator_runs` 和 `locator_run_tasks` 的状态与 `operation`。不要导出 `.env` 或完整容器环境变量。
