### 确定缺陷 A：不同采集器共享版本文件与运行目录

证据链：

1. `collector_sync_service.py:39-62` 遍历全部启用采集器，也包括停用 LOCAL 以清空目标；不是只处理 collector-local。
2. `monitoring_v1.py:1827-1832` 版本号按每个 collector 独立 MAX+1，输出根目录却相同。
3. `monitoring_compiler.py:1342` 使用 `artifact-v{version}`，路径没有 collector_id；两个采集器的 v1 写同一个目录。
4. `monitoring_v1.py:2036-2045` 对所有可发布采集器使用相同父目录建立 CollectorArtifactStore；没有 REMOTE/EDGE 分流。
5. `collector_artifact_service.py:122-129` 将整个产物同步到共享 current/runtime。
6. `monitoring_compiler.py:1136-1159` 只有 collector-local 包含 platform_hardware_inventory、platform_cadvisor 等本地平台 jobs。

影响：多启用采集器时，不同采集器会相互覆盖目标和运行版本。非默认采集器发布可从磁盘上的 scrape.yml 移除平台硬件及容器 jobs；file-SD 目标文件会被运行 vmagent 周期读取；主配置 job 删除通常在 vmagent 重启或显式 reload 后才体现。默认空库只 seed 一个 collector-local，因此这是条件性缺陷，不能当成所有单采集器新装的必然原因。

最小复现（在仓库 backend 目录执行，仅写系统临时目录，不访问数据库或设备）：

```powershell
@'
import tempfile
from pathlib import Path
from services.monitoring_compiler import compile_artifact, validate_artifact
from services.collector_artifact_service import CollectorArtifactStore
with tempfile.TemporaryDirectory(prefix="nexora-collector-repro-") as temp:
    root = Path(temp)
    first = compile_artifact([], collector_id="collector-local", config_version=1, output_root=root)
    second = compile_artifact([], collector_id="collector-edge-1", config_version=1, output_root=root)

    CollectorArtifactStore(root).publish(first["artifact_path"], config_version=1)
    print("runtime collector:", validate_artifact(root / "runtime")["manifest"]["collector_id"])
'@ | ..\.venv\Scripts\python.exe -
```

实测输出：相同路径为 True，原 local source 及发布后的 runtime 均变为 collector-edge-1。

### 确定缺陷 B：发布没有重载 vmagent 主抓取配置

`monitoring_v1.py:598-606,2040-2045` 只重载 snmp-exporter 后就标 APPLIED；全库没有对应 vmagent reload 调用。`docker-compose.yml:531-537` 没有配置 `-promscrape.configCheckInterval`。

固定版本 vmagent v1.103.0 上游源码 `lib/promscrape/scraper.go:37-45`：主配置检查默认关闭（0），file-SD 文件检查默认一分钟。因而：

- 只变更 snmp_targets.yml 等 file-SD 内容：通常可在下一次 file-SD 检查被拾取；不应错误地称所有目标变更都无效。
- 变更 scrape.yml 中的 jobs、静态目标、relabel、路径等：仅落盘不会自动热加载。
- APPLIED 目前证明 exporter reload 和文件状态，不能证明 vmagent 当前加载了同一套主配置。

上游依据：https://github.com/VictoriaMetrics/VictoriaMetrics/blob/v1.103.0/lib/promscrape/scraper.go

### 启动与健康状态边界

- 应用健康检查只验证存活；snmp-exporter 在 netops healthy 后启动（Compose:480-482）。启动自动同步运行在后台（main:503-505），可能先于 exporter 就绪。失败后周期任务约五分钟重试，不是失败后立即短间隔重试。
- `_bg_init` 的前置初始化若抛异常，会跳过本轮启动同步及尚未启动的遥测循环（main:128-160）；周期同步任务独立注册，仍可补偿发布。未找到干净新库必然触发该异常的证据。
- Docker 默认 WORKERS=1；`deploy-ubuntu.sh:651` 原生部署使用两个 worker。启动与资产触发只受进程内 threading.Lock 约束，只有周期 job 被 PostgreSQL lease 包装；多 worker 初始并发编译有竞争风险，版本 MAX+1 没有原子分配。
- 健康探测使用历史最高 APPLIED（monitoring_v1:440-473,506-535），未对照最新 last_config_version/status；新发布失败时旧配置仍可能被报告为健康。

## 2. 容器资源指标

### 已由源码和用户现场相互印证

用户现场 driver=overlayfs；宿主机 `/run/containerd/containerd.sock` 存在；cAdvisor 日志明确 Docker factory 因容器内该 socket 不存在而注册失败，指标只剩 `id="/"`。

当前 `docker-compose.yml:593-637` 提供 Docker HTTP socket proxy、/sys 和 Docker 数据目录，但没有 containerd socket。cAdvisor v0.60.6 `container/docker/factory.go:331-335` 对 overlayfs 驱动额外建立 containerd 客户端，失败则退出 Docker factory 注册。单独调整 Grafana 或 SNMP 编译不能修复这个失败。

上游依据：https://github.com/google/cadvisor/blob/v0.60.6/container/docker/factory.go

### 当前检查会漏报

- 部署契约测试只断言代理就绪与数据目录挂载，没有 overlayfs/containerd 场景（test_monitoring_v1_deployment_contract:67-90）。
- 压测探测只检查 /metrics HTTP 200（scripts/stress-test-docker-probe.sh:472）。
- 容量场景仅检查响应出现 container_cpu/container_memory（scripts/docker_capacity/runner.py:931-940）。
- 用根目录独有 CPU/内存样本调用该场景的真实 semantic 函数，结果为 `ACCEPTED_ROOT_ONLY_METRICS`。这是已运行的最小假阳性复现，没有发起网络请求。
- Grafana 使用 `{name!=""}` 的命名容器序列（monitoring/grafana/generate_dashboards.py:3245,3263,3281,3303,3314），故 HTTP UP 与宿主根指标存在不代表容器面板有数据。

后续适配需要识别宿主存储驱动与 socket 实际路径，并验证命名容器数。直接提供 containerd socket 属于额外的敏感 API 访问权限；只读挂载标志不等同于限制 RPC 为只读。本审查未改变其权限或挂载。

## 3. 硬件与无线默认本地路径

实际链路：资产关联设备 pending → A-loop 探活变 online → 本地身份/规则发现 → 传感器入库 → 周期采样 → /hardware-metrics → vmagent platform_hardware_inventory → VictoriaMetrics → Grafana。

- main:128-143 启动 TelemetryOrchestrator；orchestrator:248-301 发现名义周期60秒、并发2，采样名义tick10秒、并发4；只选 online 且有IP设备。server另走服务器指标链。
- 资产创建设备初值 pending（assets:1188），后台A-loop更新在线状态；不是创建资产后直接阻塞等待硬件发现。
- 无 discovery 记录时立即到期（snmp_hardware_poller_service:160-174）；规则首轮可从镜像内 backend/vendor/librenms 惰性导入。Dockerfile:45 复制整个 backend；未见发行过滤删除该源包。
- 60秒是调度节拍，不是首次出数上界。发现会等待一轮设备任务完成，SNMP超时与并发2形成排队；还要等待首次采样和60秒的 /hardware-metrics 抓取，不能用“等60秒必有数据”验收。

### 确认的可观测性与恢复边界

1. 凭据解析异常/未配置/invalid_configuration 在 poller:814-846 提前返回，不写 capability 失败记录；硬件 metrics 端点可能200但没有说明这些设备为什么未进入发现。
2. full discovery 的 failed/unsupported 15分钟重试，partial 60分钟；not_found及其他完整结果走24小时（poller:160-174）。零传感器首次结果之后即使外部SNMP权限修正，若没有额外失效触发也可能长时间不重做完整发现。
3. 已有无线scope的刷新另走3分钟/失败15分钟策略，不应把完整硬件发现24小时统一套给所有无线更新。
4. `LIBRENMS_REPO_PATH` 可覆盖规则读取根（librenms_rule_service:98-107），来源信任校验仍固定 backend/vendor/librenms（librenms_source_policy:13）；Docker env_file会透传自定义值，却无对应自定义目录挂载。旧主机路径遗留在 .env 时可能找不到规则或与校验不一致；默认 .env.example 未配置此覆盖，因此仅为条件性风险。
5. `/hardware-metrics` 导出DB最新值，过滤可信来源、当前版本、生命周期与质量；没有 active sensors、样本缺失或不可信均可能无业务数值。端点数据库异常返回503（grafana_metrics:975-1001）。

默认本地 CPU/内存/温度 canonical 名称与dashboard一致；默认本地无线 adapter 的类别和dashboard相符。未发现默认全链路必然写错类别的证据。多collector覆盖共享scrape主配置可使本地DB有值而Grafana无值，但需核对新现场采集器数量和vmagent实际加载配置。

可选 LibreNMS-native 支线另有断链：sync_bound_device_hardware没有运行时调用点，信任过滤不接受librenms_native来源；其无线投影类别亦与当前dashboard过滤不一致。仅影响显式使用该支线的部署，不作为默认本地SNMP现场根因。

## 5. 新部署完成后的最小验收

先确认容器内实际运行的是新实现；再按以下顺序取证，不先用手动编译发布改变现场：

1. 启动日志：初始化、CollectorAutoSync、RELOAD_PENDING、scheduler lock及后台硬件loop是否启动；保存首次启动到5分钟兜底之后的时间线。
2. 数据库只读：monitoring_collectors的id/type/enabled/最新version/status，runtime/manifest的collector_id/version是否相同；不输出凭据表。
3. vmagent当前targets是否同时有network_snmp、platform_hardware_inventory、platform_cadvisor；比较磁盘scrape.yml与实际已加载主配置，不能只检查磁盘文件。
4. cAdvisor日志Docker factory是否失败，/metrics是否有非空name的container_last_seen/CPU/memory；与宿主机运行容器数量核对。
5. 硬件DB：devices.status分布、最新capabilities.status/reason/version、sensors.enabled/lifecycle/last_quality/last_success。有传感器但无good样本时查采样；没有capability优先查凭据和是否被online过滤。
6. /hardware-metrics是否有nexora_hw_cpu_usage_percent/nexora_hw_memory_usage_percent及无线系列；然后查VictoriaMetrics同名序列。后端有而VM无则查抓取/写入，VM有而Grafana无才查变量/labels/查询。
7. VictoriaMetrics只读状态、剩余空间、vmagent remote-write错误/队列也纳入共同下游验收，避免重演存储只读导致的全空。
