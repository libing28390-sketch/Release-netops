# 采集器自动状态探测完成记录

## 完成摘要

采集器列表 API 现在自动探测 vmagent 活动目标；采集器页面每 30 秒静默刷新探测状态。页面把服务运行、配置发布和设备目标抓取分开显示，初始化和首次抓取阶段不再依赖用户手动猜测。运维弹窗也从四个按钮收敛为“编译配置”和“发布配置”两个必要步骤。

## 关键实现

- 后端复用 vmagent `/api/v1/targets`，只统计带 `asset_id` 标签的活动目标，并按健康状态、最近抓取时间和单目标抓取间隔汇总。
- 最近应用配置 manifest 用来区分真正无目标与 file-SD 尚未加载目标；过期抓取按有效采集间隔的 3 倍判异常，支持复合 duration。现场核对发现 vmagent 的 active target 对象未返回 `scrapeInterval`，修正后优先从 `discoveredLabels.nexora_scrape_interval` 读取 SNMP 单目标间隔，再回退到 API interval 或 `discoveredLabels.__scrape_interval__`，最后才使用 60 秒默认值。
- 现场确认 vmagent 有 32 个带资产标签的抓取目标、对应 17 个资产 ID；旧规则标异常的 `generic_system_std` 目标配置周期为 300 秒，vmagent `health=up` 且 `lastError` 为空。旧逻辑使用 180 秒阈值，导致目标在下一轮 300 秒抓取前短暂显示异常。
- 返回状态包括未初始化、配置待同步、服务离线、无目标、等待目标、等待首次抓取、抓取正常、部分异常、失败、未知和停用。错误只返回归一化代码，不回传 URL、原始错误或凭据。
- 页面列表及详情分别呈现服务状态、配置状态和采集探测状态；进入采集器页后每 30 秒无闪烁刷新，详情保持同步。
- 运维弹窗删除手动“状态检查”和独立“配置校验”；前者被自动探测取代，后者的校验已包含在编译和发布校验中。编译与发布仍分开，保留发布前确认。
- “抓取正常”仅指 vmagent 报告目标抓取成功，不代表 VictoriaMetrics remote-write 已持久化。

## 剩余风险与后续建议

- 本次状态依据本地 vmagent 的活动目标抓取结果；不验证 VictoriaMetrics remote-write 最终落盘。
- “新建采集器”目前只在 `monitoring_collectors` 中登记平台记录，不会安装或启动远程采集进程；远程/边缘也没有可用心跳接收链路。本轮保留了创建入口，但建议在真实注册/安装/心跳流程完成前隐藏或禁用该入口。
- 远程/边缘采集器没有可用的活动目标映射或心跳接收链路时仍显示“未知”。
- 当前目标标签不包含 collector ID，因此多个 LOCAL 记录会共享本地 vmagent 聚合状态；当前部署使用 `collector-local`，若以后支持多个并行本地采集器，应增加目标归属标签后按 collector 隔离探测。
- 页面需重新登录后可查看自动刷新后的计数；后端当前已从真实 vmagent `/api/v1/targets` 读到 32/32 正常。
