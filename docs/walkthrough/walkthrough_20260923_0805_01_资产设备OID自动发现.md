# 资产设备 OID 自动发现执行记录

## 完成摘要

已完成设备级 SNMP 身份和 OID 发现链路。当前实现读取 `sysObjectID.0`、`sysDescr.0`，按厂商和平台分类，并按设备实际返回的 CPU、内存、传感器和接口表项选择 OID 与索引。Cisco 使用专用 CPU/内存优先级规则；现有监控 OID 目录中的 Huawei、H3C、Ruijie、Juniper、Fortinet、ZTE、Maipu、DPtech、Hillstone、Sangfor、DCN、Aruba、Ruckus 以及无线模块使用目录驱动的设备级探测。发现记录保存于 PostgreSQL，原生健康轮询和 Monitoring V1 编译都可以消费该记录。

本机 PostgreSQL 现有资产范围为 2 台 Cisco C2960 网络设备，均有 SNMP 凭据；两台原有模板绑定状态为 `unverified`。本次没有把未验证模板当作已确认 OID，也没有修改设备、凭据或模板数据。

## 关键实现说明

- 新增 `snmp_device_discoveries` 表，保存身份、规则版本、发现状态、指标配置、接口能力和 exporter 模块；不保存 SNMP 凭据。
- 新增 243 迁移，将现有 OID 目录中的 20 个硬件/无线模块注册进基线采集计划，避免目录有模板但计划没有入口。
- 新增 244 迁移和 LibreNMS 规则同步服务；本机已从 LibreNMS commit `9831e4e438e438f17445000c872817eb72511b1e` 导入 807 条规则和 6619 个 OID 候选。
- LibreNMS 同步入口现在同时拉取 MIB、OS detection、OS discovery 和 OS 类定义；规则同步完成后，设备发现优先使用 `rule_source=librenms`，无可执行候选时才进入 `builtin_generated` 标准规则。
- Cisco CPU 按 5 分钟新版列、旧版列、1 分钟列、旧式 `avgBusy5` 标量的顺序选择首个返回有效数据的列；内存按增强内存池、传统内存池、CPU 内存表的顺序匹配 Used/Free 同索引；温度、风扇和电源状态也按实际环境表返回结果加入发现配置。
- 其他已存在于 OID 目录的厂商会根据其目录中的 CPU、内存、温度、风扇、电源和无线指标定义逐项探测可用表项，并生成厂商/设备级 exporter 模块；目录外厂商仍不会套用其他厂商 OID。
- 接口发现确认 `ifName`/`ifDescr` 以及 IF-HC-MIB 双向计数器能力，选择 64 位或 32 位计数模式。
- 未验证的模型模板不再直接提供健康采集 OID；没有设备级发现结果时，Monitoring V1 会跳过厂商专用模块，只保留通用 IF-MIB/系统模块。
- 设备级发现结果通过统一解析入口被健康、巡检、WAN 接口和监控编译路径复用；已验证的人工模板仍保留优先级。
- 资产模板导入现在识别 `团体字`、`Community` 等常见 community 表头别名；community 加密失败会显式报错，不再静默写入空值。
- 有设备级发现结果时，Monitoring V1 为该设备生成带哈希的自动模块，避免不同设备的 OID 选择互相覆盖。
- 编译器会比较最新配置 checksum；发现结果和目标未变化时返回 `UNCHANGED`，自动同步不会无意义地持续生成新配置版本。
- 新增 `/api/monitoring/devices/{device_id}/snmp-discovery` 只读接口，返回身份、状态、原因和 OID 发现证据。

## 剩余风险与后续建议

- 真实设备的 SNMP View 可能隐藏 CPU 或内存表，发现状态会是 `partial` 或 `no_supported_oid`；系统会保留通用指标并显示原因。
- Cisco C2960 的实际 sysObjectID 和表返回尚未在本机验证，当前不能把模拟结果当作实机兼容证明。
- 后续增加厂商时，应先读取资产库确认该厂商确实已纳管，再增加该厂商的身份和指标表适配器；未知厂商不会回退到 Cisco OID。
