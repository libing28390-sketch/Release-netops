## IP 对账功能核查

- 页面加载与“重新对账”按钮都调用 `GET /api/ipam/reconciliation`。这个接口读取 `ip_addresses` 中登记的 IP 和 `network_endpoints` 中 `is_active = 1` 的发现记录，在请求时计算差异。
- 三类结果分别是：发现到在线终端但 IPAM 没登记；IPAM 有登记但当前活跃发现表中没有对应终端；两侧同一 IP 的 MAC 或主机名不同。页面提供登记、释放、同步信息等操作。
- 发现侧的 `network_endpoints` 是 ARP/MAC 事实的投影；endpoint tracker 从 `arp_table`、`mac_table` 等现有数据生成终端记录。因此“重新对账”只重算现有数据库内容，不会发起新的 SNMP/ARP 采集。
- 当前浏览器中对账三类统计均为 0，网段页的“活跃发现 IP 数”汇总也为 0。这说明当前可供该页使用的活跃发现结果为空或未能与 IPAM 地址按范围匹配；仅凭这两个页面不能确定底层 ARP/MAC 原始表是否为空。
- 代码另有持久化 run/finding API；发现流程可创建 reconciliation run，但当前对账页面没有调用这些 run/finding API。因此页面显示的是即时计算结果，不是可追溯的持久化对账批次。
- 还有一处语义风险：页面把无活跃发现的地址描述为“长时间不活跃”，服务端却只检查它当前是否存在于活跃 endpoint 集合中，没有按 `last_seen` 做失联时长阈值（仅跳过 Loopback/VIP）。若要启用该功能作为自动回收依据，应先补采集数据可见性和失联阈值，再考虑自动操作。
