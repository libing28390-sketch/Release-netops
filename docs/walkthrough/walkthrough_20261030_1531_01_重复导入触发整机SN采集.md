# 重复导入触发整机 SN 采集

## 完成摘要
修复了重复导入 H3C 资产时整机 SN 采集未被排队的问题。重复行仍保持“跳过、不覆盖资产字段”；符合目标与凭据条件时，会用原资产保存的 SNMP 配置单独刷新机箱 SN。导入反馈显示后台采集状态及跳过原因。

## 根因
资产去重分支只安排主机名同步。提交后，SNMP 身份识别队列再次按本批 `created` 设备过滤，重复匹配到的旧设备因此被排除。新增资产的整机 SN 步骤本身无法覆盖这条重复导入路径。

本机 5400 的运行日志还确认了独立的持久化故障：`data/logs/netops.log` 在 `2026-10-30 15:24:48.064` 记录该 H3C 设备 `Asset chassis serial synchronization failed ... (UndefinedColumn)`，请求 ID 为 `req_df10ab0376d341e38fe5`。同一数据库当时已记录迁移 302/303，`asset_chassis_members` 和 `serial_number_source` 均存在，但 `physical_assets.chassis_observed_at` 不存在。`sync_asset_chassis_members()` 会读取该字段，因此 SN 同步在写入阶段失败。

## 实际修改
- `backend/api/assets.py`
  - 查询重复资产当前的厂商、平台、型号、管理 IP、端口、SNMP Profile、Community 和采集开关。
  - 仅对已登记为 H3C、管理 IP 与 SNMP 端口匹配、SNMP 采集已启用且当前配置存在的资产排队。
  - 导入行未指定 SNMP Profile 时复用原资产当前 Profile；导入行显式指定时要求与原 Profile 一致。该路径不修改原资产管理配置。
  - 重复设备使用 `refresh_existing` 标记穿过两个新建资产过滤点，并按设备去重。
  - SN-only 结果和 pending 状态附到导入行；条件不满足时返回明确跳过原因。
- `backend/services/snmp_import_identification_service.py`
  - 增加 SN-only 刷新入口，避免对旧资产重新执行会自动写入主机名、型号或平台的完整身份识别。
  - 探测地址增加导入项 IP 回退；成员持久化仍由原机箱序列号服务执行，并保留其管理 IP/资产一致性校验。
- `backend/database/migrations/m0304_asset_chassis_observed_at.py`
  - 新增幂等前向迁移 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，修复 302 已记录但 watermark 列缺失的本机 PostgreSQL schema；本机应用记录新增 304。
- `src/pages/AssetManagement/index.tsx`
  - 区分“重复资产正在后台采集整机 SN”和“未采集”的导入反馈，并列出跳过原因。
- `dist/index.html`
  - 本地构建脚本实际使用 Vite 默认 `dist/` 输出，生成构建结果时更新了该跟踪文件；这只是本地构建产物，没有部署。

## 用户现场验证方式与剩余边界
启动本机后端与前端后，重新导入一条管理 IP、SNMP 端口匹配的 H3C 资产。导入结果应提示“正在使用已登记的 SNMP 配置重新采集整机 SN”；后台完成后刷新资产列表查看 SN 或机箱成员。若没有排队，结果会指出 SNMP 关闭、缺少 Profile、管理 IP/端口不匹配或显式指定的 Profile 与原配置不同。

设备侧 `snmpwalk` 返回非空只证明该设备和该命令的凭据能读到 OID；应用端最终结果仍取决于服务进程加载了本次代码、资产保存的 SNMP 配置及服务到设备的网络连通性。若本次重采后仍为空，请提供导入反馈中的 `serial_sync` 状态和脱敏服务日志；本次没有连接用户设备验证。
