# 采集器自动同步提示走查

## 完成摘要

采集器不需要用户在正常启动时手动编译、发布。容器启动后已有自动编译发布，设备状态变化后会触发同步，后台另有每 5 分钟复查。线上日志显示自动编译发布有成功记录。

详情页过去只显示采集器在线状态和配置版本，用户看不到配置发布状态、最近生效时间，也看不到“正常无需手动操作”的说明。现已在本地详情页补充这些信息，手动按钮改为“手动编译/手动发布”。

## 现场证据

首轮启动发生于 2026-10-13（Asia/Shanghai）：

| 时间 | 自动同步日志 |
| --- | --- |
| 22:37:34 | collector-local v1 成功发布，0 assignments |
| 22:42:26、22:47:26 | 自动复查仍为 v1、0 assignments |
| 22:52:30 | v2 自动发布成功，30 assignments |
| 22:57:32 | v3 自动发布成功，30 assignments |
| 22:58:00 | 用户手动编译请求 |

因此，含 30 个分配的配置在手动操作前已由后台编译并发布。日志只能证明分配数从 0 变为 30，不能说明这个变化是由设备状态更新、资产导入完成或其他 CMDB 变化中的哪一种造成，也不能证明资产已全部导入。30 是采集分配数，不是资产数；一台设备可对应多个模块分配。随后重启的日志也显示 06:33 到 06:41 间自动同步从 v4 更新至包含 30 个分配的 v8。

## 源码流程

- backend/main.py 的 lifespan 以后台任务调用 sync_all_monitoring_collectors。
- 同一模块每 5 分钟安排一次定时复查。
- 设备状态变化处调用 trigger_async_monitoring_sync，短暂合并同一波状态更新。
- backend/services/collector_sync_service.py 对启用采集器逐个调用 compile_collector；新配置再调用 publish_collector。配置无变化且已应用时跳过重新发布。
- GET /api/monitoring/collectors 已通过 _safe_collector_view 返回 last_config_status、last_config_version、last_config_applied_at；无需新增后端契约。
- 编译器对普通 SNMP 网络设备读取 devices 表，纳入 status 为 NULL 或 online 的记录；未能解析到 SNMP 凭据/Community 或显式 auth_alias 的设备不会生成 SNMP 分配。服务器采集另读取 physical_assets 中符合条件的 server 资产，并与设备表中的服务器合并。
- 因此，没有进入相应 CMDB 表的资产不会被编译；已导入但状态、SNMP 凭据或匹配的启用采集计划/模块不符合条件的记录也可能没有分配。此次日志未核实导入批次总数。

## 剩余风险

详情显示最近成功发布状态与时间，不是正在运行的同步任务实时状态。自动同步失败会体现在服务日志；collector_sync_service 会记录单个采集器的 FAILED，但启动包装层仍会记录一条通用的自动同步结束消息。若后续需要在 UI 直接显示失败原因，需要单独设计持久化的同步任务状态。
