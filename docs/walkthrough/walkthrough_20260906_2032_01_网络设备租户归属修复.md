# 网络设备租户归属修复执行记录

## 完成摘要

已确认并修复网络设备绑定 403 的根因：资产页面新增/导入链路创建 `devices` 行时没有写入租户，历史 schema 默认值又是空字符串；平台绑定阶段读取到空租户后，与 `admin` 会话的 `tenant-default` 不一致，触发资源范围拒绝。

修复后的数据流为：

```text
登录会话 tenant_id
        ↓
设备创建 / 设备导入 / 资产自动建联
        ↓
devices.tenant_id = 会话租户（忽略客户端 tenant_id）
        ↓
平台绑定继续执行租户与资源范围复核
```

## 实际修改文件

- `backend/api/devices.py`
  - `POST /api/devices`、`POST /api/devices/import` 改为要求 Operator+ 会话。
  - 从认证会话提取非空 `tenant_id`，显式写入 `devices`。
  - 客户端提交的 `tenant_id` 不参与落库；审计主体改用认证用户。
  - 没有租户的真实认证会话返回 403，避免继续创建孤儿设备。
- `backend/api/assets.py`
  - 修复资产 `POST /api/assets`、`POST /api/assets/import` 的 `_create_linked_device` 自动建联路径。
  - 关联设备使用当前认证会话租户写入 `devices.tenant_id`。
  - 保留服务级直调用的兼容行为：没有 FastAPI 会话对象的内部调用使用 `tenant-default`；真实 HTTP 会话缺少租户仍拒绝。
- `backend/database/migrations/m0211_device_tenant_scope.py`
  - 新增 PostgreSQL 迁移 0211。
  - 将历史 `NULL`、空串和纯空白设备租户回填为 `tenant-default`。
  - 设置 PostgreSQL 列默认值 `tenant-default`，并建立租户索引。
  - 可重复执行，不修改已有明确租户的数据。
- `backend/database/schema.py`
  - 将基线 schema 中 `devices.tenant_id` 的新列默认值改为 `tenant-default`。
- `src/hooks/useDeviceFormActions.ts`
  - 新增设备请求使用统一 `authHeaders(true)`。
- `src/hooks/useInventoryImportExport.ts`
  - 旧设备导入请求使用统一 `authHeaders(true)`。
- `backend/tests/database/test_m0211_device_tenant_scope.py`
  - 覆盖历史空值回填、默认值和迁移幂等性。
- `backend/tests/rackvision/test_device_tenant_scope.py`
  - 覆盖四条真实 HTTP 写入路径：设备创建、设备导入、资产创建、资产导入。
  - 覆盖未认证拒绝、无租户会话拒绝，以及客户端伪造租户被忽略。
- `docs/plans/plan_20260906_2032_01_网络设备租户归属修复.md`
  - 本任务实施计划。

## Docker 部署说明

迁移已接入现有版本化 migration runner。将代码构建进后端镜像并启动后，应用初始化会自动执行 `m0211_device_tenant_scope`：

```text
docker compose up -d --build
```

不需要清空 `nexora-pgdata` 数据卷，也不建议手工把现有设备租户重新清空。迁移会自动修复当前已经存在的空租户设备；之后新增和导入的数据由 API 会话租户和数据库默认值共同兜底。

## 剩余风险与回滚

- 本次迁移把历史无归属设备归入现有单租户默认值 `tenant-default`，这是当前 Docker 单租户部署的安全恢复策略。若历史数据实际属于多个租户，应在迁移前根据资产/站点清单建立映射并做人工复核。
- 新增/导入 API 现在要求 Bearer 会话；前端已经补齐认证头，其他直接调用方需要遵守同一 API 契约。
- 回滚代码可回退 API、前端和 schema 变更；已完成的数据回填不建议反向清空，否则会重新引入平台绑定的租户隔离问题。
