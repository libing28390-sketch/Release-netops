## 实际修改文件

- `backend/core/scheduler_lock.py`：异步调度租约获取与释放移到线程，等待取消中的同步操作完成并清理租约。
- `backend/main.py`：请求日志的同步会话查询移到线程，请求上下文仍由请求协程维护。
- `backend/database/core.py`、`.env.example`、`docker-compose.yml`：新增 `DB_POOL_MIN_SIZE`，默认跟随 `DB_POOL_SIZE`，减少每次并发结束后关闭多数连接再重建。
- `backend/api/health.py`：同步资源/数据库路由通过 FastAPI 线程池执行，live 保持 async；资源读接口不执行告警通知，后台采样维持告警同步；告警提交并关闭连接后发送通知，异常日志仅记类型。
- `backend/services/notification_service.py`：先读取并物化所有 webhook/邮件目标、邮件配置，再关闭连接发送，保留租户、分组、通道、语言和返回结果契约。
- `backend/engine/orchestrator.py`：A/B-loop 数据库快照与 B-loop 遥测维护转在线程执行，保持设备协程、并发上限、采集周期值和维护顺序。
- `backend/tests/database/test_scheduler_lock_leases.py`：增加慢锁时事件循环推进与取消清理回归测试。
- 新增 `backend/tests/database/test_pg_pool_reuse.py`、`backend/tests/security/test_request_logging_execution.py`、`backend/tests/monitoring/test_health_resource_execution.py`、`backend/tests/monitoring/test_notification_connection_lifecycle.py`、`backend/tests/monitoring/test_telemetry_orchestrator_execution.py`。
- `scripts/diagnostics/collect_nexora_container_review.sh`：供用户在实际 Linux Docker 主机补充只读配置、统计增量、活动事务摘要、cgroup 与直连/代理 live 请求耗时。本机没有 Docker，仅检查脚本语法。

## 关键实现与协作审查

主 Agent 负责调度、请求中间件、连接池、通知服务、配置与统一验证。Luna 后端执行者只修改 health 和对应新测试，并完成租约取消、请求上下文、连接预算及通知事务顺序的只读集成审查，未发现实质阻塞项。

通知服务的补充审查确认释放连接后没有再次访问连接。对混合通道，SMTP profile 预加载失败会暂存异常、释放连接，先按原逻辑发送 webhook，再按原错误处理路径返回/抛出，避免读取前置意外改变独立通道的发送行为。新增两种 `raise_on_error` 的回归覆盖该分支。

同步线程操作无法被协程取消强制停止，故使用 shield 并等待结果：取消中的 acquire 若最终取得租约，先在线程释放再传播取消；release 同样保证多次取消不会打断清理。owner fencing 与 heartbeat 保留。

psycopg2 的 minconn 也是空闲连接保留数量。新默认每进程保留 16 个、最多 16 个池内连接，加 4 个有界 overflow；当前一个 worker 的连接预算仍最多 20。`DB_POOL_MIN_SIZE` 可降低预建和保留数量，并受池上限约束；默认会增加初始化时的固定连接数，但不会增加原有最高连接上限。

HTTP 资源接口仍返回相同字段、采样并保存资源记录，但不直接写告警状态或发送外部通知。告警状态由默认每分钟执行的后台采样维护，页面读请求不会增加通知等待。

`process_pending_locator_invalidations` 每 2 秒运行、每批最多 50 条，`max_instances=1` 和持久化 outbox 保留。跳过调度会延后处理，不删除待处理事件；本轮未用扩大并发隐藏慢批次问题，也未声称线上 skipped 警告已消失。

补充的采集循环修复只转移 `_db_quick` 物化设备快照与 `_run_telemetry_maintenance` 的同步 I/O。B-loop 仍在前序设备采集完成后等待维护结束，每 12 次成功 gather 后维护；LLDP 告警与 SSH 连接清理涉及共享状态，执行位置保留。取消 await 不会强制终止这些线程，当前 stop_loops 不等待正在执行的线程全部结束；没有新增跨进程调度能力。

## 未执行验证与剩余边界

- 未改前端与 API JSON 契约，不重复执行无关前端构建。
- 未部署，因此不能给出线上修复后的耗时、CPU 或事务年龄下降幅度；部署后用同样 5 分钟脚本复测 Handler、live 请求、事务年龄及定位任务积压。
- 资源告警沿用原有直接通知能力，没有引入持久化投递队列。告警提交后的进程退出或发送失败可能漏一次通知，后续开放告警不会自动重发；多数通道发送失败原本也由通知服务返回失败结果而不回滚状态。本轮不声称增加了可靠投递能力。
- 主机 2 CPU 的高峰争用仍可能存在，线程移出阻塞和连接复用不能替代实际 CPU 容量或慢 SQL 分析。根据下一轮采样再决定具体查询/采集批次优化。
- 用户后续引用的 Nginx/数据库对话审查确认 A/B 采集主循环原先存在同步数据库与遥测维护阻塞，本轮已补充线程隔离；LLDP 告警与 SSH 清理仍在循环上，不能声称已消除全部阻塞。详见 `walkthrough_20261006_2148_01_页面卡顿与PostgreSQL证据审查.md` 的补充修复说明。工作区修复没有部署，不能据此判断远端容器已采用新逻辑。
