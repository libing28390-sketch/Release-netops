## 后续：自动流程与手动发布差异

- compile_collector 在 checksum 不变时直接返回 UNCHANGED；already_applied 仅根据数据库 latest status 是否 APPLIED 得出，未验证 artifact_path/current/runtime 内容或服务实际加载状态。
- sync_all_monitoring_collectors 收到 UNCHANGED + already_applied=True 后跳过 publish_collector。
- 手动 publish_collector 则执行 CollectorArtifactStore.publish，重新复制 current/runtime 并调用 exporter reload。因此数据库保留 APPLIED、运行目录缺失/过旧时，自动流程可能一直跳过修复，而人工发布能重新落盘。它是确认存在的代码缺口，并非已证实的另一台主机现场根因；若版本产物本身缺失，手动发布也可能失败。
- 本机已有运行配置和匹配目标，跳过分支不会产生可见故障。连续成功日志只能证明自动任务被执行，不能单独证明发生了重新发布。
- 用实际函数 AST 在隔离 Python 进程中执行，数据库/compile/publish 均为桩，临时 runtime 目录不存在：DB APPLIED=True 时 publish_calls=0、top_status=SUCCESS、collector_status=UNCHANGED；False 时 publish_calls=1。此模拟验证控制流，不声称做过真实数据库恢复或服务故障注入。
- 模拟 publish 抛异常：collector_status=FAILED，而 top_status 仍 SUCCESS，证实状态汇总会掩盖局部失败。
- 未修改业务代码。建议修复时对跳过分支加入本地产物完整性/版本校验，并将配置应用状态、服务加载状态与设备抓取错误分开；设备 SNMP 超时不应触发重复编译发布。
