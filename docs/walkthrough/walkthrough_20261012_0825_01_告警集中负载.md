## 关键证据

- 监控概览会调用事件同步；前端概览每 5 秒轮询，后端缓存 30 秒；事件列表每 10 秒轮询。因此不能把每次概览请求都算成一次全量同步。
- 关联原为每行单条 UPSERT，新方案 520 条分成 500+20 两条 SQL。稳定内容跳过 UPDATE，减少无意义行版本；每 incident 的 conditional UPSERT 仍可能取得行锁，读写彻底解耦尚未实施。
- `set_alert_state` 在判断提前返回前持久化状态，每次评估至少一个写事务；新建活动事件至少有状态、事件、活动三个独立写事务，另按渠道/profile 入队。采集 async 路径直接执行同步 DB，存在事件循环阻塞。
- 通知队列已有持久化、默认 20 条/批、硬上限 100、行锁和退避；逐条处理并不属于无限并发。通知目标查询随 delivery 与租户用户数放大；队列处理与 API 共享服务资源。
- Compose 已有整体 netops 默认 2 vCPU/2304m、PostgreSQL 默认 2 vCPU/1g；实际部署值未读取，也没有告警专属 worker 限额。本地代码无 CPU 硬限额。
- 前端告警台分页默认 10/最多 100 条，铃铛 limit=40，没有逐条告警触发 HTTP 的路径。无变化通知轮询仍可能引起父组件更新，列为低优先级。

## Docker + Celery 方案评估

用户提供方案后，主 Agent 结合两名只读 Agent 的后端/部署核查与官方文档形成结论：资源隔离方向合理；第一阶段优先独立通知进程复用现有 PostgreSQL outbox，Celery 留作统一任务平台的可选扩展。仅更新本 plan/walkthrough 的建议，未实施新的运行时代码、迁移或部署，未为纯评估重复业务测试。

| 方案点 | 评估及本库证据 |
| --- | --- |
| Docker 限额 | 能限制通知进程自身资源；不是独占/预留 CPU，也不包含共享数据库为它执行 SQL 的负载。主 API、worker、数据库连接/查询和全栈预算需一起约束 |
| Celery 必要性 | `backend/requirements.txt:67-69` 标注 future-use，尚无 Celery app/task 实现；当前 PG outbox 已有 UNIQUE delivery_key、SKIP LOCKED、行租约、重试、attempt 审计，可直接复用 |
| 入队完整性 | `background_monitor_service.py` 的事件写入与 outbox 目前各自提交；要处理已落事件但未入队的故障窗口。Grafana webhook（`backend/api/alerts.py:2261-2268`）和 host resource（`backend/api/health.py`）仍直发，均需纳入异步化范围 |
| 消费所有权 | `backend/main.py:346-350` 每 5 秒在 API scheduler 消费 outbox；独立消费者上线须关闭/门控该任务，避免消耗仍留在 API 中。多 consumer 可由行锁保护，但所有外部投递仍存在至少一次重投边界 |
| Compose 启动 | Dockerfile 无 ENTRYPOINT，command 可以覆盖 CMD；但 `app.celery_app` 尚不存在。worker 必须覆盖 `Dockerfile:96-97` 的 HTTP healthcheck，不能导入主 app 后重启全部后台任务。`scripts/deploy-docker.sh` 已要求 Compose v2 |
| Redis 复用 | `docker-compose.yml:516-557` 使用 allkeys-lru 且 ACL 只允许 cache 命令；broker 的 list 操作/keys 不在权限中。仅增加 depends_on 不会完成适配；部署的 Redis 关闭开关也要重新定义 |
| 并发、限速、优先级 | concurrency=1 限制同时执行，不限制每秒调用；prefetch=1 默认 early ack 下仍可能有额外预取。高优先级不能中断正在发送的普通任务；需专用容量或短、可限时的任务单元 |
| 内存/吞吐 | 384 MiB 仅是实验参数，prefork 有主/子进程开销；worker 若继承默认 DB_POOL_MIN_SIZE=16，会增加数据库端开销。若 1000 次调用每次 1 秒，单消费者理论排空约 16.7 分钟，未计重试；低 CPU 不能代替通知时延验收 |

官方核查：

- concurrency、prefetch 与 ACK 行为依据 [Celery 优化文档](https://docs.celeryq.dev/en/stable/userguide/optimizing.html)；late ACK 需要幂等，不能独自保证外部通知不重复。
- 单 worker rate limit 非跨 worker 全局配额，见 [Celery Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html#Task.rate_limit)；Redis priority 近似而非严格服务优先，见 [任务路由](https://docs.celeryq.dev/en/stable/userguide/routing.html#redis-message-priorities)。
- 短 depends_on 仅等待启动，需 service_healthy 及运行中重试，见 [Compose 服务配置](https://docs.docker.com/reference/compose-file/services/#depends_on)。
- CPU 配额、memory hard/soft limit 依据 [Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)；allkeys-lru 可淘汰持久化队列 key，见 [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/)。

上述为源码及文档评估，不含真实 worker 启动、内存峰值或容器压测；当前环境未找到 Docker CLI，未验证所粘贴 Compose 示例。

## 已确定采用 Celery + Redis 的完整实施清单

用户随后要求将 plan 调整为 Celery + Redis，并直接提供完整任务清单。当前计划已明确该技术方向；上节的“Celery 可选、先直接消费 PG”属于前次评估历史，不再作为现行实施选择。

本次只修改对应 plan 和本记录，没有实施新的运行时代码、迁移、容器或生产变更。目标链路为：告警事件/outbox 同 PostgreSQL 事务 → 独立 Relay → 专用 Redis Broker → 严重/普通两个 Celery Worker → 渠道发送，投递结果和业务重试回写 PostgreSQL。

计划扩展为 **T00～T24 共 25 个任务**，覆盖基线与固定契约、同事务入队、精确领取、迁移/旧积压、发布补偿、ACK/租约/重试、独立 Broker/部署/健康检查、全告警入口、限流聚合、残留计算/数据库/前端热点、观测、集中回归、故障注入、联合压测、灰度和回滚。T02 是原有局部查询补丁；其余实施项保持未执行状态。

关键决策已纳入计划：
- Celery task 只按 delivery_id + dispatch_generation 执行，不能调用旧批量消费者领取其他通知。
- PostgreSQL 唯一负责业务 attempt/backoff/终态；Relay 发布重试和 Broker 重投不单独增加业务 attempt，旧代/失租约写回与虚假审计被拒绝。
- 告警与通知意图同事务覆盖网络告警、恢复、维护解除；Grafana 与主机资源告警一起迁入；验证码/渠道测试另有即时语义。
- 独立严重/普通消费者各 0.25 vCPU/512 MiB，合计 0.5 vCPU/1 GiB；Relay 0.1 vCPU/192 MiB、Broker 0.25 vCPU/384 MiB 另计，均是待压测初值。
- Redis Broker 与缓存分离，使用专用 ACL/noeviction/持久化/背压；CPU 配额不能替代数据库和总栈预算。
- 首批通知隔离和完整整改分别验收；Celery 上线不能代表读写/采样热点已解决。所有部署动作仍需明确授权。

实现期间的可靠性审查确认：Celery 5.6 的 late-ack 失败消息配置会 reject 且不 broker requeue。Relay 因此对已发布但 `attempts=0` 的 outbox 行持续补发，间隔按 60/120/240/480/960/1800/3600 秒递增并封顶；首次 PostgreSQL claim 后，旧代不再补发。数据库测试还验证 Grafana 飞书 webhook 缺失会作为 terminal skipped 记账。严重通知当前严格优先；normal 没有保底发布份额，因此公平调度仍未完成。

针对 CPU 放大路径，incident 的 list/detail/impact GET 默认不再同步全量投影，改由 15 秒一次的单实例调度器刷新；投影刷新时间缺少可信元数据，未声称已提供精确 freshness。LLDP 告警状态按最多 100 项分块，transition state 用 executemany，事件、活动记录和 outbox 意图与状态写入共用该批事务；失败回滚该批数据库行并恢复进程缓存。B-loop 的 LLDP 查询、扫描和批量写入已通过取消屏蔽线程工作离开 asyncio 事件循环。BGP/OSPF/BFD peer 仅从事件循环卸载，仍按 peer 独立持久化，尚未批量化。
