# 自动化备份批次历史与失败告警完成记录

## 完成摘要

- 当前 `/automation/history` 使用的统一执行历史 API 纳入配置备份批次，按批次一行展示设备总数、成功、失败、部分状态和跳过数。
- 批次详情复用 `config_backup_run_devices` 账本和现有分页接口，支持成功、失败、未知、跳过筛选；超过 100 台时继续分页。
- 移除了备份成功读取 running-config 后写入单台 Playbook 历史的副记录，历史状态现在使用备份流程校验、存储及快照入库后的最终结果。
- 失败设备通过现有告警状态生命周期按设备去重；后续最近一次完成的备份成功后自动恢复。跳过设备不会清除失败告警。
- 已知旧版 `Config Backup · ...` 单设备副记录从统一历史列表隐藏；没有尝试按时间猜测其批次归属，也没有删除审计数据。
- 配置备份历史和详情保持只读；详情及导出不包含配置快照正文。

## 实际修改文件

- `backend/services/execution_history_service.py`：统一巡检、Playbook 和配置备份来源，合并后做全局排序和分页；过滤可识别的旧副记录。
- `backend/api/inspections.py`：仅管理员在统一历史查询中获得配置备份批次来源。
- `backend/api/configs.py`：移除单设备副记录写入；批次收尾后根据各设备最近的完成结果更新告警。
- `backend/services/background_monitor_service.py`：告警来源支持 `config_backup`；PostgreSQL 中按设备行锁串行化同设备重叠批次，刷新持久告警状态后再创建/恢复。
- `src/pages/ExecutionSchedule/index.tsx`、`src/pages/ExecutionSchedule/types.ts`：适配批次来源、详情分页和历史导出。
- `src/pages/ExecutionSchedule/components/HistoryList.tsx`：展示配置备份来源和批次汇总。
- `src/pages/ExecutionSchedule/components/ExecutionDetail.tsx`：增加只读的设备结果列表、状态筛选、分页、错误详情和重试加载。
- `src/pages/alertManagementShared.ts`：为配置备份告警增加来源标签；同文件也包含 SNMP 回退来源标签。

## 关键实现说明

- 以既有 `config_backup_runs` / `config_backup_run_devices` 为唯一备份执行事实源，不新增影子表或数据库迁移。
- 批次总状态映射为历史中的 `success`、`failed`、`partial_failure`、`running` 或 `skipped`；单台设备状态仍以设备账本为准。
- 告警 key 为 `config_backup_failure:<device_id>`。失败事件记录批次 ID 和安全原因摘要，不附带原始配置输出或异常全文；成功关闭已有告警。
- 非管理员不会从该统一历史接口看到配置备份批次。既有配置备份接口没有在本次扩大可见范围。

## 剩余风险与后续建议

- 旧的单设备副记录仍保留在底层 `playbook_executions` 表中，因为它们没有可靠批次 ID；统一历史页面只过滤明确标记的配置备份副记录。
- 初次出现大范围设备故障时仍会按失败设备产生独立告警。若实际通知量过大，可在后续增加批次汇总通知，同时保留设备级告警状态供恢复追踪。
- 配置备份批次在该统一历史视图中仅管理员可见；需要扩大角色范围时，应先定义与设备/资产作用域一致的授权规则。
