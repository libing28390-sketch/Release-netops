## 精确 MIB 查询计划

对照 `backend/services/snmp_hardware_probe_service.py::_resolve_mib_symbol` 的实际过滤、join、vendor 排序及 `LIMIT 8`，在生产库使用参数化只读连接执行了 `EXPLAIN (FORMAT JSON)`，没有使用 `ANALYZE`：

```sql
SELECT n.oid, m.vendor, n.node_name
FROM snmp_mib_nodes n
JOIN snmp_mibs m ON m.id = n.mib_id
WHERE m.is_active = 1
  AND LOWER(n.node_name) = LOWER(?)
  AND TRIM(COALESCE(n.oid, '')) <> ''
ORDER BY CASE
  WHEN LOWER(TRIM(COALESCE(m.vendor, ''))) = LOWER(?) THEN 0
  WHEN LOWER(TRIM(COALESCE(m.vendor, ''))) = 'standard' THEN 1
  ELSE 2
END, m.name
LIMIT 8
```

计划顶层为 Limit → Sort → Hash Join；`snmp_mib_nodes` 分支明确为 `Seq Scan`，过滤 `lower(node_name) = 'ifname'`，估算扫描成本约5323、匹配336行。现有 `idx_snmp_mib_nodes_name(node_name)` 不支持此表达式谓词。新采集 helper 已加上同一固定查询的无 `ANALYZE` 计划探针，用于后续观测验证。

## 设备规模边界

生产汇总为17台设备、15台 SNMP 绑定设备、5,296个 active hardware sensor。设备规模远低于用户提出的300台，因此不能以当前远端采样验证300台承载能力，也不能把5,296个传感器等同于独立 SNMP 包。代码审查显示 native B-loop 按在线设备轮询，过期硬件发现会触发 MIB 符号解析；300台在约60秒 sleep 周期之外，单轮工作是否能按时完成还取决于接口/sensor 数、SNMP RTT、超时设备和发现并发。

本机隔离 PostgreSQL 已完成密度校准测试：300台在线设备中264台绑定 SNMP、36台无绑定；用 PostgreSQL `generate_series` 创建93,192个传感器（353/绑定设备），SNMP walk 全由 fake 提供。真实 telemetry B-loop 与 hardware inventory poller 单轮耗时143.799秒；264次 fake walk；186,649条 SQL，其中每个传感器一次 `SELECT ... FOR UPDATE` 和一次 `UPDATE`。这两类样本 SQL 合计118.712秒（锁定查询33.761秒、更新84.951秒），占主要数据库耗时；Windows 并发上限2。测试不包含自动 MIB discovery 或完整 `process_device_slow`，也不连接真实设备。此周期是本机隔离环境实测，不能直接外推到生产 Linux 服务器。

为减少逐传感器 SQL 往返，新增 `record_sensor_samples_batch` 并接入硬件 inventory poller。同一规模重新执行后，93,192个样本全部成功，单轮周期26.142秒；总 SQL 从186,649条降到529条，样本写入从每个传感器的锁定查询加更新改为每台绑定设备一条批量 UPDATE（264条），未发生逐样本 `SELECT FOR UPDATE`。批量更新 SQL 累计12.464秒。相较基线，本机该轮周期缩短81.8%、SQL 数减少99.7%、样本 SQL 时间减少89.5%。测量仍使用Windows并发上限2与fake SNMP，不覆盖自动 MIB discovery/完整 `process_device_slow`；结果不能作为生产耗时承诺。

首轮低密度基线曾把5,296个 sensor 摊到300台，周期9.415秒；该场景只用于观察设备循环开销，已由以上贴近生产密度的结果替代作为容量基线。
