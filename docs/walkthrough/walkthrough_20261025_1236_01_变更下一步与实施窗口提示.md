- 用户明确申请人可以实施自己的变更。移除前端 `canCurrentUserImplement/isEligibleImplementer/claim` 中额外的申请人排除条件；保留审批身份分离、执行角色/权限、窗口、MFA 和内容快照约束。后端原本没有禁止申请人兼实施人，没有扩大设备执行权限。
- 原控制表 `co_reviewer` 复用为可选“复核人”，可以选择实施人之外的任何有效用户。移除提交时的必填要求；填写时校验存在、有效、组织范围及与实施人分离。不新增重复字段或数据库迁移。
- 接通实施后结果审核，独立于实施前审批，不签发新执行 token。未选择复核人时保留原验证及关单流程。

## 流程及接口

`POST /api/change-orders/{id}/result-review`，body 为 `{action, summary}`，summary 必填。每次记录 actor、时间、意见、前后状态和审批快照并写审计。

| 当前状态 | 动作/人员 | 后续状态 |
| --- | --- | --- |
| implementing / failed | 指定实施人 submit；现有技术/业务验证门禁需通过 | implementation_review |
| implementation_review | 指定复核人 pass | completed，关单 |
| implementation_review | 指定复核人 fail | implementation_result_review，原初审人待办 |
| implementation_result_review | 原实际初审人 accept | completed，关单 |
| implementation_result_review | 原实际初审人 reject | failed，退回实施人处理 |

原初审人优先使用实际 `initial_reviewer_id`，缺失时兼容指定初审人。指定复核人可以是 Viewer，不要求 command.execute；只授予该单读取和审核自己的阶段，不授予更新、执行或任意审核权限。新状态只允许专用结果审核接口流转；旧 transition 完成、新状态重执行、审核中改附件/工单/指派均不能绕过审核。审核不受实施窗口结束影响，但执行仍受窗口约束。

结果记录：`result_detail.result_reviews[]` 包含 action/summary/actor_id/actor_username/created_at/from_status/to_status/approval_snapshot_hash；`result_review_summary` 为最近说明，`result_review_snapshot_hash` 绑定当前提交内容。原实施前审批状态和 token 不被重新授权。
