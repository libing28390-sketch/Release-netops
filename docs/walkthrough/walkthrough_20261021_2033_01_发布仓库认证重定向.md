# 发布仓库认证重定向修复

## 完成摘要

修正 Ubuntu/Linux 发布步骤访问 Release-netops 时的 GitHub HTTP 认证方式。之前把 `RELEASE_REPO_TOKEN` 放入 remote URL；GitHub 返回仓库地址重定向后，Git 再尝试交互式读取 Username，CI 无 TTY 因而以 `No such device or address` 退出。现改为无凭据的固定 remote URL，将 masked Basic Authorization header 仅传给 GitHub push 命令，并复用到可选版本标签 push。

此修改解决 URL 重定向时认证头缺失的路径；若 Actions secret 无效或没有目标仓库写权限，workflow 仍会明确失败。

## 实际修改文件

- `.github/workflows/release.yml`：token 从 job shell 中显式环境传入；检查为空并生成/遮罩 Basic header；remote URL 不含凭据；main 和 tag 的 push 命令都显式附带 GitHub HTTP extraheader。
- `backend/tests/release/test_release_repo_push_auth_contract.py`：锁定上述 Secret 注入、遮罩、无凭据 URL、主分支与 tag header 及缺失 Secret 检查。
- `docs/plans/plan_20261021_2033_01_发布仓库认证重定向.md`
- 本 walkthrough 与 `docs/fixes/fix_20261021_2033_01_发布仓库认证重定向.md`

## 复现与修复证据

- 原 Actions #748 第一次和第二次尝试都通过了后端和前端门禁，最后在 Release-netops push 失败：`warning: redirecting to ...Release-netops.git/`，接着 `fatal: could not read Username for 'https://github.com'`。
- 发布 Secret 的配置项存在；其值不读取、不显示。
- 匿名 `git ls-remote https://github.com/libing28390-sketch/Release-netops.git HEAD` 成功，确认目标 read URL 可解析、公开读操作正常；这不证明 token 的写入权限。
- 新建的纯静态发布契约测试：1 passed。
- 提取 workflow 对应 bash step 并运行 Git for Windows bash `-n`：exit 0。Windows system32 中的 bash 启动器返回 WSL 错误码，因此使用安装的 Git Bash 完成检查。
- `git -c http.https://github.com/.extraheader=... config --get-urlmatch http.extraheader https://github.com/libing28390-sketch/Release-netops.git`：返回匹配认证头，验证 Git URL 配置匹配规则。

## 发布验证

代码与契约测试提交到 main 后，需查看该精确 SHA 的 Build and Sync to Release Repo 工作流。验收要求 Linux gate 完成、Commit sanitized Ubuntu release tree 成功、目标 Release-netops main 更新到本次同步；仅源 main push 成功不表示发布仓库同步完成。若仍认证失败，核查 Actions Secret `RELEASE_REPO_TOKEN` 的有效期与目标仓库 Contents 写权限，不要将 token 写入 URL、日志或本地文件。

## 未验证项与回滚

当前记录在本修复提交和对应 Actions 运行完成前不会宣称目标仓库已更新。没有读取真实 Secret 值或直接向目标仓库推送；最终端到端授权验证由 Actions 执行。正常 revert 本修复提交即可回滚 workflow 与契约测试。
