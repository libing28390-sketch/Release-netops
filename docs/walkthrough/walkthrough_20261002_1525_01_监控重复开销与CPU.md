## 日志证据与判断

输入为用户提供的 `docker-diagnostics-20261002-150958.tar.gz`，安全解包到 `artifacts/docker_log_bundle_20261002_150958/`。附件内容仅作为诊断数据。解包限制成员数量、总大小及目录边界，不执行附件代码。

- 数据库 raw log 达到 20000 行上限，实际只覆盖约 14:38–15:09 CST；其中 **1427 条 ERROR 均为 integer = boolean**。这个 tail 没有计数溢出和拓扑主键错误，不能据此判断原日志中的两个缺陷已经恢复。原日志另有 624 条计数溢出、16 条拓扑主键错误。
- vmagent 与 SNMP exporter 各 496 行是**同一批 496 次失败**，不能加为 992 次。两台目标每台 240 次 IF-MIB 失败（约 30 秒周期）及 8 次 system 失败（约 900 秒周期）；均为 SNMP request timeout after 2 retries，exporter 的 HTTP 500 被 vmagent 再次记录。此链路的默认 socket timeout 为 3 秒，与应用 LLDP 的 30 秒整轮 walk 不是同一参数。
- netops 的 120 条匹配错误是同一 Linux 主机的 SSH/22 失败，每约 60 秒一次。该行为单独不能解释 80% CPU；日志还有 `/hardware-metrics` 的慢请求，但没有函数 CPU 栈，不能把请求耗时直接换算为 CPU 占用。
- 采样时 netops CPU 79.98%、436.1 MiB/2 GiB；exporter CPU 1.11%、vmagent 0.27%、数据库 28.81%。因此需要独立定位 netops 进程与线程。
- 11 个容器都 running、OOM=false、Exit=0、Restarts=0，local 日志轮转 10m × 3 已生效，events 文件为空。这是采样时状态，有限事件历史不能排除更早的 OOM；当前资料没有证明 OOM。

详细逐条关联保存在 `artifacts/collector_error_correlation_20261002.md`；循环调用链分析保存在 `artifacts/cpu_loop_audit_20261002.md`。早期三类 SQL 错误的原始审计为 `artifacts/error_log_audit_20261002.md`。

## 实际修改与行为

### MIB 查询与规则范围

- `backend/services/librenms_rule_service.py`
- `backend/services/snmp_hardware_probe_service.py`
- `backend/tests/snmp/test_identity_probe_scope.py`
- `backend/tests/snmp/test_snmp_hardware_probe_service.py`（两个旧 mock 接受 cache 参数，保留断言）

两处 `snmp_mibs.is_active = TRUE` 改为 INTEGER 契约对应的 `= 1`。先检查条款的系统条件、支持状态和主动 SNMP 探测资格，再解析符号 OID。保留原 clauses，避免未满足条件的规则误走 platform fallback。主动探测要求纯 SNMP 条款有已知 vendor；规则解析仍允许未知 vendor 配合已有 SNMP 证据。单次调用内缓存重复 token，跨调用立即看到 MIB 激活/禁用；字符串索引保留大小写。

### 自动发现重复开销

- `backend/services/background_monitor_service.py`
- `backend/tests/monitoring/test_discovery_retry_guard.py`

仅自动 OID discovery 使用重试保护。失败退避 120/240/480/900 秒；发现完成但无 hardware_category_results 时 900 秒再试。签名包含设备、SNMP 地址/端口/版本、凭据摘要、身份/profile、规则版本，变化立即允许重新发现；同签名 in-flight 去重。采用 monotonic、锁、过期清理及 256 条容量限制，不保存明文凭据。普通 Ping、指标、接口、现有传感器轮询及手工发现继续。保护状态随进程重启清空。

### 计数器存储与基线顺序

- `backend/database/schema.py`
- `backend/database/migrations/m0262_interface_packet_counter_numeric.py`
- `backend/tests/database/test_m0262_interface_packet_counter_numeric.py`
- `backend/services/background_monitor_service.py`
- `backend/services/snmp_counter_service.py`
- `backend/tests/monitoring/test_interface_sample_commit_order.py`

raw packet totals 及 HC 错误计数使用 NUMERIC(20,0)，覆盖三个 unsigned Counter64 的求和；单独 Counter32 错误/丢弃值使用 BIGINT；1m SUM 字段使用无 precision 上限的 NUMERIC。新表、补列和既有数据库迁移一致。迁移检查 catalog，重复 upgrade 不再 ALTER；downgrade 先核查所有值的 INTEGER 范围，拒绝截断。

raw batch 与已配置的持久化基线通过同一连接、同一事务提交；提交后才更新内存基线。raw、基线写入或 commit 任一失败均回滚并传播到已有采集失败处理，内存基线保留上次值。`save_interface_counter_sample` 新增可选调用方连接参数：有连接时不吞错误、不自行提交/关闭；原独立调用模式保持兼容。

### 拓扑 NULL 接口幂等

- `backend/services/topology_graph_service.py`
- `backend/tests/topology/test_topology_graph_null_ports.py`

沿用 NULL/空字符串等价的事实匹配，复用任意已有同事实边的主键，使用 ON CONFLICT(id) 更新，避免 PostgreSQL nullable 自然唯一键漏判后发生主键异常。自动关系按 relation_type 区分，手工关系仍优先保留，反向匹配保留持久化端点方向。更新条件校验 tenant、端点、接口和关系，自定义 ID 跨事实或跨租户冲突会拒绝并回滚。effective edge ID 确定后才标记缺失事实 stale，防止 legacy ID 被误标；同 tenant 的图投影事务使用 advisory lock 顺序执行，不删除旧数据、不修改原唯一约束。
