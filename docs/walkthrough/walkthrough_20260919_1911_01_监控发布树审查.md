## 结论

建议先处理数据真实性和权限边界，再推进告警生命周期可靠性，最后处理规模与前端一致性。本次归纳出 6 项 P1、3 项 P2。P1 表示应优先修复的生产正确性/隔离问题，不表示已在真实部署发生事故。

### R1 — P1：监控读写的租户隔离不完整

- 报表接口虽然要求 Viewer，但未使用 `_user` 的租户范围；服务直接查询全量设备和接口。多租户部署中，普通 Viewer 可以从报表读取其他租户的设备名、管理 IP、接口和遥测。导出路径同样受影响。
- Incident 列表不传用户范围；resolve 只要求 Operator，按事件 ID 更新事件及其关联告警，没有核对关联设备归属。因此其他租户的 Operator 也可能关闭该事件。
- overview 查询全网设备并使用单一缓存；仅给设备详情加范围校验不足以保护汇总/下钻。
- 已核对全局 `enforce_api_access`：它提供默认角色认证，不提供行级租户过滤。因此这里是已认证用户的对象范围缺失，不是匿名访问问题。
- 建议：让列表、详情、写操作、导出共同使用 tenant/site/device-group 范围；在 SQL 执行前过滤，并将缓存按授权范围分键。Incident 写入需连同关联设备和告警在事务中检查权限。
- 证据：[报表路由](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/api/monitoring_v1.py#L1441-L1496)、[无范围的查询](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L154-L164)、[Incident resolve](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/api/monitoring.py#L1693-L1702)、[实际更新](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_incident_service.py#L563-L585)、[overview](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/api/monitoring.py#L410-L443)。

### R2 — P1：出口报表返回硬编码健康指标及虚构出口

- `fetch_outbound_report_data` 只查目标配置，不查探测结果，却给每个目标固定返回 12.4 ms、0% 丢包及 NORMAL。
- 目标为空或查询抛错时，会补出两个示例出口：WAN-01/02，延迟 8.2/15.6 ms，均显示正常。
- 影响：未采样、失败或无配置均可能被表现为真实正常数据，且同一路径还用于下载报表。
- 建议：从 `outbound_probe_results` 与运行批次读取真实数据，定义统计窗口和成功/失败样本数；空配置显示空态，采集/查询失败显示 unavailable，示例数据不得进入生产返回值。
- 证据：[固定指标](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L510-L549)、[虚构出口](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L552-L583)。

### R3 — P1：接口报表会把不同端口的指标关联到同一个值

- VM 查询结果写入映射时优先使用 `hostname:ifIndex`，同时反复覆盖设备级的 `mapping[hostname]`。
- 报表查询时使用 `hostname:interface_name` / `ip:interface_name`，找不到便回退设备 hostname。
- 正常同时带 ifIndex/ifName 的序列因此会走设备级回退：同设备多个接口被填入最后遍历的接口数值。重复 hostname 还会扩大冲突范围。
- 影响：流量、错误/丢弃率以及容量风险判断均可能错配。
- 建议：使用稳定的 `asset_id + ifIndex` 关联，CMDB 的 ifName 仅作为显示/别名信息；禁止对端口指标使用设备级值回退。
- 证据：[映射构造](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L79-L88)、[读取与回退](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L220-L231)。
- 已隔离复现：源端口值 [100, 200]，报表得到 [200, 200]。

### R4 — P1：缺失/无效样本被当作正常，并可能推进告警恢复

- 报表 VM 查询异常返回空字典，缺失流量、错误率随后变成 0，仍生成 NORMAL/健康正常和当前 sample_time。
- 后台接口告警把缺失的 `error_rate_pct`、`bw_in_pct/bw_out_pct` 也转换为 0。首次基线、计数器异常或部分采集缺失时，这些派生指标可能根本未计算成功，但仍进入恢复分支；默认 recovery threshold 为 1。
- 影响：监控自身丢失观测能力时，可能把已有故障显示/通知为恢复。
- 建议：统一 `value / sampled_at / collected_at / quality / source` 契约，区分 0、no-data、stale、invalid；仅明确有效的恢复样本推进状态机。保留最后一次已知值时必须同时标记陈旧，不能把响应生成时间冒充采样时间。
- 证据：[查询异常吞并](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L72-L92)、[默认零值与正常评级](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_export_service.py#L220-L246)、[告警评估](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L1667-L1707)、[恢复阈值](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L908-L920)。
- 已隔离复现：VM 超时后两个接口均返回 in_bps=0、alert_level=NORMAL。

### R5 — P1：维护期结束后，仍异常的告警不会自动解除抑制

- 维护期间告警写为 suppressed，并保存在 open_alerts 中。
- 到期恢复函数 `reopen_expired_suppressed_alerts` 在发布树中仅有定义，无调用；现有循环/调度也没有接入该函数。
- 故障持续时不会重新进入创建告警分支，而 Incident 聚合明确排除 suppressed。因此到期后问题可能继续隐藏且不重新通知。
- 建议：接入有幂等/并发保护的维护到期任务，在重新确认当前观测后更新状态、记录审计并按 `notify_on_reopen_after_maintenance` 派发通知；覆盖窗口重叠和取消情况。
- 证据：[维护抑制路径](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L922-L944)、[未接入的到期恢复函数](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/alert_maintenance_service.py#L554-L594)、[Incident 排除条件](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/monitoring_incident_service.py#L118-L133)。
- 验证：全树搜索函数名只命中函数定义；未执行真实调度。

### R6 — P1：告警通知发送失败缺少可靠重试

- 实际发送前先设置 webhook_last_sent，然后通过未持久化的异步任务发送。
- 分发失败只写日志并返回，结果未进入重试队列；告警持续 active 时，后续采样不会再次进入初次打开/通知分支。
- 影响：首次通知碰到超时、5xx 或进程退出时，该次告警通知可能丢失，持续异常不会自动补发。
- 建议：使用持久化 outbox，记录事件/渠道、幂等键、尝试次数、下次重试时间和投递结果；退避重试，成功后才记成功节流状态，同时监控通知积压和失败率。
- 证据：[节流和异步发送](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L838-L882)、[仅初次打开通知](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L922-L955)、[发送结果只记录日志](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/notification_service.py#L679-L703)。

### R7 — P2：包/错误计数器缺少与字节计数器相同的回绕处理

- 错误、丢弃和 packet totals 增量使用 `max(0, current - previous)`，无法区分 Counter32 回绕、设备重启、OID 缺失或切换。
- SNMP packet 采集存在从 HC 退回 Counter32 的路径，回绕可使分母归零/错误率被低估，与 R4 结合还会误恢复。
- 建议：对所有累积计数器复用位宽感知的增量计算，携带来源 OID、位宽、uptime/discontinuity；无法解释的样本记 invalid。
- 证据：[错误率增量计算](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/background_monitor_service.py#L1576-L1591)、[packet 采集回退](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/services/snmp_service.py#L2681-L2711)。

### R8 — P2：报表切换条件时旧响应可覆盖当前结果

- `fetchData` 随标签/筛选改变发起请求，但没有 AbortController 或请求代次。
- 每个响应都调用 setReportData，旧请求的 finally 也可提前关闭新请求的 loading。
- 触发：先请求接口报表，再切设备报表；旧响应较慢时，当前设备标签下可能显示接口报表的数据。
- 建议：取消旧请求并用请求代次保护数据、错误与 loading 写入；响应应携带/核对对应查询上下文。
- 证据：[fetchData 与 effect](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/src/pages/MonitoringReportsPage.tsx#L119-L166)。

### R9 — P2：健康下钻超过 200 台时静默截断

- 前端固定 limit=200；服务端同时返回截断 items 和完整 total，但页面只保留 items，并以 items.length 显示设备数。
- 影响：规模较大时，概览里的故障设备无法全部下钻看到，且没有“仅显示部分”的提示。
- 建议：保留并展示 total，提供服务端分页或游标；切换条件取消旧请求，列表与概览使用同一授权/健康筛选语义。
- 证据：[固定上限](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/src/hooks/useMonitoring.ts#L151-L171)、[丢弃总数](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/src/components/MonitoringCenter.tsx#L475-L486)、[显示截断条数](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/src/components/MonitoringCenter.tsx#L1407-L1423)、[服务端返回](https://github.com/libing28390-sketch/Release-netops/blob/56d25aff85859bba427a7026cd6c8b542aa1867e/backend/api/monitoring.py#L1435-L1439)。

## 架构与工程建议

1. **收敛指标口径**：已有 native/shadow/VictoriaMetrics provider 抽象，但报表绕开它直接拼原始 PromQL。让页面、报表、告警共同消费有稳定标识/单位/质量/时间戳的指标契约。未知速率不要默认 1 Gbps 后计算利用率。
2. **把告警当作持久状态机**：将采样有效性、抑制/解除、恢复迟滞、确认/关闭、投递状态放入清晰的事务和重试流程。优先保证缺数据不会报恢复、窗口结束不会永久静默。
3. **按规模设计查询**：报表目前先全量查询、全网 VM 查询，再 Python 过滤和前端切页。列表应先按权限和筛选在服务端分页；大规模导出使用独立异步任务与受限资源。
4. **明确 Grafana 的授权边界**：当前 Compose 默认关闭匿名访问、要求管理员密码且 Grafana/VM 不直接映射宿主端口，这些配置合理。Grafana 自身账户/组织和 Nexora 租户是否一致仍应专项设计；前端筛选变量不能替代数据源授权。
5. **验收顺序**：先双租户读写隔离、真实出口数据与接口指标关联；再无数据/重启/回绕、维护到期、通知重试；最后并发响应和超过 200/500/5000 台的列表行为。
