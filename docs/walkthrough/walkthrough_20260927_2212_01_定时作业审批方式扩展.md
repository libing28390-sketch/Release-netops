# 定时作业审批方式扩展 Walkthrough

## 完成摘要

- 定时作业创建、编辑、重新启用和删除审批新增用户可选的 MFA 动态码、邮箱验证码、飞书验证码。
- 审批人列表只返回当前租户内已启用且配置了至少一种可用验证方式的管理员/操作员，不暴露邮箱、MFA 密钥或飞书 webhook。
- 邮箱方式复用现有 SMTP 邮件服务；MFA 使用审批人账户当前启用的 TOTP；飞书继续使用已有 webhook。
- 审批 token 绑定发起人、审批人和业务类型，验证接口要求登录，消费时继续检查操作者和类型并保持一次性使用。
- 对一次性执行计划，编辑、重新启用和删除审批使用 `execution_plan`，与后端既有类型要求一致。

## 根因与实现

原审批服务只支持飞书验证码，定时作业页面没有验证方式选择，邮箱与 MFA 能力未接入审批流程。审批验证码本身保存在进程内的短期 token 记录中，因此本次沿用 5 分钟期限、最多 3 次失败和消费后移除的现有语义。

新增安全的审批人列表接口，按当前会话的租户筛选审批人，并为每个人返回可用验证方式集合。前端在创建/编辑和删除流程中按审批人显示 MFA、邮箱、飞书选项；切换审批人或方式时会清除前一轮 token、验证码、倒计时和验证状态。MFA 申请返回 token 后由审批人提供当前 TOTP 动态码；邮箱和飞书申请则发送 6 位随机验证码。

后端不信任前端提交的可用方式：请求时重新读取审批人的账户和租户信息、确认方式仍然可用；邮箱发送失败时删除刚建立的 token。验证和审批消费检查当前会话用户及审批类型，未找到申请人时拒绝创建审批记录。

## 剩余风险与部署确认

- 运行时依赖数据库中审批人账户状态、TOTP 配置、邮箱以及启用的租户/全局 SMTP 配置。当前只做静态构建检查，未对真实 SMTP 或 TOTP 流程发送验证请求。
- 飞书 webhook 发送、邮箱送达、MFA 校验和完整定时作业审批闭环需在目标环境部署后由实际审批人确认。
- 审批 token 仍保存在单进程内存中，应用进程重启会使未完成申请失效；这是原有实现的限制，本次未引入持久化或 Redis 存储。
