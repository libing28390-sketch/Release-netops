# NetOps Workspace Rules

## 1. 计划与执行记录文档归档规范
*   **实施计划 (Implementation Plan)**：以后针对任务生成的任何实施计划，必须保存在工作区的 `docs/plans/` 目录下（若目录不存在则自动创建）。文件名必须包含时间戳、序号和任务名，格式为 `plan_YYYYMMDD_HHMM_NN_[任务名].md`（例如：`docs/plans/plan_20260713_0930_01_多厂商诊断.md`）。
*   **执行结果与验证报告 (Walkthrough / Verification Report)**：针对任务生成的执行结果、验证报告及走查记录，必须保存在工作区的 `docs/walkthrough/` 目录下（若目录不存在则自动创建）。文件名必须与对应计划使用相同时间戳、序号和任务名后缀，格式为 `walkthrough_YYYYMMDD_HHMM_NN_[任务名].md`（例如：`docs/walkthrough/walkthrough_20260713_0930_01_多厂商诊断.md`）。
*   **时间戳与序号规则**：`YYYYMMDD_HHMM` 使用当前工作区时区的创建时间；`NN` 为同一分钟内的两位序号，从 `01` 开始递增。若同一分钟内创建多个归档，必须检查已有文件并使用下一个可用序号。
*   **任务名规则**：任务名应简短、稳定、可读，优先使用中文业务名称；删除或替换路径分隔符、冒号、引号、星号等不适合文件名的字符；避免使用“修复”“优化”等过泛名称单独作为任务名。
*   **触发条件**：凡涉及代码修改、数据库迁移、跨前后端接口、网络设备适配、部署发布、批量数据处理或用户明确要求“生成计划/记录”的任务，执行前必须先创建或更新对应 `plan_*.md`。纯咨询、只读排查、状态查询、极小文案修改可不生成计划，但最终回复中需说明未归档原因。
*   **计划文档最小结构**：`plan_*.md` 至少包含任务目标、现状/问题、影响范围、拟修改文件、实施步骤、验证计划、风险与回滚思路。跨 Agent 任务还必须记录分工边界和共享文件归属。
*   **完成文档最小结构**：`walkthrough_*.md` 至少包含完成摘要、实际修改文件、关键实现说明、验证命令与结果、未执行验证及原因、剩余风险/后续建议。若任务被中止或阻塞，也必须记录阻塞原因和已完成检查。
*   **一致性要求**：同一任务的计划和完成文档必须使用相同的 `YYYYMMDD_HHMM_NN_[任务名]` 后缀；最终交付给用户时应引用对应 `docs/plans/` 与 `docs/walkthrough/` 文件路径。若执行过程中计划发生明显变化，应同步更新计划文档，而不是只在最终报告中补充。
*   **命名冲突处理**：若同名计划或完成文档已存在且属于同一任务，优先更新原文件；若是新任务或同名任务的后续批次，则使用当前创建时间和下一个可用序号生成新文件。历史旧格式文件不强制重命名，除非用户明确要求整理归档。
*   **例外情况**：除了上述归档规范，严禁向版本控制中提交个人私有的 markdown 笔记或文章，避免污染公有仓库。

## 2. 数据库选用规范
*   **PostgreSQL 绑定**：本系统在生产和部署环境一律采用 **PostgreSQL** 作为核心关系数据库。在进行数据库设计、编写 SQL 语句以及事务加锁时，应严格遵循 PostgreSQL 标准与规范（例如使用 `FOR UPDATE` 进行行级锁定，避免采用特定于 SQLite 的独立机制）。

## 3. 项目 Skills 路由

项目级 skills 位于 `.agents/skills/`。任务匹配时按以下专业领域与职责路由：

- `netops-backend`：FastAPI、Service、鉴权、调度与后端接口。
- `netops-frontend`：React、TypeScript、页面、组件、hooks 与状态管理。
- `netops-network-drivers`：多厂商 SSH、SNMP、CLI 执行、基础解析与多厂商规范化。
- `netops-data-migrations`：PostgreSQL 表结构、迁移、索引、事务与回填。
- `netops-ai-knowledge`：AI 知识库、RAG 向量检索 (pgvector/trgm)、Security Vault 脱敏与多模型网关。
- `netops-topology-engine`：网络拓扑发现、LLDP/CDP 计算、LAG/VLAN 链路推导与图谱可视化。
- `netops-monitoring-telemetry`：SNMP 遥测指标、出向探针 (SSRF 防护)、告警规则、抑制与多通道分发。
- `netops-pam-automation`：特权访问 (PAM)、Web 终端堡垒机、密码轮转、危险命令拦截与变更工单。
- `netops-textfsm-engineering`：TextFSM 模板开发、沙箱测试、多厂商 CLI 捕获组与模板目录规范。
- `netops-quality-gate`：pytest、TypeScript 检查、生产构建与回归验证。
- `netops-release`：Windows、Docker、Ubuntu、Nginx、CI 与发布打包。

跨层功能通常组合业务 skill 与 `netops-quality-gate`；涉及多领域时按最小必要集合引入对应专业 skill。

## 4. Agent 协作规则

角色说明位于 `.agents/roles/`：

- `coordinator.md`：拆解跨模块任务、分配边界并汇总结论。
- `backend-engineer.md`：后端 API、服务和数据库调用。
- `frontend-engineer.md`：前端页面、交互和 API 合约。
- `network-engineer.md`：设备接入、命令解析与多厂商适配。
- `quality-release-engineer.md`：测试、构建、迁移和发布验证。

仅当任务可以被清晰拆成彼此独立的子任务，或用户明确要求并行/多 Agent 时才启用多个 agents。每个 agent 必须先检查工作树，避免覆盖其他 agent 或用户的未提交修改；共享文件由 coordinator 统一协调。

跨 Agent 任务必须由 coordinator 维护一份统一交接摘要：当前目标、已改文件、未完成事项、验证状态、阻塞点和下一步负责人。子 agent 的结论必须回写到这份摘要或最终 `walkthrough_*.md`，避免只停留在对话上下文中。

## 5. 通用质量与安全约束

- 修改前追踪完整调用链，修改后运行与风险相称的最小测试集合。
- 涉及后端接口、数据库结构、前端路由/共享类型、网络设备适配、权限审计或发布配置的任务，交付前必须经过 `netops-quality-gate` 或等价检查。
- 不在日志、响应、测试夹具或文档中写入真实密码、密钥、Token、SNMP community。
- 网络设备配置变更、生产部署、推送和发布必须获得明确授权。
- 不修改与当前任务无关的用户未提交文件。

## 6. 代码规范与实现标准

### 6.1 通用实现原则

- **根因优先**：优先修复调用链和数据模型中的根因，避免只在 UI、日志或异常提示层做表面补丁。
- **最小变更**：每次修改只覆盖当前任务范围；不顺手重构无关模块、不批量格式化无关文件。
- **分层清晰**：API 层负责请求校验、鉴权、状态码和响应契约；业务规则放在 `backend/services/`；设备连接和协议差异放在 `backend/drivers/`、`backend/engine/` 或 normalizer 边界；前端页面避免直接堆积复杂业务逻辑。
- **显式契约**：跨前后端字段、枚举、错误码、权限语义必须在 schema/type/helper 中显式表达，避免用散落字符串和隐式约定连接模块。
- **可回滚**：涉及批量写入、配置变更、迁移和外部设备操作时，必须说明失败处理、幂等性和回滚路径。
- **可读命名**：变量、函数和文件名使用表达意图的名称；除局部循环索引外避免单字母变量。

### 6.2 后端 Python / FastAPI

- Router 保持轻量：只做 HTTP 入参、鉴权、异常映射和响应包装；复杂逻辑下沉到 service。
- Service 函数应便于单元测试：输入输出明确，避免依赖全局可变状态；必须访问数据库时由调用方传入连接或使用现有连接管理模式。
- Pydantic schema 是稳定 API 契约的首选；新增或修改字段时同步更新前端类型和调用方。
- 异常返回保持用户可读、机器可判断；已有结构化错误码不得随意改名。
- 日志只记录脱敏后的上下文，不记录明文密码、密钥、Token、SNMP community、私钥或完整敏感配置。
- 异步接口中避免直接执行长时间阻塞 I/O；必要时复用现有线程池、任务队列或调度机制。

### 6.3 前端 React / TypeScript

- 页面组件负责组合和渲染；数据获取、状态复用和复杂变换优先放入 hooks、store、context 或 domain-local helper。
- TypeScript 类型必须与后端响应契约同步；避免无边界的 `any`，必须使用时应限制在兼容旧数据或第三方库边界。
- UI 必须覆盖加载、空态、错误态、权限态和危险操作确认；后端错误应安全展示，不泄露敏感细节。
- 保持现有 Tailwind、组件风格、中英文文案和主题变量，不引入新的 UI 框架或状态库，除非用户明确批准。
- 表单输入允许用户自然编辑；提交前统一规范化、默认值填充和校验，避免在输入过程中强行重置。

### 6.4 数据库与迁移

- 生产目标数据库为 PostgreSQL；SQL、事务、锁和索引设计必须优先遵循 PostgreSQL 语义。
- 批量写入必须考虑事务原子性：任一关键行失败时要么整体回滚，要么明确记录部分成功语义并让调用方可见。
- 迁移必须可重复执行或具备幂等保护；涉及大表回填时说明批次、锁影响和回滚策略。
- 不直接依赖 SQLite 专属行为实现生产逻辑；测试兼容 SQLite 时不得牺牲 PostgreSQL 正确性。

### 6.5 网络设备与多厂商适配

- 厂商差异必须收敛在驱动、parser、normalizer 或平台映射层，不在多个 API/service 中散落 `if vendor` 分支。
- **厂商、平台、命令集必须联动**：`vendor` 是业务厂商，`platform` 是驱动和命令目录的技术键；资产表与关联设备表中的两者必须一致。前端录入/编辑、Excel 导入、后端创建/更新、资产与设备同步都必须校验并规范化该组合。
- **禁止静默回退 Cisco**：已识别厂商与 `platform` 不匹配时，必须修正为厂商默认平台或返回明确校验错误，不得继续使用 `cisco_ios` 默认命令。自动化快速查询、操作目录、巡检、备份和自定义执行必须统一从规范化后的 `platform` 选择驱动与命令。
- **不得仅凭型号判断厂商**：`S6800` 等型号可能被多个厂商使用；排障时以用户当前选择、设备实际提示符/系统信息以及数据库最新记录为准。用户主动切换厂商做测试时，不得把该变化误判为同步故障。
- **修改前核对完整映射链**：至少检查 `physical_assets.vendor/platform`、`devices.vendor/platform`、前端平台选项、后端规范化、Netmiko `device_type` 和自动化命令目录。Huawei 应使用 VRP/display 命令，H3C 应使用 Comware/display 命令，Cisco 应使用 IOS/show 命令；其他厂商按各自平台目录处理。
- **多厂商回归是交付门禁**：涉及资产录入、平台字段、驱动选择或自动化命令的修改，至少覆盖 Cisco、Huawei、H3C 的“厂商→平台→驱动→查询命令”测试，并验证厂商切换后旧平台不会残留。
- 查询/巡检命令默认按只读和最小权限处理；备份、保存配置、回滚、变更和显式特权借用才使用管理员或 enable/admin 凭据。
- 命令执行必须处理认证失败、超时、分页、提示符不匹配、设备不支持命令和输出格式异常。
- 真实设备输出样本必须脱敏；测试优先使用 fixture、mock driver 或最小可复现片段，不依赖生产设备。
- 任何可能改变设备配置的操作都必须有明确授权、审计记录和失败回滚说明。

### 6.6 测试与质量门禁

- 修改后优先运行与改动最接近的测试，再按风险扩展到模块级或全量检查。
- 后端接口、数据库、网络驱动和权限逻辑应优先补 pytest；前端契约或类型变更至少运行 `npm run lint`。
- 新增测试应验证成功路径、失败路径和边界条件；修复 bug 时尽量加入能复现原问题的回归测试。
- 不为没有测试体系的区域强行引入大型测试框架；可用轻量脚本或局部单测时优先选择最小可维护方案。

### 6.7 文档与交付

- 涉及代码、数据库、网络设备适配、发布或批量数据处理的任务，必须同步更新对应 `docs/plans/` 与 `docs/walkthrough/`。
- 最终交付应列明实际修改文件、验证命令、验证结果、未验证项和剩余风险。
- 若发现与当前任务无关的问题，只记录为后续建议，不擅自扩大修改范围。
### 6.8 跨平台脚本与环境配置

- `.env`、Compose 环境文件和部署脚本必须兼容 Linux 的 LF 与 Windows 的 CRLF；手工解析 `key=value` 时必须先去除行尾 `\r`，不得把原始回车符传给 Docker、PostgreSQL 或其他命令。
- 将 `.env` 视为数据而不是可执行代码：优先使用 Docker Compose 的 dotenv 解析或受控的专用解析逻辑；生产部署脚本不得为读取少量配置而直接 `source` 整份可能包含空格、引号或 Shell 特殊字符的 `.env`。
- 传入外部命令的配置值必须通过变量引用并正确引用，日志和错误信息不得打印密码、密钥或完整连接串。
- 修改环境配置解析逻辑时，至少用 LF 和 CRLF 两种输入做回归验证，并覆盖缺失键、默认值和命令失败路径；容器能正常启动不等于主机侧脚本解析正确。
- 生产环境不得用 `.env.example` 覆盖现有 `.env`；变更示例配置前先备份真实配置，并确认不会重置 PostgreSQL 数据卷或已有凭据。

# Git 提交修复记录规范

- 每次执行 `git commit` 前，必须在 `docs/fixes/` 新建一份 Markdown 修复记录，并与代码修改放在同一个提交中。
- 文件名格式为 `fix_YYYYMMDD_HHMM_NN_问题名.md`，时间戳和同分钟序号规则与 plan/walkthrough 一致。
- 每次提交必须使用新的修复记录文件，不得复用或覆盖历史记录；一个提交包含多个相关问题时可以合并记录，但必须完整列出。
- 修复记录至少包含：问题现象、根因、解决方案、实际修改文件、验证命令与结果、未验证项、风险与回滚方式。
- 文档、配置、重构或其他非缺陷提交也必须创建记录，并在“问题现象”中说明本次提交目的，保证每次 Git 提交都有可追溯 Markdown 说明。
- Agent 在用户要求提交 Git 时，必须先检查本次变更是否存在尚未提交的 `docs/fixes/fix_*.md`；没有则先创建，禁止直接提交。

# Git 分支与合并规范

- 本仓库唯一长期开发分支为 `main`；日常开发、修复、迁移和发布准备均直接在 `main` 工作区完成。
- 未经用户明确要求，不创建、切换、推送或保留功能分支；不得用临时分支代替对 `main` 的实际合入。
- 需要隔离检查时只能使用临时工作树或补丁作为传输手段，验证后必须把完整改动合入 `main`，并清理临时分支引用；不得把临时分支作为后续开发基线。
- 合入前必须检查 `git status`、提交图和两侧差异，保留 `main` 中已有的用户未提交改动；禁止使用 `reset --hard`、`clean` 或覆盖式复制来“解决”冲突。
- 合入后的提交应以 `main` 为父线，提交信息说明实际变更范围；按照本文件的提交记录规范在同一提交中附带新的 `docs/fixes/fix_*.md`。
- 不得向远端推送或触发发布流程，除非用户在当前任务中明确授权。
